# v0.5.0 — live capture

**Release status:** tagged `v0.5.0` on 2026-07-26.

## Objective

Make a live source drive the avatar that v0.4.0 taught to move. v0.4.0 ended at
a recorded `.vrma` clip playing back on a real rig; v0.5.0 adds the observation
side — a vendor-neutral live-capture intake feeding **the same** retarget core,
with no second pipeline and no second contract.

The release boundary is deliberate: it does not begin OpenExec. That is v0.6.0.

## What ships

- **Motion Phase D — the live-capture surface in `motionRuntime`.**
  `IMotionSource` answers "what is the pose at this evaluation time?" and
  returns a status alongside the pose — `Sampled` (real bracketing data), `Held`
  (outside the observed range), `Extrapolated` (root carried forward), or
  `Unavailable` — plus the lag. `ClipSource` wraps a finished animation and
  `LiveCaptureSource` wraps a stream; behind the interface nothing downstream
  can tell them apart.
- **Intake decisions are explicit and counted.** Confidence gating with a floor
  (a frame carrying *no* confidence array is never gated — an adapter that
  cannot measure confidence must not lose its bones for saying so), a
  missing-bone policy (hold the last observation, or leave it unbound for the
  target rig's rest pose), root-motion intake (`Passthrough` / `Ignore` /
  `DeriveVelocity`), and stale-versus-out-of-order classification. Everything is
  reported in `LiveCaptureStats` rather than applied silently.
- **The `motion-capture-trace` format** (v1) and its replay driver.
  Line-oriented text at fixed six-decimal precision, so a trace round-trips
  byte-identically and a fixture is *compared* rather than merely parsed.
  `ReplaySender` pushes frames as a caller-driven clock advances;
  `CaptureRecorder` accumulates the evaluated result back into a clip, carrying
  the per-tick status counts with it.
- **A motion corpus** —
  [six traces](../../libs/motionRuntime/tests/corpus/README.md) pinning a clean
  session, a limb dropout, confidence collapse at the extremities, irregular
  arrival, a rig that solves no legs, and a reported root velocity.
- **`motion_capture`** (`tools/motionCapture`) — replays a trace into an
  avatar-independent semantic humanoid clip. `--delivery-lag` makes the consumer
  hold and extrapolate as it would when a real transport falls behind;
  `--report` prints the intake and evaluation summary, which is also recorded
  into the clip's `capture:*` customData.
- **A CI lane for the motion layer** — written, but **not wired**; the
  v0.4.0 carry-over is not closed (see below).
- **Live-capture semantics are in the contract.**
  [`MOTION_CONTRACT.md`](../design/MOTION_CONTRACT.md) gains a Motion Phase D
  section.

## The decision the whole release rests on

**The core owns no transport and no clock.**

`LiveCaptureSource::Push` takes an already-decoded pose stamped in the capture
system's own clock. Protocol decode and coordinate conversion stay in an adapter
(motion policy §8.2), and nothing in `motionRuntime` reads a wall clock — the
caller drives the tick.

That is what makes the whole layer testable. The replay loop is the entire
definition of "live capture" in this project:

```cpp
sender.Advance(now - deliveryLag);      // what has arrived by now
recorder.Record(source.Sample(now));    // what the consumer sees now
```

A real adapter replaces the first line with a decoded packet and nothing else
changes. So replaying a recording is not a mock of the live path — it *is* the
live path, with a different frame source. The same trace and the same tick
schedule produce identical buffer contents, identical statistics, and identical
retargeted output on every run and every operating system.

## How the claim is falsifiable

"A live capture feeds the same retarget core" is easy to assert and easy to get
wrong. The end-to-end test states it as something that can fail:

1. replay a corpus trace through `LiveCaptureSource` into a semantic clip;
2. bake that clip onto `docs/design/fixtures/motion/avatar.usda` with the
   **unchanged** `motion_retarget` from v0.4.0;
3. resolve the result through a `UsdSkelSkeletonQuery` and assert the rig
   actually moves across the timeline.

Step 2 fails if the live path produced anything the offline path could not
consume. Step 3 fails if the clip binds and animates nothing — the exact v0.4.0
regression ([#64](https://github.com/animu-sphere/usd-vrm-plugins/issues/64)),
which is why the check resolves through the consumer's own query rather than
comparing the values that were just authored.

The test compares across the whole timeline rather than endpoint to endpoint:
the walk fixtures span whole gait cycles, so their first and last frames
legitimately coincide, and an endpoint check would report a moving clip as
frozen. That was a real defect in the first version of this test.

## Why the corpus is synthetic

The VRM corpus is licence-gated: real avatars are fetched, never committed. A
motion corpus recorded from a commercial capture SDK or from a performer would
inherit exactly that problem, and a fixture nobody outside the project may
redistribute is a fixture CI cannot run — which would defeat the point of Phase
D. So every trace is generated by closed-form maths in
`libs/motionRuntime/tools/generate_traces.py`: Apache-2.0 like the rest of the
repo, byte-stable across machines and operating systems, and reviewable in a
diff.

**They are not real capture data**, and this release does not claim otherwise.
They reproduce the *shapes* a live source produces — a self-occluded limb
dropping out, confidence collapsing at the extremities, irregular arrival, a
partial rig, an explicit root velocity — not the noise characteristics of any
device. Validation against a real rig needs an adapter, and remains open.

Two tests keep the corpus honest: `motionRuntime_corpus` re-emits every
committed trace through the C++ writer and compares bytes, and
`motionRuntime_traceGen` re-runs the generator and compares against what is
committed. Without the second, a hand-edited fixture would stay green while
becoming unregenerable.

## The gap that is still open

`ost ci generate` emits one job per **bundle** cell. A plain library
(`openstrata.library.yaml`) and a CLI executable have no cell shape, so
`motionCore`, `motionRuntime`, `vrmRetarget`, `vrmContainer` and both CLIs are
compiled and tested only in the plain-CMake root build — which no workflow runs.
v0.4.0 shipped that layer with zero CI coverage and named it in its release
record. **v0.5.0 ships it that way too.**

`.github/workflows/motion-ci.yml` was written to close it, by building the whole
workspace with plain CMake — the only configuration in which `libs/` and
`tools/` targets exist. Two thirds of it work, verified green on all three OS:
the `ost` bootstrap, the artifact pull and runtime materialisation, and the
**WORKSPACE.md §2 dependency-graph gate** (which has to be read out of `--json`,
because `ost plugin test --workspace` couples graph validation to testing every
bundle and so exits non-zero on a fresh checkout where nothing is built).

The remaining third does not. Configuring against the pulled runtime fails on
all three OS:

```console
pxrConfig.cmake:46  find_dependency(Python3 COMPONENTS Development
                                    Development.Module Development.Embed)
Could NOT find Python3 (missing: Development Development.Module Development.Embed)
  Development: Cannot find the directory "/usr/include/python3.13"
               Cannot find the library "/usr/lib/x86_64-linux-gnu/libpython3.13.so"
```

Those are the paths of the Python the runtime was *built* against — a deadsnakes
3.13 inside the `ubuntu:24.04` build container — not any path on a hosted
runner. `actions/setup-python` provides a dev-complete 3.13 and exports
`Python3_ROOT_DIR`; passing it again as `-DPython3_ROOT_DIR` changed nothing.
The generated lane never meets this because `ost plugin build` resolves Python
itself.

**So the lane ships disabled** — `workflow_dispatch` only, not gating pull
requests. A lane that is red on every PR trains people to ignore red lanes,
which costs more than the coverage it fails to provide. Its header records the
diagnosis and the untried next step
(`-DPython3_EXECUTABLE=$pythonLocation/bin/python3`), so finishing it is a
bounded task rather than a rediscovery.

The upstream P0 —
[report 28](../reports/ost/28-2026-07-26-v0.20.0-motion-layer-ci-gap.md) — stays
open, and [report 32](../reports/ost/32-2026-07-26-v0.20.0-motion-layer-ci-workaround.md)
records both what the workaround cost and where it stopped.

## What writing that lane found anyway

The baseline gate had been silently stale for a release. Nothing ran it against
26.08 after the runtime bump landed, because no lane ran the root build.
Refreezing produced a diff worth stating precisely:

```console
removed 220 added 220
identical after namespace normalisation: True
lines changed for any other reason: 0
```

All 220 exported symbols changed **only** by `pxrInternal_v0_26_5` →
`pxrInternal_v0_26_8`. Every other baseline artifact — flattened stages,
structural digests, the schema contract, discovery, diagnostics — is
byte-identical across the two OpenUSD versions. That is a genuinely reassuring
result about the 26.05 → 26.08 bump, and it was only obtainable by running a
gate nothing ran.

## One humanoid taxonomy

`HumanBoneParent`, `NearestPresentAncestor` and `HumanBoneJointPath` moved into
`motionCore`. The `.vrma` reader carried a private copy of the VRM humanoid
hierarchy; the live-capture path authors the same semantic skeleton, and two
tables that can disagree would produce two skeletons that look alike and do not
compose. The reader now uses the shared one and its private table is gone.

## Compatibility

- **OpenUSD 26.08 on all lanes.** The exact-pin half of what was scoped for
  v0.6.0, landed early: PR cells, the release workflow, and the new motion lane
  all pin the same three published runtimes.
- **No schema contract change.** Still version 1.
- **No change to any authored `.vrm` or `.vrma` stage.** Proven, not asserted —
  every non-symbol baseline artifact is byte-identical to v0.4.0's.
- Every workspace manifest moves to `0.5.0`; `requires` ranges move from
  `>=0.4,<0.5` to `>=0.5,<0.6`.

## Known limitations

- **No product-specific capture adapter ships.** Protocol decode and coordinate
  conversion belong under `adapters/`, the only place product names are
  permitted (motion policy §8.1). Nothing here has been validated against a real
  capture rig.
- **A trace records capture order, not delivery order.** When a frame arrived is
  a property of the transport, so out-of-order and stale classification is
  driven from the replay schedule and unit tests rather than from a fixture.
- **The motion layer still has no CI coverage.** `motion-ci.yml` exists but is
  disabled; see above. This is v0.6.0's P0-2 blocker and v0.5.0 did not clear
  it.
- **Runtime digests are pinned in two places** — `openstrata.ci.yaml` and
  `motion-ci.yml` — and must be re-pinned together once that lane is enabled. A
  motion cell left on an older OpenUSD than the bundle cells would be worse than
  no cell, because it would look like coverage.
- **The Linux cells carry a hand-added `apt-get` step** for MaterialX 1.39.5's
  X11 requirement. `ost ci generate github --force` deletes
  it silently.
- **The scheduled lane's `plugin_artifact` is still a 26.05 build**, pairing a
  26.05-built plugin with a 26.08 runtime. Carried from v0.4.0, untouched here.
- **The CLIs ship in no release artifact.** `motion_retarget` and
  `motion_capture` are executables, not bundles, so no member archive carries
  them; this needs an `ost` packaging answer.
- Expressions, look-at, generation, and OpenExec evaluation remain out of scope
  (Motion Phases E–H).
