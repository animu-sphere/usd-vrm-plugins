# v0.10.0 — canonical materials reach Hydra

**Release status:** prepared on 2026-09-27; the tag waits on the `release.yml`
dry run on `main`.

## Objective

The canonical material semantics this repository imports reach a Hydra
renderer as data, including when an expression drives them over time. VRM 0.x
and 1.0 materials carry one canonical record (`VrmMaterialAPI`,
`VrmMToonAPI`, `VrmTextureInfoAPI:<role>`), both realizations (`/preview`,
`/mtlx`) are generated from it, and `vrmImaging` exposes it to Hydra under the
frozen `vrm` locators, with per-field invalidation. The release closes the
[imaging track](../roadmap/imaging-track.md) (Steps I0–I5), carries the
[material track](../roadmap/material-track.md)'s Steps 3–7 and the
[export track](../roadmap/export-track.md)'s Step 1, and completes the motion
split.

The line was drawn on 2026-09-27: v0.10.0 ships what landed since v0.9.0 and
stops at `vrmImaging`. Every other track continues after the tag.

## What ships

### One canonical record per material

- **Three API schemas in `vrmSchema`**, additive within schema contract v1:
  `VrmMaterialAPI` (the glTF material core, `KHR_materials_unlit`,
  `KHR_materials_emissive_strength`), `VrmMToonAPI` (every non-texture field of
  `VRMC_materials_mtoon` 1.0) and `VrmTextureInfoAPI:<role>` (eleven roles,
  with sampler wrap, contribution scalars and `KHR_texture_transform`). Every
  property is a Material interface input (`inputs:vrm:*`), because a plain
  `vrm:` attribute is discarded as a connection source and draws black in
  Storm with no error (material policy §6.4.1).
- **The importer authors them for every material, VRM 0.x and 1.0 alike.** A
  VRM 0.x MToon material lands in the same fields as a 1.0 one, converted as
  UniVRM's own 0.x → 1.0 migration does, so a 0.x avatar and its migrated 1.0
  file import to the same values (material policy q10).
- **Both realizations are generated from that record alone.** `/preview` and
  `/mtlx` are functions of the Material's canonical attributes, run by the
  importer on what it reads back from the stage, and regenerating them on any
  stage that carries the schemas gives the same graphs
  (`usdvrm_realization_regenerate`). Lit materials get glTF metallic-roughness
  PBR in MaterialX, so they now draw through MaterialX in `usdview`. MToon
  materials get a headlight-lit toon approximation (q13).
- **Expression colours drive the canonical slots.** A material-colour bind
  resolves through the schema contract's table onto the Material's
  `inputs:vrm:*`, `motion_retarget` bakes the colour there as time samples,
  and both realizations read the slot through a NodeGraph interface
  connection, so an animated colour shows with nothing regenerated (q12). A
  bind of two slots of one material keeps its pairing through the new
  `vrm:materialColorTargetIndices`.

### `vrmImaging`: the record as Hydra data

- **A new bundle and product member of kind `usd-imaging`**: three UsdImaging
  API-schema adapters expose every canonical value on the material prim under
  `vrm/material/<field>`, `vrm/mtoon/<field>` and
  `vrm/textureInfo/<role>/<field>`. The locator rule is frozen:
  `inputs:vrm:<group>:<name>` is `vrm/<group>/<name>`. It ships no renderer and
  no shader; it links OpenUSD alone and needs `vrmSchema` registered.
- **Invalidation is per field.** An edit or a time move of one canonical value
  dirties that field's `vrm` locator. A time move never dirties the whole
  `material` and nothing of the bound mesh, so a baked expression costs no
  network rebuild. An *authored* edit also dirties the whole `material` on
  26.08, and the suites pin both behaviours.
- **An expression bake reaches Hydra as time** (Step I4):
  `workspace_expression_bake_imaging` and
  `workspace_expression_bake_mtoon_imaging` read a `motion_retarget` bake
  through the stage scene index at each baked time. The same MToon bake played
  in `hydra-toon`'s host session changes the MToon slot and rebuilds no
  geometry, draw packet or pipeline
  ([renderer report 11](https://github.com/animu-sphere/hydra-toon/blob/main/docs/reports/renderer/11-2026-09-27-expression-bake.md)).
- **A `.vrm` reaches Hydra as its source says** (Step I5):
  `workspace_import_imaging` imports `mtoon_vrm1.vrm` and `mtoon_vrm0.vrm` and
  compares 6 materials and 227 values per file with what the oracle derives
  from the 1.0 source, each texture's image byte for byte.
- **Discovery, invalidation and the packaged plugin are all held.**
  `vrmImaging_discovery` runs in every workspace cell, every §17.4 invalidation
  case has a suite (`matcap` was the last), and the release lane runs every
  `vrmImaging` suite against the installed product
  (`scripts/artifact_only_imaging_smoke.py`).
- **`VRM300`** (`validate_vrm.py --check-imaging`) names the three ways the
  adapters are silently absent: `vrmImaging` not registered, `vrmSchema` not
  registered, or `USDIMAGING_ENABLE_PLUGINS` off. It is off by default.
- **A `lookdev` package**, for Windows and Linux x86_64, built and tested
  L0–L5 against the canonical CY2026 `lookdev` runtime and published to
  `ghcr.io/animu-sphere/usd-vrm-plugins` as `vrmImaging-<version>-<target>`,
  with `lookdev-package-pins.json` naming the digests a Formation pins. It is
  not a product member.
- **What it supports is written down**:
  [SUPPORTED_CONFIGURATIONS.md](../reference/SUPPORTED_CONFIGURATIONS.md#hydra-imaging-vrmimaging).

### `vrm_export`: native USD with no VRM plugin

A new CLI in the product (export track Step 1). `vrm_export avatar.vrm -o
avatar.usdz` writes the imported stage with every texture localized and
referenced relatively, and a `.usdz` through OpenUSD's own packaging; the
output opens with no VRM plugin and no source `.vrm`. `--check` reopens and
validates it, `--overwrite` replaces an existing output, and the exit code
names the stage that failed.

### The motion split is complete

Generic motion is `usd-motion-plugins`' and live input `motion-connectors'`.
This repository consumes the published packages by archive digest per target
(v0.5.1) and builds none of them:

- **Consumed:** `motionCore`, `motionSampling`, `motionRecording` (MIG-1),
  `motionRetarget` and `motionUsd` (MIG-2), and the `execMotion` bundle, which
  `execVrm`'s package embeds.
- **What stayed of `vrmRetarget` is `vrmRig`**: VRM 1.0's required bones,
  `ExpressionResolver`, `LookAtEvaluator` and the material-colour slot table.
- **Gone from this repository and this product:** the recorded-file path
  (`motionSource`, `motionBvh`, `motion_bvh_*`, the producer profiles; MIG-3),
  `motion_capture` and every live input (MIG-4).
- **Held:** every `workspace_exec_parity_*` row is unchanged against the
  consumed packages. `workspace_reference_pipeline` bakes a `.vrma`, a
  converted BVH and a recorded session through one `motion_retarget` argument
  list (MIG-5), `check_cmake_boundaries.py` fails on a moved identity coming
  back, and a plain-CMake lane builds the workspace with no `ost` at all.

### The release lane

Four defects no pull request could show were found and fixed before this tag:
`release_exclude` naming three members that had left (the product could not
package since MIG-4), the runtime validated before the host Python existed,
an end-of-job cache that restored smoke imports into the next run
(`ARTIFACT_IDENTITY_CONFLICT`), and the exec smoke reading the design triplet
from where it used to be
([ost report 52](../reports/ost/52-2026-09-26-v0.23.10-the-release-lane-dry-run.md)).
The `ost` pin is 0.23.13.

## Compatibility

- **OpenUSD:** exactly 26.08, with OpenExec, on Windows x86_64, macOS arm64 and
  Linux x86_64. `vrmImaging` additionally needs the runtime's usdImaging SDK,
  and populates through the stage scene index only.
- **Schema contract:** version 1, unchanged. The three material schemas and
  `vrm:materialColorTargetIndices` are additive.
- **Package version:** a minor bump, in lockstep. Every descriptor, every
  `requires` range (`>=0.10,<0.11`), every CMake standalone fallback and the
  aggregate product read `0.10.0`: 21 files and 29 replacements, plus
  `VERSION`. It is minor because in-tree dependents use API the tagged 0.9.0
  packages lack — `vrmSchema`'s new schemas (`vrmImaging`, the importer) and
  `vrmRig`, which did not exist
  ([PACKAGE_CONTRACT.md §3.1](../architecture/PACKAGE_CONTRACT.md#31-a-requires-range-between-two-releases)).
- **Breaking for a package consumer:** `vrmRetarget` is no longer a package.
  Its generic half is `usd-motion-plugins`' `motionRetarget`
  (`SkeletonDescriptor`, `SkeletonJoint`, `RetargetMap` under
  `openstrata::motion`), and the rest is `vrmRig`. The motion libraries, the
  adapters and their tools are no longer produced here.
- **Behaviour change in an imported stage:** every material carries the
  canonical schemas, and its `/preview` and `/mtlx` graphs are generated from
  them, so every imported stage's material graphs changed. No value changed
  for a VRM 1.0 or glTF input except Seed-san's `green_emit`, which now honours
  the emissive factor and strength. A VRM 0.x MToon material now follows its
  `materialProperties` instead of the glTF fallback.
- **Behaviour change in a bake:** `motion_retarget` writes expression colours
  as time samples on the Material, where it used to warn they were not
  written. VRM 0.x `materialValues` colours are sRGB-decoded onto the slots,
  which departs from UniVRM's migration.
- **Workspace graph at the bumped version:** 6 bundles, 4 bundle edges,
  2 libraries, 13 library edges, 2 tools, valid.
- **Measured at the bumped version, on Windows, before the dry run**, with
  `ost` 0.23.13: the workspace suite is **57 of 57**. After each bundle's
  `ost plugin build` in the release lane's order,
  `ost plugin package --workspace --product` reports 6 bundle packages and
  2 tool packages, and a product of **8 members**: the six bundles,
  `motion_retarget` and `vrm_export`, every archive named `-0.10.0-`. The
  artifact-only exec and imaging smokes both pass from that product, each
  with its negative (a moved-aside registration) failing as it should. macOS
  and Linux are the dry run's to measure.

## Known limitations

Everything here was measured or attempted.

### Imaging

- **The published `lookdev` package is not yet public.** The lane builds and
  pushes it; making the GHCR package public and pulling it anonymously
  happens after the tag, and closes Step I5's last row. `hydra-toon` re-pins
  its VRM Formation to those digests in its own repository.
- **No macOS `lookdev` package**: open-strata publishes no macOS `lookdev`
  runtime.
- **The legacy `UsdImagingDelegate` gets no `vrm` data**, without an error. The
  realizations still reach a renderer there.
- **An authored canonical edit dirties the whole `material` on 26.08.** A
  consumer tells a value edit from a network edit by the `vrm` locator; a time
  move is narrow (imaging policy §28.3).
- **OpenUSD 26.08 is the only version measured.** A second version cell waits
  on a second published runtime.

### Materials

- **No renderer in this product reads MToon.** `/mtlx`'s MToon is a
  headlight-lit approximation that ignores scene lights; outline, GI
  equalization and UV animation are not realized. The MToon renderer is
  `hydra-toon`'s (material track Step 8).
- **Texture-transform expression binds stay raw** (q11), under `VRM150`.
- **No image regression test** of the realizations; the material track names
  it after this release.
- **In `usdview`, a skinned avatar needs
  `USDSKELIMAGING_ENABLE_NORMAL_COMPUTATIONS=1`**, or Storm shades it with flat
  per-triangle normals that the toon ramp shows as polygon edges.

### Export

- **Inputs are `.vrm` only**, and a `.usdc` or `.usdz` does not keep the sign
  of a zero in an integer-valued vector or array (OpenUSD's crate writer).
  Validation and usability, motion assembly and the distribution pipeline are
  the export track's Steps 2–4.

### Distribution

- **The artifact-only rows run in `release.yml`, not on a pull request**,
  including the new imaging smoke.
- **Carried from v0.9.0, unchanged:** Linux and macOS binaries keep the build
  machine's RPATH, plugin libraries carry the `__FILE__` source names of
  OpenUSD's registration macros, and with several bundles on `PATH` a shared
  library loads from the first directory that holds a copy.
- **Carried from v0.8.0, unchanged:** no Linux or macOS symbol baseline, no
  real-runtime compatibility lane, per-bundle CI cells kept only to reach a
  verb, a hand-authored `release.yml` whose last bundle still decides every
  package's libraries. See
  [current.md](../roadmap/current.md#carried-over-from-shipped-releases).
