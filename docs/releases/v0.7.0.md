# v0.7.0 — mocopi live input and generic BVH recorded-motion ingestion

**Release status:** prepared 2026-08-24.

## Objective

Give a capture product **two** surfaces into this repository and make both of
them end at the same place: a retargeted `UsdSkelAnimation` produced by an
**unchanged** `motion_retarget`. The live surface is UDP, through
`vrmAdapterMocopi`. The recorded surface is a *generic* BVH pipeline that is
deliberately not that product's importer — joint names, units, axes and root
conventions are facts about the **writer**, so they live in a declarative
producer profile and the code that reads them carries no product name.

The two are separate code meeting at `motionCore`, because a file argues about a
hierarchy, a channel order, a frame time and a rest pose where a socket argues
about packets, timestamps, restarts and tracking loss
([motion policy §8.3](../design/MOTION_ARCHITECTURE_POLICY.md)).

## What ships

### The live surface

- **`vrmAdapterMocopi`**, a plain static library covering every layer between a
  socket and a pose: a bounded UDP receiver, a packet-capture format, a decoder
  for a wire grammar that has no published specification, a joint map and basis
  change, frame assembly, and a `motion::LiveCaptureSource` bridge. A frame
  missing bones is still a frame — reported and passed on — and a source that
  restarted is detected from the stream clock **and** the frame counter, neither
  of which suffices alone.
- **`mocopi_record`**, its CLI: records a bounded live session, inspects a
  capture, and — `--inspect` only, so a recording still runs no decoder —
  exports a `motion-capture-trace` that `motion_capture` and `motion_retarget`
  consume unmodified.
- **A body that travels.** `BodyPlacementPolicy` (default `HipsOnly`) reads a
  rig whose only translating joint is the hips as body translation and composes
  `RootMotion::worldPosition` / `worldOrientation`. Before it, the live path
  silently dropped **4.81 m** of hips travel that the recorded path carried;
  `mocopi_record --export-trace` now prints that number, path and net.
- **A device drove all of it.** Five sessions off a mocopi app 2.7.2 rig reached
  this host over UDP 12351 on 2026-08-15, and the first decoded with **zero
  diagnostics** — 2190 frames, the sender's clock at 59.9453 Hz. One was baked
  onto a released avatar through the unchanged product tools and looked at.

### The recorded surface

- **`motionBvh`**, a generic BVH parser with a frozen diagnostic set, and
  **`motionSource`**, the format-neutral model above it: a source rig, a source
  animation in the source's own angle order and unit, provenance, and exactly
  one declared crossing into canonical motion.
- **The producer profile contract** and **two shipped profiles** — Sony mocopi's
  mobile export and Bandai Namco Research's Motiondataset, the latter written
  from two measured exports of a rig nobody here wrote. A third, user-defined
  profile is exercised by test: named by path with no search directory, required
  to match, and required to be **refused** against a rig it does not describe.
- **`motion_bvh_inspect`** and **`motion_bvh_convert`**, which link no OpenUSD
  at the syntax layer and refuse every file until a profile is named, because a
  BVH file declares no unit, no axis, no handedness and no humanoid bone.

### Both surfaces, compared

- **One physical session observed two ways.** The same mocopi take recorded as
  UDP *and* as the app's BVH export, driven to a canonical clip on each side,
  agrees to a median **0.084°** per bone — with the residual shown to be
  *timing* rather than value (0.0000° median wherever a bone was still).
  [Report 01](../reports/motion/01-2026-08-15-mocopi-cross-source.md).
- **What each path cannot carry is written down from evidence**, five measured
  entries, in the same report.

### Beyond the motion boundary

- **A `.vrma` clip's expressions reach the stage.** Declared expressions become
  prims under `/Animation/Expressions` carrying the name the file used verbatim,
  a type, and a time-sampled weight. Out-of-range weights are carried unclamped
  with a warning; an expression the clip declares and never drives is read from
  its node's own transform; a node stating no transform gets no weight
  attribute, because an unreported weight is not a weight of zero. Nothing is
  expanded onto a rig — that is `ExpressionResolve`, and it is not in this
  release.
- **Unlit VRM materials carry a MaterialX network, and it is the one that
  renders**, reached through `outputs:mtlx:surface`.
- **Three material-import corrections**: a `KHR_texture_transform` that was
  authored as though USD sampled glTF's UVs, an `alphaMode: OPAQUE` that let the
  base-colour factor's alpha through, and a UsdPreviewSurface network that was a
  pile of shader nodes rather than a material.

## Compatibility

- **OpenUSD:** exactly 26.08 on Windows x86_64, macOS arm64, and Linux x86_64.
- **Schema contract:** version 1, unchanged.
- **Package version:** every workspace descriptor, every CMake standalone
  fallback and the aggregate product read `0.7.0`. This release also *corrects*
  that claim, which had been made and not kept since v0.3.0 — v0.6.0 shipped
  artifacts named `…-0.5.0-<target>`.
- **No authored VRM stage contract change.** The VRMA stage gains
  `/Animation/Expressions`, which is additive: a clip declaring no expression
  authors no such scope.
- **The aggregate product has 7 members**: the four bundles and the three
  `tools/` CLIs, `motion_bvh` being new here. Both adapters and both their
  recorders stay out of it, as
  [WORKSPACE.md §5](../architecture/WORKSPACE.md) requires — see the second
  known limitation below for the `ost` version that does *not* honour that, and
  the gate that now catches it.

## Known limitations

Everything in this section is stated because it was **measured or attempted**,
not because it was foreseen.

### The release conditions this milestone did not close

- **Both paths do not run from release artifacts alone.** A packaged
  `motion_bvh` member is exactly its two executables and its descriptor; no
  member of the product carries data, so
  `share/usd-vrm-plugins/profiles/motion/` reaches no artifact and an unpacked
  converter refuses every file it is given. A plain `cmake --install` places the
  profiles correctly and is unaffected. The workaround —
  `directories: [bin, share]` — works and was rejected, because it stages the
  layer's data by copying it under one tool's member root
  ([ost report 35](../reports/ost/35-2026-08-24-v0.22.2-release-artifact-membership.md) §4).
- **The cross-source comparison covers two paths of three.** A VMC relay would
  add the third and no sender was recorded, so the VMC half of the root/hips
  decision stays open and a VMC session still retargets in place.
- **A device recovery take does not exist.** The source **restart** is recorded
  from hardware — a real stop-and-start was dark for 233 frames = 3.8833 s — but
  *tracking loss* turned out to be unproducible on this product: removing a
  sensor puts the app into re-tracking, so the stream never carries a lost
  sensor. `VRM_MOCOPI_TRACKING_LOST` stays frozen and unraised.
- **No redistributable mocopi capture is committed.** A session is a real
  person's motion and a skeleton packet is a body measurement of that person, so
  the five device sessions survive as `recorded/manifest.json` — hashes, every
  measured statistic, the diagnostics each raised — with **no bytes**. The
  second producer's BVH files are fetch-gated for licence reasons (CC BY-NC 4.0
  against an Apache-2.0 repository) and `scripts/fetch_corpus.py` retrieves
  them.

### Packaging and distribution

- **An adapter library cannot be packaged separately.** `ost` 0.22.2 has the
  verb (`ost library package`) and it composes no `requires.libraries`, so it
  configures a leaf and refuses anything with an edge — which both adapters
  have. `vrmAdapter<Name>-<version>-<target>.tar.zst` remains a naming rule.
- **The adapter exclusion is enforced by the `ost` pin, not by a declaration.**
  The release lane bootstraps `ost` 0.21.0, which does not discover
  `adapters/<group>/<name>/tools/<tool>/` — so the product has 7 members and
  §5 holds. `ost` 0.22.2 *does* discover them: the same command on a 0.22.2
  workstation packages **9**, adding `mocopi_record` and `vmc_record`, with no
  descriptor in this repository changing
  ([ost report 35](../reports/ost/35-2026-08-24-v0.22.2-release-artifact-membership.md) §3).
  Nothing in `openstrata.tool.yaml` or `openstrata.toml` can say "not a product
  member", so the boundary currently depends on a version. The release lane now
  counts the `tools/` descriptors and fails if packaging exceeds them, which
  turns the next pin bump into a decision instead of a silent shipment.
- **The Linux and macOS symbol baselines are still unfrozen.**
  `tests/baseline/symbols/` holds `windows-x86_64.txt` only; `--check` skips a
  platform with no committed file. Every other baseline artifact is verified on
  all three OS.
- **The scheduled CI lane's `plugin_artifact` is still a 26.05 build**, pairing
  a 26.05 plugin with a 26.08 runtime. OpenUSD guarantees no ABI stability
  across versions, so that lane's result means nothing until it is republished.

### Scope deliberately outside this release

- **Expressions do not reach a rig.** A VRM expression binds N morph targets
  across M meshes plus material colours — it is not one blend shape — so
  `motion_retarget` authors no `blendShapeWeights` and no `skel:blendShapes`
  binding. The prim *name* is not a join key yet either: the VRM importer
  sanitizes through its own private table and the avatar side authors no
  `vrm:expressionName`. Both are `ExpressionResolve`, in a later release.
- **Look-at is untouched, in every layer.**
- **OpenExec evaluation of any kind is v0.8.0**, along with realtime skinned
  display. VRChat OSC Trackers input and the shared OSC/transport libraries it
  forces are [their own track](../roadmap/osc-and-vrchat-trackers.md) in v0.7.5.
- No FBX reader, and no `SdfFileFormat` bundle for `.bvh`.
