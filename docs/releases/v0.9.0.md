# v0.9.0 — the OpenExec foundation

**Release status:** prepared on 2026-09-17; the tag waits on the `release.yml`
dry run on `main`.

## Objective

`execMotion` and `execVrm` evaluate a humanoid through **OpenExec**, and on the
same recorded input they agree with the offline `motion_retarget` bake. Every
node is a **thin wrapper** over `motionRuntime` or `vrmRetarget`, never a second
implementation, and each evaluates an immutable snapshot rather than a live
source (Workspace Phase 8 + Motion Phase E; the plan is
[openexec-foundation.md](../roadmap/openexec-foundation.md)).

The wrapper rule is the point, not a style. It makes this release the first
consumer of the motion libraries that is not the tool that grew up beside them,
so a node that could not be written as a wrapper is a finding about the library
API. The foundation produced fourteen of them
([boundary consolidation §1](../roadmap/boundary-consolidation.md#findings-from-the-exec-layer-as-they-land)).
They are the defects the motion migration to `usd-motion-plugins` fixes on
arrival.

## What ships

### Two OpenExec bundles

- **`execMotion`**, over `UsdSkelAnimation`: `motion.sampleAnimation`,
  `motion.filterPose`, `motion.extractRootMotion`, `motion.interpolatePose` and
  `motion.blendPoses`. The `motionCore` aggregates are registered OpenExec value
  types, and a pose crosses a computation boundary unchanged.
- **`execVrm`**, over the applied `VrmHumanoidAPI`: the target skeleton, the
  humanoid map, rest-pose correction, one sample's retarget under the four
  root-motion statements, the bake's joint-local transforms, and the retarget's
  diagnostics.
- **An OpenExec schema has exactly one declarer per session**, measured, not
  read. So the two bundles partition the schemas (`UsdSkelAnimation` to
  `execMotion`; the `Vrm*API` schemas and `UsdSkelSkeleton` to `execVrm`), and
  WORKSPACE.md §2 states the partition.
- **A clip's root places a prop on screen** through `execGeom` and
  `usdExecImaging`: `motion:root:transform` is an attribute expression, and an
  Xformable connected to it is drawn where the clip's hips go (P0-7).

### Offline and OpenExec agree

- **Five parity cases, 414 598 values compared, every one `==`**, on the
  recorded mocopi BVH export, generated fixtures, `Seed-san.vrm` and a `.vrma`
  walk. The diagnostics agree too, line for line, as frozen
  `VRM_RETARGET_*` codes both sides answer as values (P0-6, P1-1).
- **From the installed product, on all three OS.** `release.yml` installs the
  aggregate product outside the repository and runs the parity cases, the
  display suite and the checks below with the product's own tools and bundles.
  Every plugin and module the processes load is read back, and none comes from
  a build tree. With execMotion's registration hidden, the cases refuse.

### The contracts the foundation wrote down

- **The OpenExec driver contract**: ten rules a caller of these computations
  has to follow, which none of the computations can state, with
  `VRM_OPENEXEC_*` codes and `tests/parity/ExecDriver` as the executable form
  ([MOTION_CONTRACT.md](../design/MOTION_CONTRACT.md#openexec-driver-contract-after-v080)).
- **The scale policy** (P1-2): a bake states each joint's **rest** scale.
  Through v0.8.0 it stated identity, which replaced a scaled rest
  (`Seed-san.vrm`'s seven scaled hair and bag joints). A clip that animates
  scale raises `VRM_RETARGET_NON_UNIT_SCALE` and is not applied
  ([MOTION_CONTRACT.md](../design/MOTION_CONTRACT.md#scale-policy-v090)).
- **The partial skeleton policy** (P1-3): the seven ways a clip and a rig
  disagree, with what the retarget does, the code it reports and the test that
  holds each row
  ([MOTION_CONTRACT.md](../design/MOTION_CONTRACT.md#partial-skeleton-policy-v090)).
- **The snapshot rule is checked, not only stated**: `execMotion_boundaries`
  and `execVrm_boundaries` read sources, built imports, link libraries and
  schema declarations for I/O, clocks, threads, mutable state and stage access.

### A clip's face and gaze reach a rig (Motion Phase G)

Not part of the OpenExec boundary, and shipped with it because it landed on
`main` in the same interval. It is offline only: exec computes neither.

- **Expressions.** `vrm:expressionName` joins a `.vrma` clip's named weights to
  one avatar's morph-target and material-colour binds (`ExpressionResolver`),
  and `motion_retarget` authors `blendShapes` / `blendShapeWeights` on the
  animation it binds. VRM 0.x presets migrate to the VRM 1.0 vocabulary, and a
  name declared twice is `VRM152`.
- **Override arbitration.** An avatar's `overrideBlink`, `overrideLookAt` and
  `overrideMouth` are imported onto `VrmExpressionAPI` and applied before the
  binds, so two co-active expressions no longer both own the eyelid.
- **Look-at.** A `.vrma` clip's target point is carried on the pose and
  authored under `/Animation/LookAt`. `LookAtEvaluator` turns it into one rig's
  answer: eye-joint rotations for a `bone` rig, the four gaze expressions for an
  `expression` rig.

### The distribution rows

- **`motion_retarget --load-report`, `--build-info` and `--version`.** The
  product's tool bakes the textured `Seed-san.vrm` from the install, and its
  load report must show nothing loaded from a source tree.
- **Embedded textures from the artifact.** A Python host resolves all 28 of
  `Seed-san.vrm`'s textures to bytes through the product's resolver. With the
  resolver hidden, none resolve.
- **Windows DLL discovery is settled.** That environment is the product's
  activation file applied by hand, and it shows that **`PATH` is enough, for a
  Python host too**: no `os.add_dll_directory`. INSTALL.md now prescribes it.
- **Every product binary is scanned for the source tree**: no build directory,
  staging area or PDB path on any OS. Two kinds of match are counted instead
  of failed, and both are known limitations below.
- **Every executable and file format opens non-ASCII paths on Windows**
  (`workspace_unicode_paths`), and the motion layer's CTest suites are labelled
  and fail the build when one registers nothing.

## Compatibility

- **OpenUSD:** exactly 26.08, with OpenExec, on Windows x86_64, macOS arm64 and
  Linux x86_64. A runtime without the OpenExec libraries fails at configure
  time.
- **Schema contract:** version 1, unchanged.
- **Package version:** a minor bump, in lockstep. Every descriptor, every
  `requires` range (`>=0.9,<0.10`), every CMake standalone fallback and the
  aggregate product read `0.9.0`: 49 files and 86 replacements, plus `VERSION`.
  It is minor because in-tree dependents use library API added since v0.8.0,
  and a `>=0.8,<0.9` range would have admitted the packages that lack it
  ([PACKAGE_CONTRACT.md §3.1](../architecture/PACKAGE_CONTRACT.md#31-a-requires-range-between-two-releases)).
- **Workspace graph at the bumped version:** 6 bundles, 3 bundle edges,
  12 libraries, 24 library edges, 6 tools, valid.
- **Measured at the bumped version, on Windows, before the dry run:** the
  workspace suite is **154 of 154**. `ost plugin test --workspace --up-to 5`
  reports 6 bundles and 0 failed. `ost plugin package --workspace --product`
  reports 6 packages plus 6 tool packages, and a product of **9 members**: the
  six bundles and `motion_bvh`, `motion_capture` and `motion_retarget`, every
  archive named `-0.9.0-`. The artifact-only exec and BVH smokes both pass from
  that product. macOS and Linux are the dry run's to measure.
- **Behaviour change in a bake:** `scales` now carries each joint's rest scale.
  On a rig with no scaled rest the output is unchanged. `motion_retarget`
  gains three options and loses none.
- **`vrmRetarget`'s `TargetJoint` gains a field** (`restScale`), part of its
  `operator==`. A consumer that aggregate-initialises it positionally must add
  it.

## Known limitations

Everything here was measured or attempted.

### OpenExec

- **Realtime skinned-avatar display is not in this release.** OpenUSD 26.08
  resolves exec prim adapters from a hard-coded list, so P0-7 ships an
  exec-computed `UsdGeomXformable` instead. The fix is upstream.
- **Exec computes no gaze and no expressions.** A bake with a gaze onto a
  bone look-at rig differs from exec on the two eye joints. `--no-look-at`
  agrees. Both follow on the `ExecIr` track.
- **Nothing but fixtures and the parity harness authors the stage conventions
  the exec bundles read**: `motion:timeCodesPerSecond`, `motion:filter:*`,
  `motion:root:*`, `vrm:retarget:sourceSkeleton` and the four `vrm:retarget:*`
  root statements. They are handed to the motion migration's producer contract
  (MIG-0), not frozen here for identities that are leaving.
- **A one-joint clip that keys nothing samples to a pose nobody stated**: hips
  at identity and a root at the origin, from 26.08's fallback delivery.
  Kept and pinned rather than refused, because the callback cannot tell it from
  an authored origin.
- **The parity rows no producer reaches are asserted, not run on both sides**:
  a rig whose rests do not pair, a binding to a missing joint, two bones on one
  joint, and the rest of the parity report's §7 list. The gate is agreement on
  the same recorded input, which holds.
- **The fourteen boundary findings are recorded, not fixed.** Several library
  entry points still exist only in `motion_retarget`, so a bundle restates
  them. One was closed in this release: the rest decomposition, which both now
  call from `vrmRetarget`.

### Distribution

- **The artifact-only rows run in `release.yml`, not on a pull request.** A
  pull request proves the build tree; the release dry run proves the product.
- **Eight plugin libraries carry 23 source *file* names**, the `__FILE__` that
  OpenUSD's registration macros expand. They are names, not dependencies. The
  scan counts them.
- **Linux and macOS binaries keep the build machine's RPATH.** Measured in the
  v0.9.0 dry run: every product `.so` / `.dylib` and tool executable carries
  the runtime directory it was built against as an RPATH / RUNPATH / LC_RPATH
  entry, and `usdVrmFileFormat`, `usdVrmPackageResolver` and
  `usdVrmaFileFormat` also carry the build tree's
  `.strata/targets/<target>/workspace-prefix/lib`. Packaging does not rewrite
  them. On a user's host those directories do not exist and are skipped, and
  the smoke's load reports show nothing loaded from them. On a host where one
  exists, it is searched first. The scan counts them rather than failing, and
  the fix belongs in packaging (an `$ORIGIN` / `@loader_path` rewrite, or none).
- **The non-`ost` path is covered from an installed prefix, not from
  hand-extracted per-bundle archives.** The smoke applies the activation by
  hand, but it still extracts with `ost plugin product install`.
- **With several bundles on `PATH`, a shared library loads from the first
  directory that holds a copy.** On Windows `vrmContainer.dll` answered from
  `execMotion`'s. The copies are the same library, and INSTALL.md says so.
- **`release.yml` stays hand-authored**, and its last bundle still decides
  every package's libraries (ost report 40). `check_product_libraries.py` is
  the check.
- **Carried from v0.8.0, unchanged:** no Linux or macOS symbol baseline, no
  real-runtime compatibility lane, per-bundle CI cells kept only to reach a
  verb, no adapter artifact in a release, and the operator evidence of v0.7.0
  (a VMC relay session, a producible tracking loss, a labelled rolled take, a
  redistributable mocopi capture). See
  [current.md](../roadmap/current.md#carried-over-from-shipped-releases).
