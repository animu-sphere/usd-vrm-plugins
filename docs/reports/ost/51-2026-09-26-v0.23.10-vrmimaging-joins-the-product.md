## TL;DR

**Report 50's P1 is delivered, and `vrmImaging` is a bundle and a product
member.** 0.23.10 took the first of the three options report 50 offered: the
kind no longer requires `hydra-preview`, and the usdImaging SDK in the
resolved runtime is what it checks. The workspace keeps the `usd` profile and
its lock.

1. **Adopted** (§1). `plugins/vrmImaging` has a `usd-imaging` descriptor that
   provides both adapters, is a workspace member and a release member, and is
   discovered by the root glob like every other bundle.
2. **Every release-lane step passes locally** (§2). This includes a
   digest-reproducible product of eight members, and `vrmImaging` passing
   L0–L4 both from the build tree and from its package, with the native
   `imaging.registration` L2 constructing both adapters.
3. **The negative cases hold** (§3). A descriptor that asks for
   `hydra-preview` explicitly is still refused under `usd`, and
   `USDIMAGING_ENABLE_PLUGINS=0` still fails L2 and names the variable.
4. **One defect of ours, found on the way** (§4). The release lane's
   artifact-only exec smoke had been reading a fixture directory that #233
   moved. No pull-request event runs that lane, so a tag would have been the
   first to fail on it.

## 1. What was adopted

The descriptor is report 50 §1's draft with three changes. It drops
`hydra-preview`, as 0.23.10's migration note says. It lists both adapters,
because Step I1 added `VrmMaterialAPI` after that draft was written. And it
lists both fixtures.

```yaml
plugin:
  name: vrmImaging
  version: 0.9.0
  kind: usd-imaging
runtime:
  openusd: "==26.08"
  cxx_abi: inherit
provides:
  - usd-imaging:VrmMaterialAPI
  - usd-imaging:VrmMToonAPI
requires:
  capabilities: [usd-stage-read]
  bundles:
    - { id: vrmSchema, version: ">=0.9,<0.10", contract: 1 }
usd:
  plug_info: plugin/resources/vrmImaging/plugInfo.json
tests:
  smoke: [tests/fixtures/material_core.usda, tests/fixtures/mtoon_materials.usda]
```

Around the descriptor:

- `openstrata.toml` names `plugins/vrmImaging` in `members` and `vrmImaging`
  in `release_members`.
- The root `CMakeLists.txt` no longer adds the directory by name. The bundle
  glob finds it.
- `release.yml` builds it in the per-bundle loop, before the last bundle
  (`usdVrmaFileFormat`, whose closure has to stay last; report 40).
- `usdvrm_baseline` has the bundle in its session. `discovery.json` adds the
  two adapter types it registers, `UsdVrmImagingMaterialAPIAdapter` and
  `UsdVrmImagingMToonAPIAdapter`, and nothing else (report 50 §4).

## 4. Ours: a release-lane fixture path

`scripts/artifact_only_exec_smoke.py` passed `--design-fixtures
docs/design/fixtures/motion` to the parity harness. #233 moved that design
triplet to `tests/motion/fixtures/design_triplet/`, and the PR lane's own
parity tests were updated to the new path. The release lane was not, and
nothing but `release.yml` runs this script. On the packaged product,
`generated_thirty_fps` and `vrma_walk` failed with `no avatar file at
...docs/design/fixtures/motion/avatar.usda`. The script now names the new
path, and all five cases and the negative case pass.

This is the same shape as the release-lane traps this series has recorded
before: a green pull request proves nothing about `release.yml`. It is not an
`ost` finding.

## 5. Not measured

- **Linux and macOS, as a bundle.** 0.23.10's release notes leave native
  downstream acceptance on those platforms open, and no pull-request lane
  here closes it. Every workspace cell is `verify: test`. It validates the
  graph with `vrmImaging` in it, builds the plugin and runs its suites, but
  it never runs `plugin test --workspace` or `plugin package`. Those run
  only in `release.yml`. So L1 `runtime.usd_imaging`, L2
  `imaging.registration` and the packaged plugin are measured on Windows
  only, until a `release.yml` run covers the other two platforms.
- **The hosted release cell.** No pull-request event runs `release.yml`. A
  `workflow_dispatch` dry run is how to prove it.
- **What the adapters contribute, from the product.** L2 proves that the
  packaged plugin registers and constructs both adapters. The scene-index
  values and invalidation are proved by `vrmImaging_mtoon` and
  `vrmImaging_material` against the build tree. Neither `ost` nor this
  repository runs them against the package yet (imaging track Step I5).
