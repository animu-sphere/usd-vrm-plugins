# The release lane's first execution was three releases late

- Date: 2026-09-01
- Version exercised: `ost 0.22.8`, on this workstation
  (`cy2026-windows-x86_64-py313-usd`) and on `windows-2022`, `macos-15` and
  `ubuntu-24.04` through `release.yml`'s `workflow_dispatch` dry run
- Occasion: v0.8.0 release preparation — the dry run the release checklist puts
  in front of the tag, run for the first time since the staging step was
  rewritten
- Prior report: [38](38-2026-08-30-v0.22.8-workspace-cell-verbs-and-orphaned-lanes.md)
- Next ask target: `ost 0.23.0`

## TL;DR

**The defect this found is ours, and the reason it survived to be found here is
not.** The dry run went red on all three OS at the same step, on a shell script
this repository wrote — and that step had never executed, on any host, since it
was rewritten around an `ost` feature that arrived *after* the last tag.

1. **The finding, restated as a cost.** Report 38's P2 said `kind: workspace`
   cells take `verify: graph|build|test`, so the two verbs a release turns on are
   inexpressible and `release.yml` is hand-authored. This report is what that
   cost: a workflow no `pull_request` event runs accumulated **two** silent
   divergences across three releases — a jq expression that cannot have ever run,
   and an `ost` bootstrap pin two patch versions behind the CI contract it is
   supposed to mirror (§2, §3).
2. **P2, restated with evidence** — a *release* contract, or any generated
   construct that runs the release verbs. Every mitigation available inside this
   repository is a convention: mirror the pins by hand, remember to dry-run.
   Both were followed here, and the dry run is the only one that worked (§5).
3. **P3 — nothing compares a hand-authored workflow's `ost` pin to
   `bootstrap.ost.version`.** `ost ci validate` runs in every generated job and
   is silent about the file beside it. We added a repo-side check rather than
   wait; upstream, `ci validate` knowing which workflows it does *not* own would
   be the general answer (§3).

**What went right, and it is most of the run.** `preflight` passed — tag equals
`VERSION`, changelog section finalized. Every 0.22.3 ask this step depends on is
delivered and behaved exactly as documented: `.data.release_members` resolves
`[workspace].release_members` minus `release_exclude`, `.data.product.members`
reports **7**, `.data.packages` carries all **10**, and `ost` would have failed
with `AGGREGATE_MEMBERSHIP_MISMATCH` before this step ran had the declaration and
the tree disagreed. The shapes are right; the consumer of them was wrong.

## 1. What was being done

v0.8.0 was prepared and merged, and `docs/roadmap/current.md`'s before-the-tag
list carries a row that exists because of this workflow's history:

> `release.yml` is dry-run with `workflow_dispatch --ref` before the tag — a
> green PR lane proves nothing about it.

So the dry run was run before the tag rather than after it. It failed, which is
the entire argument for the row.

```
preflight (tag = VERSION, changelog finalized)   success
release-macos-arm64                              failure   Stage the release artifacts
release-linux                                    failure   Stage the release artifacts
release-windows                                  failure   Stage the release artifacts
assemble release (draft)                         skipped
```

Three platforms, one step, one error:

```
jq: error (at .ost-ci/package.json:354): Cannot index array with string "name"
```

## 2. The defect, and why it could not have been caught

The staging step selects the aggregate's members out of everything `ost`
packaged:

```bash
release_members="$(jq -c '.data.release_members // empty' .ost-ci/package.json)"
jq --argjson rel "$release_members" \
   '[.data.packages[] | select($rel | index(.name))]' .ost-ci/package.json
```

`index()` evaluates its argument against **its own input**, and its input here is
`$rel` — the membership array. So `.name` is asked of an array, and jq refuses.
The fix binds the name before the pipe:

```bash
'[.data.packages[] | select(.name as $n | $rel | index($n))]'
```

(Index `0` is truthy in jq — only `false` and `null` are not — so `vrmSchema`,
first in `release_members`, selects correctly.)

**That expression cannot ever have run successfully.** It is guarded by a check
that exits when `.data.release_members` is absent, and `.data.release_members`
arrived in `ost` 0.22.3 on 2026-08-25 — after v0.7.0 was tagged. The step was
rewritten to consume it (correctly, in intent: reading `.data.packages` directly
is what had made it count six tools against three descriptors), and then nothing
executed it. `release.yml` runs on tag push and `workflow_dispatch` only; no
`pull_request` event reaches it, by design, for fork-PR safety.

So the sequence is: an `ost` ask is delivered → this repository adopts it in the
one workflow that has no automatic trigger → three releases' worth of PRs go
green → the first execution is a human remembering to dry-run.

**This is not an `ost` defect and the report says so.** What it is evidence for
is that report 38's P2 has a failure mode beyond job-count inflation. A lane that
cannot be generated is a lane that cannot be exercised, and an unexercised lane
does not stay correct across the toolchain changes it consumes.

## 3. The second divergence, found while fixing the first

`release.yml` bootstrapped **`ost` 0.22.6**. `openstrata.ci.yaml`'s
`bootstrap.ost.version` reads **0.22.8**, re-pinned in report 38's consolidation
on 2026-08-30. The generated lanes moved; the hand-authored one did not, because
regeneration does not touch it.

The three runtime digests in the same file *were* correct — they were updated by
hand at the same time as the contract's. So the mirroring is not neglected; it is
partial, which is the harder failure to see. Nothing reports it: `ost ci
validate` runs in every generated job and says nothing about a workflow it does
not own, and `ci plan` and `ci generate --force` are equally silent — the same
silence report 38 §3 measured for an orphaned lane, in a different direction.

The pin is now 0.22.8, and a check in `scripts/check_docs.py` compares
`release.yml`'s three occurrences of the version against
`bootstrap.ost.version`. That is a repo-side answer to a general problem, and it
is offered upstream in §5 rather than kept as a local trick.

**What it did not cost:** nothing in the failure was attributable to 0.22.6.
Both the bootstrap and the packaging behaved as documented on it; the error is
in the jq. Report 38's observation that a 0.22.6 → 0.22.8 re-pin renders as
deletions and nothing else is consistent with that.

## 4. What behaved, in detail

Worth recording because the staging step consumes four separate 0.22.3
deliverables and every one of them was shaped as documented. Measured on this
workstation with `ost plugin package --workspace --product --json`:

| Field | Value |
| --- | --- |
| `.data.packages` | 10 entries — 4 `member: "bundle"`, 6 `member: "tool"` |
| `.data.release_members` | `vrmSchema`, `usdVrmFileFormat`, `usdVrmPackageResolver`, `usdVrmaFileFormat`, `motion_bvh`, `motion_capture`, `motion_retarget` |
| `.data.product.members` | `7` |
| `.data.product.data_files` | present (the motion profiles, `[[workspace.install_data]]`) |

The three adapter CLIs — `mocopi_record`, `vmc_record`, `vrchat_osc_record` —
are packaged and are correctly absent from `release_members`.

One shape worth naming for anyone reading the JSON: **`.data.product` is `null`
unless `--product` is passed.** `ost plugin package --workspace --json` alone
packages every member and produces no aggregate, which is correct and is not
obvious from the field's presence in the schema. `release.yml` passes
`--product`; a script that omits it and then reads `.data.product.members` gets
`null` and, in bash arithmetic, an error one step later than the cause. Not an
ask — the behaviour is right — but the `null` is worth a sentence in the docs.

## 5. Asks

**P2 — a release contract, restated from report 38 with a second failure mode.**
`openstrata.ci.yaml` cannot express `ost plugin test --workspace` or `ost plugin
package --workspace`, so the workflow that runs them is hand-authored, and a
hand-authored workflow is one nothing keeps honest. Report 38 costed this in
jobs; this report costs it in correctness. Either the `release:` contract, or
`verify: package` / `verify: pyramid` on a `kind: workspace` cell, removes both
costs at once. This is the same P2, and it is now carrying two receipts.

**P3 — let `ci validate` know what it does not own.** A repository has workflows
`ost` did not generate, and today `ci validate` cannot say anything about them.
The narrow version is enough: a way to declare that a file mirrors
`bootstrap.ost.version` (and, ideally, the runtime digests) and to have `ci
validate` fail when it stops matching. The general version — `ost` owning the
release lane — is the P2 above; this is what closes the gap in the meantime, for
every repository that has one hand-authored workflow it cannot delete.

**P3 (documentation) — say that `.data.product` is `null` without `--product`.**
One sentence beside the field.

## 6. What this changes here

- `release.yml`: the jq fixed, the `ost` pin moved 0.22.6 → 0.22.8, and the trap
  written into a comment above the line so the next reader does not re-derive
  jq's `index()` evaluation order from a red run.
- `scripts/check_docs.py`: a check that `release.yml`'s `ost` version agrees with
  `bootstrap.ost.version`, made to fail before it was believed.
- The before-the-tag row that produced this report stays exactly as written. It
  earned its place: the dry run was the only thing standing between a rewritten
  step that had never run and a tag.
