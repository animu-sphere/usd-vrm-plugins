# OST v0.20.0 dogfooding — a runtime can demand a host package the CI contract cannot name

- Date: 2026-07-26
- Version exercised: `ost 0.20.0`, `ost ci generate github`, on GitHub-hosted
  `ubuntu-24.04` / `macos-15` / `windows-2022`
- Occasion: [report 30](30-2026-07-26-v0.20.0-macos-2608-runtime-publish.md)
  re-pinned every lane to OpenUSD 26.08. The Windows and macOS cells went green
  on the first run; all four Linux cells failed at configure in under 20
  seconds. This report is the diagnosis and the resulting ask.
- Related reports: [30](30-2026-07-26-v0.20.0-macos-2608-runtime-publish.md)
  (the re-pin that exposed this),
  [29](29-2026-07-26-v0.20.0-openusd-2608-runtime-publish.md) (the Linux 26.08
  runtime involved), [22](22-2026-07-17-v0.17.0-evidence-gate-v0.18.0-asks.md)
  (the last time a generated gate could not be satisfied from inside the
  contract)
- Next ask target: `ost 0.21.0`

## TL;DR

Upgrading the runtime from OpenUSD 26.05 to 26.08 changed what the **host** must
have installed, and there is no way to say so in `openstrata.ci.yaml`.

26.08 bundles MaterialX 1.39.5, whose exported `MaterialXConfig.cmake` gained an
unconditional `find_dependency(X11 REQUIRED COMPONENTS Xt)` on non-Apple UNIX.
`pxrConfig.cmake` `find_dependency(MaterialX)`s, so *every* Linux consumer of a
26.08 runtime now needs X11 development headers merely to **configure** — before
compiling a single file. The GitHub-hosted `ubuntu-24.04` image does not have
them.

The fix is one `apt-get install libx11-dev libxt-dev`. The problem is that
`openstrata.ci.yaml` has exactly one host-provisioning knob, `host_python`, so
the fix has to be hand-written into `ost ci generate`'s output — the one thing
this repo's CI policy forbids, and something the next `--force` regeneration
silently deletes.

**A runtime artifact is not self-contained: consuming it can require host
packages. Neither the artifact nor the CI contract can currently say which.**

## 1. What actually failed

Four cells, all Linux, all ~19s, all identical. The runtime pulled and
materialized fine — `artifact pull` passed every gate, exactly as report 30
verified locally. The failure is one step later:

```console

CMake Error at .../FindPackageHandleStandardArgs.cmake:233 (message):
  Could NOT find X11 (missing: X11_X11_INCLUDE_PATH X11_X11_LIB Xt)

  .../CMakeFindDependencyMacro.cmake:76 (find_package)
```

The chain is worth reading in full, because every link is inside the runtime we
publish: our `find_package(pxr)` → the runtime's `pxrConfig.cmake` → the
runtime's `MaterialXConfig.cmake` → `find_dependency(X11 REQUIRED)`.

## 2. Why it appeared exactly now

Not a regression in `ost`, and not caused by the macOS publish. It is a
MaterialX minor-version bump that rode along with OpenUSD 26.08:

| | MaterialX | X11 block in `cmake/modules/MaterialXConfig.cmake.in` |
| --- | --- | --- |
| OpenUSD 26.05 | 1.39.4 | **absent** |
| OpenUSD 26.08 | 1.39.5 | **present** (lines 42–43) |

```cmake
if(UNIX AND NOT APPLE)
    find_dependency(X11 REQUIRED COMPONENTS Xt)
    if("RenderGlsl" IN_LIST MaterialX_FIND_COMPONENTS)
        find_dependency(OpenGL REQUIRED)
    endif()
endif()
```

Two properties make this bite harder than it looks:

- **The guard is platform-only.** It does not test whether MaterialX was built
  with X11, or whether the consumer asked for any render component. Linux gets
  the hard `REQUIRED` unconditionally. Rebuilding the Linux runtime differently
  would not remove it.
- **It is `REQUIRED` inside a transitive `find_dependency`.** The consumer never
  asked for MaterialX, let alone X11; it asked for `pxr`. There is no
  `MaterialX_FIND_QUIETLY`-style escape a consumer can set from outside.

This also explains the platform split cleanly, and confirms it is not a
digest/registry problem: macOS is `APPLE` and Windows is not `UNIX`, so neither
enters the branch. The macOS 26.08 runtime published in report 30 went green on
its first CI run.

## 3. Ask (P0) — the CI contract cannot express a host package

`openstrata.ci.yaml` describes cells with `runner`, `runtime_artifact`,
`runtime_remote`, `bundle`, `platform`, `profile`, `up_to`, and `host_python`.
`host_python` is the *only* host-provisioning knob, and it exists precisely
because a runtime turned out to need something from the host that the artifact
could not carry (report 14, the Windows `python.exe` case). This is the same
shape of problem one package manager over, and there is no knob for it.

So the fix had to go into the generated workflow by hand:

```yaml
- name: Install X11 dev headers required by MaterialX 1.39.5 (hand-added)
  if: ${{ matrix.hosted && runner.os == 'Linux' }}
  run: sudo apt-get install -y --no-install-recommends libx11-dev libxt-dev
```

That is a deliberate, commented exception to this repo's policy that
`ost-*.yml` is renderer output. It is also **fragile in a way ost controls**:
`ost ci generate github --force` deletes it without a word, and the next person
to regenerate will turn four cells red and have to rediscover this report.

**Ask.** A per-cell (or per-runner) host-dependency declaration that
`ci generate` renders into the appropriate provisioning step — `apt-get` on
Linux, `brew` on macOS, and a clear error on Windows. Something like:

```yaml
  - name: usdvrmfileformat-pr-linux
    runner: linux-hosted
    host_python: "3.13"
    host_packages:            # rendered as the runner's native installer
      apt: [libx11-dev, libxt-dev]
```

Two acceptance criteria matter more than the syntax:

1. It must live in `openstrata.ci.yaml`, so regeneration is lossless and the
   policy "the matrix is the contract" stays true.
2. `ci generate` must not silently drop hand-added steps it does not understand
   — or, better, must make them unnecessary. Today a `--force` regeneration is
   an unreviewable, silent semantic change to CI.

## 4. Ask (P1) — a runtime should declare the host packages it needs to consume

The deeper issue is that the artifact knows this and does not say it. The Linux
26.08 runtime *contains* the `MaterialXConfig.cmake` that hard-requires X11. ost
packed that file, publishes it, and `runtime validate` passes 7/7 on a machine
where consuming it is impossible.

`validate` already checks that the runtime's own tools work (`usdcat-present`,
`schema-gen-deps`, `bin-tools-executable`). It does not check that a *consumer*
can `find_package(pxr)`. On the producer's machine — a build container that
necessarily had X11 headers, since it just built MaterialX — that gap is
invisible. It only surfaces on a clean consumer, which is CI.

**Ask.** Either:

1. Record consumption requirements in the runtime manifest (a
   `host_requirements` list ost can render into CI and check at
   `artifact pull`), or
2. Add a `consumer-configure` check to `runtime validate` that runs a trivial
   `find_package(pxr)` against the materialized runtime in a scratch directory.

Option 2 is cheap and would have caught this at publish time, on the producer's
machine, before the digest ever reached `openstrata.ci.yaml`. It is the same
argument report 30 §1 makes about the macOS deployment target: **ost measures
what a runtime *is* far more carefully than what a runtime *needs*.**

## 5. Not an ost problem, recorded for completeness

MaterialX 1.39.5's `find_dependency(X11 REQUIRED COMPONENTS Xt)` is arguably an
upstream bug — a config package should not impose a hard GUI dependency on
consumers who requested no render components. That belongs upstream with
MaterialX (or with OpenUSD, for exporting it transitively through
`pxrConfig.cmake`), and this report makes no claim that `ost` should work around
it. The ask here is only that ost let the contract *say* what the host needs,
and ideally notice at publish time that a consumer would fail.
