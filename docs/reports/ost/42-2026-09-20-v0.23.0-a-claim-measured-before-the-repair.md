## TL;DR

**Report 41's P1 is delivered and measured. The same upgrade turns every
hosted Linux and Windows lane in three repositories red, on a claim whose
subject the next step of the same job repairs.**

1. **P1: `ost runtime validate`'s new `consumer-link` claim runs before the
   repair `ost` performs for every other consumer of the same prefix.**
   `relocate_baked_python_if_stale` is called from `configure` and
   `plugin build`; `runtime validate` does not call it. A generated job's step
   order is *pull runtime → validate → build*, so the claim is always measured
   against an unrepaired prefix. On the three pinned 26.08 leaves that means
   Linux and Windows fail and macOS passes. The generated workflow is not
   hand-editable, `runtime validate` has no opt-out, and the step is in every
   cell that materializes a runtime — so the upgrade is refused as a whole
   (§2.1).
2. **The artifact is not the defect.** Pulled onto this workstation and given
   a simulated clean host, the pinned Windows leaf fails the claim with CI's
   exact message; one `ost configure` prints `relocated baked Python include
   in 2 runtime CMake file(s)`; `ost runtime validate` then passes. That
   sequence is the measurement this report exists for (§2.2).
3. **P2: the claim's detail names nothing that would find the cause.** It
   carries CMake's trailing *Manually-specified variables were not used* block
   and `CMake Generate step failed`, and neither is the error. Diagnosis
   required pulling the pinned artifact and reproducing locally (§3).
4. **Report 37's P1 is the underlying condition and is still open.** What
   changed is where it surfaces: `ost build` has always hidden it, and
   `runtime validate` now reports it one step early (§4).
5. **P3: `artifact.source: file://` takes a package-output directory, not the
   `dist/` root the reference's phrase names, and the refusal's hint spells a
   plugin's layout rather than a library's** (§5).

## 1. What was being done

Report 41's P1 asked for a `requires.libraries` entry that can name a library
artifact from another repository, because the motion migration
([the migration track](../../roadmap/motion-foundation-split.md)) split this
workspace across three and every consuming half has been blocked on it since
2026-09-19. `ost 0.23.0` delivers it.

The change under test is only the pin: `bootstrap.ost.version` 0.22.8 → 0.23.0
here (0.22.10 → 0.23.0 in the two destinations), the workflow re-rendered from
it, and `release.yml`'s hand-mirrored pin updated with it. No cell, digest,
runtime or source file moved.

Locally that is green: `ost ci validate` 7 cells, the workspace graph valid at
6 bundles / 12 libraries / 24 library edges, and `ost build` + `ost test`
159/159.

## 2. The defect

### 2.1 Measured on the hosted lanes

Every cell that materializes a runtime runs, from the generated workflow:

```yaml
- name: Validate the materialized runtime (runnable tools)
  run: ost runtime validate <platform> --profile <profile> --json
```

Under 0.22.8 that passed. Under 0.23.0, on `usd-motion-plugins` #17,
`workspace-pr-linux`:

```text
  "detail": "find_package(pxr) configures against .../openstrata-cy2026-linux-x86_64-py313-usd",
  "name": "consumer-configure",
  "status": "pass"

  "detail": "linkable consumer configure failed:     CMAKE_POLICY_VERSION_MINIMUM /
             Python3_EXECUTABLE /     Python_EXECUTABLE /     Python_INCLUDE_DIR /
             Python_LIBRARY / CMake Generate step failed.  Build files cannot be
             regenerated correctly.",
  "name": "consumer-link",
  "status": "fail"
```

`workspace-pr-windows` fails identically; `workspace-pr-macos-arm64` passes.
`usd-vrm-plugins` #211 fails the same way on its Linux and Windows workspace
and bundle cells. That is 2 of 3 platforms in three repositories, on a pin
bump.

`consumer-configure` — the claim 0.22.x had — passes in the same run. The
release notes say 0.23.0 "distinguishes a CMake configure result from a C++
consumer that links and runs against the selected OpenUSD export", and this is
that distinction firing.

### 2.2 Reproduced locally, with the repair

The pinned Windows leaf (`sha256:ebb0c7da…`, pulled from its `oci://`
reference into an isolated `OST_HOME` so this workstation's adopted runtime
was untouched) **passes** `consumer-link` here. It passes because the path
baked into its CMake package exists on this host: this workstation is the
machine that produced it. `pxrTargets.cmake` names the producer's
`Python313/Include` in 16 imported targets, and `pxrConfig.cmake` bakes the
same path once more in its native separator form.

Rewriting that one path to a directory that does not exist — in **both**
separator forms, which is what makes the host clean rather than merely
inconsistent — reproduces CI exactly:

```text
$ ost runtime validate cy2026 --profile usd            # simulated clean host
consumer-configure  pass
consumer-link       fail   linkable consumer configure failed: … Generate step failed.

$ ost configure --target cy2026 --profile usd
==> relocated baked Python include in 2 runtime CMake file(s)

$ ost runtime validate cy2026 --profile usd            # same prefix, after the repair
consumer-configure  pass
consumer-link       pass
ok = true
```

`crates/ost-cli/src/commands/configure.rs` calls
`relocate_baked_python_if_stale` before it writes the toolchain, and
`plugin build` calls it too. `runtime validate` does not. The claim is
therefore measured against a state that no build ever compiles against, and
reports a failure the next step of the same job removes.

The guard on the repair is what hides this from a producer: it rewrites only a
baked path that is absent on the current host, so the machine that exported the
artifact — and only it — passes the claim as published. A first attempt at this
measurement rewrote only the forward-slash occurrences and changed nothing,
because the marker the repair reads (`set(Python3_INCLUDE_DIR [[…]])`) is in
backslash form and still resolved.

## 3. The detail does not carry the error

The failing detail is the tail of CMake's output: the *Manually-specified
variables were not used by the project* block, then `CMake Generate step
failed`. The unused list is a consequence of the probe passing `Python_*`
overrides the project did not consume, and the generate error itself — the
imported target whose include directory is absent — is not in it. Nothing in
the message names a path, a target or a file, so the only way to the cause was
to pull the artifact and reproduce it.

A claim that runs a CMake configure should carry the first error line of that
configure, not its last.

## 4. Report 37's P1, and where it surfaces

[Report 37](37-2026-08-30-v0.22.6-runtime-python-paths-from-the-producer.md)'s
P1 — a pulled runtime's CMake package names the Python of the machine that
built it — is the condition underneath this. It has been open since 2026-08-30
and is unchanged. Two things have moved:

- 0.22.10 made **newly exported** artifacts relocatable. The three leaves
  pinned across this ecosystem predate it, so they still carry the producer's
  paths, and only a republish can change their bytes.
- `ost` has meanwhile learned to repair a materialized prefix on the consumer
  side, which is why every lane that builds has been green regardless. 0.23.0
  now measures the prefix before that repair, so the condition surfaces as a
  hard failure for the first time.

So this is not a regression in the artifacts and not a new defect in the
runtime; it is an ordering defect in a new claim. Republishing the leaves would
also resolve it, and is worth doing on its own merits, but a claim that
disagrees with the toolchain's own behaviour on the same prefix should not need
a republish to pass.

## 5. Asks

- **P1: apply the materialized-prefix repair before the consumer claims, or
  run the claims after it.** Either `runtime validate` calls
  `relocate_baked_python_if_stale` for the prefix it is about to probe, or the
  generated workflow validates after the first step that repairs. Failing both,
  a documented way for a cell to record the claim as known-failing would at
  least let a repository upgrade; today the step is unconditional and the
  workflow is not hand-editable (report 38's P2 again).
- **P2: carry the configure error in the claim's detail.** The first error of
  the failing CMake run, not the trailing warning block.
- **P3: say which directory `artifact.source: file://` takes.** The reference
  calls it "an air-gapped `file://` dist directory", and a library's `dist/`
  root is refused — `PRECONDITION_FAILED: … has no manifest.json — point at a
  package output directory (e.g. dist/plugins/<name>/<version>/<target>/)`. The
  hint spells a plugin's layout; a library's is
  `dist/<library>/<version>/<target>/`. Both the reference and the hint should
  name the library shape.
- Report 37's P1 stands. This report is a second receipt for it.

## 6. What worked

**Report 41's P1 is delivered, and it is the reason to take this pin.**
Measured here on a disposable branch: `libs/motionCore` removed from
`[workspace].members`, its nine consumers' `requires.libraries` given
`artifact.targets` with the published digest and a `file://` source, and the
library packaged out of `usd-motion-plugins` with `ost library package`:

```text
$ ost plugin test --workspace --graph-only
Workspace dependency graph: 6 bundle(s), 3 bundle edge(s), 11 libraries,
24 library edge(s), 6 tool(s), valid

$ ost library pull --target cy2026 --profile usd
Pulled 1 external library artifact(s)

$ ost library build libs/motionRuntime
… cl.exe … -external:I<repo>/.strata/external-libraries/cy2026-windows-x86_64-py313-usd/motionCore/131a6c79…/include …
```

The library count drops by one and **the 24 library edges do not**: the
dependency is still declared, still validated and still in the graph, which is
exactly what report 41 §2.2 refused to give up. The only failure is
`motionCore/Humanoid.h`, which is this repository's own rename work against the
destination's `MotionPose.h`.

- The empty-workspace half of report 41 (its P3) is delivered too.
- `ost library pull` is a no-op success where no external artifact is declared
  (`{"libraries": []}`, `ok: true`), so the new step costs a repository nothing
  until it uses it.
- The render now passes `--require-openusd` and `--require-openusd-version`
  positionally, which is 3DGS report 04's finding, and no cell here declares
  neither.

## 7. Answered in `ost 0.23.1`, the same day

All three asks are delivered in
[v0.23.1](https://github.com/animu-sphere/open-strata/blob/main/docs/releases/v0.23.1.md),
published 2026-09-20. Re-measured here before the pin moved, against the same
pinned Windows artifact in the same isolated `OST_HOME`, from a **simulated
clean host** — because this workstation produced that artifact, its own green
is not evidence:

- **P1.** With the baked Python path rewritten in both separator forms to a
  directory that does not exist, `ost runtime validate cy2026 --profile usd`
  now answers `consumer-configure pass`, `consumer-link pass`, `ok = true`.
  The repair is the mechanism and not a tolerance: after the run, the 16
  imported targets in `pxrTargets.cmake` and the marker in `pxrConfig.cmake`
  name this host again. `--json` still emits one document, so the relocation
  notice does not corrupt a parsed step.
- **P2.** With the repair made impossible (the `set(Python3_INCLUDE_DIR [[…]])`
  marker hidden, so nothing can be relocated), the claim fails and its detail
  is now `linkable consumer configure failed: CMake Error in CMakeLists.txt: /
  Imported target "tf" includes non-existent path`. That is the error §3 asked
  for: the first one, naming the target. Under 0.23.0 this same state produced
  only the trailing unused-variable block.
- **P3.** The release records the `file://` shape — a package output directory
  holding `manifest.json`, `dist/<library>/<version>/<target>/` for a library —
  in both the reference and the refusal's hint.

One consequence of the claim is worth recording, because it is not a defect
and it did cost a red cell here: `consumer-link` **runs** the consumer it
links. On Windows that executable loads `python313.dll` through pxr, and the
Windows runtime bundles no interpreter, so a cell that declares no
`host_python` builds the consumer and then fails it at `0xC0000135`. Six of
this repository's seven cells already declared 3.13; the seventh
(`usdvrmfileformat-pr-windows`, capped at L4) did not, and now does. Any
repository pinning a `py313` runtime on Windows needs a host interpreter of
that ABI from 0.23.x onward, whatever its pyramid level.

Report 37's P1 is untouched by this and stays open: the published leaves still
carry producer-local paths in their immutable bytes, and only a republish
changes that. What 0.23.1 changes is that a consumer is no longer told those
bytes are unusable when its own toolchain repairs them.

The pin this repository takes is therefore **0.23.1**, and `consumer-link` is
evidence rather than an obstacle.
