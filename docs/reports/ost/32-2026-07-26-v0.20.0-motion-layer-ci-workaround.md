## Forward-note on report 28

Report 28's P0 — *plain libraries and CLI executables have no CI cell* — is
**still open**, and v0.5.0 did not manage to work around it either.

v0.5.0 wrote `.github/workflows/motion-ci.yml` to cover the layer by building
the whole workspace with plain CMake. Two thirds of it work; the configure step
does not, for a reason that is itself an ost finding (§5). The lane ships
**disabled** rather than red on every PR.

This report therefore records two things: what the workaround cost to get that
far, and where it stopped. Both strengthen the original ask — the second more
than the first, because it shows the hand-rolled path runs into a problem
`ost plugin build` already solves internally and does not expose.

## TL;DR

**The workaround does not currently work, and that is the headline.** A repo
cannot reproduce by hand what `ost plugin build` does, because the part that
matters is not documented or exposed: configuring against a pulled runtime with
a bare `cmake` fails to resolve Python's development components (§5).

Getting as far as it did took **~210 lines of workflow YAML per repo**, of which
**~120 are a verbatim copy of generated logic** — the `ost`
bootstrap, the artifact pull, the runtime materialisation, and the Linux X11
workaround from report 31. Every one of those is a line that `ost ci generate`
already knows how to emit correctly and that now has a second, hand-maintained
copy which will drift.

The remaining ~70 lines are the only part that is genuinely repo-specific, and
they are three commands.

## 1. What the workaround actually needs

The insight that made it tractable: **`ost plugin run` exports
`CMAKE_PREFIX_PATH`.**

```console
$ ost plugin run plugins/vrmSchema -- python -c "import os; print(os.environ['CMAKE_PREFIX_PATH'])"
C:/Users/snkm/.ost/runtimes/openstrata-cy2026-windows-x86_64-py313-usd
```

So a plain-CMake build of the whole workspace does not have to reach into the
runtime store's directory layout — it runs inside a session:

```yaml
- run: ost plugin run plugins/vrmSchema -- cmake -S . -B build/motion-ci -DUSDVRM_BUILD_TESTS=ON
- run: ost plugin run plugins/vrmSchema -- cmake --build build/motion-ci --config Release
- run: |
    ost plugin run plugins/usdVrmaFileFormat --with plugins/vrmSchema \
        -- ctest --test-dir build/motion-ci -C Release -R "motion|vrmRetarget|vrmContainer"
```

That is the whole repo-specific part. It covers 13 CTest assertions across
`motionCore`, `motionRuntime` (including the Phase D live-capture surface and
the capture corpus), `vrmRetarget`, `vrmContainer`, and both CLI tools — none of
which any generated cell reaches.

**This is the shape the ask should take.** A `library` cell kind that did the
above, or a `plugin test --workspace --build` that compiled and ran plain
libraries' tests, would delete the entire hand-written file.

## 2. What had to be copied, and will drift

| Copied from the generated lane | Lines | Why it cannot be shared |
| --- | --- | --- |
| `ost` bootstrap (pinned asset + SHA-256 verify + PATH export) | ~40 | No `ost ci bootstrap` step or reusable action to call |
| Artifact pull + cache-hit check + `runtime pull --from-artifact` | ~20 | Same |
| Runtime digest pins per OS (3 × artifact + 3 × OCI reference) | ~12 | `openstrata.ci.yaml` is not readable by a hand-written workflow without a parser |
| Linux X11 host packages (report 31) | ~10 | Still no host-package knob in the CI contract |
| Billing notice, cache key, `setup-python` | ~15 | Same |

The digest pins are the dangerous ones. There are now **two** places in this
repo that must be re-pinned together on every runtime republish, and a motion
cell silently left on an older OpenUSD than the bundle cells would be worse than
no cell — it would look like coverage. Both files carry a comment saying so;
that is a mitigation, not a fix.

### Ask (P1, `ost 0.21.0`)

Let a hand-written workflow read the resolved matrix, e.g.
`ost ci matrix --json --lane pull_request`, emitting the cells with their
runtime artifact and remote reference. That alone removes the drift risk from
this and every other repo that needs a lane `ost ci generate` cannot express.

## 3. The gate that had never run

Wiring the lane surfaced something worth recording separately: the same root
build registers `usdvrm_baseline`, the whole-workspace behavior gate, and **it
had been silently stale for a release**. The committed symbol baseline was
frozen against OpenUSD 26.05; nothing ran it against 26.08 after the runtime
bump landed, because no lane runs the root build.

Refreezing produced a diff that is worth quoting in full, in summary form:

```console
$ git diff -U0 tests/baseline/symbols/windows-x86_64.txt | ...
removed 220 added 220
identical after namespace normalisation: True
lines changed for any other reason: 0
```

All 220 exported symbols changed **only** by `pxrInternal_v0_26_5` →
`pxrInternal_v0_26_8`. Every other baseline artifact — flattened stages,
structural digests, the schema contract, discovery, diagnostics — is
byte-identical across the two OpenUSD versions.

That is a genuinely reassuring result about the 26.05 → 26.08 bump, and it was
only obtainable because someone ran a gate no lane runs. Both are now in
`motion-ci.yml`.

## 4. The graph gate cannot be run on its own

`ost plugin test --workspace` does two separable things: it validates the
dependency graph, then it tests every discovered bundle. Only the first is
whole-workspace; the second is what the twelve generated cells already do.

They are welded together. On a fresh checkout the verb validates the graph,
reports it valid, and then fails — because nothing has been built yet:

```console
$ ost plugin test --workspace
Workspace dependency graph: 4 bundle(s), 1 bundle edge(s), 4 libraries, 7 library edge(s), valid

error[WORKSPACE_LIBRARY_RUNTIME_MISSING]: library 'vrmContainer' 0.5.0 has no installed
  runtime directory under './.strata/targets/cy2026-linux-x86_64-py313-usd/workspace-prefix'
  hint: run `ost plugin build .../plugins/usdVrmFileFormat` so the validated library
        closure is installed before test/run
```

`--up-to 0` does not decouple them; it just changes which per-bundle check
fails first (`plugin.shared_library`, "no shared library in lib/").

That leaves a repo wanting the graph gate as a cheap, early PR check with two
bad options: build all four bundles in a lane whose whole purpose is to cover
what those bundles' own cells do *not*, or parse JSON. This lane parses JSON —
`data.graph` is a discrete object with its own `passed` and `issues`:

```yaml
ost plugin test --workspace --up-to 0 --json > workspace.json || true
python3 -c 'import json,sys; g=json.load(open("workspace.json"))["data"]["graph"]; ...'
```

Verified both ways on a clean checkout: it passes with nothing built, and a
deliberately broken range fails it with the right code —

```console
ISSUE: WORKSPACE_LIBRARY_DEPENDENCY_VERSION_MISMATCH: library 'motionRuntime'
       requires library 'motionCore' at >=0.9,<1.0, but the workspace has 0.5.0
```

A gate that cannot fail is worse than no gate, so that second check matters more
than the first.

### Ask (P1, `ost 0.21.0`)

Split the verb: `ost plugin validate --workspace` (or
`plugin test --workspace --graph-only`) that runs the dependency-graph checks
and nothing else, exits on their result, and needs no build. It is the one gate
WORKSPACE.md has demanded since Phase 1, it costs milliseconds, and today it
cannot be asked for directly.

## 5. Where it stopped: a bare `cmake` cannot configure against the runtime

This is the blocking finding, and the one that most argues for the P0.

`ost plugin run` exports `CMAKE_PREFIX_PATH` (§1), which is enough to *find* the
runtime — but not enough to configure against it. On all three OS:

```console
pxrConfig.cmake:46  find_dependency(Python3 COMPONENTS Development
                                    Development.Module Development.Embed)

Could NOT find Python3 (missing: Development Development.Module Development.Embed)
      (found suitable exact version "3.13")
  Development: Cannot find the directory "/usr/include/python3.13"
               Cannot find the library "/usr/lib/x86_64-linux-gnu/libpython3.13.so"
```

Those paths are where Python lived **in the runtime's build container** (a
deadsnakes 3.13 in `ubuntu:24.04`), not anywhere on a hosted runner. So a
consumer of the published runtime needs a Python 3.13 with development files,
and needs `FindPython3` to actually select it.

What was tried, and did not help:

| Attempt | Result |
| --- | --- |
| `actions/setup-python` 3.13 on all three cells (it exports `Python3_ROOT_DIR` and `pythonLocation`) | still resolves to `/usr/...` |
| Passing `-DPython3_ROOT_DIR=$pythonLocation -DPython3_FIND_STRATEGY=LOCATION` explicitly | no change |

`ost plugin build` configures the very same bundles against the very same
runtime without any of this, on the same runner images — so ost knows how to
resolve Python here and a hand-written lane has no way to ask for it.

### Ask (P0-adjacent, `ost 0.21.0`)

Either of these unblocks it:

1. **Document or expose the configure contract.** What does `ost plugin build`
   pass to CMake beyond `CMAKE_PREFIX_PATH`? If it is a set of `-D` hints, an
   `ost plugin env --cmake` (or having `plugin run` export them) would let any
   plain-CMake consumer configure against a runtime correctly.
2. **Make the runtime self-sufficient.** A published runtime that
   `find_dependency`s host Python development components, at paths that only
   existed in its build container, is not relocatable in the way its
   distribution implies. This is the same shape as report 31's MaterialX/X11
   finding: a runtime demanding host state the contract cannot name.

Until then, the honest position is the one this repo took: the lane is written,
its working parts are verified, and it is disabled rather than pretending.

## 6. Not an ask, but worth knowing

`ost artifact pull` from a public GHCR reference needs no credentials and passes
the full evidence chain unattended:

```console
$ ost artifact pull oci://ghcr.io/animu-sphere/openstrata-runtime-cy2026-usd@sha256:184cdbb4... \
      --expect-artifact sha256:e3368364... --require-kind runtime
  passed  oci_digest        passed  pinned_artifact_digest   passed  sbom
  passed  manifest_schema   passed  archive_safety           passed  provenance
  passed  archive_digest    passed  file_digests             passed  local_import
```

This is what makes the hand-rolled lane viable at all on hosted runners, and it
is the same path a contributor uses to move their own workstation onto a new
runtime.

| 1 | **P0** (restated from [report 28](28-2026-07-26-v0.20.0-motion-layer-ci-gap.md)) | A CI cell shape for plain libraries (`openstrata.library.yaml`) and CLI executables — or `plugin test --workspace --build` that compiles and runs their tests |
| 2 | P1 | `ost ci matrix --json` so a hand-written workflow can consume the resolved cells instead of duplicating digest pins |

| 4 | P2 (restated from [report 28](28-2026-07-26-v0.20.0-motion-layer-ci-gap.md)) | Ship an executable as an aggregate-product member, so `motion_retarget` and `motion_capture` can appear in release artifacts |
| 5 | P1 | Split graph validation out of `plugin test --workspace`, so the WORKSPACE §2 gate can run early and unbuilt instead of having to be parsed out of `--json` (§4) |
| 6 | **P0-adjacent** | Expose or document the configure contract (`ost plugin env --cmake`), or make a published runtime resolvable without the host state its build container had. Today a bare `cmake` cannot configure against a pulled runtime at all, which is what stopped this lane (§5) |
