## TL;DR

**0.23.4 delivers all three of report 45's asks. The new pins reach every
`ost plugin` session and never reach the root build, and in this workspace the
root build is where every consumer of them lives.**

1. **Delivered: `ost plugin build` and `ost library build` follow the
   runtime.** Every bundle tree that 0.23.3 left behind was rebuilt once, and
   the next build reused it. A tree whose runtime identity record named another
   digest was discarded and came back with `pxr_DIR` on the selected runtime
   (§2).
2. **Delivered: `requires.bundles[].artifact`.** `execVrm` pinned a built
   `execMotion`, and `plugins/execMotion` was deleted. The graph validates the
   pin, `ost plugin test` materializes the bundle and composes it into the
   session. Inside `ost plugin run`, every suite that composes the two bundles
   passes against it: four `execVrm` suites, the driver contract, and all five
   parity cases (§3).
3. **Delivered: `requires.tools[]`.** A pin to the `motion_convert` archive
   that `usd-motion-plugins` v0.5.0 actually attached is materialized, and the
   tool runs by bare name inside `ost plugin run` (§4).
4. **P1: none of it reaches the root build or its CTest suite.** The root
   configure materializes a member's external *libraries* only. Every test here
   that composes `execMotion` or a moved tool is a root CTest suite. With the
   copy deleted, the root suite drops from 48 tests to 32 and none of the
   composing tests pass: three crash, two checks fail, and six stop being
   registered. The rendered CI has no lane that runs them any other way (§5).
5. **A correction to report 45 §5**, which was wrong. `usd-motion-plugins`
   v0.5.0 *attached* `execMotion` to its release but never pushed it to a
   registry, so a pin had nothing to point at until that repository published
   it. That is its v0.5.1 (#26), not an `ost` matter (§6).

## 1. What was being done

The pin moved from 0.23.3 to 0.23.4 in four repositories. Each re-render changed
nothing but the version. Each repository rebuilt its tree under 0.23.4, and its
whole suite passed locally: 48 tests here, 53 in usd-motion-plugins, 87 in
motion-connectors and 32 in usd-mmd-plugins.

The 0.23.4 notes list two items as still open downstream: a rerun of this
repository's standalone build sequence against an intentionally stale tree,
and "an end-to-end downstream migration" of `execMotion` and `motion_convert`.
This report is both. The migration was done on a scratch branch and thrown
away, because §5 means it cannot merge yet.

## 2. What worked: member trees follow the runtime

In the release lane's order, root `ost build` came first, then each of the six
`ost plugin build plugins/<bundle>`:

- Every one was green, and every one configured from scratch exactly once:
  compiler ABI detection ran, and a `.openstrata-runtime-identity.json`
  appeared beside each tree. The trees 0.23.3 wrote had no such record, and the
  notes say they are rebuilt once. They were.
- A second `ost plugin build plugins/execVrm` reused its tree.
- **The stale tree.** Report 45 found a tree whose cache named the pulled
  runtime while `pxr_DIR` still pointed at an older adopt. That state was
  reproduced by hand on `execVrm`: the identity record's digest edited to
  `sha256:0000…`, and the cache's `pxr_DIR` set to
  `C:/usd/openusd-26.08-usdview`. The next build discarded the tree, and
  `pxr_DIR` came back as the selected runtime.
- `ost library build` for `vrmContainer` and `vrmRig` reused the trees that
  the bundle builds had just rebuilt through composition.
- The product then packaged (7 members), and `artifact_only_exec_smoke.py`
  passed against it.

One observation, not an ask. With the identity record left intact and only
`pxr_DIR` edited, the tree was kept, and it builds against the old prefix.
`ost` never writes that state; getting there takes a hand edit to the cache. The
record is the check, and it is written only after a configure succeeds, which
is what report 45 asked for.

## 3. What worked: a bundle from another repository

On a scratch branch:

- `plugins/execMotion` was deleted and removed from `members` and
  `release_members`.
- `execVrm`'s `requires.bundles` entry became
  `execMotion >=0.5,<0.6` with an `artifact.targets` pin.
- The pin named a `usd-motion-plugins` 0.5.0 bundle built on this machine and
  imported into the local store, because none was in a registry yet (§6).

Then:

- `ost plugin test --workspace --graph-only`:
  `5 bundle(s), 3 bundle edge(s), 2 libraries, 15 library edge(s), 1 tool(s), valid`.
- `ost plugin build plugins/execVrm` is green.
- `ost plugin test plugins/execVrm --up-to 5`:
  `OK (11 pass, 0 fail, 5 skip)`. The bundle was materialized at
  `.strata/external-bundles/<target>/execMotion/<digest>/`. The report's
  `environment.json` prepends its `plugin/resources/execMotion` to
  `PXR_PLUGINPATH_NAME`, and its `lib/`, `python/` and four
  `runtime/libraries/*/lib` directories to `PATH`.

The pyramid does not evaluate a computation, though: L3–L5 read, open and
round-trip the fixtures, and L2's discovery check is `usd-fileformat` only. So
the pass above says the session is composed, not that `execVrm` can reach
`execMotion`'s nodes. The suites that do say that are CTest suites. They were
run inside the composed session, with
`ost plugin run plugins/execVrm -- ctest --test-dir build/<target> -R …`:

| Suite | Result |
| --- | --- |
| `execVrm_retarget`, `_joint_transforms`, `_diagnostics` | pass |
| `execVrm_retarget_without_exec_motion` | pass |
| `workspace_exec_driver` | pass, over the bundle's own shipped `tests/fixtures/filtered_clip.usda` |
| `workspace_exec_parity_*`, all five cases | pass: every rotation and translation row `exact` or `rounding`, divergence 0 in every case, and "parity holds" |

The last two rows needed two scratch-only edits to the root CMake tree. The
guard `TARGET ExecMotion` had to go, as did the `add_dependencies` on it, since
neither exists once the copy does not. Outside the session, the same parity case
reports `joints: 0 equal`. So the bundle that passed is the external one: no
other `execMotion` was left on the machine to find.

That is the migration's rule met by hand, once: the parity rows re-run against
the consumed package before the copy goes. §5 is why it could not be met in a
change.

## 4. What worked: a tool from another repository

A scratch `requires.tools` entry on `execVrm` pinned `motion_convert`
`>=0.5,<0.6` to `sha256:06324f0c…`. That is the archive `usd-motion-plugins`
v0.5.0 attached to its release, downloaded and imported as it stands.

- The graph was still valid.
- `ost plugin run plugins/execVrm -- motion_convert --help` printed the tool's
  usage.
- `where motion_convert` inside the session named
  `.strata/external-tools/<target>/motion_convert/06324f0c…/bin/motion_convert.exe`.

So the published bytes are verified, materialized and on `PATH`, as the notes
say.

## 5. The root build sees neither

`ost configure` prepends the materialized prefix of every external library a
member declares (`crates/ost-cli/src/commands/configure.rs`, since 0.23.2).
Nothing composes an external bundle or tool there: `external_member::materialize`
is called from `plugin package`, `run`, `test`, `test --workspace`, `view` and
`test-view`, and never from `configure`, `build` or `test`.

In this repository, that is every consumer of both:

- The four `execVrm` suites above set their session from sibling paths
  (`plugins/execMotion/lib`, `plugins/execMotion/plugin/resources/execMotion`).
- `tests/parity/` holds the driver contract and the five parity cases. It is a
  composition of both exec bundles, `motion_retarget` and the file-format
  readers, registered from the root because only the composed build has all of
  them.
- The real-capture suites that report 45 §6 is about, the ones that had to
  commit a published tool's output, are root suites too.

With the copy deleted and nothing else changed, the root build is green and
`ost test` reports **5 failures out of 32**, where it ran 48:

| Test | Result |
| --- | --- |
| `execVrm_retarget`, `_joint_transforms`, `_diagnostics` | `0xc0000409`: exec finds no `motion.sampleAnimation` |
| `execVrm_boundaries` | fails: it reads `execMotion`'s declarations from the sibling directory |
| `workspace_ctest_labels` | fails: the `motion.openexec` label lost its registrations |
| `workspace_exec_driver`, `workspace_exec_parity_*` (6) | not registered: their guard is `TARGET ExecMotion` |

The rendered CI gives these no other home. A `kind: workspace` cell runs root
`ost build` and `ost test`. A `bundle:` cell runs `ost plugin test`, whose
pyramid never evaluates a computation (§3). A generated job cannot be told to
wrap CTest in `ost plugin run`. Rewriting the tests to find the materialized
directory by globbing `.strata/external-bundles/` would pass only on a machine
where some earlier `ost plugin` command happened to materialize it. A workspace
cell has had none, so the suites would skip there.

The edge is declared correctly; what is missing is its composition into the
one tree that tests it.

## 6. Correction: report 45 §5 was wrong about the artifact

Report 45 §5 says `usd-motion-plugins` "published `execMotion` 0.5.0 as a
bundle artifact on three targets". It attached the archive and its manifest to
the GitHub release. It pushed only the seven libraries to
`ghcr.io/animu-sphere/usd-motion-plugins`, and its `release.yml` said why:
nothing could pin a bundle or a tool by digest yet. So even with 0.23.4, a
pin's `source` had nothing to name, and a hosted lane would have failed
`WORKSPACE_MEMBER_ARTIFACT_MISSING`.

That is that repository's to fix, and
[usd-motion-plugins #26](https://github.com/animu-sphere/usd-motion-plugins/pull/26)
does it. It prepares v0.5.1, whose release lane imports and pushes every
packaged bundle and tool the way it pushes a library, and whose pin table gains
a `bundles` and a `tools` section. The push was rehearsed against a throwaway
local registry. The report here is kept as it was written, and this section is
the correction.

## 7. Asks

- **P1: compose members' external bundles and tools into the root build.**
  Materialize every `requires.bundles[].artifact` and `requires.tools[]` a
  member declares in `ost configure`, as `workspace_external_libraries` does
  for libraries. Then expose each one to the tree, for example as
  `OPENSTRATA_EXTERNAL_BUNDLE_<id>_ROOT` / `OPENSTRATA_EXTERNAL_TOOL_<id>_DIR`
  cache variables written into the root toolchain. A CTest suite can then name
  the bundle's `plugin/resources/<id>` and `lib/` in its own
  `ENVIRONMENT_MODIFICATION`, as it names a sibling's today. That includes the
  suites that must *remove* it, such as `execVrm_retarget_without_exec_motion`,
  which uses `set`. An ambient environment from `ost test` alone would not let
  a suite state what it composes. Graph validation already covers these pins;
  the root tree is the one consumer that cannot see them.
- Not re-measured here: 0.23.4's claim that packaging embeds an external bundle
  under `runtime/bundles/<id>/`. The product was not packaged on the scratch
  branch, because §5 kept that branch from being a candidate change.
