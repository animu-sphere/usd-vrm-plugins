# A workspace cell cannot say `package`, so the matrix said it twelve times

- Date: 2026-08-30
- Version exercised: `ost 0.22.8`, on this workstation
  (`cy2026-windows-x86_64-py313-usd`) and against the generated lanes for
  `windows-2022`, `macos-15` and `ubuntu-24.04`
- Occasion: consolidating this repository's PR matrix from sixteen cells to
  seven, after finding that nine of the twelve `bundle:` cells were measurably
  redundant against the three `kind: workspace` cells
- Prior report: [37](37-2026-08-30-v0.22.6-runtime-python-paths-from-the-producer.md)
- Next ask target: `ost 0.23.0`

## TL;DR

Nothing broke. This report is about a **shape** the CI contract imposes, found
by trying to remove jobs it had quietly caused us to add.

1. **P2 — `kind: workspace` takes `verify: graph | build | test` and nothing
   else.** The two verbs a release actually turns on — `ost plugin test
   --workspace` and `ost plugin package --workspace` — are not expressible in
   `openstrata.ci.yaml` at all. `release.yml` runs both by hand, and that lane
   is hand-authored precisely because the contract cannot say them. The only way
   to get pyramid and packaging coverage into a *generated* PR lane is one
   `bundle:` cell per bundle per platform — bundles × platforms jobs to say what
   one workspace cell could say once. That is where a sixteen-cell matrix came
   from, and it is why three bundle cells survive a consolidation whose
   evidence otherwise retires all twelve (§2).
2. **P3 — `ci generate` never retires a workflow it has stopped emitting.**
   Removing the last cell of a lane leaves that lane's generated file on disk,
   still on its `schedule:`, still firing. `generate --force`, `ci validate` and
   `ci plan` are all silent about it. Measured directly (§3).
3. **P3 — `ost test` reports one flat total for a whole workspace, so a member
   that contributes zero tests is invisible.** One of ours did, on every lane, on
   three platforms, for months — and the run that hid it was reporting 100%
   passing (§4).

And one thing that went right and is worth saying: across a `0.22.6 → 0.22.8`
re-pin **and** a nine-cell removal, `ost ci generate github --force` produced a
diff of **162 deletions and nothing else**. No renderer churn, no reordering, no
incidental step rewrites. That is the property that made this consolidation a
contract edit rather than a workflow rewrite (§6).

## 1. What was being done

This repository's PR lane had grown to sixteen cells: twelve `bundle:` cells —
each of four bundles on each of `windows-2022`, `macos-15`, `ubuntu-24.04` —
plus three `kind: workspace` cells and one graph cell. The question asked was
whether the bundle cells still earned their place now that the workspace cells
(adopted in [report 33](33-2026-07-28-v0.21.0-workspace-ci-adoption.md)) run the
root CTest suite on the same three platforms.

The measurement, from run `33300220549`:

| bundle | in the workspace suite | what its `bundle:` cell adds |
| --- | --- | --- |
| `vrmSchema` | `vrmschema_plugin` | L2 registration, L4 apply, L5 golden |
| `usdVrmFileFormat` | `usdvrm_transform_util`, `usdvrm_python_smoke` (every fixture), `usdvrm_corpus_smoke`, `usdvrm_negative`, `usdvrm_validate`, `usdvrm_baseline` | L2–L5 against one fixture |
| `usdVrmPackageResolver` | `usdvrmresolver_boundaries`, `usdvrmresolver_python` | L2–L5 against one fixture |
| `usdVrmaFileFormat` | **nothing** — see §4 | its only coverage |

A bundle cell's L2–L5 is discovery, one `usdcat` read, one stage open and one
golden. Against a suite that runs the same plugin over every fixture, a corpus,
a negative corpus and a whole-workspace baseline gate, on the same three hosts,
that is a strict subset. Nine cells went.

## 2. P2 — the verbs a workspace cell does not have

`WorkspaceVerify` is `graph | build | test`. A `kind: workspace` cell renders,
in order: `ost plugin test --workspace --graph-only`, `ost build`, and — only
under `verify: test` — `ost test`.

What it cannot render is the rest of what a release does. From this
repository's `release.yml`, hand-authored:

```yaml
- name: Run the verification pyramid against the build tree (whole workspace)
  run: ost plugin test --workspace --target ... --up-to 5 --json
- name: Package the workspace (lean bundles + aggregate product + split debug symbols)
  run: ost plugin package --workspace --product --target ... --json
```

Both verbs exist, both take `--workspace`, and neither has a spelling in
`openstrata.ci.yaml`. So a project that wants pyramid or packaging coverage on
PRs has exactly one generated construct available: the `bundle:` cell, which is
per-bundle and per-platform. Four bundles on three platforms is twelve jobs to
express *"run the pyramid, and package what you built"* — a sentence
`ost plugin test --workspace` and `ost plugin package --workspace` already say
in two commands, and which the three workspace cells were already positioned to
run.

**This is the whole reason three bundle cells survived.** The evidence in §1
retires all twelve on behavioral grounds. What it does not retire is that a
`bundle:` cell is the only lane that configures a bundle **standalone** — `ost
plugin build <bundle>` against a pulled runtime with no root CMake tree in scope
— and the only PR lane that runs `ost plugin package`, whose staging is
per-platform (on Windows the linked libraries land under
`runtime/libraries/{lib,bin}`). Neither is reachable from a workspace cell.
Without them, both are proved only by `release.yml` at tag time, and this
repository has a documented history of a green PR lane proving nothing about the
release lane. So `usdVrmFileFormat` stays on all three platforms as the
representative — it is the only bundle carrying both a `requires.libraries` and
a `requires.bundles` edge, so its package is the one with a `dependencies.json`
and staged siblings to get wrong.

### The ask

**P2 — extend `WorkspaceVerify` past `test`, so the contract can say what a
release already does.** Two values would do it:

- `verify: pyramid` — renders `ost plugin test --workspace --up-to <n>` after
  the build. `up_to` is already a cell key; today the schema rejects it on a
  workspace cell, which is the right rejection for `graph`/`build`/`test` and
  the wrong one for this.
- `verify: package` — renders the pyramid and then `ost plugin package
  --workspace` (with `--product` where the workspace declares an aggregate).

With those, this matrix is **four cells**: one graph, three workspace. Every
remaining bundle cell here exists to reach a verb, not a bundle.

**Not blocking, and cheap to work around badly.** The workaround is the twelve
cells we just deleted, which is why this is worth filing: the contract's missing
verbs do not fail, they inflate. A matrix grows by bundles × platforms and every
cell looks individually justified.

**One thing `verify: package` would not cover**, and it should be said plainly
rather than folded into the ask: `ost plugin package --workspace` packages from
a composed root build, and `ost plugin build <bundle>` standalone is a different
configure. If the intent is that a workspace cell can replace a bundle cell
entirely, the standalone configure needs its own answer — perhaps a workspace
cell flag that builds each member standalone rather than composed. If not, then
one bundle cell per platform is the honest floor and this repository is already
at it.

## 3. P3 — a generated workflow outlives the lane that generated it

Removing the last `lane: scheduled` cell removes the scheduled lane. It does not
remove `.github/workflows/ost-support-matrix.yml`, which `ost ci generate`
wrote, whose header says *"Generated by `ost ci generate github` ... do not edit
the jobs by hand"*, and which carries its own `on: schedule:` trigger.

Measured, with the orphan restored to disk:

```
$ ost ci generate github --force
Generated .github/workflows/ost-source-ci.yml from openstrata.ci.yaml
  7 cell(s) total

$ ls .github/workflows/
docs-check.yml  ost-source-ci.yml  ost-support-matrix.yml  package-consumer.yml  release.yml

$ ost ci plan | grep workflow
  workflows:        .github/workflows/ost-source-ci.yml

$ ost ci validate
Matrix openstrata.ci.yaml: 7 cell(s), structure OK        (exit 0)
```

`plan` knows the file is no longer one of its outputs — it lists one workflow —
and says nothing about the one sitting beside it that it used to own. `validate`
exits 0. `generate --force` overwrites what it emits and ignores what it
doesn't. The file keeps running on its cron until a human notices.

In our case a human did not, for five weeks (§5).

### The ask

**P3 — `ci generate` should account for the workflows it no longer emits.**
Deleting is the aggressive reading and may be wrong for a repository that has
hand-added files to the same directory; a warning naming the file is enough:

```
warning: .github/workflows/ost-support-matrix.yml was generated from this
         matrix and is no longer emitted (no `scheduled` cells). It still
         has an `on:` trigger. Remove it or re-add a cell.
```

`ci plan` and `ci validate` are equally good places for it — arguably better,
since they run in CI (`ost ci validate` is a step in every generated job) and
would surface the orphan on the next PR rather than the next regeneration.

## 4. P3 — a workspace member with zero tests reads as success

This one is our bug, and it is filed here because the tooling had every fact
needed to surface it and reports a shape that cannot.

`plugins/usdVrmaFileFormat/CMakeLists.txt` guarded its test subdirectory on
`USDVRMA_BUILD_TESTS`, while the repo root defines `USDVRM_BUILD_TESTS` and the
three sibling bundles read that. In a composed root build `PROJECT_IS_TOP_LEVEL`
is false in the bundle's scope, so the option defaulted **off** and the bundle
registered no CTest target at all. Every lane compiled and linked
`libUsdVrmaFileFormat` on three platforms and ran none of its tests. The
committed build caches record it without ambiguity — `USDVRMA_BUILD_TESTS:BOOL=OFF`
in every root cache, `ON` in the standalone bundle cache — and nobody reads build
caches.

What `ost test` reports is a flat total for the invocation:

```json
"totals": { "failed": 0, "passed": 2, "total": 2 }
```

`--no-tests=error` is passed to CTest, so an entirely empty suite is caught. A
suite of 113 in which one member contributes zero is not — it is *100% tests
passed*, on every run, for as long as it takes someone to count.

`ost` already knows this workspace's members: `ost plugin test --workspace`
discovers them ("immediate subdirectories and `plugins/*` with a plugin
manifest"), and `ost plugin package --workspace` enumerates them again.

### The ask

**P3 — attribute test counts to workspace members in `ost test --json`.** A
`members` map beside `totals`, keyed the way `--workspace` already keys
discovery, with a count per member. A member at zero is then one line in a JSON
artifact every lane already uploads, and a consumer can gate on it. A warning in
the human output for any *discovered* member contributing no tests would have
closed this months earlier:

```
warning: workspace member 'plugins/usdVrmaFileFormat' contributed 0 tests
```

The general shape — a check that is absent rather than failing — is the same
class as [report 25](25-2026-07-18-v0.18.0-from-package-workspace-correction.md)'s
correction and as the `Python3_Interpreter_FOUND` trap this repository has hit
twice: **nothing red, nothing skipped, nothing there.** Skips are reported;
absences are not.

## 5. An observation, not an ask

The scheduled cell removed here, `usdvrmfileformat-support-windows-cy2026`,
targeted a self-hosted runner (`usd-windows-real`) that does not exist. Every
weekly firing from 2026-07-27 onward was **cancelled by GitHub** after queueing
for a runner that never claimed it; the newest five were checked before the lane
was removed. It also pinned a plugin artifact built against OpenUSD 26.05
against a 26.08 runtime, which this repository's own matrix comment said not to
trust until the plugin was republished.

`ost ci plan` described it accurately throughout — `operator-managed:
usd-windows-real` — and that is the correct answer to the question `ost` can
answer. Whether a declared runner exists, and whether a lane has ever completed,
is GitHub's knowledge and not the contract's. **We are not asking `ost` to fix
this.** It is recorded because it is what §3's orphan cost: a lane nobody could
see was a lane nobody looked at, and it survived a re-pin, a release and two
report cycles.

## 6. What worked

Across a `0.22.6 → 0.22.8` re-pin *and* the removal of ten cells, regenerating
produced a workflow diff of **162 deletions and nothing else**:

```
$ git diff --stat -- .github/workflows/ost-source-ci.yml
 .github/workflows/ost-source-ci.yml | 162 ------------------------------------
 1 file changed, 162 deletions(-)
```

Zero added or modified lines. No step rewrites, no reordering, no version-string
churn beyond what the cells themselves carry. This is what let the change be
reviewed as *"which cells, and why"* instead of *"what did the renderer do to
our CI."* Report 36 §12 said the 0.22.x line had earned back the trust the four
consumer-side defects cost it; this is the quieter half of that.

`ost ci validate` and `ost ci plan` were also the whole verification loop for the
matrix edit — 7 cells, `pull_request 7, scheduled 0`, one workflow — before a
single job ran.

## 7. What this repository did

- Renamed `USDVRMA_BUILD_TESTS` → `USDVRM_BUILD_TESTS` in
  `plugins/usdVrmaFileFormat/CMakeLists.txt`. Workspace suite 113 → 115;
  the bundle still registers both tests when configured standalone.
- Removed nine `bundle:` cells and the `lane: scheduled` cell from
  `openstrata.ci.yaml`, and the `usd-windows-real` runner with it. Sixteen
  cells → seven; 21 jobs per PR → 12.
- Deleted `.github/workflows/ost-support-matrix.yml` by hand, because §3.
- Recorded in `openstrata.ci.yaml` what was measured and what to re-measure
  before adding cells back, so the next reader does not re-derive it from CI
  logs.

## 8. Ask summary

| # | Priority | Ask |

| 1 | **P2** | `WorkspaceVerify` past `test` — `verify: pyramid` and `verify: package`, so `ost plugin test --workspace` and `ost plugin package --workspace` are expressible in the contract instead of hand-authored. Retires bundles × platforms cells that exist to reach a verb |
| 2 | **P3** | `ci generate` / `plan` / `validate` should name a generated workflow they no longer emit. It keeps its `on:` trigger and runs until a human notices |
| 3 | **P3** | Per-member test attribution in `ost test --json`, and a warning for a discovered member contributing zero tests. An absent test is not a skipped test and is reported nowhere |

hands every consumer the producer's Python paths, and only a republished runtime
can close it.
