# OST v0.21.0 adoption — six asks delivered, and what the workspace build costs

- Date: 2026-07-28
- Version exercised: `ost 0.21.0` on Windows x86_64 (local workspace), cy2026 /
  OpenUSD 26.08
- Occasion: upgrading from 0.20.0 and re-verifying the consolidated ask list
- Prior report: [32](32-2026-07-26-v0.20.0-motion-layer-ci-workaround.md)
- Next ask target: `ost 0.22.0`

## TL;DR

**All six live asks from report 32 are delivered, and every one of them was
exercised rather than read out of `--help`.** The headline is that the
blocking finding — a bare `cmake` cannot configure against a pulled runtime —
is gone: `ost plugin run` now exports `CMAKE_TOOLCHAIN_FILE`, and the toolchain
it points at pins the Python development artifacts by absolute path, which is
exactly the thing `-DPython3_ROOT_DIR` could never supply.

The adoption deleted `motion-ci.yml` — 210 lines, of which ~120 duplicated
generated logic — and replaced it with four cells in `openstrata.ci.yaml`.

Two new findings came out of doing it, both about the *root* build (§4, §5):
upgrading `ost` re-identifies an unchanged runtime, and the root build silently
invalidates the per-bundle managed-output provenance that packaging checks.
Neither blocks anything; both cost a confusing hour.

### The configure contract, concretely

This is the one that mattered most, so it is worth quoting what was missing:

```console
$ ost plugin run plugins/vrmSchema -- python -c "import os; print(os.environ['CMAKE_TOOLCHAIN_FILE'])"
…/plugins/vrmSchema/.strata/targets/cy2026-windows-x86_64-py313-usd/toolchain.cmake
```

```cmake
# Python: pinned host interpreter 3.13 (Development artifacts).
set(Python3_EXECUTABLE  ".../python.exe")
set(Python3_LIBRARY     ".../libs/python313.lib")
set(Python3_INCLUDE_DIR ".../Include")
```

`FindPython3`'s `Development` component wants the *library and headers*.
`Python3_ROOT_DIR` only tells it where to look, and report 32 tried exactly
that, twice, on three OS. The toolchain sets the artifacts themselves, which is
why the same `cmake` invocation that failed under 0.20.0 now reports:

```console
-- Found Python3: .../python313.lib (found suitable exact version "3.13.14")
   found components: Development Development.Module Development.Embed
```

`runtime validate` also gained a `consumer-configure` check that configures a
trivial `find_package(pxr REQUIRED)` with those same pins, so the gap is now
caught at publish time rather than by a consumer:

```console
[ok  ] consumer-configure — find_package(pxr) configures against …/openstrata-cy2026-windows-x86_64-py313-usd
```

## 2. What the adoption changed in this repo

- **`motion-ci.yml` is deleted.** Four cells replace it: `workspace-graph-pr`
  (`verify: graph`) plus `workspace-pr-{windows,macos-arm64,linux}`
  (`verify: test`). The graph cell renders as a job that stops after the
  checkout — it never pulls or materializes a runtime, so it costs seconds.
- **The standing hand-edit exception is retired.** Every Linux cell declares
  `host_packages`, so `ost ci generate github --force` re-renders the X11 step
  instead of deleting a hand-added one. `release.yml` is hand-authored and
  still carries its own copy; that is now the only one.
- **The runtime digests are pinned in one place again.** The second copy lived
  in `motion-ci.yml`.
- **The CLIs reach the release.** `tools/motionRetarget/openstrata.tool.yaml`
  and `tools/motionCapture/openstrata.tool.yaml` make them tool members;
  `release.yml` asserts 4 bundle + 2 tool packages by `member` kind rather than
  a bare count of 6, so a tool dropping out cannot be masked.

The 22 CTest assertions the workspace cells now run are the ones no bundle cell
reaches: `motionCore`, `motionRuntime` (including the Phase D live-capture
surface and the capture corpus), `vrmRetarget`, `vrmContainer`, both CLI tools,
and `usdvrm_baseline` — the whole-workspace behavior gate that report 32 found
had been silently stale for a release.

## 3. The tool contract wants the build to stage into the member root

`openstrata.tool.yaml` declares executables by name and searches
`directories:` (default `[bin, lib]`) **below the member root**, not in the
build tree. A workspace whose CLI targets land only in
`build/<target>/tools/<name>/` is refused:

```console
error[PRECONDITION_FAILED]: tool 'motion_capture' declares executable
  'motion_capture.exe', which is not in bin under '…/tools/motionCapture'
  hint: build the workspace first (`ost build`), or correct `executables` /
        `directories` in openstrata.tool.yaml
```

The build *had* run. The fix is the same `RUNTIME_OUTPUT_DIRECTORY` staging
every bundle's CMake already does for its shared library, applied to the tool:

```cmake
set_target_properties(motion_capture PROPERTIES
    RUNTIME_OUTPUT_DIRECTORY "${CMAKE_CURRENT_SOURCE_DIR}/bin")
```

### Ask (P2, `ost 0.22.0`)

Lead the hint with the actual cause — the executable is not under the declared
directory — and name the staging requirement, since it is a CMake property the
adopter has to add and the bundle templates already set. Better still: `ost
build` already records the tool executables it produced (`plugin package`
reports `matched (ost-managed)` for them), so it could stage them the way it
stages a bundle's library and remove the requirement altogether.

## 4. Upgrading `ost` re-identifies an unchanged runtime

Nothing re-pulled or re-materialized the cy2026 runtime, yet:

```console
# plugins/vrmSchema/.strata/targets/…/target.lock.json  (written by 0.20.0)
"runtime": { "digest": "sha256:acebd2e4…" }
# .strata/targets/…/target.lock.json                    (written by 0.21.0)
"runtime": { "digest": "sha256:3873e4eb…" }
```

The store's `runtime.json` was rewritten the first time a 0.21.0 command touched
it — 0.21.0 records more about a runtime than 0.20.0 did (the concrete
`site-packages` directory, the measured ABI floor), so the record, and therefore
its identity, changed. `runtime validate` re-run afterwards leaves the file
byte-identical, so this is a one-time migration, not a mutating verb.

The consequence is what makes it worth reporting: **every bundle's managed-build
record now mismatches, and packaging fails closed** with a message that reads
like the runtime changed underneath you.

```console
error[PLUGIN_PACKAGE_OUTPUT_MISMATCH]: plugin 'vrmSchema' staged package output does not
  match its last managed build: last managed build target/runtime identity does not match
  selected target 'cy2026-windows-x86_64-py313-usd' runtime 'openstrata-…@sha256:3873e4eb…'
```

### Ask (P2, `ost 0.22.0`)

Say so. When the mismatch is explained by a record migration rather than a
different runtime, name it: *"the runtime record was migrated by an `ost`
upgrade (0.20.0 → 0.21.0); rebuild the bundle."* The remedy is already right;
the diagnosis sends you to check whether your pinned runtime is still the one
you think it is.

## 5. The root build invalidates the per-bundle managed-output provenance

This one is structural, and the new workspace cell makes it reachable.

`ost build` at the workspace root compiles the bundles too, and writes their
shared libraries to the *same* place `ost plugin build` stages them
(`plugins/<bundle>/lib/`). But only `plugin build` records bundle-managed
provenance, so after a root build:

```console
error[PLUGIN_PACKAGE_OUTPUT_MISMATCH]: plugin 'usdVrmFileFormat' staged package output does
  not match its last managed build: digest-mismatch 'lib/libUsdVrmFileFormat.dll'
  (expected sha256:2a4f9600…, observed sha256:5749065a…)
```

Both binaries are legitimate products of the same source and the same runtime.
The order that works is **root build first, per-bundle builds second, package
third** — which is what `release.yml` now does, with a comment saying why. In
generated CI it never bites, because a workspace cell and a bundle cell are
different jobs with different checkouts.

### Ask (P1, `ost 0.22.0`)

Make the root build's bundle outputs count as managed provenance — it is the
same `ost`, the same target lock, and the same runtime, one command earlier — or
have the root build stage bundle libraries somewhere the bundle packager does
not read. Today a repo that runs both in one tree has to know the order, and
nothing tells it.

## 6. Smaller observations, not asks

- A `verify: graph` cell must still pin `runtime_artifact` / `runtime_remote`
  that its rendered job never uses. The starter matrix says so deliberately
  ("a graph cell still pins one for the record"), so this is a note, not a
  complaint.
- A workspace cell renders bare `ost test`, i.e. the whole CTest suite. The CLI
  has `--filter`, but the cell cannot declare one, so a repo whose root suite
  overlaps its bundle cells pays for the overlap. Here it is 22 fast tests and
  not worth a knob; a larger workspace might disagree.
- `ost ci validate` exits non-zero on this workstation for a pre-existing
  reason — the scheduled lane's `plugin_artifact` (a 26.05 build) has no SBOM or
  provenance and the gate is `all`. Hosted runners do not hold that artifact, so
  the same command inside the generated job passes. Worth knowing before reading
  a local red as a regression.
- `runtime pull --build` gained `--sdk` and `--deployment-target` (report 30's
  asks) and `--build-arg` is documented as reaching the component set (report
  29's ask). Neither was re-exercised here: both need a from-source runtime
  build, which this pass did not do.
