# No plugin kind for a UsdImaging adapter

- Date: 2026-09-26
- Version exercised: `ost 0.23.8`, the published `x86_64-pc-windows-msvc`
  asset, on this workstation (`cy2026-windows-x86_64-py313-usd`). The CI
  lanes bootstrap the pinned `ost 0.23.6`, which has the same kind list. The
  kind list was also read on open-strata `main` at `807f0de` (the 0.23.8
  merge): it is unchanged there.
- Occasion: `vrmImaging`, a new plugin in this repository — UsdImaging
  API-schema adapters that expose the canonical VRM material schemas to Hydra
  ([#243](https://github.com/animu-sphere/usd-vrm-plugins/pull/243) policy,
  [#245](https://github.com/animu-sphere/usd-vrm-plugins/pull/245) Step I0)
- Prior report: [48](48-2026-09-24-v0.23.6-the-product-packages-again.md)
- Next ask target: the next `ost` release

## TL;DR

**`ost` has no plugin kind for a UsdImaging adapter, so a plugin of that kind
cannot be a bundle.** This is not a defect in anything `ost` supports. It is a
missing kind, and one P2 asks for it.

1. **P2, new: a `usd-imaging` plugin kind** (§2, §4). `vrmImaging` is an
   ordinary Plug plugin: a shared library and a `plugInfo.json`, discovered
   through `PXR_PLUGINPATH_NAME`, loaded by UsdImaging's adapter registry.
   `ost` 0.23.8 refuses its descriptor at parse time. The plugin therefore
   has no descriptor. The root `CMakeLists.txt` adds it by name, the root
   build compiles and tests it, and nothing packages it. `ost plugin
   build|test|package`, `requires.bundles`, the verification pyramid and
   product membership are all out of reach.
2. **Two things a kind should carry**, both measured on OpenUSD 26.08 (§3):
   - UsdImaging keys API-schema adapters by schema name and lets the last one
     registered win without a word, which is a conflict `ost` can see
     statically.
   - An adapter is inert in two sessions that load it without complaint: one
     that lacks the schema it adapts, and one with
     `USDIMAGING_ENABLE_PLUGINS=0` set.
3. **Not an `ost` defect, noted for a template** (§5): OpenUSD 26.08's
   `hd/retainedDataSource.h` does not compile as C++20 under GCC 13, and
   `ost`'s toolchain compiles C++20.

## 1. What was built

`plugins/vrmImaging` is a UsdImaging API-schema adapter for `VrmMToonAPI`, an
applied schema of this repository's `vrmSchema` bundle. It contributes
`vrm/mtoon/<field>` data sources to the Hydra material prim, and it maps a
changed canonical attribute to the one locator that attribute feeds. Its
`plugInfo.json` is the whole registration:

```json
"Info": {
    "Types": {
        "UsdVrmImagingMToonAPIAdapter": {
            "bases": ["UsdImagingAPISchemaAdapter"],
            "apiSchemaName": "VrmMToonAPI"
        }
    }
}
```

A test consumer reads it through `UsdImagingStageSceneIndex` with the plugin
found on `PXR_PLUGINPATH_NAME` and not linked. That is the same shape as
`execVrm`, which `ost` builds as a `usd-exec` bundle. It is green in the root
build on Windows: 47 of 48, with the one long-standing local-only skip.

## 2. The kind list

`ost plugin new --help` lists `usd-fileformat | usd-asset-resolver |
usd-package-resolver | usd-exec | usd-schema | usdview-plugin`, the six
variants of `PluginKind` in `crates/ost-plugin/src/model.rs`. A descriptor
naming anything else is refused before any other check:

```text
> ost plugin inspect <scratch>/vrmImaging
error[PARSE_FAILED]: could not parse openstrata.plugin.yaml: plugin.kind:
unknown variant `usd-imaging`, expected one of `usd-fileformat`,
`usd-asset-resolver`, `usd-package-resolver`, `usd-exec`, `usd-schema`,
`usdview-plugin` at line 6 column 9
```

In a workspace this is worse than one refused member. I put the same
descriptor in this repository's tree as a probe and ran `ost plugin test
--workspace --graph-only`, which is the lanes' graph step. Both ways of
placing it stop the whole workspace graph:

| Descriptor | Result |
| --- | --- |
| in the tree, not in `[workspace].members` | `WORKSPACE_DESCRIPTOR_NOT_DECLARED` (members are fail-closed) |
| in `[workspace].members` | the `PARSE_FAILED` above |

So the only workable choice was to have no descriptor at all. What that costs
here:

- **Not packaged, not in the product.** `release_members` names bundles and
  tools, and this is neither, so a deployment that wants MToon in Hydra has
  to assemble the plugin by hand.
- **No `requires.bundles`.** The adapter needs `vrmSchema` registered in the
  session (§3). Nothing can state that, so no session `ost` composes knows
  it.
- **No pyramid.** `ost plugin test` never sees the plugin, and the checks
  that exist for it are two CTest cases in the root suite.
- **A special case in the workspace root.** The root's bundle glob keys on
  `openstrata.plugin.yaml`, so this is the one plugin directory the root adds
  by name. It is recorded as an exception in this repository's
  `WORKSPACE.md` §4.

It is not only this repository's shape. `usd-mmd-plugins` has fixed the same
design for its own material schema (a planned `mmdImaging`), and
`hydra-toon`, the renderer both are for, lists "an API-schema adapter per
schema" as its preferred read path (its MAT-Q1).

## 3. What UsdImaging does with an external adapter

Read from OpenUSD 26.08's `usdImaging/adapterRegistry.cpp` and
`adapterManager.cpp`, and measured in `vrmImaging`'s suite where marked:

- **Keyed by schema name, last registration wins.** `apiSchemaName` becomes
  the key of `_apiSchemaTypeMap[apiSchemaName] = type`. A second plugin
  declaring the same name replaces the first with no diagnostic. (Prim
  adapters, keyed by `primTypeName`, at least raise a runtime error on a
  duplicate.) This is the same one-declarer-per-key situation as OpenExec's
  `Exec.Schemas`, which `ost` already treats as a bundle's `provides`.
- **Asked only about schemas the prim definition includes.** When the schema
  bundle is absent, no prim's definition contains `VrmMToonAPI`, so the
  adapter is never called and the session shows nothing
  (`vrmImaging_mtoon_without_schema`, measured).
- **Dropped by an environment variable.** With `USDIMAGING_ENABLE_PLUGINS=0`,
  the registry skips every adapter whose metadata does not say
  `isInternal: true`. An external plugin must not say that, so it is dropped
  with only a `TF_DEBUG` message.
- **Scene-index hosts only.** Adapters are consulted when UsdImaging
  populates through `UsdImagingStageSceneIndex`. The legacy
  `UsdImagingDelegate` never calls them.
- **Needs an imaging runtime.** The plugin links `hd` and `usdImaging`. A
  runtime built without imaging (a `core` leaf) cannot build or load it.

## 4. Asks

### P2 — a `usd-imaging` plugin kind

The bundle lifecycle the other kinds have, for a plugin whose `plugInfo.json`
declares types based on `UsdImagingAPISchemaAdapter` (and, for completeness,
`UsdImagingPrimAdapter`):

1. **The kind itself**, with `plug_info` staging, `requires.bundles`,
   `plugin build|test|package`, and aggregate membership, exactly as
   `usd-exec` has them.
2. **`provides` keyed by the adapted schema**: `usd-imaging:VrmMToonAPI`
   for an API-schema adapter, `usd-imaging-prim:<primTypeName>` for a prim
   adapter, or whatever spelling `ost` prefers. `ost` should refuse two
   bundles in one session that provide the same key, because UsdImaging will
   not (§3).
3. **A runtime requirement on imaging.** `runtime validate` / L1 should
   refuse a runtime without `usdImaging` for this kind, with a clear message,
   rather than let it fail at link time.
4. **An L2 that can fail.** After registration, construct
   `UsdImagingAdapterRegistry` in the session and require
   `HasAPISchemaAdapter(<name>)` for every provided name. In the same check,
   report `USDIMAGING_ENABLE_PLUGINS=0` in the session environment as an
   error for this kind, since every adapter is dropped under it.

### P3 — a template, when there is one

If `ost plugin new usd-imaging` gets a template, it should build its
contribution without `hd/retainedDataSource.h`, or at least say why (§5).

## 5. A C++20 note for templates (OpenUSD, not `ost`)

OpenUSD 26.08's `hd/retainedDataSource.h` declares a constructor as
`HdRetainedTypedSampledDataSource<bool>(const bool& value)`, a template-id
that C++20 no longer accepts in that position. GCC 13 rejects it and MSVC
accepts it. `ost`'s generated toolchain sets `CMAKE_CXX_STANDARD 20`, so the
first `vrmImaging` push was green on Windows and failed to compile on
`workspace-pr-linux`. The repro is one command, `g++-13 -std=c++20
-fsyntax-only`, against the Linux leaf.

`vrmImaging` stopped including the header and nests its containers with a
private one-child container. Any imaging adapter built by `ost` hits this the
moment it reaches for `HdRetainedContainerDataSource`, which is the obvious
thing to reach for.
