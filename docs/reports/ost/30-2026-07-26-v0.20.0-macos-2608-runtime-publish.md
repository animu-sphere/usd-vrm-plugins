# OST v0.20.0 dogfooding — the macOS 26.08 runtime, and the SDK nobody records

- Date: 2026-07-26
- Version exercised: `ost 0.20.0` on macOS 14.5 arm64 (Darwin 23.5.0, 8 cores)
- Occasion: [report 29](29-2026-07-26-v0.20.0-openusd-2608-runtime-publish.md)
  published the Windows and Linux 26.08 runtimes and left macOS arm64 as the one
  platform still on 26.05, blocking the v0.6.0 P0-1 gate "one OpenUSD version
  across three OS". This report closes it.
- Related reports: [29](29-2026-07-26-v0.20.0-openusd-2608-runtime-publish.md)
  (the Windows/Linux publish and the `--build` finding this report confirms),
  [13a](13a-2026-07-10-v0.11.0-macos-ghcr-runtime-publication.md) (the macOS
  publish recipe), [11a](11a-2026-07-05-v0.8.0-macos-plugin-build-blockers.md)
  (the `--codesign-id -` workaround this host still needs)
- Next ask target: `ost 0.21.0`

## TL;DR

The macOS arm64 26.08 runtime is published, verified, and anonymously pullable.
All three OS now sit on one OpenUSD version, and every lane in
`openstrata.ci.yaml` — plus the hand-authored `release.yml` — is re-pinned to
26.08.

Report 29's three macOS-relevant findings all reproduce here verbatim:
`runtime pull --build` still cannot be talked out of `--no-examples`, `--slim`
would still discard the `share/` tree that holds every 26.08 example, and
`usdGenSchema` still needs a `jinja2` ost does not ship.

The new finding is macOS-specific and cost two failed builds. **OpenUSD 26.08
cannot be compiled against the macOS 14.5 SDK at C++17.** It needs Apple clang
16 *and* the macOS 15.2 SDK, and installing the compiler does not get you the
SDK — `xcrun` keeps selecting the SDK that matches the running OS. Nothing in
`ost` observes, steers, or records any of that: a macOS runtime artifact is
stamped `macos-arm64-py313` and carries no compiler, SDK, or deployment target,
even though ost measures precisely this class of fact on Linux (`glibc238`) and
Windows (`msvc143`).

## 1. Ask (P0, new) — macOS needs an SDK ost cannot see, steer, or record

Two full builds failed at 73% before this landed, both on the same translation
unit:

```console
$SDKROOT/usr/include/c++/v1/__memory/shared_ptr.h:303:37: error: calling a
protected constructor of class 'HdRetainedTypedSampledDataSource<TfToken>'
        ::new ((void*)__get_elem()) _Tp(_VSTD::forward<_Args>(__args)...);
make[2]: *** [pxr/imaging/hd/CMakeFiles/hd.dir/backPlateSchema.cpp.o] Error 1
```

This is not a misconfiguration, and it is not one file. OpenUSD's data sources
keep their constructors `protected` and rely on `std::allocate_shared` routing
construction through `HdDataSourceAllocator::construct`, which
`HD_DECLARE_DATASOURCE` declares a friend:

```cpp
#define HD_DECLARE_DATASOURCE(type) \
    HD_DECLARE_DATASOURCE_ABSTRACT(type) \
    _HD_ALLOCATOR_FRIEND \
    template <typename ... Args> \
    static Handle New(Args&& ... args) { \
        return std::allocate_shared<type>( \
            PXR_NS::HdDataSourceAllocator<type>{ }, \
            std::forward<Args>(args)...); \
    }
```

The macOS **14.5** SDK's libc++ only takes the allocator path under C++20:

```cpp
#if _LIBCPP_STD_VER >= 20
        ... allocator_traits<_TpAlloc>::construct(__tmp, __get_elem(), ...);
#else
        ::new ((void*)__get_elem()) _Tp(_VSTD::forward<_Args>(__args)...);
#endif
```

OpenUSD builds at C++17, so it takes the `#else` branch, the allocator is
bypassed, and the friendship never applies. The macOS **15.2** SDK's libc++ does
it unconditionally. A 25-line reproduction of the pattern confirms the split
cleanly — 14.5 SDK: 1 error, 15.2 SDK: 0 errors — so the whole difference is the
standard library header, not the compiler.

Three things make this an `ost` problem rather than an OpenUSD one:

**Installing clang 16 is not enough, and the failure looks identical.** The
second build ran on Apple clang 16.0.0 and failed the same way, because `xcrun`
resolves the SDK matching the *running OS* (14.5), not the newest installed.
"Command Line Tools for Xcode-16.2" installs both `clang-1600` and
`MacOSX15.2.sdk`, and you get the compiler by default but not the SDK. Note also
that `/Applications/Xcode.app` at 15.4 ships the same clang 15 as the CLT, so
`xcode-select --switch` is not a fix either.

**`ost runtime pull --build` has no way to express this.** The fix is an SDK
selection that reaches `build_usd.py`; OpenUSD accepts it via
`apple_utils.GetSDKRoot`, which scans `--cmake-build-args` for a
`CMAKE_OSX_SYSROOT` entry and feeds it to `xcrun --sdk`. Reaching that through
`ost` means `--build-arg --cmake-build-args=...`, i.e. the same appended-argument
channel report 29 §1 already showed cannot override ost's own decisions — and it
would compete with the `-DCMAKE_POLICY_VERSION_MINIMUM=3.5` this host also needs
for oneTBB under CMake 4.1, since `--cmake-build-args` is a single string.

**Nothing records what was used.** This is the part worth fixing first. The
published runtime's manifest is:

```json
"variant": { "abi": "native", "arch": "arm64", "os": "macos", "python": "313" },
"target": "macos-arm64-py313"
```

No compiler, no SDK, no deployment target. Yet ost already treats exactly this
class of fact as first-class elsewhere: Linux gets its glibc floor *measured*
and stamped into the target (`linux-x86_64-glibc238-py313`, report 14), and
Windows carries `msvc143`. macOS gets `native`, which asserts nothing. The
deployment target is not cosmetic — it decides which macOS versions can load the
runtime, exactly as the glibc floor does on Linux. This build pinned
`-DCMAKE_OSX_DEPLOYMENT_TARGET=14.5` deliberately, so that building against a
15.2 SDK did not silently produce a runtime unloadable on the 14.5 host that
built it. **A consumer cannot currently tell that from the artifact**, and
`--require-target macos-arm64-py313` passes regardless.

**Ask.** In priority order:

1. Measure and record the macOS deployment target and SDK the way the Linux
   glibc floor already is, and reflect the floor in the target string (e.g.
   `macos-arm64-macos145-py313`). Until then `--require-target` cannot catch a
   runtime that will not load.
2. Give `runtime pull --build` a first-class `--macos-sdk` / `--sysroot` knob, so
   the fix does not have to be smuggled through `--cmake-build-args`.
3. Detect the situation: ost knows the host OS and can ask `xcrun --show-sdk-path`
   before spawning a multi-hour build. For OpenUSD ≥ 26.08 on a macOS SDK < 15,
   one sentence up front beats a `protected constructor` error at 73%.

## 2. Confirmed from report 29 — `--build` still will not surrender `--no-examples`

Report 29 §1 found that `runtime pull --build` hardcodes `--no-examples
--no-tutorials --no-docs --no-tests` and appends `--build-arg` values after them,
so `--examples` is unreachable. That reproduces on macOS unchanged, and this
runtime was therefore built by driving `build_usd.py` directly and adopting with
`--from-usd`, at the cost of the `build` provenance:

```console
note: adopted OpenUSD reports version 26.08 (catalog default was 25.05.01)
Adopted runtime openstrata-cy2026-macos-arm64-py313-usd (local)
```

All three 26.08 runtimes are consequently recorded `source: local`. The ask is
unchanged from report 29 §1 and is now three-for-three across platforms.

The build that worked, for the record:

```sh
PATH="$HOME/Library/Python/3.13/bin:$PATH" \
python3.13 build_scripts/build_usd.py \
  --examples \
  --python-install-dir=lib/python \
  --codesign-id - \
  --cmake-build-args="-DCMAKE_POLICY_VERSION_MINIMUM=3.5 \
                      -DCMAKE_OSX_SYSROOT=macosx15.2 \
                      -DCMAKE_OSX_DEPLOYMENT_TARGET=14.5" \
  --src <src> --build <build> -j 8 <prefix>
```

Four host-specific items are load-bearing there and none are discoverable from
`ost`: `--codesign-id -` (report 11a — this host has no Xcode, and
`apple_utils.GetCodeSigningIdentifiers()` throws on `xcodebuild` being absent),
`CMAKE_POLICY_VERSION_MINIMUM=3.5` (report 06a — oneTBB 2020.3 under CMake 4.1),
`CMAKE_OSX_SYSROOT` (§1), and `pyside6-uic` on `PATH` or `build_usd.py` refuses
to start.

## 3. Confirmed from report 29 — `--slim` would still drop the examples

## 5. Delivered — `--build-metadata` works off-CI on a third platform

Recorded as a confirmation. Report 22 §5 asked for an env-agnostic provenance
path and report 29 §4 confirmed it on Windows and Linux; it works here too. A
JSON file naming `source.repository`, `source.revision`, `builder.id` and a
populated `builder.identity` produced `provenance.intoto.jsonl` beside
`sbom.spdx.json`, and the artifact verifies `trust: attested` from a clean
`OST_HOME` with no CI involved.

`artifact push` also printed the OCI-digest-churn warning report 22 §6 asked
for, which is what re-pinned `expected_oci_digest` in `openstrata.ci.yaml`
without a repeat of that report's ten-minute breakage.

## 6. Not an ost problem, recorded for completeness

The OpenUSD checkout this build started from was on `dev` at "Bump to
anticipated next version 26.11", exactly the trap report 29 §6 warned about —
`cmake/defaults/Version.cmake` read `26.11`. It was caught before the build by
checking `git describe`, and the build ran from a detached worktree at `v26.08`
so the working branch was never disturbed. Report 29 §6's advice holds and is
worth repeating: check the tag before a multi-hour build, because publishing is
one of the few operations where the version is an input rather than an output.

Separately, the scheduled lane's `plugin_artifact`
(`sha256:87ee36e4…`, `usdVrmFileFormat` 0.1.0) was built against the **26.05**
runtime. Re-pinning the runtime to 26.08 leaves that lane validating a
26.05-built plugin against a 26.08 runtime, and OpenUSD guarantees no ABI
stability across versions. The plugin must be republished before that lane's
result means anything; this is tracked in the roadmap, not here.
