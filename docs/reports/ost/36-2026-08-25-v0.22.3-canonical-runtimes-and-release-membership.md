# The runtimes we pinned were deleted, and four asks landed in the same release

- Date: 2026-08-25
- Version exercised: `ost 0.22.3` on Windows x86_64 (local workspace), cy2026 /
  OpenUSD 26.08; §8 re-verifies the two §7 blockers against `ost 0.22.4`
- Filename keeps `v0.22.3`: that is the version this report exercises. 0.22.4
  appears only as the resolution to what it found.
- Occasion: `ost` 0.22.3 published the CY2026 runtimes as a canonical matrix and
  removed the artifacts this repository pinned, so every lane had to be re-pinned
- Prior report: [35](35-2026-08-24-v0.22.2-release-artifact-membership.md)
- Next ask target: `ost 0.23.0`

## TL;DR

All three of report 35's P1 asks are **delivered** in 0.22.3, and the occasion
for finding out was not a planned upgrade: the runtimes this repository has
pinned since v0.5.0 no longer exist.

1. **Every runtime pin was dangling.** 0.22.3 publishes the CY2026 runtimes as
   16 canonical leaves of one declared matrix, and the hand-driven artifacts
   that preceded them are gone from GHCR. All six digests in
   `openstrata.ci.yaml` and `release.yml` resolved to `MANIFEST_UNKNOWN`. The
   re-pin is not a matter of taste: a `core` leaf is built `--no-imaging`, and
   this workspace refuses at configure time any runtime without `usdExecImaging`,
   so `gl`/`metal` is the floor.
2. **`ost library build|test|package` composes `requires.libraries`** (ask 1,
   P1). The verb reaches the member it was written for now: the mocopi adapter
   builds with `dependencies: 3`, tests 20/20, and packages as
   `vrmAdapterMocopi-0.7.0-<target>.tar.zst` — the artifact
   [WORKSPACE.md §5](../../architecture/WORKSPACE.md) has named since before
   anything could emit it.
3. **A workspace can declare its aggregate's membership** (ask 4, P2).
   `[workspace].release_members` / `release_exclude` in `openstrata.toml` replace
   the version pin that was holding the adapter CLIs out of the product, which is
   what §6 of report 35 said had to be decided rather than discovered.
4. **A workspace can own shared data** (ask 2, P1).
   `[[workspace.install_data]]` puts `profiles/motion` in the aggregate as
   product-owned data, without copying the layer's files under one tool's member
   root. The staging is measured; the artifact-only *run* it was asked for is
   now possible and still unwritten.
5. **The unmanaged-provenance warnings are gone** (ask 3, P1). All ten members
   packaged `matched (ost-managed)` out of one root build, where 0.22.2 called
   three of five `untracked (external-or-unmanaged)`.

Two new findings, neither blocking: an explicit member list is not optional in
practice, because a wildcard selects directories and one `__pycache__` refuses
the graph (§5.1); and a per-member build directory survives a compiler that no
longer exists, failing as a raw CMake error (§5.2).

**§7 through §10, appended after the lanes ran, are required reading beside
item 1.** They cost three `ost` releases in two days, and §10 records 0.22.5
closing five asks in one commit — then §11 records the lanes moving a third
time, and corrects §10: the render probe passed on this workstation only because
it happens to have PySide6 installed, and `usdrecord` needs Qt bindings the
runtime does not ship. §12 takes 0.22.6, which answers both of §11's asks, and
records the lanes going **17 of 17** — with Windows exercising one fix and macOS
the other, and `openusd-render` skipping on all three platforms because no cell
in this matrix has both a device and Qt.
The pins are correct, and 0.22.3 could consume only the Linux one: the macOS
leaf failed `artifact pull`, and every Windows cell failed `runtime validate`
with ten checks ok, two skipped and zero failures. Both were **consumer**
defects, already fixed on `ost`'s `main` and absent from the release this
contract pinned — no artifact was ever wrong and none was republished. 0.22.4
clears both, and `bootstrap.ost.version` is what changed. §7.1's ask was aimed
at the wrong repository, and §8 says why the wrong reading was tempting. **The lanes
then moved rather than went green**: 0.22.4's Windows device probing makes the
render check run for real, and it ran `usdrecord` against whatever `python` was
first on `PATH` — 3.12 on a hosted runner, against a py313 runtime (§9). 0.22.5
resolves the interpreter from the runtime's own contract, and closes the two P2s
from §5 in the same commit (§10).

## 1. The pins were dangling, and `core` cannot replace them

0.22.3 expands `support/openusd-runtime-matrix.json` into 16 immutable leaves —
OpenUSD 26.05 and 26.08 × Linux/Windows `core`/`gl`/`vulkan` and macOS arm64
`core`/`metal` — each published under
`ghcr.io/animu-sphere/openstrata-runtime-cy2026-usd` as
`<version>-<variant>-<os>-<arch>`. The repository's tag list is exactly those
sixteen. The three runtimes this repository pinned are not among them and are
not reachable by digest either:

```console
$ curl -s .../manifests/sha256:1a873111e4edf0cec7fdcf03e7bd2bbdf9723e1019cadcbcab9280c3229ac3af
{"errors":[{"code":"MANIFEST_UNKNOWN","message":"manifest unknown"}]}
```

That is the whole occasion for this report. It is worth stating plainly because
the CI contract's own header used to say the opposite: *"the OCI manifest digest
is NOT stable across republishes … while `runtime_artifact` stays put."* Both
move. The header says so now.

**Which variant is not a preference.** `cmake/UsdVrmOpenUsd.cmake` probes six
OpenExec components and refuses a runtime missing any of them; one of the six is
`usdExecImaging`, whose header lives under `pxr/usdImaging`. A `core` leaf is
planned as `--no-imaging --no-examples`, so it carries neither that header nor
the ExecIr examples, and this workspace cannot configure against it at all. The
three leaves pinned are therefore `26.08-gl-windows-x86_64`,
`26.08-gl-linux-x86_64` and `26.08-metal-macos-arm64`.

What that buys beyond a runtime that configures is evidence. The runtimes they
replace recorded:

```json
"openusd_verification": {"compile":"passed","link":"passed","loader":"not-run","physical_device":"not-run","render":"not-run"}
```

and each canonical imaging leaf records `passed` for all five, produced by a
platform-local adapter that loads the backend, observes a device and renders
through it before export. The Windows leaf pulled clean on the first try:

```console
$ ost artifact pull oci://…@sha256:d3ff79a6… --expect-artifact sha256:ebb0c7da… \
      --require-kind runtime --require-openusd cy2026/windows/x86_64/gl \
      --require-openusd-version 26.08 --require-sbom --require-provenance
  trust: effective=attested (required=local)
  verification: archive_digest, archive_safety, file_digests, kind_match,
                local_import, manifest_schema, oci_digest, openusd_requirement,
                openusd_selector, pinned_artifact_digest, provenance, sbom  — all passed
```

`--require-openusd PLATFORM/OS/ARCH/VARIANT` and `--require-openusd-version` are
new and are exactly the right shape for this repository's problem: the variant is
a hard requirement here, and until now nothing in the pull could state it. They
are not expressible in `openstrata.ci.yaml` — see §5.3.

**One identity changed under the rename.** The macOS target is
`macos-arm64-macos130-py313`, where the runtime it replaces carried no
deployment target in its id; Windows (`windows-x86_64-msvc143-py313`) and Linux
(`linux-x86_64-glibc238-py313`) are unchanged. Nothing here pins
`--require-target`, so nothing broke, but a consumer that did would fail on the
macOS cell alone and the failure would look platform-specific rather than
matrix-wide.

Local verification against the new Windows leaf, whole root tree:

```console
$ ost build   # 178 targets
$ ost test
100% tests passed out of 105
```

## 2. The per-library verb composes its closure (report 35 ask 1 — delivered)

Report 35 measured `ost library build` putting only the runtime on
`CMAKE_PREFIX_PATH`, so a library with `requires.libraries` failed at
`find_package` and the verb was usable on 2 of 8 libraries — neither of them an
adapter, which is what the ask had been written for. Same commands, one patch
release later:

```console
$ ost library build libs/motionSource
Built library motionSource 0.7.0
  dependencies: 1
  files:   13

$ ost library build adapters/liveCapture/mocopi
Built library vrmAdapterMocopi 0.7.0

$ ost library test adapters/liveCapture/mocopi

```

The install prefix contains `bin/mocopi_record.exe` beside the library and its

And the artifact WORKSPACE.md §5 has named since before anything could produce

```console
$ ost library package adapters/liveCapture/mocopi
Packaged library vrmAdapterMocopi 0.7.0
  archive: …/vrmAdapterMocopi-0.7.0-cy2026-windows-x86_64-py313-usd.tar.zst
  dependencies: 3

$ ost library package libs/liveTransport
Packaged library liveTransport 0.7.0
  dependencies: 0
  files:   9
```

That second command settles a prediction §5 of WORKSPACE.md wrote down to be
checked: `liveTransport` would be the first artifact on the excluded side the
toolchain could emit, *because* its edge set is empty where an adapter's is not.
Right about the outcome, wrong about the reason — by the time it was tested both
sides packaged.

No lane publishes either archive. Whether a release should carry adapter
artifacts is now a decision this repository can actually make, and it is
deliberately not made in this change.

## 3. The aggregate's membership is declared (report 35 ask 4 — delivered)

Report 35 §3 and §6 recorded the sharpest version of this: the rule "an adapter
is never part of the aggregate product" was true only because `ost` 0.21.0 did
not discover `adapters/<group>/<name>/tools/<tool>/`, the release lane pinned
0.21.0, and *nothing in any descriptor could decline membership*. Bumping the pin
would have published ten members without any file in this repository changing.

0.22.3 adds `[workspace].release_members` and `release_exclude`. `openstrata.toml`
declares the seven and names the three adapter CLIs, and packaging reports the
resolved set:

```console
$ ost plugin package --workspace --product --json
```
```json
"release_members": ["vrmSchema","usdVrmFileFormat","usdVrmPackageResolver",
                    "usdVrmaFileFormat","motion_bvh","motion_capture","motion_retarget"],
"packages":       [ … 10 entries, every discovered member, adapters included … ],
"product":        {"members": 7, "data_files": 3, …},
"warnings":       []
```

**Ten and seven are both correct, and the difference cost an edit.**
`.data.packages` is every member packaged; `.data.release_members` is the
aggregate. `release.yml`'s staging step counted `.data.packages[] | select(.member
== "tool")` against the `tools/` descriptors in the tree — six against three
under 0.22.3 — so the assertion that existed to catch exactly this class of drift
would have failed the lane on a correct build. It reads `release_members` now,
and stages only those. This is not a complaint: the JSON carries both facts under
distinct names, and the consumer that needed changing was ours.

The membership check fails closed. It is `AGGREGATE_MEMBERSHIP_MISMATCH` when the
discovered set minus the exclusions is not exactly the declared list, which fires
before the aggregate is written.

## 4. Shared data reaches the product (report 35 ask 2 — delivered)

Report 35 §4 asked for a data-only member or a member source path outside the
member root, because `directories: [bin, share]` — the one thing that worked —
staged the profiles by copying them under `tools/motionBvh/`, and the copy that
shipped would have stopped being the file `scripts/check_motion_profiles.py`
validates.

0.22.3's answer is the second shape, owned by the project rather than by a
member:

```toml
[[workspace.install_data]]
source = "profiles/motion"
destination = "share/usd-vrm-plugins/profiles/motion"
```

Measured: the product manifest reports `data_files: 3`, the archive stages the
directory as `data/0000/…` with the destination recorded in
`openstrata.product.json`, and no member archive changed. The source stays the
directory the validator reads.

**What is proven is the staging, not the run.** v0.7.0 shipped with
*both paths run from release artifacts alone, profiles included* recorded as an
unmet condition, and the reason it was unmet — no mechanism could put the data in
the product — is gone. The condition is not closed by that: nothing here has yet
extracted the product to a prefix and driven `motion_bvh_convert` from it. The
mechanism arriving and the test existing are different things, and this report
would rather say so than let the changelog imply otherwise.

One small thing about the mapping: it takes the whole directory. The CMake rule
it parallels filters `PATTERN "*.yaml"`, so `profiles/motion/README.md` now ships
where it did not before. Harmless in the artifact — and not harmless in the
staging tree, where it broke an unrelated check: `scripts/check_docs.py` walks
`**/*.md`, found the copy under `.strata/…/plugin-product-stage/data/0000/`, and
reported all five of that README's repository-relative links as broken. The fix
is ours (skip generated trees), but it is the kind of second-order effect worth
recording: `install_data` puts authored files somewhere no authored file had
been.

## 5. New findings

### 5.1 A wildcard member pattern selects directories, and residue is a directory

`[workspace].members` is fail-closed by design — a descriptor no pattern covers
is an error, which is the property that makes the declaration worth having. The
inverse also holds, and it is sharper than it looks:

```console
$ ost plugin test --workspace --graph-only
error[WORKSPACE_MEMBER_DESCRIPTOR_MISSING]: declared workspace member
  'C:\dev\usd-vrm-plugins\tools\__pycache__' has no OpenStrata member descriptor
  hint: add openstrata.plugin.yaml, openstrata.library.yaml, or
        openstrata.tool.yaml, or narrow [workspace].members
```

`tools/*` matched a `__pycache__` left by a test run, and the whole graph refused
to resolve — including for commands that would never have touched that
directory. The scan that *finds* uncovered descriptors already skips `.strata`,
`target`, `build`, `out`, `node_modules` and hidden directories; the pattern that
*selects* them does not skip anything. The workaround is to name all twenty
members explicitly, which this repository now does and does not regret — but it
is a workaround, and a project that follows the reference's `plugins/*` example
will hit this the first time a test writes a cache.

The error is also slightly misdirected: the hint offers "add a descriptor" first,
for a directory that is plainly build residue.

#### Ask (P2, `ost 0.23.0`)

Apply the same skip list to member *selection* that already governs the
uncovered-descriptor scan, or ignore a wildcard-matched directory that contains
no descriptor and no source. Failing that, name the pattern that matched in the
error, so the fix is visible without re-reading the manifest.

### 5.2 A per-member build directory outlives the compiler it was configured for

Visual Studio was upgraded in place on this machine (2022 → 18). The root
`ost build` handled it. Every per-member verb did not:

```console
$ ost plugin build plugins/vrmSchema
==> loaded MSVC environment (42 vars) from …\Microsoft Visual Studio\18\Community\…\vcvars64.bat
-- The CXX compiler identification is unknown
CMake Error at CMakeLists.txt:24 (project):
  The CMAKE_CXX_COMPILER:
    C:/Program Files/Microsoft Visual Studio/2022/Community/VC/Tools/MSVC/14.34.31933/bin/Hostx64/x64/cl.exe
  is not a full path to an existing compiler tool.
error[EXTERNAL_TOOL_FAILED] (phase: configure): the configure phase failed (exit 1)
```

`ost` loaded the *new* toolchain's environment in the line directly above the
failure, then handed CMake a build directory whose cache names the old one. Nine
directories had to be deleted by hand — four bundles and five libraries — each
discovered one failure at a time, because the verbs stop at the first one.

`ost` is the party that knows: it resolves the toolchain, stamps `msvc143` into
the target id, and owns the build directory under
`.strata/targets/<target>/`. A cached `CMAKE_CXX_COMPILER` that no longer exists
is a reconfigure, not an error to forward.

#### Ask (P2, `ost 0.23.0`)

Detect a per-member build directory whose cached compiler does not match the
resolved toolchain and reconfigure it (or delete and reconfigure), the way the
root build already survives. If that is too aggressive, fail with `ost`'s own
diagnostic naming the stale cache and the command to clear it, rather than
forwarding CMake's.

### 5.3 The CI contract cannot state the variant the pull can now require

`ost artifact pull` grew `--require-openusd cy2026/windows/x86_64/gl`, and for
this repository that flag is the difference between a runtime that configures and
one that cannot. `openstrata.ci.yaml`'s cell schema has no field for it: a cell
pins `runtime_artifact`, `runtime_remote`, `platform` and `profile`, and the
variant is only implicit in the digest. So the contract can pin *these bytes*
but cannot say *what kind of runtime the project requires* — and a re-pin to the
wrong leaf is caught at CMake configure on three runners rather than by the
matrix validator in milliseconds.

#### Ask (P3, `ost 0.23.0`)

Let a cell (or the matrix header) declare the required normalized OpenUSD cell
and version, and render them into the generated pull as `--require-openusd` /
`--require-openusd-version`.

## 7. Added 2026-08-25: the re-pin is correct and 0.22.3 cannot consume two thirds of it

Appended after PR #140 ran the generated lanes against the leaves §1 pins.
Nothing above is withdrawn — the pins are the right ones and Linux proves the
whole pyramid on them. Two of the three leaves are refused by `ost` itself
before any of this repository's code runs, and both reproduce on a local
workstation, so neither is a runner artifact.

```text
linux    4 bundle cells + workspace-graph  PASS
windows  5 cells                           FAIL at `ost runtime validate`
macos    5 cells                           FAIL at `ost artifact pull`
```

### 7.1 The macOS leaf is refused by its own producer's validation

```console
$ ost artifact pull oci://…@sha256:8486d942… \
      --expect-artifact sha256:8d132212… --require-kind runtime
error[ARTIFACT_MANIFEST_INVALID]: fetched manifest.json is not a producer
manifest: manifest is invalid: producer manifest OpenUSD compatibility identity
has unverified or contradictory provider versions
```

Identical on the hosted macOS runner and on a Windows workstation, so it is not
a runner artifact. The transport verifies the OCI digest and the archive digest
first and both pass, so the bytes arrive intact and it is the record inside them
that is rejected.

**Reading that as a bad artifact would have been wrong, and §8 is why this
paragraph does not.** The obvious inference from "the manifest fails producer
validation" is that the leaf needs republishing, and its shape invites it: the
compatibility block is the only place a macOS leaf differs from the two that
work, carrying an extra `macos` object (`sdk 15.5`, `deployment_target 13.0`)
beside `toolchain` (`apple-clang 17.0.0`, libcxx `>=17.x`). The artifact is
fine. `>=17.x` is a floor constraint carrying a wildcard, and 0.22.3's
`version_satisfies_constraint` handed the whole remainder after the operator to
a numeric parser that rejects `x` — so *every* operator-plus-wildcard constraint
was unsatisfiable, and libc++ 17.0.0 failed its own CY2026 cell. A consumer
defect, in the half of the message that says "unverified".

What the diagnostic cost is worth recording anyway: "unverified or
contradictory provider versions" names neither which provider nor which of the
two conditions, and those two point at opposite owners — *unverified* is a
predicate the consumer evaluates, *contradictory* is a claim about the bytes.

### 7.2 A `gl` runtime cannot pass `runtime validate` off Linux (P0)

Every check passes or skips, and the result is `FAILED`:

```console
$ ost runtime validate cy2026 --profile usd
  [ok  ] manifest-schema … [ok  ] openusd-opengl-loader — loaded host opengl
         loader 'opengl32.dll' and resolved 'glGetString'
  [skip] openusd-opengl-device — physical OpenGL device probing is currently
         supported for approved Linux cells
  [skip] openusd-render — the selected Hgi backend has no passing
         physical-device observation
Result: FAILED     (exit 5)
```

Ten `ok`, two `skip`, zero failures — and in the JSON both skipped checks carry
`"passed": true` while `"validation": "failed"` and `"ok": false`. Reproduced on
this workstation, which has a real GPU and a working OpenGL loader; the probe
does not decline for lack of a device but because the platform is not an
approved cell. Linux passes the identical command on the identical variant,
which is why only ten of the seventeen cells are red.

Whichever half is intended, the consumer's position is the same: a leaf whose
*producer* recorded `physical_device: passed` and `render: passed` is refused at
consume time on the platform it was built for, and the refusal names no failing
check. And there is no way around it here — §1 rules out `core`, so the variants
this workspace can use are exactly the ones this gate rejects off Linux.

The cause is a consumer one again. `GraphicsDeviceProbe.passed` means "a device
was observed" and `Check.passed` means "this does not fail validation", and the
device checks copied the first field straight into the second. A probe that
could not run reports `passed: false, skipped: true`, which displays as `[skip]`
and fails the report anyway — against `ost`'s own documented rule that a skipped
check never fails validation.

The generated lane runs `ost runtime validate` as its own step, so this is not
avoidable by editing the CI contract; it is a fail-closed gate the workflow
renderer emits.

Both defects sit inside the v0.22.3 release notes' own known limitation ("the
full host-specific OpenUSD builds, protected GHCR publication, and clean
pull-by-digest pass are post-release validation work"). This is that pass,
performed by the downstream consumer. It says the Linux third is clean, and §8
says what happened to the other two.


## 8. Added 2026-08-26: both were already fixed, and one ask was aimed at the wrong repository

`ost` 0.22.4 was released the same day and clears both. Neither artifact was
republished, because neither artifact was ever wrong.

```console
$ ost --version
ost 0.22.4

$ ost runtime validate cy2026 --profile usd
  [ok  ] openusd-opengl-loader — loaded host opengl loader 'opengl32.dll' and resolved 'glGetString'
  [ok  ] openusd-opengl-device — created a WGL context on 'NVIDIA RTX A5000/PCIe/SSE2'
  [ok  ] openusd-render — usdrecord rendered a 64px frame through gl (1716 bytes)
Result: passed

$ ost artifact pull oci://…@sha256:8486d942… --expect-artifact sha256:8d132212… --require-kind runtime
  passed  local_import
  import: imported (…/artifacts/objects/sha256/8d132212…)
```

Both fixes were on `main` before §7 was written, and neither was in the release
CI bootstraps. `855380a` drops a trailing wildcard before a comparison, so
`>=17.x` measures against `17`; `1ff348a` maps a skipped probe to a passing,
skipped check. A third, `524af38`, is why the Windows line above reads `ok`
rather than `skip`: 0.22.4 probes OpenGL devices on Windows, so a host with a
GPU attests the runtime instead of merely not failing it.

**Two things this is worth keeping for.**

The first is the ask that was wrong. §7.1 asked for a republished macOS leaf and
there was nothing to republish — the artifact was correct and the tool reading
it was not. What made the wrong reading tempting is that the failure was
*reproducible everywhere*: the same error on the hosted runner and on a Windows
workstation, which reads as a property of the bytes. It is equally a property of
a deterministic bug in every copy of one released binary. Identical failures
across hosts separate "the artifact" from "the runner" and say nothing at all
about "the artifact" versus "the consumer".

The second is what a consumer's lane is for. Both defects were fixed upstream
before this repository ever hit them, in commits three days newer than the
version its CI contract pinned. Nothing here found a new bug. What it found is
that a pinned toolchain is a snapshot of *bugs* as much as of features, and that
a support matrix pinning both an artifact and the tool that reads it can be
stale in the second axis while every digest in it is exact. `bootstrap.ost.version`
is the one field in `openstrata.ci.yaml` whose staleness a digest cannot express.

That line is `0.22.4` now. The runtime digests are unchanged from §1: they were
always right.


## 9. Added 2026-08-26: the render probe runs `usdrecord` against the host's `python`

0.22.4 cleared both §7 blockers and the lanes moved rather than went green.
`ost artifact pull` succeeds on the macOS leaf, so macOS reaches the same step
Windows does — and ten of seventeen cells now fail one check, for a reason that
is neither of the previous two:

```json
"name": "openusd-opengl-device", "status": "pass",   "skipped": false
"name": "openusd-render",        "status": "fail",
"detail": "usdrecord did not produce a non-empty frame (exit Some(1), 0 bytes):
    File \"C:\\hostedtoolcache\\windows\\Python\\3.12.10\\x64\\Lib\\importlib\\__init__.py\", line 90
    ImportError: DLL load failed while importing _tf: The specified module could not be found."
```

The runtime is `…-py313-usd`. The interpreter in that traceback is the hosted
runner's default **3.12**, so `_tf` cannot load — and the check reports the
runtime as failing. macOS fails identically after
`Metal created the system default MTLDevice`.

**The previous fix is what exposed it.** Before 0.22.4 these two checks skipped
on every non-Linux host and `1ff348a` made a skip non-fatal, so the render probe
never ran. `524af38` added WGL device probing on Windows and the Metal probe
observes a device on macOS, so on both platforms `openusd-opengl-device` now
*passes* — and a passing device observation is what makes the render stage run
for real. Linux is green for the opposite reason: the hosted `ubuntu-24.04`
runner presents no device, both checks still skip, and the skip is not fatal.
Three platforms, three different outcomes, one command.

Reproduced locally on a machine whose runtime validates cleanly, by changing
nothing except which `python` comes first on `PATH`:

```console
$ ost runtime validate cy2026 --profile usd
Result: passed

$ PATH=/some/other/python/Scripts:$PATH ost runtime validate cy2026 --profile usd
  [ok  ] openusd-opengl-device — created a WGL context on 'NVIDIA RTX A5000/PCIe/SSE2'
  [FAIL] openusd-render — usdrecord did not produce a non-empty frame (exit Some(103), 0 bytes):
         No Python at '…\Python310\python.exe'
Result: FAILED
```

Same runtime, same GPU, same everything the check claims to be about. This is a
false negative: what failed is the probe's environment, and what is reported is
the runtime.

There is a second-order half worth naming separately. The generated workflow
emits `Validate the materialized runtime` **before** `Set up host Python for
schema tooling`, so even a cell that declares `host_python: "3.13"` — the
workspace cells do, for the reason their comment gives — has 3.12 on `PATH` at
the moment this check runs. Reordering would mask the primary defect on a
runner and leave it in place for a developer.

`ost runtime validate` takes no flag that skips or scopes the graphics checks,
and the step is renderer output, so there is nothing to change in
`openstrata.ci.yaml`. The lane is red on a runtime this repository builds,
tests, packages and ships against.

### Ask (P0, `ost 0.22.5`)

Run the render probe in an environment that satisfies the runtime's own declared
Python contract — the manifest carries
`python: {family: cpython, version_constraint: "3.13.x"}`, and `ost plugin run`
already composes exactly such an environment. Where no interpreter satisfying it
can be found, report the check **skipped** rather than failed: that is the rule
`1ff348a` established one layer up, and the same argument applies — a probe that
could not run has observed nothing about the runtime.

Secondary, and not a substitute: have `ci generate` emit the host-Python step
before the validate step for cells that declare `host_python`.


## 10. Added 2026-08-26: 0.22.5 closes every ask that blocked a lane

`ost` 0.22.5 lands one commit — *report probes and patterns as themselves, not
as what they measured* — and it answers five of the asks below —
including the two P2s that had nothing to do with why the lanes were red.

| ask | §  | 0.22.5 |
| --- | --- | --- |
| render probe under the runtime's own Python | 9 | resolved, and `skipped` when nothing satisfies the contract |
| `host_python` step before `runtime validate` | 9 | emitted in that order by `ci generate` |
| wildcard member patterns vs. residue | 5.1 | a wildcard is a filter now; `__pycache__` joins the scan exclusions |
| a per-member build tree outliving its compiler | 5.2 | dropped and reconfigured |
| name the provider *and* the condition in a compatibility refusal | 7.1, 8 | every refusal names one provider, its constraint, its observed version, and which of the two held |

Three are re-verified here. The other two are not, and this section says which.

**The render probe.** The §9 reproduction is the test: change nothing but which
`python` comes first on `PATH`.

```console
$ PATH=/some/other/python/Scripts:$PATH ost runtime validate cy2026 --profile usd
  [ok  ] openusd-opengl-device — created a WGL context on 'NVIDIA RTX A5000/PCIe/SSE2'
  [ok  ] openusd-render — usdrecord rendered a 64px frame through gl under
         …\Python313\python.exe (1716 bytes)
Result: passed
```

Where 0.22.4 reported `[FAIL] openusd-render` for the same runtime on the same
GPU. The detail names the interpreter now, which is what makes the check
readable: the previous version's message described a frame that was not
produced and said nothing about the thing that had gone wrong.

The cause upstream turned out to be one layer below the diagnosis in §9. It is
not that `ost` chose the host's `python`; it is that OpenUSD installs
`usdrecord` behind a PATH-dependent launcher — on Windows a shim that is
literally `@python "%~dp0usdrecord" %*`, on Unix a shebang naming the
*producer's* interpreter — so invoking the installed tool at all hands the work
to whatever `python` resolves. 0.22.5 resolves the interpreter the way
`ost plugin run` does and passes the script to it, and classifies installed
tools by shebang rather than by extension.

**The generated order.** `Set up host Python for schema tooling` is now emitted
before `Validate the materialized runtime`, so a cell that declares which
interpreter its lane uses is not validated against the runner's default. Both
halves of §9's ask landed, and the primary one is what makes the secondary safe
— reordering alone would have masked the defect on a runner and left it for a
developer.

**Wildcard members.** Measured against the same `tools/__pycache__` that refused
the graph in §5.1: `members = ["plugins/*", "libs/*", "tools/*", "adapters/*/*",
"adapters/*/*/tools/*"]` now reports `4 bundle(s), 1 bundle edge(s), 10
libraries, 16 library edge(s), valid` — identical to the explicit list. A
literal member without a descriptor still fails and names the pattern that
selected it, and a pattern that reaches only residue is now
`WORKSPACE_MEMBER_PATTERN_EMPTY`.

`openstrata.toml` keeps the explicit list anyway, and the comment there now says
why: the workaround became a choice. What kept it is the reason that never
depended on the defect — adding a member should be a visible edit, which is the
same demand `release_members` makes.

**Not re-verified, and stated rather than implied.** The stale-build-tree fix
(§5.2) cannot be re-exercised here: the nine directories were deleted by hand
when this report was written, and reproducing it needs another in-place Visual
Studio upgrade. The commit's own account of it is worth recording because it is
a better diagnosis than §5.2's — the compiler lock could not have caught this,
since the `host` policy records no path, so upgrading in place left the
fingerprint identical while every cached `cl.exe` went away. The
compatibility-refusal message (§7.1) is not re-verified either: producing one
now requires a manifest that fails validation, and the artifact that used to
supply it passes.

## What this report cost, in the end

Nothing in it found a defect in an artifact. Every one of the five was in the
tool, and four of the five were invisible to the producer that published these
runtimes because they are consumer-side paths: a pull, a validate, a member
scan, a build directory. Three of them only appear when a real project pins a
real matrix on three real hosts, and two of those only appeared *after* an
earlier fix stopped an earlier failure from masking them.

The re-pin that started this changed no behaviour of this repository. It moved
`bootstrap.ost.version` three times in two days, and that line — the one field
in `openstrata.ci.yaml` that names something mutable — is what every one of
these turned on.


## 11. Added 2026-08-26: the render probe needs Qt, and this workstation had it

0.22.5 resolves the interpreter, and the lanes moved again rather than went
green. The same ten cells fail the same check, and the interpreter in the
message is now the right one:

```text
[ok  ] openusd-opengl-device — created a WGL context on 'GDI Generic'
[FAIL] openusd-render — usdrecord did not produce a non-empty frame under
       C:\hostedtoolcache\windows\Python\3.13.15\x64\python.exe (exit 1, 0 bytes):
         File "…/runtimes/openstrata-cy2026-windows-x86_64-py313-usd/bin/usdrecord",
           line 356, in main
             glWidget = _SetupOpenGLContext(args.imageWidth, args.imageWidth)
           line 39, in _SetupOpenGLContext
             from PySide2 import QtOpenGL
       ModuleNotFoundError: No module named 'PySide2'
```

macOS is byte-identical in shape, under
`/Library/Frameworks/Python.framework/Versions/3.13/bin/python3.13`.

`usdrecord`'s `_SetupOpenGLContext` tries `PySide6` first and falls back to
`PySide2`; the message names the fallback because both failed. So the probe's
dependency is not the runtime's — it is the runtime's *viewer* stack. OpenUSD
26.08 built without `--usdview` installs `usdrecord` and no Qt bindings for it,
which is exactly what these leaves are, and nothing in a lane installs any.

**The correction this section owes.** §10 reported the §9 reproduction inverting
on this workstation and called the render probe fixed. Half of that was right:
the interpreter *is* resolved from the runtime's contract now, and the detail
names it. What §10 did not establish is that the probe can run on a host that
has nothing extra, and it cannot — the local run passed because this machine's
py313 has **PySide6 6.11.1** installed from unrelated usdview work. It has no
PySide2 at all, which is why the CI message and a local reproduction would not
even name the same module. A green local render check said nothing about a
clean one, and this report published it as though it did.

**A second, smaller thing the log gives away.** `created a WGL context on 'GDI
Generic'` — the hosted Windows runner has no GPU, and WGL fell back to the
software rasterizer, which reports OpenGL 1.1 and cannot run Storm at all. The
device check passes on it. So even with Qt bindings present, the Windows render
would fail on its merits; macOS would not, since `MTLCreateSystemDefaultDevice`
returns a real device there. `openusd-opengl-device` passing on `GDI Generic` is
a false positive in a check whose name is *physical device*.

There is again no lever in the consumer's contract: `host_packages` accepts
`apt` and `brew` only, so a Windows lane cannot install a Python module, and
`runtime validate` still has no flag that scopes its graphics checks.

### Ask (P0, `ost 0.22.6`)

Render through the context `ost` already creates. The device probe builds a WGL
/ Metal context one check earlier and reports what it observed; shelling out to
`usdrecord` throws that away and re-acquires a context through a Qt stack the
runtime does not ship. A probe whose dependency set is the runtime's own is the
only version of this check that can pass on a clean host.

If it must keep using `usdrecord`, then a missing Qt binding is a probe that
could not run, and belongs in the `skipped` bucket with the others — the same
rule for the third time, one layer further out each time.

Separately (P2): treat a software rasterizer as no physical device.
`GDI Generic`, `llvmpipe` and `softpipe` are known names, and a check called
`openusd-opengl-device` that passes on one is claiming something the host cannot
back.


## 12. Added 2026-08-26: 0.22.6 takes both §11 asks, and this host cannot check either

`ost` 0.22.6 lands *distinguish render probe prerequisites from runtime
failures*, and it is both halves of §11:

- The Qt imports are preflighted under the resolved interpreter, in the same
  child process and timeout as the render itself. When neither binding imports,
  a dedicated exit code and diagnostic marker produce `openusd-render: skip`,
  with a detail naming the interpreter, the missing prerequisite, and that no
  render was attempted. Real tool, `pxr` and Hydra failures stay failures.
- `GDI Generic`, `llvmpipe` and `softpipe` are reported as software renderers
  rather than physical devices, so they no longer enable the render probe. A
  real NVIDIA or AMD observation still does.

Upstream's own note on it is
`docs/reports/2026-08-26-usd-vrm-ci-render-prerequisites.md`, and it corrects
one thing §11 got slightly wrong in passing: the trailing `PySide2` in the
traceback is only the *fallback* failing, and does not mean PySide2 is the
preferred binding or that interpreter selection was still broken. §11 said the
first part; it did not say the second clearly enough.

**Neither fix is verifiable on this workstation, and that is the point of
saying so.** This machine has a real GPU, so the software-renderer path never
runs; its py313 has PySide6, so the preflight always succeeds. Running
`ost runtime validate` here produces exactly what it produced under 0.22.5:

```console
[ok  ] openusd-opengl-device — created a WGL context on 'NVIDIA RTX A5000/PCIe/SSE2'
[ok  ] openusd-render — usdrecord rendered a 64px frame through gl under …\Python313\python.exe
Result: passed
```

Putting a Qt-less venv first on `PATH` does not change it either: `ost` resolves
the interpreter from the runtime's contract rather than from `PATH`, which is
0.22.5's fix working, and it lands on the same py313 with PySide6. The only
honest local statement is that nothing regressed here. **The lanes are the
test**, and this section is being written before they have run, deliberately —
§11 exists because §10 reported a local pass as though it settled a question
about a clean host.

The pin is `bootstrap.ost.version: "0.22.6"`. Runtime digests unchanged, for the
fourth time.
