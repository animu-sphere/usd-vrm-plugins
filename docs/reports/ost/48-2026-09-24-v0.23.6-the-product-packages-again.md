## 1. What changed

0.23.6 contains a single commit, "align workspace bundle package outputs with
installed stage". Per its release notes:

- A dependency bundle still installs into the shared workspace prefix.
- It now also installs into its own target-local bundle stage.
- The managed build's completion record hashes that stage.

As a result, a file that `cmake --install` does not copy, such as MSVC's
`.exp`, is no longer claimed as a package output. The repin touches three
files: the pin in `openstrata.ci.yaml`, the regenerated `ost-source-ci.yml`,
and the six places where `release.yml` mirrors the pin.

## 3. A published library names its producer's disk

A plain-CMake build of this repository composes the published `execMotion`
the way `ost` does, from the same pinned archive. It is being added as a
separate CI lane. On Linux it failed two suites, `execVrm_diagnostics` and
`workspace_exec_driver`, and passed the other 38. `ost test` passes the same
two suites, in the same container, with the same archive. The cause:

```text
$ readelf -d execMotion/lib/libExecMotion.so | grep RUNPATH
 Library runpath: [/home/runner/work/usd-motion-plugins/usd-motion-plugins/
   .ost-ci-home/runtimes/openstrata-cy2026-linux-x86_64-py313-usd/lib:
   /opt/hostedtoolcache/Python/3.13.15/x64/lib]
```

- The `RUNPATH` is the producer's hosted-runner checkout, which exists on no
  consumer machine.
- The library needs OpenUSD libraries that a test executable has not
  necessarily loaded yet (`usdSkel`, `exec`, `python`). Those are found only
  through `LD_LIBRARY_PATH`.
- With `LD_DEBUG=libs`, the failing run's loaded set ends before
  `libusd_usdSkel.so`, `libusd_usdGeom.so` and `libExecMotion.so`. With
  `LD_LIBRARY_PATH` naming the runtime's `lib/`, all three load and both
  suites pass. Setting `PXR_PLUGINPATH_NAME`, `PYTHONPATH` or a thread limit
  changes nothing.
- The suites that passed without it have executables that link those
  libraries themselves.

This is consistent with the bundle's own contract. Its
`openstrata.activation.json` names `LD_LIBRARY_PATH` as the loader variable,
and `ost test` activates the runtime. So nothing that `ost` runs can see the
problem. What went wrong was this repository's suites: they prepended only
`PATH`, which is the loader variable on Windows only. They now add the
platform's loader variable wherever they compose the bundle.

## 4. Asks

- **P3: do not ship a producer's absolute `RUNPATH` in a packaged library.**
  Either rewrite it to `$ORIGIN`-relative entries that hold inside the
  package, or strip it. The activation contract already supplies the loader
  path. What the packaged library carries is a path to someone else's disk,
  and it only ever matches by accident. A strip would also make two producers'
  builds of the same source more alike.
- Report 47's P1 is delivered. Report 46's observation (a hand-edited
  `pxr_DIR` with an intact identity record) is still not revisited.
