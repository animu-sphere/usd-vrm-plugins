# A plain library two directories down is invisible to the workspace

- Date: 2026-07-29
- Version exercised: `ost 0.21.0` on Windows x86_64 (local workspace), cy2026 /
  OpenUSD 26.08
- Occasion: scaffolding the first input adapter,
  `adapters/liveCapture/vmc` ([plan](../../roadmap/adapters-mocopi-vmc-ardy.md))
- Prior report: [33](33-2026-07-28-v0.21.0-workspace-ci-adoption.md)
- Next ask target: `ost 0.22.0`

## TL;DR

Adding the first plain library outside `libs/` turned up two gaps, and both cost
the workspace contract a claim it had been about to make.

1. **`--workspace` discovers plain libraries at two fixed locations only** — the
   project root's immediate subdirectories, and `libs/*`. A descriptor at
   `adapters/liveCapture/vmc/openstrata.library.yaml` is not found, so its
   declared `requires.libraries` edges are never validated. Measured by watching
   the reported library count, not by reading `--help`.
2. **A plain library has no per-library command at all.** `plugin build`,
   `plugin test`, and `plugin package` all take a *bundle*; `ost build` /
   `ost test` / `ost package` all take the whole *project*. There is nothing in
   between, so a library is only ever built as part of the root tree and can
   only ship inside a whole-workspace artifact.

Neither blocks the adapter. The root workspace tree builds it, and the three
`verify: test` workspace cells report 33 landed pick its tests up on all three
OS with no CI edit at all, which is that adoption working exactly as intended.
What is lost is the *graph* gate, and with it the enforcement the workspace
contract wanted to lean on.

Report 33's three asks are unchanged and restated at the end.

## 1. The discovery gap, measured

The adapter declares the only two edges
[WORKSPACE.md §2](../../architecture/WORKSPACE.md) permits it:

```yaml
# adapters/liveCapture/vmc/openstrata.library.yaml
schema: openstrata.library/v1alpha1
library:
  id: vrmAdapterVmc
  version: 0.5.0
requires:
  libraries:
    - id: motionCore
      version: ">=0.5,<0.6"
    - id: motionRuntime
      version: ">=0.5,<0.6"
```

The graph gate does not see it:

```console
$ ost plugin test --workspace --graph-only
Workspace dependency graph: 4 bundle(s), 1 bundle edge(s), 4 libraries, 7 library edge(s), valid
```

Four libraries — `motionCore`, `motionRuntime`, `vrmContainer`, `vrmRetarget`.
The fifth descriptor is present, well-formed, and simply not looked at. Nothing
in the output says so, which is the part that would have caught us: the gate
exits 0 and reports "valid", and a reader with no count in their head concludes
the adapter's edges were checked.

Bisecting the depth with a throwaway descriptor pins it exactly:

| Descriptor location | Discovered |
| --- | --- |
| `libs/<name>/openstrata.library.yaml` | yes (the four above) |
| `<name>/openstrata.library.yaml` (project root child) | **yes** — count moves to 5 |
| `adapters/<name>/openstrata.library.yaml` | no |
| `adapters/<group>/<name>/openstrata.library.yaml` | no |

So it is not a depth limit as such: a library is found in the project root's
immediate subdirectories or under the well-known `libs/`, and nowhere else. That
matches the bundle rule `--help` states — "immediate subdirectories and
`plugins/*` with a plugin manifest" — applied to libraries with `libs/`
substituted, which is a reasonable default and an unreasonable *only*.

### Why this repository cannot just move the directory

The obvious workaround is to flatten to `adapters/<name>/` or move the adapter
under `libs/`. Neither is available. The `adapters/liveCapture/` vs
`adapters/generators/` grouping is fixed by
[WORKSPACE.md §1](../../architecture/WORKSPACE.md) and exists to keep an
input-protocol leaf and a generation leaf visibly different kinds of thing; and
`adapters/` is the one directory in the repository where a product, SDK, or
protocol name is permitted at all, which is exactly what `libs/` must never
contain. The layout is a contract, and it predates this scaffold by a day.

### Ask (P1, `ost 0.22.0`)

Let a project say where its members are, rather than inferring it. A `members:`
list in `openstrata.toml` would do — the same shape `openstrata.tool.yaml`
members already take at packaging time:

```toml
[workspace]
members = ["plugins/*", "libs/*", "tools/*", "adapters/*/*"]
```

Failing that, glob recursively for `openstrata.library.yaml` under the project
root, excluding build and `.strata` directories.

Either way, one smaller thing is worth doing on its own: **when `--workspace`
finds a descriptor it does not intend to load, say so.** A silent skip and a
successful validation are indistinguishable from the outside, and this gate's
whole value is that a green result means something.

## 2. A plain library has no command of its own

`ost plugin build` refuses a library directory, correctly and unhelpfully:

```console
$ ost plugin build libs/motionRuntime --dry-run
error: no openstrata.plugin.yaml in 'libs/motionRuntime' (is this a plugin bundle? try `ost plugin new`)
```

That is the right refusal — a library is not a bundle — but there is no other
verb to reach for. The three `plugin` subcommands take a bundle path; `ost
build`, `ost test`, and `ost package` take the project's build target. Between
"one bundle" and "the entire project" there is nothing, so:

- a library cannot be built or tested in isolation, which is what a
  standalone-build invariant asks for (WORKSPACE.md §4 requires exactly this of
  every *bundle*, and the same reasoning applies to a library that consumers
  resolve with `find_package`);
- a library cannot be packaged, so `vrmAdapterVmc-<version>-<target>.tar.zst`
  — the artifact name WORKSPACE.md §5 assigns every adapter — is not producible.
  §5 now says so explicitly rather than implying the release lane emits one.

The second point is the one that matters for this track. Adapters are
deliberately **not** part of the aggregate product: they carry optional SDK,
network, and model dependencies whose licence terms should stay out of the core
distribution, and each should be free to take its own release cadence later.
That boundary is a packaging boundary, and today it has no packaging command.

Note this is not a regression caused by treating adapters as libraries. The
earlier contract wording called them bundles, which could not have produced a
loadable `openstrata.plugin.yaml` either — an adapter registers nothing with
OpenUSD, so it has no `kind` to claim and no `plugInfo.json` to point at. Both
readings arrive at the same missing verb.

### Ask (P2, `ost 0.22.0`)

`ost library build|test|package <DIR>`, or `--library <DIR>` on the existing
verbs. Packaging is the half we actually need: a `tar.zst` of one library's
install tree, named from its descriptor, so an optional component can ship
outside the product artifact.

## 3. What worked without any change at all

Worth recording, because it is the counterfactual for report 32's hand-rolled
lane. The adapter needed **no CI edit whatsoever**:

```console
$ ost build
-- OpenStrata: adding input adapter 'adapters/liveCapture/vmc'
[5/8] Linking CXX static library adapters\liveCapture\vmc\vrmAdapterVmc.lib
      Built target cy2026-windows-x86_64-py313-usd

$ ost test
25/25 Test #25: vrmAdapterVmc_boundaries .........   Passed    0.07 sec
100% tests passed out of 25
      Tested target cy2026-windows-x86_64-py313-usd: 25 of 25 passed (Release)
```

Report 33's `kind: workspace` cells build the root tree and run its whole CTest
suite, so a new library under a new top-level directory is covered on Windows,
macOS arm64, and Linux the moment the root `CMakeLists.txt` adds it — tests #24
and #25 above joined the suite without `openstrata.ci.yaml` being touched. Under
0.20.0 this would have needed a cell shape that did not exist.
The gap in §1 is real, but it is a gap in the *graph* gate specifically, not in
coverage.

## 4. Smaller observations, not asks

- `ost build` re-globs correctly when a new directory appears
  (`[0/2] Re-checking globbed directories...`), so `CONFIGURE_DEPENDS` over
  `adapters/*/*` behaves as it does over `plugins/*`.
- **The same source links to a different closure per OS, and the macOS cell is
  what caught it.** The adapter's test executable imports `usd_gf` alone on
  Windows and Linux, and `usd_gf` + `usd_boost` + `usd_python` on macOS arm64.
  Gf's imported target carries OpenUSD's vendored Boost and its Python layer
  transitively, and Apple's ld64 records every dylib that satisfied a symbol on
  the link line where Linux's default `--as-needed` and Windows' import
  libraries drop them. Not an `ost` issue and not something this repository
  authored — but a link-closure assertion written from one host is wrong on
  another, and only the three-OS lane says so.
- The whole configure-and-build for the new library took 4.8 s including the
  MSVC environment capture, so adding an adapter costs nothing measurable in the
  root lane.
