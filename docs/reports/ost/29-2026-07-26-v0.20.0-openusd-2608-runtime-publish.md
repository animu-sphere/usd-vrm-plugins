# OST v0.20.0 dogfooding — publishing the OpenUSD 26.08 runtimes, and the flags `--build` will not surrender

- Date: 2026-07-26
- Version exercised: `ost 0.20.0` on Windows x86_64 (host) and inside an
  `ubuntu:24.04` container (Linux x86_64)
- Occasion: the v0.6.0 direction pins OpenUSD to **26.08 exactly** and adopts
  OpenExec, so the `cy2026` / `usd` runtime had to be rebuilt from 26.08 and
  republished — with `--examples`, because that is where OpenUSD ships its
  ExecIr reference material.
- Related reports: [12](12-2026-07-09-v0.9.0-oci-publish-v1.0.0-rc1-asks.md)
  (the original publish recipe), [14](14-2026-07-11-v0.12.0-linux-glibc-fix-v0.13.0-asks.md)
  (the portable-Linux container recipe),
  [22](22-2026-07-17-v0.17.0-evidence-gate-v0.18.0-asks.md) (the evidence gate),
  [28](28-2026-07-26-v0.20.0-motion-layer-ci-gap.md) (the other live v0.21.0 asks)
- Next ask target: `ost 0.21.0`

## TL;DR

Two OpenUSD 26.08 runtimes are published, verified, and anonymously pullable —
and three of the four asks that made the 26.05 publish painful are **delivered**
in 0.20.0. `--build-metadata` (report 22 §5) means a workstation can now produce
an artifact that passes ost's own evidence gate; `artifact import` says out loud
that it attached evidence (report 22 §3); and `artifact push` prints the
OCI-digest-churn warning that report 22 §6 asked for. The publish path is, for
the first time, a path rather than a set of workarounds.

The one thing that did not work is the thing this release actually needed.
**`ost runtime pull --build` hardcodes `--no-examples --no-tutorials --no-docs
--no-tests` and appends `--build-arg` values after them**, so
`--build-arg --examples` produces `--no-examples --examples` and `build_usd.py`
rejects the pair outright. There is no override, and the flag ost forces off is
the one that carries OpenUSD's OpenExec/ExecIr examples. Both runtimes were
therefore built by driving `build_usd.py` directly and adopting the result with
`--from-usd`, which costs the `build` provenance: they are recorded as `local`.

Both from OpenUSD `v26.08` (`ee47c679abde5b467a7b6a41f3b2285564a4222e`), Python

OpenUSD tag and the `ost` pin, and `runtime export` measured the same honest
`glibc_floor: "2.38"`.

Verification, on both: anonymous `artifact pull` from a registry-free `OST_HOME`
passes every gate (`oci_digest`, `pinned_artifact_digest`, `kind_match`,
`target_match`, `sbom`, `provenance`, `local_import`), and the gate `ci generate`
renders — `artifact verify --minimum-trust local --require-sbom
--require-provenance` — returns `trust: attested`, `result: PASS`. The Linux
image was additionally pulled onto a bare `ubuntu:24.04` with no build toolchain:
`runtime validate` 7/7, `sdfdump --help` runs once `libpython3.13.so.1.0` is
present (as the generated lane's `host_python: 3.13` step provides), and
`readelf`-visible glibc errors are absent.

OpenExec is present in both without asking for it — `usd_exec`, `usd_execGeom`,
`usd_execIr`, `usd_execUsd`, `usd_usdExecImaging`, `usd_vdf`, 198 headers under
`include/pxr/exec`, and an importable `pxr.ExecIr`. 26.08's `build_usd.py` has no
OpenExec toggle. This matters for the v0.6.0 gate "the build fails on an
OpenExec-less runtime": at 26.08 there is no such runtime to fail on, so the
gate is about *detecting* the libraries, not about a build option.

## 1. Ask (P0) — `--build` will not let go of `--no-examples`

`ost runtime pull cy2026 --profile usd --build <src> --build-arg --examples`
fails in seconds. The invocation ost echoes says why:

```console
==> building OpenUSD (build_usd.py) into C:\usd\ost-home-2608\runtimes\openstrata-cy2026-windows-x86_64-py313-usd (one-time, heavy)
    …\python.EXE …\build_usd.py --no-examples --no-tutorials --no-docs --no-tests -j 32 --examples --python-install-dir=lib/python …
build_usd.py: error: argument --examples: not allowed with argument --no-examples
error[EXTERNAL_TOOL_FAILED]: build_usd.py failed (exit 2)
```

`--build-arg` is documented as "Extra argument forwarded to the builder", and it
is exactly that: **appended**, never substituted. `build_usd.py` puts
`--examples`/`--no-examples` (and `--tutorials`, `--docs`, `--tests`, `--tools`,
`--usdview`, …) in `argparse` mutually exclusive groups, which error on the
*pair* rather than letting the later flag win. So every component ost decides
for you is not a default — it is a hard constraint, and `--build-arg` cannot
reach it.

That would be a minor annoyance if the forced-off set were uninteresting. It is
not. OpenUSD 26.08 ships its OpenExec/ExecIr reference material as examples:

```text
share/usd/examples/plugin/{usdSchemaExamples,usdResolverExample,usdDancingCubesExample,
                           usdRecursivePayloadsExample,usdObj,hdTiny,hdParticleField}
share/exec/examples/{include,plugin}/irExampleAuthoringCode
lib/python/pxr/{IrExampleAuthoringCode,IrExampleUsdviewPlugin,UsdResolverExample,UsdSchemaExamples}
```

`irExampleAuthoringCode` and `irExampleUsdviewPlugin` are the working ExecIr
rig-authoring sample. This repo's v0.7.0 milestone is an ExecIr responsibility
audit against real 26.08 code, so "build the runtime the project needs" and "use
`ost runtime pull --build`" are currently incompatible requirements.

**The workaround costs provenance.** Driving `build_usd.py` directly and then
`ost runtime pull cy2026 --profile usd --from-usd <prefix> --force` works
perfectly — the adopt path detected `26.08` correctly (`note: adopted OpenUSD
reports version 26.08 (catalog default was 25.05.01)`), validate passed, export
and push were unremarkable. But the runtime record now reads `source: local`
instead of `source: build`, i.e. the artifact no longer claims ost built it.
Trading away build provenance to turn on a build flag is a bad trade to have to
make, and report 12 §Finding A made the same trade for a different reason.

**Ask.** Any one of these closes it:

1. Pass ost's component decisions as *defaults* the caller can override — e.g.
   detect that a `--build-arg` names the positive half of a mutually exclusive
   pair and drop ost's negative half.
2. First-class knobs for the components ost has an opinion about
   (`--with-examples`, `--with-tutorials`, `--with-tests`, …), so the common case
   needs no `--build-arg` at all.
3. Failing both, a `--build-args-only` / `--no-default-build-args` escape that
   hands the whole `build_usd.py` argument vector to the caller.

Option 1 is the smallest and would have made this report unnecessary.

Secondary, and cheap: ost knows the exact argv it is about to run, and
`argparse`'s mutual-exclusion failure is deterministic. Detecting the conflict
*before* spawning a build would turn a confusing 2-line `argparse` usage dump
into one sentence naming the two flags.

## 2. Ask (P1) — `--slim` drops `share/`, and 26.08 puts examples there

Report 12 §Finding E was that `--slim` dropped the top-level `resources/` that
`MaterialXConfig.cmake` `set_and_check`s. That is **fixed**: 0.20.0's help now
reads "include, lib, bin, plugin, cmake, libraries, resources, and CMake config".

`share/` is not in that list, and in 26.08 `share/` is where every example lands
(§1). So a slim 26.08 export silently ships a runtime whose examples were built
and then discarded. Both runtimes here were exported **full** for that reason;
with `src/` and `build/` steered outside the prefix via `build_usd.py --src
--build`, full costs almost nothing anyway (`dropped_referenced_layout: []`,
`excluded_top_level: []`).

**Ask.** Either keep `share/` in the slim layout, or make `--slim` report what
it dropped rather than dropping it silently — the same complaint report 22 §8
made about the MaterialX `resources/` case, one directory over. A one-line
`dropped_top_level: ["share"]` in the `--json` payload would be enough.

## 3. Ask (P1) — 26.08 moved the Python bindings; say which layout ost requires

OpenUSD 26.08's changelog: *"Python modules are now installed under
`lib/pythonX.Y/site-packages` on Linux and MacOS and `Lib/site-packages` on
Windows by default. This location can be customized via the
`--python-install-dir` argument in build_usd.py or `PXR_PYTHON_INSTALL_DIR`."*

The runtime record's `layout` array names `lib/python`, and `runtime validate`
has both a `pxr-package` and a `schema-gen-deps` check that must find it. Rather
than discover what 26.08's new default does to those checks, both builds pinned
the old location with `--build-arg --python-install-dir=lib/python`, which also
keeps the 26.08 runtimes drop-in compatible with the 26.05 ones this repo's CI
already consumes. **The 26.08 default layout was therefore not exercised here,
and this report makes no claim about whether it works.**

**Ask.** State the contract. If `lib/python` is required, `runtime pull` should
pass `--python-install-dir` itself for OpenUSD ≥ 26.08 rather than depending on
the operator knowing a changelog entry; if `lib/site-packages` is equally
supported (ost's binary contains that string), say so in the layout
documentation and in `runtime validate`'s output, so a publisher can choose
deliberately.

## 4. Delivered since report 22 — the produce side is a path now

Recorded as confirmations, not asks. All three were acceptance criteria written
in report 22 and all three behave as asked.

**`runtime export --build-metadata` (report 22 §5).** Provenance is no longer
GitHub-Actions-only. A JSON file with `source.repository`, `source.revision`,
`builder.id`, and a populated `builder.identity` produces
`provenance.intoto.jsonl` beside `sbom.spdx.json`, and the result verifies
`trust: attested`. These are the **first artifacts this project has published
that were built and attested entirely off CI** — report 22 §1.1's "a local
build, however long, can never satisfy the generated gate" no longer holds. The
`BUILD_METADATA_INCOMPLETE` error's hint ("describe the builder concretely — for
a self-hosted producer that is typically its host, pipeline and triggering ref")
is good guidance and was enough to author the file without reading source.

**`artifact import` reports the evidence it attached (report 22 §3).** The
Linux dist was produced in the container and imported on the Windows host — a
cross-platform handoff — and import printed:

```console
Imported runtime openstrata-cy2026-linux-x86_64-py313-usd 26.08 for linux-x86_64-glibc238-py313
  digest: sha256:70b47d1b…
  evidence attached: sbom.spdx.json, provenance.intoto.jsonl
```

That line is precisely the observability report 22 §3 asked for. The underlying
`already_present` short-circuit was not re-tested here (both digests were new to
every registry involved), so §3's core bug is **not** re-verified — only the
reporting around it.

**`artifact push` warns about OCI digest churn (report 22 §6).** The push output
now ends with a paragraph explaining that `expected_oci_digest` changes on every
republish because evidence layers embed the producing commit, while
`runtime_artifact` does not. Report 22 broke `main` for ten minutes learning
that; it is now in the CLI where it belongs.

## 5. Still open from report 12 — `usdGenSchema` needs a `jinja2` ost does not ship

Report 12 §Finding D asked that a runtime bundling `usdGenSchema` also bundle
its Python dependencies. It still does not: both 26.08 builds needed

```console
pip install --target <prefix>/lib/python jinja2      # pulls MarkupSafe too
```

before adoption, exactly as in 2026-07-09. What *has* improved is detection —
`runtime validate` now runs a `schema-gen-deps` check, so a runtime missing
`jinja2` fails validation on the producer's machine instead of failing a clean CI
runner deep inside `plugin build`'s schema-generate phase. The blast radius is
much smaller; the manual step remains.

**Ask (P2).** Provision `jinja2` + `MarkupSafe` into `lib/python` during
`runtime pull --build` (or vendor them at `runtime export`) whenever
`bin/usdGenSchema` is present. ost already knows the requirement well enough to
assert it.

## 6. Not an ost problem, recorded for completeness

The OpenUSD checkout this build started from was on the `dev` branch at
"Bump to anticipated next version 26.11", not at `v26.08` — `cmake/defaults/
Version.cmake` read `26.11` while the directory was named for 26.08. Nothing in
the toolchain would have caught it: ost's adopt path reads the *built* `pxr.h`
and would have faithfully stamped `26.11`, and the tag it was published under is
whatever the operator types. Publishing a runtime is one of the few places where
the version is an input rather than an output, so it is worth checking `git
describe` before a multi-hour build rather than after.
