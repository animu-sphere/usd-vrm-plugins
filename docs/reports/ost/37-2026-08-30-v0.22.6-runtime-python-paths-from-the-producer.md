# A published runtime hands every consumer the Python paths of the machine that built it

- Date: 2026-08-30
- Version exercised: `ost 0.22.6`, then `0.22.8` (which this repository re-pins
  to in the same change and which does **not** close the finding — §7), on the
  three GitHub-hosted runners — `windows-2022`, `macos-15`, `ubuntu-24.04` — against
  cy2026 / OpenUSD 26.08 leaves `26.08-gl-windows-x86_64`,
  `26.08-metal-macos-arm64` and `26.08-gl-linux-x86_64`
- Occasion: the first run of the installed-package consumer lane
  ([packaging-hardening.md](../../roadmap/packaging-hardening.md) PKG-4), which
  is the first thing in this project to configure CMake against a pulled runtime
  **without** `ost build`
- Prior report: [36](36-2026-08-25-v0.22.3-canonical-runtimes-and-release-membership.md)
- Next ask target: `ost 0.23.0`

## TL;DR

A pulled runtime's CMake package carries **the absolute Python paths of the
machine that produced it**, in two layers, and on a host that is not that
machine `find_package(pxr)` fails at configure time.

1. **`pxrConfig.cmake` sets `Python3_EXECUTABLE`, `Python3_LIBRARY` and
   `Python3_INCLUDE_DIR`** to the producer's before calling
   `find_dependency(Python3 "3.13" EXACT COMPONENTS Development)`. Overridable:
   the values are guarded with `if (NOT DEFINED ...)`, and OpenUSD's own comment
   beside them says as much.
2. **`pxrTargets.cmake` writes the producer's Python include directory into the
   `INTERFACE_INCLUDE_DIRECTORIES` of sixteen imported targets.** Not
   overridable by anything: CMake refuses at generate time with *Imported target
   "tf" includes non-existent path*.

The Windows leaf names `C:/Users/<producer>/AppData/Local/Programs/Python/Python313/Include`
— a home directory that exists on no runner. The Linux leaf names
`/usr/include/python3.13`, the `/usr` of the container it was built in, which is
not where `ubuntu-24.04` keeps a 3.13. The macOS leaf's baked paths resolved on
`macos-15` and it ran all twelve packages green.

**This is not something `ost build` is immune to.** Three explanations for the
green lanes were tested and all three are wrong (§3.2, §3.3): it is not the
toolchain file, it is not the Ninja generator, and `ost build` has no repair of
its own — it fails against a foreign path exactly as a plain `cmake` does.
Why `workspace-pr-linux` is green on a runner where the lane measured the same
directory missing is **still unexplained**, and is recorded as such.

With both layers answered in the lane's setup, the lane is **green on all three
platforms** and criterion 6 is met (§6).

## 1. What the lane ran

Twelve external CMake projects, one per installed package, each configured
against a prefix holding that package's transitive closure and nothing else.
Before a consumer is configured, the driver has to *produce* that prefix: it
configures, builds and installs the package from its own source directory with
plain `cmake`, against the pulled runtime.

That install configure is where all three platforms met OpenUSD for the first
time without `ost` in the middle. Two of them stopped there.

| Platform | Result |
| --- | --- |
| macOS (`macos-15`, `26.08-metal-macos-arm64`) | 12 of 12 green |
| Windows (`windows-2022`, `26.08-gl-windows-x86_64`) | 4 of 12; the other 8 never configured |
| Linux (`ubuntu-24.04`, `26.08-gl-linux-x86_64`) | 4 of 12; the same 8 |

The four that passed on every platform are exactly the four whose contract
closure never reaches `pxr`: `vrmContainer`, `liveTransport`, `osc` and
`vrmAdapterVrchatOsc`. The eight that failed are exactly the eight that do.
Nothing about these packages differs, and nothing about the two platforms
differs except which machine built the runtime they pulled.

**They failed as exit 2, not exit 1** — the distinction PKG-2 built into the
driver, doing its job on the first real occasion it had one. A package that does
not meet its contract is a different fact from a run that could not be set up,
and only the first means *fix the config*. (The lane's own summary line did
collapse the two, which is a defect this run found in it and which is fixed.)

## 2. The mechanism, in two layers

### 2.1 The variables, which are overridable

From the Windows leaf's `pxrConfig.cmake`, with the producer's own comment:

```cmake
# ... Use the same LIBRARY and INCLUDE_DIR settings from the original build if
# they were set. This can be overridden by specifying different values when
# running cmake.
if(ON)
    if (NOT DEFINED Python3_EXECUTABLE)
        if (NOT [[C:/Users/<producer>/AppData/Local/Programs/Python/Python313/python.EXE]] STREQUAL "")
            set(Python3_EXECUTABLE [[C:/Users/<producer>/.../python.EXE]])
        endif()
    endif()
    ...
    find_dependency(Python3 "3.13" EXACT COMPONENTS Development)
endif()
```

On Linux the consumer therefore saw:

```
Could NOT find Python3 (missing: Development Development.Module Development.Embed)
    Reason given by package:
        Development: Cannot find the directory "/usr/include/python3.13"
                     Cannot find the library "/usr/lib/x86_64-linux-gnu/libpython3.13.so"
```

`setup-python` had put a 3.13 with full Development artifacts on that runner,
under `/opt/hostedtoolcache`. It was never consulted, because the values were
already `set()`.

**`Python3_ROOT_DIR` does not fix this**, which is worth stating because it is
the obvious first attempt. These are `set()` *before* FindPython3 is reached, so
a root hint arrives too late; pointing one at a directory that does not exist
changed nothing at all and the run passed. What does fix it is setting the same
three variables the guard tests, which was then proved to win by naming a
library path that does not exist and reading `Cannot find the library
"C:/nowhere/python313.lib"` — our value in the failure text, not the runtime's.

### 2.2 The imported targets, which are not

With the variables supplied, both platforms moved on to the second layer:

```
CMake Error in CMakeLists.txt:
  Imported target "tf" includes non-existent path

    "C:/Users/<producer>/AppData/Local/Programs/Python/Python313/Include"

  in its INTERFACE_INCLUDE_DIRECTORIES.
```

`cmake/pxrTargets.cmake` carries that directory as literal text on sixteen
targets:

```cmake
set_target_properties(tf PROPERTIES
  INTERFACE_INCLUDE_DIRECTORIES "${_IMPORT_PREFIX}/include;C:/Users/<producer>/.../Include"
```

`${_IMPORT_PREFIX}` is how the *runtime's own* include directory survives
relocation. The Python one does not go through it, and no `-D` reaches static
text in an exported targets file.

## 3. What was measured on the way

### 3.1 The failure reproduces on a workstation

Substituting a foreign directory for the baked one in a local runtime's
`pxrTargets.cmake` — 16 occurrences — reproduces the CI failure exactly, and
restoring the file byte for byte afterwards leaves nothing behind. Every claim
in §2 was checked that way rather than read off a log.

### 3.2 `ost build` is not immune to it

The natural hypothesis was that `ost build`'s generated `toolchain.cmake` — which
sets exactly the three variables of §2.1 — is what has kept seventeen lanes
green. It is not sufficient: configuring the **whole workspace tree** with that
toolchain file against the same foreign runtime fails with

```
CMake Error in libs/motionCore/CMakeLists.txt:
  Imported target "gf" includes non-existent path
```

So the toolchain file answers §2.1 and nothing answers §2.2.

### 3.3 Why `workspace-pr-linux` is green is not explained here

On the same pull request, on the same runner image, with the same pulled
runtime, the workspace cell configures, builds and tests successfully while the
consumer cell reports `/usr/include/python3.13` non-existent — and the lane now
says so in its own output on every run: *repaired ... 16 imported-target include
entries named `/usr/include/python3.13`, which is not a directory on this host*.

Three explanations were tested and eliminated:

- **The toolchain file.** It sets the §2.1 variables and nothing else; §3.2.
- **The generator.** `ost build` uses Ninja and the lane used the platform
  default. Configuring the same package with `-G Ninja` against a foreign
  runtime exits 1 and writes no `build.ninja`, exactly as the default generator
  does.
- **A repair inside `ost build`.** One run appeared to restore a broken
  `pxrTargets.cmake`, which would have explained everything. It does not
  reproduce: with a marker line added to prove whether a file is rewritten or
  replaced, `ost build` failed at `configuring-cmake` with the same
  *non-existent path* errors and left the file untouched. The one restoring run
  is unexplained too, and is recorded rather than built on.

So this report does not know why the two cells disagree, and will not invent a
reason. The practical consequence is the same either way: **the workspace lane's
green result is not evidence that a pulled runtime is consumable, and it was
being read as though it were.**

## 4. What this repository did

Both layers are answered in the lane's setup, and neither touches a package
under test. The runtime is an external prefix — the thing that "arrives the way
it arrives for anyone else" — so repairing a defect in it is a different act
from editing a fixture or a config file, which the packaging track forbids.

- **§2.1** — `scripts/run_package_consumer_lane.py` derives
  `Python3_EXECUTABLE`, `Python3_LIBRARY` and `Python3_INCLUDE_DIR` from the
  interpreter the lane already pins to the runtime's version, and
  `scripts/check_package_consumer.py` passes them to both the install configure
  and the consumer configure. Every derived path is checked to exist first: a
  variable naming a file that is not there would replace a possibly-right value
  with a definitely-wrong one, and the failure would then read as a defect in
  the package.
- **§2.2** — the lane substitutes the baked include directory in the
  *materialized* runtime's `pxrTargets.cmake` for the host's, once, before
  anything is configured. The path is **read rather than guessed**:
  `pxrConfig.cmake` names the producer's own `Python3_INCLUDE_DIR` in a literal,
  so the substitution is exactly that string. If it is a directory on this host
  there is nothing to repair, and macOS is that case. `--no-repair-runtime`
  turns it off, which is what the unrepaired artifact does.

Two defects in that repair were found by making it work rather than by reading
it, and both are the kind that would have produced a misleading green:

- **It wrote the host's path in the host's spelling.** A Windows path with
  backslashes lands inside a quoted CMake argument where `\U` and `\P` are
  escapes, and `pxrTargets.cmake` stops parsing — `Syntax error in cmake code`,
  which reads as a corrupt runtime rather than as a bad substitution. It writes
  CMake's spelling now.
- **It reported "no repair needed" when nothing had matched.** Two different
  facts — *the baked path exists here* and *the baked path is nowhere in the
  targets file* — printed the same reassuring line. They are three outcomes now,
  and the one that means *nothing is known* says so.

## 5. The ask

**P1 — a runtime's exported CMake package should be consumable from a host that
did not build it.**

An `ost` runtime is distributed as an immutable artifact, pulled by digest, onto
machines that by construction are not the producer. Its CMake package currently
encodes the producing environment's Python paths in two places, one of which no
consumer can override. The only reason this project has not tripped over it in
five releases is that nothing here had ever configured against a pulled runtime
without `ost build` in front of it — and §3.2 shows that even that is not a
defence, only a habit.

Either half would close it:

1. **Neutralize the paths at export.** `Python3_EXECUTABLE`, `Python3_LIBRARY`
   and `Python3_INCLUDE_DIR` in `pxrConfig.cmake` are a build-time convenience
   of OpenUSD's install, and a redistributable artifact is the case they were
   not written for. Clearing them lets the `find_dependency` resolve against the
   consuming host — the right answer on every machine including the producer's.
   The `INTERFACE_INCLUDE_DIRECTORIES` entries need the stronger fix: they must
   become a reference to whatever Python the consumer resolved, the way
   `${_IMPORT_PREFIX}` already handles the runtime's own include directory.
2. **Publish the toolchain values without a build.** `ost env <platform>
   --profile <profile> --json` already reports the prefix and the environment. A
   consumer that could ask it for the same `Python3_*` values `ost build` writes
   into `toolchain.cmake` would need no derivation of its own. Today those exist
   only under `.strata/targets/<target>/`, written by a build — and a build tree
   is precisely what a clean-prefix consumer check must not have. **This alone
   does not close the ask**, because it answers §2.1 and not §2.2.

The first is the fix; the second is a convenience worth having anyway.

**Not blocking.** The lane carries both workarounds, they are about thirty lines,
and each is commented with its mechanism at the place it is applied. What is lost
without the fix is that every external consumer of a published runtime has to
discover this the way this project did.

## 6. The lane after both workarounds

Green on all three platforms, twelve packages each, and criterion 6 met: every
workspace target in every closure is present on all three or on none, and the
one documented platform difference is present in both directions —
`Threads::Threads` on macOS and Linux, `ws2_32` on Windows.

Two things the run says that this report could not have predicted:

**The repair fires on two of the three platforms, and the lane says which.**
Linux repaired 16 entries naming `/usr/include/python3.13`; Windows 16 naming
the producer's home directory. macOS repaired none — its baked paths resolve
there — and printed *no Python 3 Development artifacts derived*, because the
derivation in §4 returns nothing on that host's `sysconfig` layout. **macOS is
therefore green on the runtime's own baked paths and neither workaround has ever
been exercised there**, which is a latent gap rather than a passing grade: if
that leaf is ever republished from a machine whose paths do not resolve on a
runner, the lane will fail there with nothing to fall back on. It is left as
measured-and-stated rather than fixed, because fixing a derivation for a host
this project cannot run is guesswork, and the note is what makes the gap visible
on every run.

**The synthetic verification had the right shape and the wrong counts.** The
comparison's ten cases were checked against predicted POSIX closures, and the
prediction stated in advance that it was one. What the real run measured:
OpenUSD's platform link line is three entries on Windows (`Dbghelp.lib`,
`Shlwapi.lib`, `Ws2_32.lib`), **two** on Linux (`dl`, `m`) and three on macOS
(those two plus `-framework Foundation`) — 10 external entries against 9 and 9,
where the prediction had 10 against 10. The rules fired where they were aimed;
what they would see was approximate.

## 7. `ost 0.22.8` does not close this

This repository re-pins `bootstrap.ost.version` from 0.22.6 to 0.22.8 in the
same change, and the finding survives it — which is what should be expected, and
is recorded because the alternative is someone assuming a version bump fixed it.

- **The materialized CMake package is byte-identical.** Re-pulling the same
  artifact under 0.22.8 leaves `pxrConfig.cmake` and `cmake/pxrTargets.cmake`
  with the same MD5s they had under 0.22.6, and the producer's include directory
  is still on sixteen imported targets. The defect is in what was *exported*,
  not in the tool that pulls it, so only a republished runtime can close it.
- **`ost ci generate` renders no semantic change.** The regenerated lanes differ
  from the 0.22.6 output in the version string and nothing else.
- **`runtime validate` is fully green on this workstation**, `openusd-render`
  included, which 0.22.6 skipped here — and that includes a
  **`consumer-configure`** check reporting *find_package(pxr) configures against
  &lt;runtime&gt;*. That check passed on the Linux runner too, on the same runtime the
  consumer lane could not link against. It is presumably configure-only, since a
  probe that linked an imported target would have met §2.2 — so it is not a
  substitute for this lane, and reading it as one is the same mistake as reading
  the workspace cell's green as evidence.
- 0.22.7/0.22.8 do bring composed-runtime locking and a `runtime env
  --composition` verb. Neither is the second half of the §5 ask: they describe a
  *composed* SDK, and the values a consumer of a pulled runtime needs are still
  only written by a build.

## 8. What this says about the packaging track

Nothing in §1 through §3 is a defect in a package this repository ships. All
twelve configs remain correct, and macOS confirmed it by running all twelve
green through the same code path.

What the run demonstrates is the track's own premise, arriving from a direction
the track did not predict. PKG-4 was written to catch a *package* that could not
be consumed from outside. The first thing it caught was a *runtime* that could
not be consumed from outside — found for exactly the same reason, that no lane
had ever configured against one without the tool that hides it.
