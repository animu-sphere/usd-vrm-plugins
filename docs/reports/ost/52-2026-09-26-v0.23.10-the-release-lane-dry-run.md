# The release lane's dry run, and two defects of ours

- Date: 2026-09-26
- Version exercised: `ost 0.23.10`, the pinned release asset, on the three
  hosted release cells (`release-linux`, `release-macos-arm64`,
  `release-windows`), plus a local Windows reproduction
- Occasion: [report 51](51-2026-09-26-v0.23.10-vrmimaging-joins-the-product.md)
  §5 left Linux and macOS acceptance of the `usd-imaging` kind, and the hosted
  release cell, to a `release.yml` run. Three `workflow_dispatch` dry runs of
  #249's branch made that run, before #249 merged.
- Prior report: [51](51-2026-09-26-v0.23.10-vrmimaging-joins-the-product.md)
- Next ask target: the next `ost` release

## TL;DR

**The third dry run passed on all three platforms**
([36231189296](https://github.com/animu-sphere/usd-vrm-plugins/actions/runs/36231189296)),
with `vrmImaging` in the product. That closes report 51 §5's first two
items. Getting there took two fixes to `release.yml`. Both defects were
ours, and neither could show on a pull request.

1. **Delivered on Linux and macOS** (§1). `runtime.usd_imaging` and the
   native `imaging.registration` L2 pass on all three platforms. The
   eight-member product packages, and every later release-lane step passes.
2. **Ours: the runtime was validated before the host Python existed** (§2).
   Since `ost` 0.23.1, `runtime validate` runs a consumer executable, and
   `release.yml` validated before `setup-python`. The first dry run failed on
   Windows and Linux. The release lane had been unable to pass since the
   0.23.1 pin on 2026-09-20, and nothing ran it until today.
3. **Ours: the registry cache kept the smoke's imports** (§3). A successful
   run cached a registry that held the workspace packages the clean-install
   smoke had imported. The next run restored it and failed with
   `ARTIFACT_IDENTITY_CONFLICT`.
4. **One P3** (§4): a `consumer-link` loader failure could name the library
   that did not load.

## 2. Ours: the validate step ran before its interpreter

Run [36229916537](https://github.com/animu-sphere/usd-vrm-plugins/actions/runs/36229916537):
`release-linux` and `release-windows` failed at "Verify and materialize the
pinned runtime SDK" with exit code 5. `release-macos-arm64` passed.

That step ran `ost runtime validate ... --json > /dev/null` straight after
`ost runtime pull`. The host Python is set up two steps later. The generated
PR lanes do it the other way round: they validate in a separate step after
the host packages and the host Python. Since `ost` 0.23.1 ("validate
OpenUSD consumer link and execution"), `consumer-link` builds and **runs** a
C++ consumer. The runtime's USD libraries import the host interpreter's
library, so without it the consumer cannot start.

Reproduced locally on Windows by removing every Python directory from
`PATH`:

```text
[FAIL] consumer-link — consumer test failed: 1/1 Test #1: ost_consumer
       .....Exit code 0xc0000135***Exception ...
Result: FAILED     (exit 5)
```

With Python on `PATH`, the same command passes. The Linux cause was not
observed directly, because the lane had sent the output to `/dev/null`. It
passed once the step moved (runs 36230497491 and 36231189296), and nothing
else changed between those runs on Linux. macOS passed before the move.
Whether that is because its runtime finds an interpreter on its own was not
measured.

`release.yml` now validates in its own step after `setup-python`, as the PR
lanes do, and keeps the JSON. The lane had been broken this way since the
0.23.1 pin (2026-09-20). v0.9.0 was tagged on 2026-09-17, and no release run
happened in between. This is the trap this series has recorded before: a
green pull request says nothing about `release.yml`.

## 3. Ours: the cache outlived the smoke's imports

Run [36230497491](https://github.com/animu-sphere/usd-vrm-plugins/actions/runs/36230497491):
Linux and Windows passed. `release-macos-arm64` failed at the clean-install
smoke:

```text
error[ARTIFACT_IDENTITY_CONFLICT]: artifact sha256:9bef44868086 is already
stored with different source, dependency, OpenUSD compatibility, or
verification identity
CalledProcessError: ost artifact import .../plugins/vrmSchema/dist/plugins/vrmSchema/0.9.0/cy2026-macos-arm64-py313-usd
```

Here is how it happened:

- `release.yml` cached `.ost-ci-home/artifacts` with `actions/cache`, which
  saves at the end of a successful job.
- The first run's macOS job succeeded, so it saved the registry, including
  the workspace packages the clean-install smoke imports.
- The second run restored that cache ("Cache hit ... Cache restored
  successfully").
- The `vrmSchema` package was byte-identical between the two commits, so it
  had the same archive digest. It came from a different commit, so it had a
  different identity. `ost` refused the second import.

The PR lanes cannot hit this: they restore and save separately, and save
straight after the runtime is pulled. `release.yml` now does the same.
The three caches the release runs had saved on the branch, whatever they
held, were deleted before the third run.

A tag run could have hit the same conflict. A tag can restore caches saved
on the default branch, and a successful dispatch on `main` would have saved
exactly such a cache. `ost`'s refusal is correct: the same bytes under two
identities is what the identity check exists to stop. The defect was in
what we cached.

## 4. P3: a loader failure could name what did not load

`consumer-link` reported `Exit code 0xc0000135` and a CTest summary.
0xC0000135 is Windows' "a DLL was not found", and it does not say which DLL.
It took a local reproduction to see that the missing library was the host
interpreter's. `runtime validate` already knows the runtime's host
interpreter requirement, so when the consumer exits with a loader failure,
it could say which library the runtime expects the host to provide
(`python313.dll` here), or where it looked. A lane that captures the output
would then have found this in one read.
