# One workspace prefix answers for every bundle, and the last build decides what it holds

- Date: 2026-09-13
- Version exercised: `ost 0.22.8` on this workstation
  (`cy2026-windows-x86_64-py313-usd`), and `ost 0.22.10` (the published
  `x86_64-pc-windows-msvc` asset, checksum-verified) on a **fresh clone** of
  `main` at `5dc0b9f`, which has no `libs/*/build/`, no `.strata/` and no
  `dist/` — the state a CI runner starts from
- Occasion: the first run of the OpenExec bundles from the **installed
  product** (the OpenExec plan's P0-4 step 7 and P0-7, "from packaged
  plugins"), which is the first time anything here loaded a `.vrm` through a
  product built since `execMotion` joined the release
- Prior report: [39](39-2026-09-01-v0.22.8-release-lane-first-execution.md)
- Next ask target: `ost 0.23.0`, or a 0.22.x patch — the P1 below breaks a
  release lane that follows the documented build order

## TL;DR

**The product this repository would tag today cannot open a `.vrm` file, and
every step between the build and the archive says it can.**

1. **P1 — `plugin package` (and `plugin test --workspace`) stage every
   bundle's plain-library runtime out of one shared prefix, which each
   `ost plugin build` wipes and refills with *its own* closure.** So a
   workspace packaged after a loop of bundle builds carries the **last** bundle's
   closure in every package. Since 2026-09-06 our release loop has ended with
   `execVrm`, which links only static libraries: no `vrmContainer` binary
   reaches any package, the importer, resolver and VRMA reader fail to load,
   and the release lane would have gone red at its pyramid step — while the
   packaging step after it exits 0 on the same tree. Reproduced on a fresh
   clone with 0.22.10; reordering the loop and nothing else reverses it (§2,
   §3).
2. **The record says the binary is there.** A library counts as staged when
   its runtime *directory* exists in the prefix, not when its file does, so
   `WORKSPACE_LIBRARY_RUNTIME_MISSING` never fires and every broken package's
   `dependencies.json` records `vrmContainer` at `runtime/libraries/lib` — a
   directory holding another bundle's `.lib` files and no `vrmContainer` at all
   (§2.2). This is the half we can check without `ost`, and now do (§4).
3. **P3 — a product's activation lists a dependency bundle once per bundle
   that carries it.** `execMotion`'s `plugInfo.json` is on
   `PXR_PLUGINPATH_NAME` twice and `vrmSchema`'s three times. OpenUSD keeps the
   first plugin it registers under a name, and reads plugInfo files in parallel,
   so which copy answers is not determined. Harmless while the copies are
   byte-identical, which inside one product they are (§5).
4. **P3 — a package's `runtime/libraries/` is the prefix's directory, not the
   library's files.** Every package carries the last closure's static archives,
   CMake configs and another bundle's `libvrmSchema`; in the run that passed,
   the `vrmContainer` the importer actually loaded was the copy **`execMotion`**
   carries and does not declare (§3.3).

**What went right, and it is the run this report exists for.** Once the
product carried its libraries, the whole OpenExec parity suite ran from it:
the product's own `motion_bvh_convert` and `motion_retarget` produced the input
and the bake, the product's `execMotion` and `execVrm` evaluated it, and all
five cases held bit for bit — with every module the harness mapped read back
and none of this workspace's coming from anywhere but the install prefix.
`ost plugin product install`'s activation file is the whole of the glue that
needed (§6).

## 1. What was being done

The OpenExec plan owes one run it had never made: computation discovery from a
packaged plugin rather than a build tree. Every exec suite loads a *built*
bundle through its source directory. The plan scheduled that run as P0-4 step
7 and as P0-7's "works from packaged plugins", and noted that one run closes
both.

OpenExec has no Python binding, so the run needs a C++ driver, and the parity
harness is already one: `tests/parity/exec_parity` links only static workspace
libraries and OpenUSD and finds both bundles through `PXR_PLUGINPATH_NAME`. The
plan was to package the product the way `release.yml` does, install it outside
the repository, and hand the parity driver the product's tools instead of the
build tree's.

The first case to run, the recorded mocopi export onto `Seed-san.vrm`, did not
reach exec. The product's `motion_retarget` could not open the avatar:

```text
Coding Error: in _Load at line 244 of pxr/base/plug/plugin.cpp -- Failed to
load plugin 'UsdVrmFileFormat': <the module could not be found, in CP932>
 in '<prefix>/bundles/usdVrmFileFormat/lib/libUsdVrmFileFormat.dll'
```

There is no `vrmContainer.dll` anywhere in the installed product.

## 2. The defect

### 2.1 The prefix is rebuilt per bundle, and read for all of them

`ost plugin build <bundle>` composes the bundle's closure into
`.strata/targets/<target>/workspace-prefix`, and it starts by deleting it
(`crates/ost-cli/src/commands/plugin.rs`, the composed-build path:
`remove_dir_all(prefix)`, then `build_library_one` / `build_one` for each
dependency). Watching the prefix across `release.yml`'s own loop, on the fresh
clone with 0.22.10:

| after `ost plugin build` | `workspace-prefix/bin` | shared libraries in `workspace-prefix/lib` |
| --- | --- | --- |
| `plugins/vrmSchema` | — | — |
| `plugins/usdVrmFileFormat` | `vrmContainer.dll` | `libvrmSchema.dll` |
| `plugins/usdVrmPackageResolver` | `vrmContainer.dll` | — |
| `plugins/usdVrmaFileFormat` | `vrmContainer.dll` | — |
| `plugins/execMotion` | — | — |
| `plugins/execVrm` | — | `libvrmSchema.dll` |

That is the documented contract — "the prefix is target-specific and rebuilt
for a composed build" (`docs/reference/plugin-workspace.md`). The defect is on
the reading side. The same document says "a plugin package materializes **its
selected** plain-library runtime under `runtime/libraries/`", and
`selected_library_package_runtime` maps each of the bundle's libraries'
`runtime.directories` out of that one prefix — whichever bundle last rebuilt
it. `plugin test --workspace` reads the same prefix for its session loader
path.

### 2.2 A directory stands in for a file

`runtime.directories` defaults to `["bin", "lib"]`, and a library counts as
materialized when `prefix/<directory>` **is a directory**. After `execVrm`,
`prefix/lib` exists — it holds `motionCore.lib`, `motionRuntime.lib`,
`vrmRetarget.lib` and `libvrmSchema.dll` — so `vrmContainer`'s `lib` "exists",
`WORKSPACE_LIBRARY_RUNTIME_MISSING` does not fire, and the whole directory is
staged as the importer's `runtime/libraries/lib`. The package's
`dependencies.json` then says:

```json
{ "id": "vrmContainer", "runtime_directories": ["runtime/libraries/lib"],
  "provenance": "source-workspace", "version": "0.8.0" }
```

and that directory contains no `vrmContainer` binary. Nothing between the
build and the archive compares the two.

`selected_library_package_runtime`, `installed_runtime_dirs` and
`default_runtime_directories` are unchanged between 0.22.8 and 0.22.10, and
neither release note mentions the prefix.

## 3. Measurements

### 3.1 The order is the whole cause

Same fresh clone, same `ost 0.22.10`, same root build. Only the order of the
per-bundle builds differs:

| | loop ends with `execVrm` (`release.yml` since #180) | loop ends with `usdVrmaFileFormat` |
| --- | --- | --- |
| `ost plugin test --workspace --up-to 5` | **3 of 6 fail**: `usdVrmFileFormat` and `usdVrmaFileFormat` from L2 `plugin.discovery`, `usdVrmPackageResolver` from its registration probe | 6 of 6 pass |
| `ost plugin package --workspace --product` | exit 0 | exit 0 |
| `vrmContainer` binary in the product | **none** | in all five packages that stage libraries, `execMotion` and `execVrm` included |
| Seed-san parity from the product | `motion_retarget` cannot open the avatar | holds, 853 samples × 128 joints |

The loop has ended with an exec bundle since `execMotion` joined it on
2026-09-06 (#174), and `release.yml` last ran on 2026-09-01. No run of the
lane has seen the broken state; no `pull_request` event runs `release.yml`
(report 39 §5).

### 3.2 Why no PR lane saw it

The PR matrix builds the root tree and runs CTest, which loads bundles from
their build trees with sibling libraries on explicit paths, and the three
standalone `usdVrmFileFormat` cells build that one bundle, whose own closure
is exactly what it needs. Only a lane that builds **several** bundles and then
tests or packages them **as a workspace** reads a prefix some other bundle
filled — which is `release.yml`, and nothing else.

### 3.3 In the product that works, the wrong package answers

In the reordered product, `exec_parity`'s record of every module it mapped
shows the importer loaded `vrmContainer.dll` from
`bundles/execMotion/runtime/libraries/bin/` — a copy `execMotion` carries and
does not declare. The product activation puts every bundle's library
directories on one loader path, execMotion's first, so any copy answers, and
the one that answers is whichever bundle sorts first. That is not wrong today
(one build, identical bytes). It is the reason a check has to be per package
and against the record, not "does the product run".

## 4. What this repository did

- **The release loop ends with `usdVrmaFileFormat`**, whose closure holds the
  one shared workspace library any release member needs. An ordering
  workaround, commented as one.
- **`scripts/check_product_libraries.py`** installs the product and holds each
  bundle's bytes to its own `dependencies.json`: for every workspace library
  built `SHARED` (read off its `add_library`), the binary has to be in a
  directory the record names, on the bundle's and the product's loader path.
  On the broken product it fails three times, by bundle and library; on the
  reordered one it passes and **notes** the two undeclared copies rather than
  failing on them, since §2 puts them there. It runs in `release.yml` straight
  after packaging, before the smokes whose loader errors arrive as CP932.
- **`scripts/artifact_only_exec_smoke.py`** is the packaged run itself, in
  `release.yml` on all three OS: the five parity cases with the product's
  tools and bundles, the display suite, a provenance check over every module
  `exec_parity` mapped, and a negative — every copy of execMotion's
  `plugInfo.json` in the prefix moved aside, and the case must refuse with
  ExecMotion loaded from nowhere.

## 5. Asks

- **P1 — compose each bundle's own closure when testing or packaging a
  workspace**, the way the `ost library` lifecycle already does with
  owner-specific `library-prefix` directories. Failing that, **fail closed at
  file granularity**: a library is materialized when the files its install
  recorded are present, not when a directory of the same name is. Either one
  would have made our loop order irrelevant, and the second alone would have
  turned a shipped defect into a packaging error naming `vrmContainer`.
- **P3 — stage a library's own files, not the prefix directory.** Every
  package here carries static archives, CMake package configs and another
  bundle's shared library under `runtime/libraries/`; §3.3 is what that costs
  in attribution.
- **P3 — one plugin path per bundle identity in a product's activation.** The
  plugin-workspace reference already states the rule: duplicate bundle
  identities are rejected or deduplicated after identity, version and contract
  agree, and "path order must not silently pick a provider". A product
  activation lists `execMotion` twice and `vrmSchema` three times, and OpenUSD
  keeps whichever plugInfo its parallel reader registers first.

## 6. What worked

- `ost 0.22.10` built a fresh clone's root tree and all six bundles first
  time, and `ost plugin product verify` / `install` behaved exactly as in
  0.22.8. The C1083 a first attempt hit was this workstation's path length
  under the scratch directory, not `ost`.
- The product's `openstrata.activation.json` was all a packaged exec run
  needed: runtime environment from `ost env`, then the activation's loader and
  plugin lists, and the product's `execMotion` and `execVrm` were discovered,
  loaded and evaluated with no path from this repository on either variable.
- **Parity from the product is the build tree's, bit for bit**: the five
  `workspace_exec_parity_*` cases pass unchanged with every tool and bundle
  swapped for the installed one, and the display suite passes under the same
  environment.
