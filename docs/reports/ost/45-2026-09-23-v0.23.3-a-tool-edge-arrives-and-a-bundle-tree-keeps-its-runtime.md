# A tool edge arrives, and a bundle tree still keeps its runtime

- Date: 2026-09-23
- Version exercised: `ost 0.23.3`, the published `x86_64-pc-windows-msvc`
  asset, on this workstation (`cy2026-windows-x86_64-py313-usd`), in the
  default `OST_HOME`; and the pinned release asset on every hosted lane of four
  repositories
- Occasion: the pin moving to 0.23.3 across the ecosystem, and the two
  consuming changes it unblocked:
  [#221](https://github.com/animu-sphere/usd-vrm-plugins/pull/221), where
  `motion_retarget` reads its clip through the published `motionUsd`, and
  [#223](https://github.com/animu-sphere/usd-vrm-plugins/pull/223), which
  deletes `motionSource`, `motionBvh` and the BVH tools (MIG-3)
- Prior report: [44](44-2026-09-23-v0.23.2-a-tool-edge-reaches-nothing-and-a-tree-keeps-its-runtime.md)
- Next ask target: `ost 0.23.4`

## TL;DR

**Report 44's first P1 is delivered. The second is delivered for the root
build only, and the per-bundle path now hides the defect it still has.**

1. **Delivered: a tool's library edges are pulled, graphed and validated.**
   `ost library pull` materializes an artifact only a tool declares, the root
   toolchain prepends it, the graph carries the tool's edges (15 library edges
   became 22), and a tool edge to a missing library fails with
   `WORKSPACE_LIBRARY_DEPENDENCY_MISSING`, exit 5. `motion_retarget` consumes
   `motionUsd` over exactly that edge, green on every lane (§2).
2. **Delivered for `ost build`: a root tree configured against another runtime
   is discarded.** The unmarked tree was discarded and rebuilt once, reused on
   the next run, and discarded again when its recorded digest was edited (§3).
3. **P1: `ost plugin build` does not do the same, and now stamps the new
   runtime's identity into the stale tree.** A bundle's own build tree kept
   `pxr_DIR` at the adopt of 2026-09-04 and gained
   `OPENSTRATA_RUNTIME_DIGEST` for the pulled artifact in the same run, so the
   check that would catch it on the next `ost build` of that tree now passes
   (§4).
4. **P2: a bundle cannot be consumed from another repository.**
   `requires.bundles` has no artifact pin. `usd-motion-plugins` published
   `execMotion` in its v0.5.0, and this repository's last MIG-2 item is
   waiting on `ost`, not on that repository (§5).
5. **P2, second time measured: a workspace cannot consume another repository's
   tool.** MIG-4 and now MIG-3 both had to commit a published tool's *output*
   as a fixture, because no descriptor can name the tool (§6).

## 1. What was being done

The ecosystem moved its `ost` pin to 0.23.3 in one step — this repository
([#221](https://github.com/animu-sphere/usd-vrm-plugins/pull/221)),
`usd-motion-plugins` ([#24](https://github.com/animu-sphere/usd-motion-plugins/pull/24)),
`motion-connectors` ([#16](https://github.com/animu-sphere/motion-connectors/pull/16))
and `usd-mmd-plugins` ([#21](https://github.com/animu-sphere/usd-mmd-plugins/pull/21)).
Each re-render changed nothing but the version, and each repository rebuilt
its tree under 0.23.3 and passed its whole suite locally (53, 87 and 32 tests)
before its hosted lanes went green.

Verifying the second of them in the release lane's own order also found a
defect of this repository's, not of `ost`'s: `release_exclude` still named the
three adapter CLIs MIG-4 deleted, and `ost` rightly refused to package a
product whose exclusion names a member it does not discover
(`AGGREGATE_MEMBERSHIP_MISMATCH`). No pull-request lane packages the product,
so it had been latent since 2026-09-21; #222 empties the list.

Two changes here rode on the pin. `motion_retarget` is the only consumer
`motionUsd` has in this workspace, so its descriptor is the only place the
edge can be declared: report 44 §3's case exactly. And MIG-3, the deletion of
the recorded-file path, had been listed as waiting on the same fix.

## 2. What worked: tool edges

Measured in #221's tree:

- `ost library pull --json` lists five libraries — `motionUsd` among them,
  declared by `tools/motionRetarget/openstrata.tool.yaml` and nowhere else —
  with no warnings, and `.strata/external-libraries/` holds five directories.
  The root toolchain prepends the fifth prefix, and the tool compiles and links
  against it.
- `ost plugin test --workspace --graph-only` reports
  `6 bundle(s), 3 bundle edge(s), 4 libraries, 22 library edge(s), 2 tool(s), valid`,
  where 0.23.2 counted 15 edges: the seven tool edges are graphed now.
- Renaming the tool's `vrmRig` entry to `vrmRigDoesNotExist` fails the graph:
  `FAIL [WORKSPACE_LIBRARY_DEPENDENCY_MISSING] tool 'motion_retarget' requires missing library 'vrmRigDoesNotExist'`,
  exit 5. Under 0.23.2 the same edit was `valid`.

`motion-connectors`, whose `vrchat_osc_record` was the first tool descriptor in
the ecosystem to pin an external artifact of its own, pulled three artifacts
and validated 25 library edges across four tools under the new pin.

## 3. What worked: the root tree follows its runtime

The root tree of this repository had been rebuilt by hand under 0.23.2 (report
44 §4), so it carried no runtime markers. The first `ost build` under 0.23.3
discarded it — `build.log` gone with the directory — and rebuilt 131 steps,
leaving in the cache:

```text
OPENSTRATA_RUNTIME_DIGEST:STRING=sha256:3a4e3993…
OPENSTRATA_RUNTIME_PREFIX:STRING=C:/Users/snkm/.ost/runtimes/openstrata-cy2026-windows-x86_64-py313-usd
pxr_DIR:PATH=C:/Users/snkm/.ost/runtimes/openstrata-cy2026-windows-x86_64-py313-usd
```

A second `ost build` reused the tree. Editing the recorded digest to
`sha256:0000` by hand and running `ost build` again discarded it and rebuilt
all 131 steps, restoring the true digest. That is the behaviour report 44 asked
for, measured three ways.

## 4. `ost plugin build` keeps the runtime, and now hides it

The release lane builds every bundle standalone after the root build
(`ost plugin build plugins/<bundle>`), and packaging checks each bundle's
output against that build. Running that sequence locally to verify MIG-3's
release-lane changes, the first standalone build of `execMotion` failed, and
its tree said why:

| Where | Says |
| --- | --- |
| `plugins/execMotion/.strata/targets/…/toolchain.cmake` | `set(pxr_ROOT "C:/Users/snkm/.ost/runtimes/…")`, `OPENSTRATA_RUNTIME_DIGEST "sha256:3a4e3993…"` |
| `plugins/execMotion/build/…/CMakeCache.txt` | `OPENSTRATA_RUNTIME_DIGEST:STRING=sha256:3a4e3993…`, and `pxr_DIR:PATH=C:/usd/openusd-26.08-usdview`, `TBB_DIR` and `OpenSubdiv_DIR` under the same adopt |
| `…/CMakeFiles/CMakeConfigureLog.yaml` | eleven configure runs appended; a tree configured fresh holds one |

So the tree was not discarded, and the `execVrm`, `usdVrmFileFormat` and
`vrmSchema` trees said the same: artifact digest marker, adopt `pxr_DIR`.
Two things combine:

- The runtime check 0.23.3 added is called from `ost configure` and
  `ost build`. The bundle and library build paths
  (`crates/ost-cli/src/commands/plugin.rs`, the bundle build and the library
  build) call only the compiler check,
  `invalidate_plugin_build_tree_if_toolchain_moved`.
- The toolchain they render is the shared one, which now sets
  `OPENSTRATA_RUNTIME_DIGEST` and `OPENSTRATA_RUNTIME_PREFIX` with `FORCE`. So
  a stale bundle tree gets the new runtime's identity written into its cache by
  the very run that keeps the old `pxr_DIR`.

The second point is what makes this worse than 0.23.2. A tree that lacked the
markers was at least detectable: `ost build` treats an unmarked tree as stale.
After one `ost plugin build`, the markers are there and agree with the lock,
so any later check that reads them — the one 0.23.3 added included — passes a
tree that compiles against another OpenUSD.

Removing `plugins/*/build` and running the bundle builds again produced trees
whose cache names the artifact, and all six built — the `execMotion` failure
went with the stale tree. That is the manual repair report 44 described for the
root. Hosted lanes are not affected: they start from a clean checkout,
and no stale tree exists there. Every workstation that ever changed its runtime
under an existing bundle tree is.

## 5. A bundle from another repository cannot be consumed

`requires.bundles` entries carry `id`, `version` and `contract`, and no
`artifact` (`crates/ost-plugin/src/model.rs`, `BundleDependency`). A library
entry has taken an `artifact.targets` pin table since 0.23.0.

`usd-motion-plugins` published `execMotion` 0.5.0 as a bundle artifact on
three targets on 2026-09-20. This repository's `execVrm` reads `execMotion`'s
nodes by name at run time, and the migration's rule is that the parity rows
are re-run against the consumed package before the copy here is deleted. With
no way to declare the edge, the copy stays, and it is the last generic motion
code this repository builds. The migration track here had recorded this item
as waiting on that repository to publish, which it did three days ago; it is
waiting on this.

## 6. A tool from another repository cannot be consumed either

Both deletions this week that removed a tool had tests composing that tool
with one that stays: `motion_capture` → `motion_retarget` (MIG-4), and
`motion_bvh_convert` → `motion_retarget` over the real-capture suites
(MIG-3). Neither could re-point the first leg at the published tool, because
nothing in a descriptor names a tool from another repository. Both committed
the published tool's output instead, with the archive digest and the command in
a README — a 59 KB clip for MIG-4, and a 1.7 MB one for MIG-3.

That works, and it is honest about what it proves. But it is a snapshot: when
`motion_convert` changes what it writes, nothing here notices until someone
regenerates the file by hand.

## 7. Asks

- **P1: apply the runtime check to `ost plugin build` and `ost library build`,
  before the toolchain is written.** Discard a bundle or library tree whose
  cache records another runtime, or none, exactly as `ost build` does. And stop
  the toolchain from writing the markers into a tree the check has not passed:
  a marker that one command writes and another command trusts is only as good
  as the least careful writer.
- **P2: an artifact pin for `requires.bundles`**, in the shape
  `requires.libraries` already has (`artifact.targets.<target>.{digest, source}`),
  so a workspace can compose a published bundle into its session and its
  package closure.
- **P2: a way to consume a published tool for tests**, e.g. `requires.tools`
  with the same pin table, materialized onto the test environment's `PATH`.
- Report 44's P3 (`layout-complete` checks contents) is described as shipped
  in the 0.23.3 notes and was not re-measured here: nothing in these changes met
  a gutted runtime.
