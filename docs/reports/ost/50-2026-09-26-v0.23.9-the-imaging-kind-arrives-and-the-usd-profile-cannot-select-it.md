# The imaging kind arrives, and the `usd` profile cannot select it

- Date: 2026-09-26
- Version exercised: `ost 0.23.9`, the published `x86_64-pc-windows-msvc`
  asset, on this workstation, in the default `OST_HOME`. Two runtimes:
  `cy2026-windows-x86_64-py313-usd`, the pinned canonical leaf
  `26.08-gl-windows-x86_64` (the one CI pulls), and
  `cy2026-windows-x86_64-py313-lookdev`, a local adopt of an OpenUSD 26.08
  build with usdview. The CI lanes still bootstrap `ost 0.23.6`, and nothing
  pinned in this repository changed.
- Occasion: adopting `usd-imaging`, the kind 0.23.9 adds in answer to
  [report 49](49-2026-09-26-v0.23.8-no-plugin-kind-for-a-usdimaging-adapter.md)'s
  P2, for `vrmImaging`
- Prior report: [49](49-2026-09-26-v0.23.8-no-plugin-kind-for-a-usdimaging-adapter.md)
- Next ask target: the next `ost` release

## TL;DR

**Report 49's P2 is delivered, and this repository cannot adopt it.** The
kind works when it is given a `lookdev` runtime. This workspace builds
against the `usd` profile, and every runtime `ost` publishes is a `usd`
runtime.

1. **Delivered: the kind, its metadata check and its L2** (§2). A
   `usd-imaging` descriptor for `vrmImaging` parses and passes L0, and the
   workspace graph accepts it. Under `--profile lookdev`, `vrmImaging`
   passes L0–L4 (13 pass, 0 fail). The new native `imaging.registration`
   check constructs the real adapter. With `USDIMAGING_ENABLE_PLUGINS=0` set,
   the same check fails and names the variable.
2. **P1, new: nothing that builds with the `usd` profile can use the kind**
   (§3). `usd-imaging` requires `hydra-preview`, and only the `lookdev`
   profile promises it. This repository's project profile is `usd`, and so is
   every canonical leaf, including the `gl` and `metal` imaging variants. The
   pinned Windows leaf has the usdImaging SDK: `vrmImaging` has built and
   passed on all three CI lanes from these leaves since #245. Under `usd`,
   `plugin build`, `plugin test` and `plugin test --workspace` all refuse.
   Under `lookdev`, `plugin package` refuses because the project lock names
   the `usd` runtime. The workspace cannot move to `lookdev` either, because
   no `lookdev` runtime is published.
3. **Our side, noted for adoption** (§4). `usdvrm_baseline` requires every
   bundle with a descriptor to be registered in its session, so the
   descriptor alone turns it red. The fix is this repository's, and it waits
   for the P1.

## 1. What was tried

The descriptor below was placed at `plugins/vrmImaging/openstrata.plugin.yaml`.
`plugins/vrmImaging` was added to `[workspace].members`, and the root
`CMakeLists.txt` stopped adding the plugin by name, so the bundle glob
discovers it like every other plugin:

```yaml
plugin:
  name: vrmImaging
  version: 0.9.0
  kind: usd-imaging
runtime:
  openusd: "==26.08"
  cxx_abi: inherit
provides:
  - usd-imaging:VrmMToonAPI
requires:
  capabilities: [usd-stage-read, hydra-preview]
  bundles:
    - { id: vrmSchema, version: ">=0.9,<0.10", contract: 1 }
usd:
  plug_info: plugin/resources/vrmImaging/plugInfo.json
tests:
  smoke: [tests/fixtures/mtoon_materials.usda]
```

The existing `plugInfo.json` was not changed. It already declares one type,
`UsdVrmImagingMToonAPIAdapter`, based on `UsdImagingAPISchemaAdapter` with
`apiSchemaName: VrmMToonAPI`. The generated `usd-imaging-cpp` 0.1.0 template
was also read, and it has the same shape. The change was reverted after
measurement (§5).

## 3. P1: nothing that builds with the `usd` profile can use the kind

`PluginManifest::required_capabilities()` adds `hydra-preview` for
`usd-imaging` whatever the descriptor lists. Every `ost plugin` verb checks
the result with `selection_for_capabilities`, which compares it against the
**profile catalog**. It does not consult the resolved runtime. In the catalog,
only `lookdev` promises `hydra-preview`. `lookdev` also promises `usdview`,
`usd-materialx` and `ocio-display`.

The pinned runtime has the imaging SDK. The pinned `usd` leaf contains
`include/pxr/usdImaging/usdImaging/adapterRegistry.h` and
`lib/usd_usdImaging.dll`, which is exactly what 0.23.9's
`has_usd_imaging_sdk` looks for. `vrmImaging` has compiled, linked and
passed `vrmImaging_mtoon` and `vrmImaging_mtoon_without_schema` against
this leaf and its Linux and macOS siblings in every workspace cell since
#245. The runtime's `runtime.json` nevertheless lists only `python-tooling`,
`image-io`, `color-management`, `usd-stage-read`, `usd-stage-write` and
`usd-shading`. Every leaf in open-strata's
`support/openusd-runtime-matrix.json` is `"profile": "usd"`, and that
includes the `gl`, `vulkan` and `metal` variants built with imaging.

What each path does with the member added:

| Command | Profile | Result |
| --- | --- | --- |
| `ost plugin build plugins/vrmImaging` | usd (project) | `PROFILE_CAPABILITY_UNSATISFIED: profile 'usd' does not promise required capabilities [hydra-preview]` |
| `ost plugin test plugins/vrmImaging --up-to 2` | usd | the same |
| `ost plugin test --workspace --up-to 0` | usd | graph valid, then the same, so no bundle is tested |
| `ost plugin package plugins/vrmImaging --profile lookdev` | lookdev | `PACKAGE_RUNTIME_LOCK_MISMATCH: selected or packaged runtime '...-lookdev@sha256:138cb083...' (source local) does not match strata.lock runtime '...-usd@sha256:3a4e3993...' (source artifact)` |

The rendered workspace cells run `ost plugin test --workspace` and
`ost plugin package --workspace --product` with `--profile usd`, and so does
the hand-authored `release.yml`. Adding the member would turn all of those
red, on every platform, with no change to the code.

None of the other ways out works here:

- **Move the project to `lookdev`.** No `lookdev` runtime is published, so
  there is nothing for a hosted lane to pull. Even if one were published,
  `lookdev` promises `usdview`, and report 36 §11 found that the canonical
  leaves do not ship the Qt bindings that `usdview` and `usdrecord` need.
- **Leave `hydra-preview` out of the descriptor.** The requirement is
  intrinsic to the kind, so this changes nothing.
- **Keep the descriptor out of `members`.** This fails with
  `WORKSPACE_DESCRIPTOR_NOT_DECLARED` (report 49 §2).

### Ask

**P1: let a runtime that has the imaging SDK satisfy `usd-imaging`, whatever
its profile is named.** `ost` already has the check it needs:
`has_usd_imaging_sdk`, which L1 `runtime.usd_imaging` and `runtime validate`
use. Any of these would unblock this repository. The choice is `ost`'s:

- make the kind's intrinsic requirement the SDK itself, checked against the
  resolved runtime, rather than a capability promised by a profile;
- have the canonical imaging leaves (`gl`, `vulkan`, `metal`) declare
  `hydra-preview` in their runtime manifest, and let capability selection
  accept what the resolved runtime declares, not only what its profile
  promises;
- split `hydra-preview` from `usdview`, so that a published profile can
  promise imaging without promising a viewer.

Whichever is chosen, `ost plugin package --workspace --product` needs to be
able to take a `usd-imaging` member under the project's locked runtime. That
is where this workspace's product is made.

## 4. Our side: the baseline test

`tools/baseline_freeze.py`'s discovery section reads every bundle descriptor
in the workspace and requires each bundle's plugin to be registered in its
session. It also freezes the union of their registered types. With the
descriptor present, the plugin became one of those bundles, the test's
session did not include it, and `usdvrm_baseline` failed with
`plugin 'VrmImaging' not discoverable`. When this repository adopts the kind,
the test's session must include the bundle and the frozen baseline must be
regenerated to include `UsdVrmImagingMToonAPIAdapter`. This is not an `ost`
finding.

## 5. What this repository does meanwhile

Nothing is adopted. The descriptor, the member entry and the root change
were reverted. `vrmImaging` stays as #245 left it: added by name, built and
tested by the root build, and in no package. The pin stays at 0.23.6 because
0.23.9 changes nothing this repository can use until the P1 is resolved.
Report 49's forward-note and the imaging track's Step I5 point here.
