## Root Cause

Two macOS runtime/CI assumptions were wrong:

1. The macOS runtime artifact is `py313`, but it does not materialize a
   `bin/python3.13` interpreter. `ost plugin build` invokes `python3.13` from the
   host PATH to run the runtime's `usdGenSchema`. My local machine has Python
   3.13 installed, so local schema generation succeeded. The hosted macOS runner
   did not have `python3.13` on PATH at that point.
2. The first published macOS GHCR runtime materializes `bin/` tools without
   executable bits. Locally, `ost plugin test --up-to 5` failed at `usdcat`
   until I ran `chmod +x <runtime>/bin/*`. CI would have hit the same issue
   after build; the first attempt failed earlier at schema generation.

The previous `source_checks` workaround was too late because generator-supported
source checks run after `ost plugin test`, while the Python/runtime-bin repair is
needed before `ost plugin build`.

## Fix Applied To The Branch

`openstrata.ci.yaml` keeps the macOS PR cell at L5:

```text
usdvrm-pr-macos-arm64
runs_on: macos-15
runtime_artifact: sha256:64365b...
runtime_remote: oci://ghcr.io/animu-sphere/openstrata-runtime-cy2026-usd@sha256:ee9d0774...
up_to: 5
```

The generated workflow has a temporary macOS-only pre-build guard:

```text
actions/setup-python@ece7cb06caefa5fff74198d8649806c4678c61a1 # v6
python-version: "3.13"
```

and, after runtime materialization but before plugin build:

```sh
eval "$(ost env cy2026 --profile usd)"
runtime_bin="${PATH%%:*}"
chmod +x "$runtime_bin"/*
```

This is intentionally temporary. The durable fix is to republish the macOS
runtime artifact with executable bits preserved, and either bundle a Python
interpreter or document/setup the required host Python version in generated CI.
