# A tool's library edge reaches nothing, and a build tree keeps the runtime it was born with

- Date: 2026-09-23
- Version exercised: `ost 0.23.2`, the published `x86_64-pc-windows-msvc`
  asset, on this workstation (`cy2026-windows-x86_64-py313-usd`), in the
  default `OST_HOME` and in an isolated one holding the pinned runtime
- Occasion: MIG-2's retarget item
  ([usd-vrm-plugins #218](https://github.com/animu-sphere/usd-vrm-plugins/pull/218)).
  `vrmRetarget`'s generic half is deleted in favour of `usd-motion-plugins`'
  published `motionRetarget`, pinned by digest in `execVrm` and in the
  `motion_retarget` tool, and what stayed is renamed `vrmRig`. The first
  consuming change of the migration ran under 0.23.2 two days earlier (#217)
- Prior report: [43](43-2026-09-20-v0.23.1-the-root-build-cannot-see-an-external-library.md)
- Next ask target: `ost 0.23.3`

## TL;DR

**Report 43's P1 is delivered, and the external edge now works from every
member kind but one. And the local builds this migration was verified with
compiled against a runtime other than the one `ost` recorded.**

1. **Delivered: the root build composes a member's external library
   artifacts.** The root `toolchain.cmake` prepends every materialized prefix
   the members declare, and the whole workspace configures, builds and tests
   against four `usd-motion-plugins` packages with no per-member workaround
   (§2).
2. **P1: a tool descriptor's `requires.libraries` is read by nothing.**
   `ost library pull` does not materialize an external artifact that only a
   tool declares, and `ost plugin test --workspace --graph-only` neither
   graphs a tool's edges nor checks them: a tool declaring a library that does
   not exist is `valid`. Three identities of the migration wait on it,
   because a tool is the only consumer each has left here (§3).
3. **P1: a build tree keeps the OpenUSD it was first configured against.**
   The build directory is keyed by target id, not by runtime. When the
   selected runtime changes under an existing tree — a different `OST_HOME`,
   or an adopt replaced by the pulled artifact — `ost build` rewrites
   `toolchain.cmake` and `target.lock.json` for the new runtime, and CMake
   keeps the cached `pxr_DIR` and `TBB_DIR` of the old one, which win over the
   toolchain's `pxr_ROOT`. The build succeeds, the lock records the new
   runtime's digest, and every translation unit includes the old prefix's
   headers. Measured on this tree, which had been doing exactly that since a
   runtime swap on 2026-09-04 (§4).
4. **P3: `layout-complete` passes a runtime that has lost its files.** An
   isolated `OST_HOME` under `%TEMP%` was emptied by the OS down to four files;
   `runtime validate` fails it on `usdcat-present` and `consumer-configure`,
   and still reports `layout-complete` as ok. Nothing in `ost build` or
   `ost test` looks, so with item 3 the gutted runtime went unnoticed behind
   green builds (§5).

## 1. What was being done

The migration moves every generic motion identity from this repository to
`usd-motion-plugins`, and this repository consumes them as published library
artifacts, each pinned by archive digest per target in the descriptor that
names it. After #217 (`motionCore`, `motionSampling`, `motionRecording`),
#218 adds `motionRetarget`:

- `plugins/execVrm/openstrata.plugin.yaml` and
  `tools/motionRetarget/openstrata.tool.yaml` declare it, with the three
  targets' digests and `oci://` sources from `usd-motion-plugins` v0.5.0's
  generated pin table;
- the root `CMakeLists.txt` resolves it once, after `pxr`;
- `libs/vrmRig` (what stayed) declares only `motionCore`.

Verification was the root `ost build` / `ost test`, `ost plugin test
--workspace --graph-only`, and the repository's installed-package consumer
lane (`scripts/run_package_consumer_lane.py`), which configures each package's
fixture from scratch outside the workspace.

## 2. What worked: report 43's P1

The root toolchain carries the external prefixes:

```cmake
# Digest-pinned external library artifacts declared by this workspace's members.
list(PREPEND CMAKE_PREFIX_PATH ".../.strata/external-libraries/cy2026-windows-x86_64-py313-usd/motionCore/f06fef79…" ...)
```

With it the whole workspace — six bundles, four libraries, three tools —
configures and builds against `motionCore`, `motionSampling`,
`motionRecording` and `motionRetarget` from their artifacts, and the suite is
75 of 75. The graph carries the external edges a bundle or a library declares,
with their per-target digests (`"external": true`, `artifact_targets`), 15
library edges in all. `ost library pull` materialized all four, verified, in
under a second on a warm store. Nothing in #217 or #218 needed a hand-written
CI step, which was the constraint report 43's P1 was written against.

## 3. A tool's `requires.libraries` is read by nothing

`motion_retarget` is a tool (`openstrata.tool/v1alpha1`). Its descriptor
declares `vrmRig`, `motionCore`, `motionRetarget` and `motionSampling`. The
edges are real — the tool links all four — and the three external ones carry
digests like any other member's. Measured in a scratch worktree of #218:

1. **Declared only by the tool, never materialized.** Add a fifth entry,
   `motionUsd`, with its v0.5.0 digests and sources, to the tool descriptor
   and nowhere else. `ost library pull --json` reports four libraries —
   `motionCore`, `motionRecording`, `motionRetarget`, `motionSampling`, each
   declared by some bundle or library — and no `motionUsd`, with an empty
   `warnings` array and exit 0. `.strata/external-libraries/` holds four
   directories.
2. **Not in the graph.** `--graph-only --json` lists `library_edges` whose
   `from_kind` is `bundle` (12) or `library` (3), and nothing from a tool;
   `data.tools` is a count (3). `motionUsd` appears nowhere in it.
3. **Not validated.** Rename the tool's `vrmRig` entry to
   `vrmRigDoesNotExist`. The graph is still
   `6 bundle(s), 3 bundle edge(s), 4 libraries, 15 library edge(s), 3 tool(s), valid`,
   and `ost library pull` still exits 0. The same misspelling in `execVrm`'s
   bundle descriptor, measured the same way, is
   `FAIL [WORKSPACE_LIBRARY_DEPENDENCY_MISSING] bundle 'execVrm' requires missing library 'vrmRigDoesNotExist'`,
   exit 5.

**What it stops.** A tool is the last consumer several migrating identities
have here. `motion_retarget` is the only one `motionUsd` would have (it
replaces the tool's own stage reader), and `motion_bvh` is the only one
`motionSource` and `motionBvh` have. None of the three can be switched to its
published package until the tool's own declaration materializes it: the root
build would configure without the prefix, as report 43 measured for a member,
and nothing would say why. So those identities stay built here, as copies of
what `usd-motion-plugins` already publishes, which is the one state the
migration's rules forbid lasting.

**Why the tool's edges matter beyond pull.** A tool descriptor is also what
`ost plugin package --workspace --product` ships a tool by. If its library
edges are never checked, a tool's descriptor can say anything, and the product
closure is only as right as the bundles around it happen to make it. We found
one by review rather than by `ost`: after #218, `motion_retarget` still linked
`motionRecording`, declared nowhere in its descriptor and reachable only
because `execVrm` declares it — nothing flagged the undeclared edge.

## 4. A build tree keeps the runtime it was born with

**Measured state of this repository's root tree,
`build/cy2026-windows-x86_64-py313-usd`, before the fix:**

| Where | Says |
| --- | --- |
| `.strata/targets/…/target.lock.json` | `runtime.digest = sha256:3a4e3993…` (the pulled artifact) |
| `.strata/targets/…/toolchain.cmake` | `set(pxr_ROOT "C:/Users/snkm/AppData/Local/Temp/ostpin/runtimes/…")`, `list(PREPEND CMAKE_PREFIX_PATH` the same) |
| `CMakeCache.txt` | `pxr_DIR:PATH=C:/usd/openusd-26.08-usdview`, `TBB_DIR:PATH=C:/usd/openusd-26.08-usdview/lib/cmake/TBB` |
| `build.log` | `C:\usd\openusd-26.08-usdview\include\pxr/imaging/hd/dataSource.h(132)…` |

`C:/usd/openusd-26.08-usdview` is a runtime this workstation **adopted** on
2026-09-04 (a local OpenUSD build with usdview, adopted into the default
`OST_HOME` so `ost plugin view` works). It has since been replaced in that
home by the pulled artifact, and the migration's verification ran with
`OST_HOME` pointed at an isolated home holding the pinned artifact (report
43 §4). Both rewrote `toolchain.cmake` and `target.lock.json`. Neither reached
the build: `find_package(pxr)` found `pxr_DIR` in the cache, the config file
there was valid, and CMake never consulted `pxr_ROOT`. The same held for
`TBB_DIR`.

So every root build since the swap compiled and linked against the adopt,
while `ost` recorded the artifact. Both are OpenUSD 26.08, which is why
nothing broke; a runtime that differed in a way that matters — another OpenUSD,
another ABI, another Python — would have been reported as the new one and
built as the old.

**The fix, and the measurement that it is one.** Remove `CMakeCache.txt` and
run `ost build` again: the cache is regenerated with
`pxr_DIR:PATH=C:/Users/snkm/.ost/runtimes/openstrata-cy2026-windows-x86_64-py313-usd`
and the matching `TBB_DIR`, ninja recompiles the whole tree (131 steps, every
`-external:I` now under the artifact's prefix and none under the adopt's), and
the suite is 75 of 75 against the artifact. The consumer lane, which always
configures from scratch, had been measuring the artifact all along. (The
target's `build.log` is appended to, not replaced, so the adopt's paths are
still in its earlier runs; `build.ninja` is the record of what the current tree
compiles against.)

**Why this is `ost`'s to answer, not CMake's.** CMake is doing what it
documents: a cached `<Pkg>_DIR` wins. But the build directory's name is the
target id, which does not change when the runtime does, and `ost` is the one
component that knows both identities — it writes the new digest into
`target.lock.json` in the same step. A tree whose cache was configured against
a different runtime is detectable at exactly the point `ost` rewrites the
lock.

## 5. `layout-complete` passes a gutted runtime

The isolated `OST_HOME` lives under `%TEMP%`, and the OS's temporary-file
cleanup removed everything in its runtime except four files it had touched
recently: `pxrConfig.cmake`, `cmake/pxrTargets.cmake`,
`cmake/pxrTargets-release.cmake`, `runtime.json`. The directory skeleton
stayed; `lib/cmake/TBB` is empty and `bin` is empty. That is our environment's
doing, not `ost`'s. What `ost` said about it:

```text
[ok  ] layout-complete
[FAIL] usdcat-present — no usdcat in …\bin
[ok  ] pxr-package
[FAIL] consumer-configure — find_package(pxr) failed … Could not find a package configuration file provided by "TBB"
```

`layout-complete` checks that the directories exist, which they do. A claim
under that name reads as "the runtime's contents are there", and a runtime
with four files is the case it should catch first. And nothing short of an
explicit `runtime validate` looks at all: with §4's cache in place, every
`ost build` / `ost test` under this home was green.

## 6. Asks

- **P1: materialize and graph a tool's external library edges.** `ost library
  pull` should pull every artifact any workspace member declares, tools
  included, and the root toolchain should prepend it as it does for the
  others. The graph should carry a tool's edges and validate them as it does a
  library's — an edge to a library that does not exist is
  `WORKSPACE_LIBRARY_DEPENDENCY_MISSING` wherever it is declared.
- **P1: do not build a tree against a runtime other than the one recorded.**
  When `ost build` finds an existing CMake cache configured against a
  different runtime than the one it is about to record, reconfigure it fresh
  (or refuse, naming both). A cheap signal exists: record the runtime digest
  in the cache (an `OPENSTRATA_RUNTIME_DIGEST` entry the toolchain sets) and
  compare it on the next run. Setting `pxr_DIR` from the toolchain would fix
  OpenUSD and leave every other package the runtime carries — `TBB_DIR` here,
  and whatever else the runtime's configs pull — as stale as before.
- **P3: make `layout-complete` mean contents.** Check the files the runtime's
  manifest records (or at least the entry points the other claims need —
  `pxrConfig.cmake`'s dependencies, `bin/usdcat`), and consider a fast
  integrity check at `ost build` / `ost test` time for a runtime materialized
  into a location the OS may clean.
- Report 43's P3 (say what a runtime mismatch wants) was not re-measured:
  nothing in this change took the refusal path.
