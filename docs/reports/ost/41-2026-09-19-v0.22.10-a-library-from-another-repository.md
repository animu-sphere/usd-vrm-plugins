> **Forward-note (2026-09-20):** P1 and P3 below are delivered in `ost`
> 0.23.0 and re-verified in
> [42](42-2026-09-20-v0.23.0-a-claim-measured-before-the-repair.md) §6 —
> `requires.libraries` takes a digest-pinned `artifact`, the declared edge
> survives in the graph, and an empty workspace renders its CI. §4's
> condition (report 37's P1) is unchanged, and report 42 records the new
> failure it now produces.

- Date: 2026-09-19
- Version exercised: `ost 0.22.10` (`cy2026-windows-x86_64-py313-usd` on this

  `motionCore` left this repository for `usd-motion-plugins` that day
  (usd-motion-plugins #2, merged). This repository now has to consume it as an

## TL;DR

**The ecosystem split one workspace into three repositories, and `ost` can
only express dependencies inside one.**

1. **P1: `requires.libraries` names a sibling member and nothing else.** A
   `LibraryDependency` is `{id, version}`, and its only provider is a
   member of the same workspace. When `libs/motionCore` leaves, nine members
   fail the graph with `WORKSPACE_LIBRARY_DEPENDENCY_MISSING` (§2.1), and no
   field can say "this comes from `usd-motion-plugins` v0.1.0". This is the
   one thing blocking MIG-1 on this side (§1).
2. **The only way through is to lie to the graph.** If the declaration is
   dropped, `ost library build` configures against the external package that
   an ambient `CMAKE_PREFIX_PATH` supplies (§2.2). The edge then exists in
   CMake and nowhere else. The graph cell, `library verify-consumer`, every
   `dependencies.json`, the rendered CI and the product's provenance stop
   seeing a dependency that every one of them should know about. We are not
   doing that. Moving rule 1 forbids keeping two copies, so MIG-1 waits.
3. **P3: an empty workspace cannot render CI.** `members = []` is
   `MANIFEST_INVALID`, and every rendered workspace job runs
   `--graph-only`, which refuses a workspace with no member. Both new
   repositories committed their CI contract unrendered for exactly that
   reason (§3).
4. **A second receipt for report 37's P1.** `usd-motion-plugins`' first
   package that links OpenUSD (`motionCore`, through `gf`) failed its
   installed-consumer lane on hosted Linux and Windows. The runtime's
   `pxrConfig.cmake` names the Python of the machine that built it. macOS and
   this workstation passed. The workaround is the one report 37 recorded:
   forward `Python3_EXECUTABLE`, `Python3_LIBRARY` and `Python3_INCLUDE_DIR`
   (§4).

## 1. What was being done

The `usd-motion-plugins` design policy moves generic motion out of this
repository. Every identity that moves arrives in its destination with its
history, is published as an installed package, and the change here then
deletes the in-tree copy and consumes the package through `find_package`. That
is [WORKSPACE.md §9.2](../../architecture/WORKSPACE.md#92-moving-rules), rule 1,
and it is written so that two copies never exist at once.

The destination half of MIG-1 landed on 2026-09-19. `motionCore` arrived in
`usd-motion-plugins` with 23 commits of history and renamed types
(`openstrata::motion::MotionPose` and the rest), became that workspace's first
member, and passed its first rendered CI on all three platforms (6/6 each,
including an installed-consumer lane that consumes it from a clean prefix).

This half is to switch this repository's nine consumers of `motionCore` to
that package. In CMake that is already true: every consumer calls
`find_package(motionCore CONFIG)` behind `if(NOT TARGET motionCore::motionCore)`,
so the build does not care where the package comes from. `ost` does care, and
it has no answer.

## 2. The defect

### 2.1 A missing sibling, measured

On a clone of `main` at `f5ecb1c` with `libs/motionCore` removed from the tree
and from `[workspace].members`:

```text
$ ost plugin test --workspace --graph-only
Workspace dependency graph: 6 bundle(s), 3 bundle edge(s), 11 libraries, 15 library edge(s), 6 tool(s), 9 issue(s)
  FAIL [WORKSPACE_LIBRARY_DEPENDENCY_MISSING] bundle 'execMotion' requires missing library 'motionCore'
  FAIL [WORKSPACE_LIBRARY_DEPENDENCY_MISSING] bundle 'execVrm' requires missing library 'motionCore'
  FAIL [WORKSPACE_LIBRARY_DEPENDENCY_MISSING] library 'motionRuntime' requires missing library 'motionCore'
  FAIL [WORKSPACE_LIBRARY_DEPENDENCY_MISSING] library 'motionSource' requires missing library 'motionCore'
  FAIL [WORKSPACE_LIBRARY_DEPENDENCY_MISSING] bundle 'usdVrmaFileFormat' requires missing library 'motionCore'
  FAIL [WORKSPACE_LIBRARY_DEPENDENCY_MISSING] library 'vrmAdapterMocopi' requires missing library 'motionCore'
  FAIL [WORKSPACE_LIBRARY_DEPENDENCY_MISSING] library 'vrmAdapterVmc' requires missing library 'motionCore'
  FAIL [WORKSPACE_LIBRARY_DEPENDENCY_MISSING] library 'vrmAdapterVrchatOsc' requires missing library 'motionCore'
  FAIL [WORKSPACE_LIBRARY_DEPENDENCY_MISSING] library 'vrmRetarget' requires missing library 'motionCore'
```

That is correct for what the descriptor can say. `crates/ost-plugin/src/model.rs`
defines `LibraryDependency { id, version }` with `deny_unknown_fields`, and
`workspace.rs` resolves `id` against the member providers only. No field
names an artifact, a remote, a digest or a repository, and the reference's
source-workspace composition (plugin-workspace.md, "Source-workspace
composition") composes only sibling closures. A bundle's `--with` is additive
for bundles, but no library-side equivalent exists.

### 2.2 The workaround, and why it is refused

With the declaration removed from `libs/motionRuntime/openstrata.library.yaml`
and nothing else changed except
`CMAKE_PREFIX_PATH=<motion-prefix>` in the environment (`<motion-prefix>` being
an install of `usd-motion-plugins` at its merge commit):

```text
$ ost library build libs/motionRuntime
... cl.exe ... -external:I<motion-prefix>\include -external:I<usd-root>\include ...
motionRecording/CaptureTrace.h(75): fatal error C1083: cannot open include file 'motionCore/MotionPose.h'
```

The configure succeeded. `find_package(motionCore)` resolved the external
package, and its include directory is on the compile line. The compile error
is the rename (`Humanoid.h` is `MotionPose.h` there) and is this repository's
own work. It shows that the ambient prefix is honoured.

So the build can do it. But everything `ost` knows about the build would then
be wrong:

| Surface | With the edge undeclared |
| --- | --- |
| `--graph-only` | passes, and would also pass if `motionCore` were missing entirely |
| `library verify-consumer` | excludes ambient prefixes by design (the reference says so), so it fails, or has to be dropped |
| `dependencies.json`, package provenance | records no `motionCore`, so a product ships with an unrecorded input |
| rendered CI | has no step that obtains the package, so a hand-written step goes into a workflow the contract says not to hand-edit (report 38's P2 again) |
| version agreement | `find_package(motionCore 0.1)` checks it and nothing else does. `ost` never learns that the pin exists |

This repository has spent three releases making the declared graph match the
build (reports 28, 33, 35, 36). Undeclaring an edge to get past the graph gate
gives that up, so MIG-1 is held rather than worked around.

## 3. An empty workspace cannot render its CI

Both destination repositories were scaffolded on 2026-09-19 with no member.
`ost` 0.22.10 refuses `[workspace] members = []` as `MANIFEST_INVALID`
("workspace.members must declare at least one member pattern"). A tree with
no `[workspace]` table builds and tests fine with root `ost build` and
`ost test`. But every rendered workspace job runs
`ost plugin test --workspace --graph-only` whatever the cell's `verify`, and
that step refuses a workspace with no member ("no bundles, libraries, or
tools found in the workspace member set", `PRECONDITION_FAILED`). So both
scaffolds committed `openstrata.ci.yaml` and **not** its workflow.
`usd-motion-plugins` rendered it with its first import; `motion-connectors`
still cannot.

## 4. Report 37's P1, again

`usd-motion-plugins`' installed-consumer lane configures a consumer outside
the repository against the installed prefix and the pulled runtime, with no
toolchain file. Its first run with a package that links OpenUSD failed on
Linux:

```text
Could NOT find Python3 (missing: Development Development.Embed) (found suitable exact version "3.13.15")
    Development: Cannot find the library "/usr/lib/x86_64-linux-gnu/libpython3.13.so"
```

It failed the same way on Windows. macOS and this workstation passed. That is
report 37's P1 as written: the runtime's CMake package carries the Python
paths of the machine that built it, and `ost build` hides this because its
toolchain file sets them first. The workaround is report 37's too. The root
build forwards the three `Python3_*` variables it used, and the lane passes
them to the consumer (usd-motion-plugins `459679d`). After that all three
platforms ran 6/6.

## 5. Asks

- **P1: a library dependency that names an external package.** For example:

  ```yaml
  requires:
    libraries:
      - id: motionCore
        version: ">=0.1,<0.2"
        source:
          artifact: oci://ghcr.io/animu-sphere/usd-motion-plugins-motionCore@sha256:...
  ```

  The spelling is yours. What we need from it:
  - `ost library package` output from another repository is materialized into
    the consumer's prefix the way sibling closures are, and prepended to
    `CMAKE_PREFIX_PATH`.
  - The graph validates the declared version against the artifact's recorded
    one, and fails closed on a mismatch or a missing artifact.
  - `dependencies.json` and product provenance record the artifact digest.
  - `library verify-consumer` treats it as part of the declared closure.
  - `ci generate` emits the pull, with a cache keyed by digest, as it does for
    the runtime.

  A runtime-pinned (OpenUSD 26.08) artifact is required, because the package
  links `gf` (moving rule 5: same OpenUSD). The ecosystem now has four
  repositories consuming each other (`usd-vrm-plugins`, `usd-mmd-plugins` and
  `motion-connectors` all depend on `usd-motion-plugins`), so this is the
  shape every one of them needs, not a one-off.
- **P3: let an empty workspace render and pass its CI.** Either accept
  `members = []`, or let the graph step pass or skip with no member. The
  next repository that starts empty will hit it too.
- Report 37's P1 stands, with the receipt above.

## 6. What worked

- The graph gate did its job. Removing a library that nine members declare
  fails loudly, names every consumer, and cannot be satisfied by an ambient
  prefix. The gap is in the vocabulary, not in the enforcement.
- `ost ci generate github` rendered `usd-motion-plugins`' first workflow
  (graph cell plus three workspace cells) from an unchanged contract as soon
  as there was a member, and it went green on the second run.
- `ost plugin test --workspace --graph-only` on the new repository:
  0 bundles, 1 library, valid, on its first try.
