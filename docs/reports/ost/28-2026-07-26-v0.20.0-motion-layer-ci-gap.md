# OST v0.20.0 dogfooding — plain libraries and CLI tools have no CI cell

- Date: 2026-07-26
- Version exercised: `ost 0.20.0` on Windows x86_64 (local workspace), cy2026 / OpenUSD 26.05
- Occasion: Workspace Phase 6b + Motion Phase C (`motionRuntime`, `vrmRetarget`, `motion_retarget`) for v0.4.0
- Related reports: [26](26-2026-07-23-v0.19.0-v0.20.0-asks.md), [27](27-2026-07-23-v0.19.0-aggregate-product-reproducibility.md)
- Next ask target: `ost 0.21.0`

## TL;DR

Two findings, one good and one blocking.

**The good one:** `ost plugin test --workspace` validates plain libraries, not
only plugin bundles. It discovered all four `openstrata.library.yaml`
descriptors and all seven library edges, and it caught a real dependency
version mismatch that no per-bundle cell could have seen. This is the first time
the graph gate has paid for itself on this repo, and it raises the cost of the
still-unwired CI gate tracked in [WORKSPACE.md §8](../../architecture/WORKSPACE.md).

**The blocking one:** `ost ci generate github` emits **one job per bundle
cell**, and `ost plugin test --workspace` tests *bundles*. A plain library and a
CLI executable are therefore invisible to CI: v0.4.0 adds two libraries and one
tool with 20 CTest assertions between them, and no lane compiles any of it. The
repo's only coverage is the plain-CMake root build, which no workflow runs.

## 1. The graph gate does cover plain libraries

Workspace Phase 6b added `libs/motionRuntime` and `libs/vrmRetarget`, each with
an `openstrata.library.yaml` declaring `requires.libraries`. Before the repo-wide
version bump, the new descriptors declared `motionCore >=0.4,<0.5` while
`VERSION` still read `0.3.0`:

```console
$ ost plugin test --workspace --up-to 1
Workspace dependency graph: 4 bundle(s), 4 libraries, 2 issue(s)
  FAIL [WORKSPACE_LIBRARY_DEPENDENCY_VERSION_MISMATCH] library 'motionRuntime' requires library 'motionCore' at >=0.4,<0.5, but the workspace has 0.3.0
  FAIL [WORKSPACE_LIBRARY_DEPENDENCY_VERSION_MISMATCH] library 'vrmRetarget' requires library 'motionCore' at >=0.4,<0.5, but the workspace has 0.3.0
```

After bumping `VERSION`, `openstrata.toml`, and every bundle/library manifest in
lockstep:

```console
$ ost plugin test --workspace --up-to 1
Workspace dependency graph: 4 bundle(s), 1 bundle edge(s), 4 libraries, 7 library edge(s), valid
```

This is the third time this repo has hit the requires-range bump trap, and the
first time a tool caught it instead of a human. Worth stating plainly: the
diagnostic named both offending libraries, the range, and the actual version,
which is exactly enough to fix it without opening a file.

**No ask here** — this behavior is correct and useful. It is recorded because
the roadmap's "wire the graph gate into CI" item was previously justified only
by the *bundle* edges, and this measurement widens the justification to the
library edges too.

## 2. Ask (P0): a CI cell that is not a bundle

`openstrata.ci.yaml` cells each name a `bundle:`, and `ost ci generate github`
renders one job per cell. There is no cell shape for:

- a **plain library** (`openstrata.library.yaml`) that no bundle requires, and
- a **CLI executable** built from the workspace against the runtime.

Both are legitimate workspace members that this project's own architecture
requires. `vrmRetarget` deliberately has no bundle consumer: WORKSPACE.md §2
forbids `usdVrmaFileFormat -> vrmRetarget`, and its only future bundle consumer
is `execVrm`, which does not exist until Workspace Phase 8. So "make a bundle
depend on it" is not available — the dependency would itself be a contract
violation.

What v0.4.0 ships with no CI coverage:

| Member | Kind | Local tests |
| --- | --- | --- |
| `libs/motionRuntime` | plain static library | `motionRuntime_unit`, `motionRuntime_boundaries` |
| `libs/vrmRetarget` | plain static library | `vrmRetarget_unit`, `vrmRetarget_boundaries` |
| `tools/motionRetarget` | CLI executable | `motion_retarget_design_triplet` (end-to-end bake vs. the frozen design triplet) |

All five pass locally in the plain-CMake root build. None runs in CI.

**Ask.** Either of these closes it:

1. A cell that targets a library or a workspace rather than a bundle — e.g.
   `library: libs/motionRuntime`, or a `workspace: true` cell that runs
   `ost plugin test --workspace` plus the workspace's own CTest registrations.
2. A documented, supported way for a bundle cell to *also* build and run the
   workspace's non-bundle CTest targets, so the existing twelve cells extend
   rather than multiply.

Option 1 is preferred: it would also give the repo the workspace graph gate in
CI, which is a separate open item that this same cell shape would satisfy.

## 3. Ask (P1): the aggregate product has no place for an executable

`ost plugin package --workspace --product` composes member archives from
bundles. `motion_retarget` is a user-facing deliverable of v0.4.0 — the whole
point of Motion Phase C is that a user can bake a clip onto an avatar — but
there is no member archive that can carry it.

**Ask.** A way to declare an executable as a product member, so the aggregate
archive ships `bin/motion_retarget` alongside the four bundles. Until then the
release either omits the tool or the repo hand-rolls a second packaging path,
and hand-rolled packaging is what
[report 27](27-2026-07-23-v0.19.0-aggregate-product-reproducibility.md) was
about.

## 4. Not an ost problem, recorded for completeness

`tools/baseline_freeze.py` resolved its bundle by `kind: usd-fileformat`, which
stopped identifying exactly one bundle when `usdVrmaFileFormat` shipped in
v0.3.0. v0.4.0 changes the lookup to key on `provides: usd-fileformat:vrm`.
Underneath it, `tests/baseline/discovery.json` was frozen before
`usdVrmaFileFormat` existed, so the registered-type union no longer matches and
the check stays red until the baseline is deliberately re-frozen under a full
workspace session. Both are this repo's bugs, not `ost`'s; they are noted here
because the second one is the kind of staleness a workspace-scoped CI cell
(§2, ask 1) would have caught the day it appeared.
