# OpenStrata Dogfooding Report for v0.8.0 - 2026-07-05

## Summary

- Host: macOS arm64
- OpenStrata: `ost 0.8.0`
- Target bundle: `plugins/usdVrm`
- Runtime target/profile: `cy2026` / `usd`
- Result: `ost plugin build plugins/usdVrm` is reproducibly failing on this host.

Primary blockers observed in order:

1. `python` command resolution failure during co-hosted schema regeneration.
2. After a local `python -> python3` shim, plugin loading fails because `plugInfo.json` points to `.dll` on macOS.
3. With additional local hacks, compile/link can finish, but `ost` then fails because `plugInfo.json` must exist at the end of the build flow.

## Reproduction

### 1) Baseline failure on v0.8.0

```sh
ost --version
ost plugin build plugins/usdVrm
```

Observed:

```text
ost 0.8.0
...
error[IO_ERROR]: i/o error at run python: No such file or directory (os error 2)
```

### 2) Workaround probe: provide `python` shim

```sh
mkdir -p .ost-bin
ln -sf "$(command -v python3)" .ost-bin/python
PATH="$PWD/.ost-bin:$PATH" ost plugin build plugins/usdVrm
```

Observed (next blocker):

```text
Failed to load plugin 'UsdVrmFileFormat':
.../plugins/usdVrm/lib/libUsdVrmFileFormat.dll (no such file)
...
Failed to load plugin UsdVrmFileFormat for UsdVrmPackageResolver
```

### 3) Workaround probe: push further to identify deepest stage

Temporary probes used only for diagnosis:

- temporary symlink: `libUsdVrmFileFormat.dll -> libUsdVrmFileFormat.dylib`
- temporary move of `plugin/resources/usdVrm/plugInfo.json` during schema-generation phase

Observed:

- `usdGenSchema` phase completes.
- CMake configure/generate/build completes.
- Final step fails due to missing `plugInfo.json` (because it is required by the flow).

## What this means for v0.8.0 dogfooding

Current v0.8.0 behavior is not robust on macOS for this plugin workspace unless environment/project-specific hacks are applied.

The core issue is not C++ compilation itself; the strongest evidence is that compile/link can complete when forced past early loader checks. The reliability problem is around toolchain/loader assumptions during schema regeneration and plugin discovery.

## Findings (Actionable)

1. `ost plugin build` implicitly requires a bare `python` executable name.
2. Schema-regeneration path can trigger plugin load too early, making build success depend on existing plugin binary/path correctness before the build has recreated artifacts.
3. Cross-platform `LibraryPath` handling is fragile when committed `plugInfo.json` uses a platform-specific extension (`.dll`) on non-Windows hosts.

## Requests to OpenStrata v0.8.x

1. Resolve Python via runtime interpreter path (or `python3` fallback) instead of hard depending on `python` in host `PATH`.
2. Avoid early plugin load during schema generation, or isolate that phase from bundle `plugInfo` plugin discovery.
3. Improve platform-aware `LibraryPath` handling in co-hosted schema/plugin build flows.
4. Add explicit diagnostics that identify whether failure happened in schema phase, loader phase, or compile/link phase (currently mixed signals increase triage time).

## Local state after dogfooding

- No tracked source files were modified.
- Temporary probe artifacts were removed after verification.
- Existing built artifact remains at:
  - `plugins/usdVrm/lib/libUsdVrmFileFormat.dylib`

# OpenStrata Dogfooding Report for v0.12.0 - 2026-07-10

- Host: macOS arm64, Command Line Tools only (`xcodebuild -version` reports that full
  Xcode is not active)
- OpenStrata binary used: `ost 0.11.0` (recorded as a v0.12.0-targeted dogfooding
  follow-up)
- Target bundle: `plugins/usdVrm`
- Runtime target/profile: `cy2026` / `usd`
- Python: `Python 3.13.14`; no bare `python` executable is present in `PATH`

## What is fixed since v0.8.0

1. **Bare `python` dependency:** fixed for this flow. Schema generation was invoked as
   `python3.13 .../bin/usdGenSchema`, and the host still has no `python` command.
2. **Early plugin load during schema generation:** fixed or at least no longer
   reproduced. The build reaches schema generation, configure, compile, and link before
   plugin-discovery validation.
3. **Diagnostics:** improved. The `.dll` vs `.dylib` problem is now reported directly
   as a platform-specific precondition failure.
4. **Runtime build ergonomics:** improved enough to build OpenUSD `26.05` via
   `ost runtime pull --build`, but the CLT-only macOS codesign case still needs a
   manual `--codesign-id -` retry.

## What is still not fixed

1. **Platform-aware `LibraryPath`:** unchanged source bundles with a committed
   `.dll` `LibraryPath` still fail on macOS. The build succeeds only after a local
   `.dylib` correction.
2. **Tracked resource churn before final failure:** `ost plugin build` mutates the
   committed `generatedSchema.usda` / `plugInfo.json` resources before the final
   `LibraryPath` precondition failure. The diffs were only ordering/newline/doc-string
   formatting churn in this run, but a failing build should ideally leave tracked
   source clean or write target-specific resources under `.strata/`.
3. **macOS build script retry UX:** `ost` prints the right hint for CLT-only hosts, but
   a more automatic fallback to ad-hoc codesign would make the source-build path fully
   hands-off on this common setup.

## Requests to OpenStrata v0.12.0

1. Generate or stage target-specific `plugInfo.json` for source bundles before final
   plugin discovery, so macOS receives `.dylib`, Windows receives `.dll`, and Linux
   receives `.so` without requiring committed platform-specific JSON.
2. Keep generated schema/resource writes target-local during `ost plugin build`, or
   avoid mutating tracked files until all preconditions have passed.
3. For `ost runtime pull --build` on Apple Silicon + Command Line Tools-only hosts,
   either auto-pass `--codesign-id -` or retry once with that argument after detecting
   the `xcodebuild`/codesign-ID failure.
4. Keep the current improvements: runtime interpreter resolution for schema generation,
   schema generation isolated from early plugin loading, and the clearer failure phases.
