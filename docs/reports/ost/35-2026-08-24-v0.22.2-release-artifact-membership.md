# The verb that ships an adapter reaches only a leaf, and no member carries data

- Date: 2026-08-24
- Version exercised: `ost 0.22.2` on Windows x86_64 (local workspace), cy2026 /
  OpenUSD 26.08
- Occasion: v0.7.0 release preparation, against the milestone's own release
  condition — *both paths run from release artifacts alone, profiles included*
  ([roadmap](../../roadmap/current.md))
- Prior report: [34](34-2026-07-29-v0.21.0-adapter-library-discovery-gap.md)
- Next ask target: `ost 0.23.0`

## TL;DR

Report 34's two adapter asks are **delivered** in 0.22.x, and preparing a
release against them turned up the shape of what is left.

1. **Plain-library discovery now reaches an adapter** (ask 1, P1). The graph
   gate counts 8 libraries and 13 library edges where report 34 measured 4 and
   7, so `adapters/liveCapture/*/openstrata.library.yaml` is loaded and its
   declared edges are validated.
2. **`ost library build|test|package` exists** (ask 3, P2) — and it composes
   nothing. `requires.libraries` is validated by the graph gate and then ignored
   by the verb, so a library configures against the runtime alone. In this
   workspace that leaves the verb usable on 2 of 8 libraries, and **both
   adapters — the members the ask was written for — are the ones it cannot
   reach**.
3. **The aggregate product silently gained both adapters' tools.** It is 9
   members where v0.6.0 shipped 7: `mocopi_record` and `vmc_record` are in it.
   [WORKSPACE.md §5](../../architecture/WORKSPACE.md) says adapters are
   deliberately *not* part of the aggregate product, and that boundary is now
   decided by a discovery rule rather than by anything either side declares.
   **§6, added the same day, is required reading beside this**: the release lane
   pins `ost` 0.21.0 and therefore packages 7. Everything measured in this
   report is a 0.22.2 workstation, and this item is the one where that matters.
4. **No member carries data.** All 9 member archives are executables or
   libraries plus a descriptor; `share/` appears in none of them. The BVH
   path's producer profiles therefore reach no artifact, and a converter
   extracted from the product refuses every file it is given. The fix is one
   descriptor word away — `directories: [bin, share]` stages a member-root
   `share/` tree correctly — but only by **copying the layer's data under one
   tool's member root**, which is the wrong owner.

Nothing here blocks the v0.7.0 code. Item 4 is what keeps one of that release's
conditions open, and it is recorded as a known limitation rather than worked
around, because the workaround puts data in the wrong place.

## 1. Discovery reaches an adapter now (report 34 ask 1 — delivered)

Report 34 measured the gate reporting `valid` over a library set that silently
excluded the adapter. Same command, same repository, one `ost` minor later and
two adapters present:

```console
$ ost plugin test --workspace --graph-only
Workspace dependency graph: 4 bundle(s), 1 bundle edge(s), 8 libraries, 13 library edge(s), valid
```

Eight is every descriptor in the tree — the six under `libs/` plus
`vrmAdapterMocopi` and `vrmAdapterVmc` two directories down under
`adapters/liveCapture/`. The count is the evidence, exactly as report 34 said it
would have to be: the exit code and the word `valid` read identically either
way.

That closes the P1 half of report 34 and, with it, the roadmap's *"the workspace
graph gate does not reach an adapter"* carry-over. The per-adapter binary link
check that stood in for it stays — it checks a different thing — but it is no
longer the only enforcement.

## 2. The per-library verb composes nothing

Report 34 ask 3 is delivered, and stops short of what it was for. `ost library`
is there, with the three subcommands the ask named:

```console
$ ost library --help
Commands:
  build    Configure, build, and install one plain CMake library
  test     Run CTest for one completed library build
  package  Package one library's isolated install tree as a tar.zst artifact
```

On a leaf it does exactly what was asked for, first try:

```console
$ ost library build libs/motionCore
Built library motionCore 0.5.0
  install: ...\libs\motionCore\.strata\targets\cy2026-windows-x86_64-py313-usd\library-prefix
  files:   8

$ ost library package libs/motionCore
Packaged library motionCore 0.5.0
  archive: ...\motionCore-0.5.0-cy2026-windows-x86_64-py313-usd.tar.zst
  digest:  sha256:320ecc4908d4c8671f1238b248087fc9b31d8595c918815d7c9be708b0489452
  files:   8
```

One directory up the dependency chain it stops:

```console
$ ost library build adapters/liveCapture/mocopi
CMake Error at CMakeLists.txt:52 (find_package):
  Could not find a package configuration file provided by "motionCore"
  Add the installation prefix of "motionCore" to CMAKE_PREFIX_PATH or set
  "motionCore_DIR" to a directory containing one of the above files.
error[EXTERNAL_TOOL_FAILED] (phase: configure): the configure phase failed (exit 1)
```

The adapter declares that edge, and §1's gate had just validated it:

```yaml
# adapters/liveCapture/mocopi/openstrata.library.yaml
requires:
  libraries:
    - id: motionCore
      version: ">=0.5,<0.6"
    - id: motionRuntime
      version: ">=0.5,<0.6"
```

**This is not a "build your dependencies first" ordering problem**, which is the
reading we started with and had to discard. `motionCore`'s `library-prefix` was
already on disk from the run above when this next one failed:

```console
$ ost library build libs/motionSource      # requires motionCore, built one command ago
CMake Error at ... (find_package):
  Could not find a package configuration file provided by "motionCore"
```

So a built, installed, descriptor-declared dependency in the same workspace is
not composed into the configure. There is no `--with` on `library build` the way
there is on `plugin run`, and `--help` lists nothing else that would do it.

The arithmetic of what that leaves: of 8 libraries here, `motionCore` and
`vrmContainer` are leaves. The other six declare edges, and the two the ask was
raised for — the adapters, at depth 2 — are the furthest from usable. A verb for
shipping optional components outside the aggregate product currently ships the
two components nobody asked to ship separately.

### Ask (P1, `ost 0.23.0`)

Compose `requires.libraries` in `ost library build`: resolve each declared
dependency to a sibling's `library-prefix` (building it first, or refusing with
the reason) and put it on `CMAKE_PREFIX_PATH`. Failing that, `--with DIR`,
repeatable, with the same meaning `plugin run --with` already has — the graph
the gate validates is exactly the input this needs, so the resolution is already
computed somewhere.

## 3. The product's membership rule and the workspace contract disagree

Packaging the workspace for the release:

```console
$ ost plugin package --workspace --product
== vrmSchema 0.5.0 ==
== usdVrmFileFormat 0.5.0 ==
== usdVrmPackageResolver 0.5.0 ==
== usdVrmaFileFormat 0.5.0 ==
== mocopi_record 0.6.0 (tool) ==
== vmc_record 0.5.0 (tool) ==
== motion_bvh 0.6.0 (tool) ==
== motion_capture 0.5.0 (tool) ==
== motion_retarget 0.5.0 (tool) ==

Workspace: 4 package(s), in dependency order, plus 5 tool package(s)
  members: 9 exact package(s)
```

v0.6.0's product manifest lists seven members and neither `*_record` tool. The
two joined without a descriptor changing, so tool discovery now reaches
`adapters/<group>/<name>/tools/<tool>/` — the same widening §1 is the good half
of.

For us this is mostly welcome: it is what makes the live path's artifact-only
run possible at all, since `mocopi_record` is how a session leaves the adapter.
But it is welcome by accident. WORKSPACE.md §5 states the opposite boundary in
so many words — adapters carry optional SDK, network and model dependencies
whose licence terms stay out of the core distribution, and each should be free
to take its own cadence — and report 34 §2 recorded that boundary as a
*packaging* boundary with no packaging command. Half of it now has one, in the
aggregate, silently.

We are not asking for the widening to be reverted. We are asking for the
decision to be **declarable by the project rather than inferred from a path**.

### Ask (P2, `ost 0.23.0`)

A way to say that a discovered member is not an aggregate-product member — a
`product: false` (or `optional: true`) key in `openstrata.tool.yaml`, or a
`product.members` list in `openstrata.toml`. Nothing in either descriptor's
schema or in `plugin package --help` expresses it today, so a project whose
layout separates "in the distribution" from "in the workspace" cannot say so.

Whichever way it lands, **print the membership set as a decision**: nine members
where seven were expected is a diff a release lane should be able to fail on,
and the only place it appears today is a count at the end of a successful run.

## 4. No member carries data, and one release condition depends on it

Every member archive is code plus its descriptor:

```console
$ tar -tf members/motion_bvh/motion_bvh-0.6.0-cy2026-windows-x86_64-py313-usd.tar.zst
bin/motion_bvh_convert.exe
bin/motion_bvh_inspect.exe
openstrata.tool.yaml

$ tar -tf members/motion_retarget/motion_retarget-0.5.0-<target>.tar.zst
bin/motion_retarget.exe
openstrata.tool.yaml
```

The BVH half of v0.7.0 cannot run on that. A producer profile is the file that
says what one writer's export *means* — joint names, units, axes, root
convention — and the converter refuses without one by design, because a BVH file
declares none of it
([recorded-motion-sources.md §2](../../roadmap/recorded-motion-sources.md)).
Extracted from the product and run against a real capture, that refusal is what
you get:

```console
$ motion_bvh_convert valid-minimal-root.bvh --profile mocopi-mobile-bvh-default-v1 --output clip.usda
motion_bvh_convert: no profile 'mocopi-mobile-bvh-default-v1' was found. Looked for
'mocopi-mobile-bvh-default-v1.yaml' in:
  <prefix>\share\usd-vrm-plugins\profiles\motion
  <parent-of-prefix>\profiles\motion
exit=2
```

The tool was written for the artifact layout — the first directory it names is
the one an installed prefix would have — and the artifact simply has no `share/`
in it. Staging the two shipped profiles there by hand makes the same binary,
from the same archive, convert a real 853-frame mocopi export:

```console
$ motion_bvh_convert mocopi-mobile-arm-raise-turn.bvh --profile mocopi-mobile-bvh-default-v1 ...
profile:  mocopi-mobile-bvh-default-v1 (Sony mocopi (mobile app))
joints:   27 read, 22 bound, 5 ignored
frames:   853 at 50 Hz (17.04 s)
output:   clip.usda
exit=0
```

So the gap is staging, and it is one word wide. `directories:` accepts more than
`bin`, and it works:

```yaml
# tools/motionBvh/openstrata.tool.yaml — measured, then reverted
directories: [bin, share]
```

```console
$ tar -tf motion_bvh-0.6.0-<target>.tar.zst
bin/motion_bvh_convert.exe
bin/motion_bvh_inspect.exe
openstrata.tool.yaml
share/usd-vrm-plugins/profiles/motion/bandai-namco-research-bvh-motiondataset-v1.yaml
share/usd-vrm-plugins/profiles/motion/mocopi-mobile-bvh-default-v1.yaml
```

**We reverted it rather than shipping it, and the reason is ownership.**
`directories:` names subdirectories of the *member root*, so this only works if
`profiles/motion/` is copied into `tools/motionBvh/share/...` — putting the
layer's data inside one tool's directory. The profiles are not that tool's:
they are read by `motion_bvh_convert` today and by anything that consumes a
recorded source tomorrow, they are validated in place by
`scripts/check_motion_profiles.py`, and they are the one part of this repository
that is deliberately *data, never code*
([WORKSPACE.md §1](../../architecture/WORKSPACE.md)). A second consumer means a
second copy, and the copy that ships stops being the file that is checked.

### Ask (P1, `ost 0.23.0`)

Either of these closes it; the first is cleaner.

- **A data-only member.** `openstrata.data/v1alpha1` — an id, a version, a
  source directory, an install destination, no build. It packages, it gets a
  manifest and an SBOM entry like anything else, and other members declare it in
  `requires:` so the product carries it once and the dependency is a stated fact
  rather than a copy.
- **A member path outside the member root.** Let `directories:` (or a new
  `data:`) take a project-relative source and a destination in the archive, so
  `profiles/motion` reaches `share/usd-vrm-plugins/profiles/motion` without the
  files being duplicated in the tree.

Until one exists, v0.7.0 records *"both paths run from release artifacts alone,
profiles included"* as unmet, with this section as the reason.

## 5. Smaller observations

- **Three of five tools packaged as unmanaged, in the same run that called the
  other two managed.** `vmc_record`, `motion_bvh` and `motion_retarget` printed
  `build: untracked (external-or-unmanaged)`; `mocopi_record` and
  `motion_capture` printed `build: matched (ost-managed)`. All five came out of
  one root `ost build`. This is report 33 §3's ask surfacing again — the root
  build stages tool executables it records no provenance for — but the split
  across five otherwise identical members in one invocation is new, and we could
  not find what separates the two groups.
- **The warnings name nothing.** The three above arrive as three identical
  lines at the very end of the run, after all nine members, with no member name
  in any of them: `warning: the last managed build recorded no outputs for this
  tool; treating them as external or unmanaged`. You match them to members by
  counting. *(P3: name the member in the warning.)*
- The four bundles all reported `build: matched (ost-managed)` after the
  `ost build` → per-bundle `ost plugin build` → `ost plugin package` order
  report 33 established. That order is still required and still undocumented in
  `--help`.
- `ost library package` refuses an unbuilt library with a hint that names the
  exact command to run, which is the right refusal and saved a lookup:
  `hint: run 'ost library build <DIR>' first`.

## 6. Added 2026-08-24: the release lane is on 0.21.0, and §3 is a workstation

Appended after a `workflow_dispatch` dry run of the v0.7.0 release lane, which
is what caught it. Nothing above is withdrawn; this says which machine it
describes.

`openstrata.ci.yaml` pins `bootstrap.ost.version: "0.21.0"` and `release.yml`
bootstraps and *verifies* that exact string. So the widening §3 measured is not
in the release lane:

```console
# this workstation, ost 0.22.2
  members: 9 exact package(s)          # 4 bundles + 5 tools

# release runners, ost 0.21.0, all three OS
  "members": 7,                        # 4 bundles + 3 tools
declared: 4 bundle(s), 5 tool(s); packaged: 4 + 3
```

Three consequences, and the first is the one that cost a dry run.

**A member-count gate written from a workstation is wrong on the lane.** The
first version of this fix counted `tools/` *and* `adapters/` descriptors, got 5,
and failed all three cells at the staging step — after every build, both
packaging runs and the digest-reproducibility proof had passed. The gate now
counts `tools/` only, because that is what the *contract* says belongs in the
product; the pin merely happens to agree today.

**The exclusion §3 reports as violated is, on the shipped artifact, intact** —
and held by a version pin rather than by anything either descriptor declares,
which is exactly what §3's ask is for. v0.7.0 ships 7 members and WORKSPACE.md
§5 holds. A pin bump to 0.22.x would put two adapter CLIs into the aggregate,
and now fails the lane instead, which is the behaviour we want from a boundary
nobody can declare.

**A dogfooding report's version line is a claim about a machine, not about the
project.** This series has always named the version exercised; what it has not
done is say when that version differs from the one the project's own lanes run.
Reports 33–35 were all written from a workstation ahead of the CI pin. Worth
stating once here rather than re-deriving it the next time a measurement does
not reproduce.

### Ask (P3, `ost 0.23.0`)

`ost` knows both numbers — the running binary's version, and the
`bootstrap.ost.version` its own CI contract pins. When a command's *result*
depends on a discovery rule that changed between them, say so:
`note: this project's CI contract pins ost 0.21.0, which discovers 3 tool
member(s) here rather than 5`. A workspace command that behaves differently on
the developer's machine and the project's lane is worth one line of output.
