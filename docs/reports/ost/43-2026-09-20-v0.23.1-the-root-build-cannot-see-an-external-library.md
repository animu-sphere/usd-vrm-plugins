# The root build cannot see an external library its own member declares

- Date: 2026-09-20
- Version exercised: `ost 0.23.1`, the published `x86_64-pc-windows-msvc`
  asset, on this workstation against the pinned
  `cy2026-windows-x86_64-py313-usd` runtime in an isolated `OST_HOME`
- Occasion: the first real consumption of a cross-repository library artifact.
  `usd-motion-plugins` v0.5.0 published seven of them on 2026-09-20, and
  `motion-connectors` imported `motionTracking` as `motionConnectorTracking`
  and declared `motionCore` as an external dependency — the shape
  [report 41](41-2026-09-19-v0.22.10-a-library-from-another-repository.md)
  asked for and [42](42-2026-09-20-v0.23.0-a-claim-measured-before-the-repair.md)
  cleared the way for
- Prior report: [42](42-2026-09-20-v0.23.0-a-claim-measured-before-the-repair.md)
- Next ask target: `ost 0.23.2`

## TL;DR

**The per-library verb composes an external library artifact. The root build
does not, and the root build is what a workspace's CI runs.**

1. **P1: `ost build` at the root omits the materialized external prefix from
   `CMAKE_PREFIX_PATH`.** `ost library build` prepends it and configures;
   the root build of the same tree, one minute later, fails with
   `Could not find a package configuration file provided by "motionCore"`.
   The two toolchain files are side by side in §2, and the difference is one
   line. Every rendered workspace cell with `verify: build` or `verify: test`
   runs the root build, so a workspace with one such member has no green lane
   (§2).
2. **This is the shape of every consuming repository, not one repository's
   layout.** `motion-connectors`, `usd-vrm-plugins` and `usd-mmd-plugins` all
   compose their members from one root CMake tree and all consume
   `usd-motion-plugins` packages. The import that found this is one library;
   `usd-vrm-plugins`' consuming change is nine members at once (§3).
3. **P3: a workstation whose runtime is an adopt cannot consume a published
   artifact, and the refusal does not say what would.**
   `WORKSPACE_LIBRARY_ARTIFACT_RUNTIME_MISMATCH` is correct — the rule is one
   OpenUSD across the ecosystem — but a developer reading it is not told which
   runtime identity the artifact wants or how to get it (§4).
4. **What worked, and it is most of it:** the declaration, the pull, the
   identity checks, the graph edge, the link and the tests (§5).

## 1. What was being done

`motionTracking` moved to `motion-connectors` as `motionConnectorTracking`
(this repository's MIG-4). It links `motionCore`, which now lives in
`usd-motion-plugins` and is published as a digest-pinned artifact, so its
descriptor declares:

```yaml
requires:
  libraries:
    - id: motionCore
      version: ">=0.5,<0.6"
      artifact:
        targets:
          cy2026-windows-x86_64-py313-usd:
            digest: sha256:f06fef79…
            source: oci://ghcr.io/animu-sphere/usd-motion-plugins@sha256:7e5c67b9…
```

That is exactly report 41's P1 as delivered, and every part of it works
(§5). What does not work is building the workspace afterwards.

## 2. The defect, measured

```text
$ ost library pull --target cy2026 --profile usd
Pulled 1 external library artifact(s)

$ ost library build libs/motionConnectorTracking
… Built library motionConnectorTracking 0.1.0

$ ost build                      # the same tree, the same target
CMake Error at libs/motionConnectorTracking/CMakeLists.txt:65 (find_package):
  Could not find a package configuration file provided by "motionCore" with
  any of the following names:
    motionCoreConfig.cmake
  Add the installation prefix of "motionCore" to CMAKE_PREFIX_PATH …
```

The two generated toolchains say why. The per-library one:

```cmake
# libs/motionConnectorTracking/.strata/targets/<target>/toolchain.cmake
list(PREPEND CMAKE_PREFIX_PATH "<OST_HOME>/runtimes/openstrata-cy2026-windows-x86_64-py313-usd")
list(PREPEND CMAKE_PREFIX_PATH "<repo>/.strata/external-libraries/<target>/motionCore/<digest>" "<repo>/libs/motionConnectorTracking/.strata/targets/<target>/library-prefix")
```

The root one, in full, for the same target:

```cmake
# .strata/targets/<target>/toolchain.cmake
list(PREPEND CMAKE_PREFIX_PATH "<OST_HOME>/runtimes/openstrata-cy2026-windows-x86_64-py313-usd")
```

The artifact **is** materialized — `.strata/external-libraries/<target>/motionCore/`
exists and holds the package — and the root build simply does not name it.
Nothing in `ost build --help` adds it: there is no `--with`, and
`[build.intents.<name>.cache]` would mean writing a digest-bearing absolute
path into `openstrata.toml` by hand, which is a mirror that drifts on the next
republish.

The root target directory also records nothing about the materialization
(`toolchain.cmake`, `env.json`, `CMakePresets.json`, the lease and the logs),
so a root `CMakeLists.txt` cannot honestly read `ost`'s own answer either.

## 3. Why this stops the migration rather than one import

The generated workspace cell runs the root build: `verify: build` and
`verify: test` are both root-tree verbs, and `ost test` runs the root CTest
suite. So a workspace with one external-consuming member has no green cell,
and a repository cannot adopt the edge at all — which is the same shape as
report 42's P1, one layer down.

Three repositories are waiting on this edge, and each composes its members
from one root CMake tree:

| Repository | Members that consume a `usd-motion-plugins` package |
| --- | --- |
| `motion-connectors` | `motionConnectorTracking` today; the three connectors next |
| `usd-vrm-plugins` | nine, in one change (report 41 §2.1 lists them) |
| `usd-mmd-plugins` | `mmdMotionAdapter` |

## 4. A developer's runtime

On this workstation the first pull was refused:

```text
error[WORKSPACE_LIBRARY_ARTIFACT_RUNTIME_MISMATCH]:
  library 'motionCore' artifact sha256:f06fef79… was built for a different runtime
```

The rule behind it is right and is the ecosystem's own (one OpenUSD release,
moving rule 5). The workstation's `cy2026/usd` is a local adopt of a real USD
build; the artifact was produced against the pinned runtime. Materializing the
pinned runtime into a separate `OST_HOME` made the pull succeed.

What the message does not say is any of what a reader needs: which runtime
identity the artifact was built for, which one is selected here, or that
materializing the pinned artifact is the way through. A developer who has
never published one cannot act on it.

## 5. What worked

Everything up to the root build, which is why this report is a P1 and not a
reversal:

- **The declaration.** `artifact.targets` with three targets, archive digest
  plus `oci://` source, taken verbatim from the release's generated pin table.
- **The graph.** `ost plugin test --workspace --graph-only` reports
  `3 libraries, 1 library edge(s), valid` — the edge is the external one, and
  it is in the graph rather than hidden in CMake, which is the whole of report
  41's P1.
- **The pull.** `ost library pull` materialized it, checked the archive bytes,
  the library/version/target identity and the runtime identity, and refused
  the wrong runtime (§4) before it checked anything else.
- **The build and the tests.** `ost library build` configured, compiled and
  linked against the materialized package; `ost library test` is 3/3.
- **An anonymous pull needs no credential.** Measured separately, from a clean
  `OST_HOME` with no `OST_REGISTRY_*` set: `ost artifact pull` of the published
  `motionCore` verified its digest, SBOM and provenance and imported it. A
  consumer's CI does not need a token to reach these.

## 6. Asks

- **P1: compose a member's external library artifacts into the root build.**
  The root `toolchain.cmake` should prepend the same materialized prefixes the
  per-library toolchain does, for every member of the workspace that declares
  one. Failing that, any documented path that a rendered workspace cell can
  take — the constraint is that the cell runs `ost build` and the workflow is
  not hand-editable (report 38's P2, report 42's P1).
- **P3: say what a runtime mismatch wants.** Name the artifact's runtime
  identity and the selected one in the error, and point at materializing the
  pinned runtime.
- Report 37's P1 stands, as recorded in report 42 §4.
