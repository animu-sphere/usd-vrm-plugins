> re-verified in [48](48-2026-09-24-v0.23.6-the-product-packages-again.md), where the product packages and every release-lane step passes on Windows.

  default `OST_HOME`
- Occasion: the consuming change report 46 was waiting for,
  [#227](https://github.com/animu-sphere/usd-vrm-plugins/pull/227). `execVrm`

## TL;DR

**Report 46's P1 is delivered, and it closed MIG-2. The same release breaks
this repository's product package.**

1. **Delivered: the root build composes a member's external bundle.**
   - `ost build` pulled `execMotion` from GHCR by digest and materialized it.
   - It wrote `OPENSTRATA_EXTERNAL_BUNDLE_execMotion_ROOT` into the root
     toolchain, together with the bookkeeping list that clears stale entries.
   - Every root CTest suite that composes the bundle now reads it through that
     variable: four `execVrm` suites, the driver contract and five parity
     cases. All pass, 38 of 38 (§2).
2. **P1, regression: `ost plugin package` fails on `vrmSchema`.**
   - `vrmSchema` is the one bundle other members link. Its managed build
     records `lib/vrmSchema.exp`, and the per-target stage 0.23.5 packages from
     does not carry that file.
   - The product package fails with `PLUGIN_PACKAGE_OUTPUT_MISMATCH`, from a
     clean tree. The same tree packaged under 0.23.4 the same morning.
   - No pull-request lane packages the product, so only the release lane shows
     it (§3).
3. **A consumer-side trap, not an ask** (§4). The exported variable lands in
   the cache, so any directory can read it. But a helper that turns it into
   ordinary variables must not use `include_guard(GLOBAL)`. It did here at
   first, and the parity cases silently stopped registering.

## 1. What was being done

`usd-motion-plugins` v0.5.1 pushed its bundle and CLIs to
`ghcr.io/animu-sphere/usd-motion-plugins` next to the libraries
(usd-motion-plugins #26). With 0.23.5 installed, the deletion that report 46
had rehearsed on a scratch branch became a real change:

- `execVrm` pins the bundle per target.
- `plugins/execMotion` leaves `members`, `release_members` and the tree.
- Every suite that composed the sibling directory now composes the consumed
  bundle.

## 2. What worked: the root tree sees the bundle

The generated root toolchain after the first `ost build`:

```cmake
foreach(_ost_external_var IN LISTS OPENSTRATA_EXTERNAL_MEMBER_VARIABLES)
  unset(${_ost_external_var} CACHE)
endforeach()
set(OPENSTRATA_EXTERNAL_BUNDLE_execMotion_ROOT ".../.strata/external-bundles/cy2026-windows-x86_64-py313-usd/execMotion/2c41a664…" CACHE PATH "Verified external bundle root" FORCE)
set(OPENSTRATA_EXTERNAL_MEMBER_VARIABLES "OPENSTRATA_EXTERNAL_BUNDLE_execMotion_ROOT" CACHE INTERNAL "…" FORCE)
```

The digest is v0.5.1's Windows archive (`sha256:2c41a664…`). No local copy
existed to shadow it, because the store only held the 0.5.0 digests imported
for report 46.

This repository's `cmake/UsdVrmExecMotion.cmake` turns that root into the
bundle's `lib/` and `plugin/resources/execMotion`, and each composing suite
names them in its own `ENVIRONMENT_MODIFICATION`, as report 46 asked. Then:

- Root `ost test`: **38 of 38**, where the tree had 48 with the copy. The ten
  missing are `execMotion`'s own suites, which left with it.
  - `execVrm_retarget_without_exec_motion` still `set`s the plugin path
    without the bundle and still passes. The pinned bundle does not leak into a
    suite that must not see it.
  - The five `workspace_exec_parity_*` cases run with `PXR_PLUGINPATH_NAME`
    naming `…/external-bundles/…/execMotion/2c41a664…/plugin/resources/execMotion`,
    and report "parity holds" with divergence 0.
- A standalone `ost plugin build plugins/execVrm` does not get the variable.
  That is as the notes describe: only the root toolchain carries it. So those
  suites are built there and not registered, and the configure says so.
- The product embeds the bundle exactly once, under
  `bundles/execVrm/runtime/bundles/execMotion/`. That is 0.23.4's packaging
  claim, which report 46 did not re-measure. `artifact_only_exec_smoke.py`
  passes from that product, including its negative: with the one
  `execMotion` registration moved aside, the parity case is refused.

## 3. `vrmSchema`'s staged output loses a file

In the release lane's order (root `ost build`, then each bundle's
`ost plugin build`, then `ost plugin package --workspace --product`):

```text
error[PLUGIN_PACKAGE_OUTPUT_MISMATCH]: plugin 'vrmSchema' staged package output
does not match its last managed build: missing 'lib/vrmSchema.exp' (expected
sha256:65296125…, observed absent)
```

`ost plugin package plugins/<bundle>` for each bundle separately:

- `vrmSchema` fails the same way.
- `execVrm`, `usdVrmFileFormat`, `usdVrmPackageResolver` and
  `usdVrmaFileFormat` package fine.

What the two sides hold:

| Where | Contents |
| --- | --- |
| `plugins/vrmSchema/build/<target>/.ost-build-complete.json` `outputs` | `lib/libvrmSchema.dll`, `lib/vrmSchema.exp`, `lib/vrmSchema.lib`, and three `plugin/resources/vrmSchema/` files |
| `plugins/vrmSchema/lib/` | `libvrmSchema.dll`, `vrmSchema.exp`, `vrmSchema.lib` |
| `plugins/vrmSchema/.strata/targets/<target>/bundle-stage/lib/` | `cmake/`, `libvrmSchema.dll`, `vrmSchema.lib` |

The reading, from `crates/ost-cli/src/commands/plugin.rs`:

- `vrmSchema` is the bundle that installs into the workspace prefix, so its
  plugin build takes the `install_to_workspace` path. `built_bundle` is then
  the source tree, and the completion record hashes `lib/` as the linker left
  it, `.exp` included.
- The package stage is assembled from the installed bundle stage.
- `.exp` is a link by-product that `cmake --install` never copies, so a
  managed output goes missing between the record and the stage.

Bundles that nothing links take the other path, where the record is written
from the stage itself, and they agree.

It is not a stale-tree effect:

- It first appeared with two stale August `.pdb` files as well. Deleting them
  left only the `.exp`.
- `git clean -fdX plugins` followed by the whole sequence again, and deleting
  the root `plugin-product-stage`, both gave the same error with the same
  build fingerprint.
- Under 0.23.4 this tree packaged at 01:26 the same day, and that product
  passed the same smoke.

Hosted lanes will see it too. The `.exp` comes from MSVC's link of any DLL
that exports symbols, so the Windows release cell fails on a fresh checkout.
Linux and macOS produce no `.exp`, and were not measured.

## 4. A trap in the consumer's own CMake

`OPENSTRATA_EXTERNAL_BUNDLE_execMotion_ROOT` is a cache variable, visible
everywhere. The first version of the helper that turns it into
`USDVRM_EXEC_MOTION_BUNDLE` carried `include_guard(GLOBAL)`, and three
directories include it:

- The first includer is a bundle's `tests/` directory, and it got the
  variables.
- The root, which includes it later to decide whether to add `tests/parity`,
  got nothing, so it skipped the parity cases with a status line.

The root suite ran 32 tests instead of 38. Six had quietly gone missing, and
31 passed. The one failure was `workspace_ctest_labels`, which caught the
`motion.openexec` registrations that had disappeared; see
[`scripts/check_ctest_labels.py`](../../../scripts/check_ctest_labels.py). This
is not `ost`'s to fix. It is recorded because the next consumer of these
variables will write the same helper.

## 5. Asks

- **P1: package a workspace-installed bundle from the outputs its build
  records, or record the outputs the stage will hold.** A bundle that other
  members link must package from the same set of files its managed build
  hashed. Today the record is the source tree and the stage is the install,
  and a file `cmake --install` does not copy (`.exp`, and before it a `.pdb`)
  fails the comparison. Either hash the installed stage for these bundles as
  the other path does, or limit the comparison to what the stage is meant to
  carry. `--allow-unmanaged-output` is not a workaround: it records an
  override in the product's provenance.
- Report 46's observation (a hand-edited `pxr_DIR` with an intact identity
  record) was not revisited.
