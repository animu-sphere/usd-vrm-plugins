# OpenUSD 26.08 OpenExec, a retarget in the shape of an animation sample

- Date: 2026-09-13
- Version exercised: **OpenUSD 26.08**, the pinned `cy2026`/`usd` runtime. Like
  [the retarget report](26.08-openexec-retarget.md), this run used a local build
  of that release adopted as the runtime, not the published GHCR leaf.
- Occasion: [the OpenExec plan](../../roadmap/openexec-foundation.md) §6, P0-5.
  `vrm.computeJointLocalTransforms` is `execVrm`'s fifth and last planned node.
  The retarget already answers in joint-local rotations and translations, so
  this node is the question of what shape a `UsdSkelAnimation` sample is, not a
  second retarget.
- Method: **run, one node on from the retarget report.** Everything marked
  **(test)** is asserted by `execVrm_joint_transforms`, which drives both built
  bundles through `PXR_PLUGINPATH_NAME` without linking either, over
  `retargeted_rig.usda`, or by `execVrm_rig`, which tests the seam with no
  stage. **(negative)** claims were measured by changing one line, rebuilding (a
  `Building CXX object` line confirming it), watching suites go red, and
  restoring it. **(probe)** claims were asserted against UsdSkel before anything
  here depended on them. **(measured)** is a throwaway run against a corpus file
  or the built `motion_retarget`, not committed. **(read)** is read off the
  source and not run.
- What this does **not** supersede: any earlier report.

## TL;DR

1. **The node is the retarget with the two things a bake adds, and nothing
   else.** The rotations, translations and timestamp pass through bit for bit.
   It adds the rig's `joints`, verbatim and in the rig's order, and one
   `(1, 1, 1)` scale per joint. (test)
2. **Authored the way `motion_retarget` authors it, the value is what UsdSkel
   resolves**: the skeleton query's joint-local transforms equal
   `UsdSkelMakeTransforms` over the value, exactly. Leave `scales` out, or make
   the arrays one joint short, and UsdSkel resolves **the rig's rest**, with no
   error. So `scales` is part of the value and a non-pairing pose is refused.
   Neither is strictness. (test, probe)
3. **The identity scale overwrites a scaled rest pose, in both implementations.**
   The fixture's arm rests at scale 2. With the clip at its own rest, every
   joint lands on the rig's rest within 1e-6 except the arm, which comes back at
   scale 1. The importer can produce this: `Seed-san.vrm` has seven scaled skin
   joints, all non-humanoid, off unit by at most 1.38e-3. This is P1-2's
   question, not a P0-6 row. (test, measured)
4. **A driver's override of the retarget reaches the node.** That override is
   the only way to get a pose that does not pair with the rig, or one with no
   rig behind it, and the node refuses both. (test, negative)
5. **A result type that is not registered costs every computation in every
   session.** This is the retarget report's input finding on the output side.
   Without `RegisterType(JointLocalTransforms{})`, six of the seven suites died
   with a fatal error and a segfault. (negative)
6. **`motion_retarget` places a sample at `(frame / rate) × rate`, and that is not
   always `frame`.** A 30 fps clip keyed at 31 and 62 bakes to
   `31.000000000000004` and `62.00000000000001`. Read back at frame 62, the hips
   rotation is `(1, 0, 1.74e-16, 0)` where the key is `(1, 0, 0, 0)`. A P0-6 row
   of the rounding kind, and an instruction to the parity harness. (measured)

## 1. What ran

`vrmRetarget` gains one type, `JointLocalTransforms`, beside `RetargetedPose`,
with the exact `operator==` the registry requires. One computation is new:

| Computation | On | Reads | Answers |
| --- | --- | --- | --- |
| `vrm.computeJointLocalTransforms` | applied `VrmHumanoidAPI` | `vrm.humanoidRetarget` on its own prim; `vrm.computeTargetSkeleton` across `vrm:skeleton` | `vrmRetarget::JointLocalTransforms`: `timestamp`, `joints`, `translations`, `rotations`, `scales` |

The fixture is the retarget report's `retargeted_rig.usda`, unchanged. Its rig's
`J_Bip_L_UpperArm` rests turned 90° about +Z and **scaled by 2**, which the
retarget report never needed and this one does (§4).

**Why components and not matrices.** UsdSkel spells the question both ways:
`UsdSkelAnimQuery::ComputeJointLocalTransforms` answers matrices, and
`ComputeJointLocalTransformComponents` answers the three arrays. The node
answers the components, for three reasons:

- they are what `motion_retarget` authors, and so what P0-6 compares against;
- they are what the plan's P0-6 list names: joint order, translations,
  rotations, identity scales;
- the matrices are UsdSkel's own composition of them, and §3 measures that
  composition exactly.

A consumer that wants matrices can get UsdSkel's own answer with one call. The
reverse direction, decomposing matrices, loses the quaternion's sign, so it is
not the one to offer. The plan's name for the node is kept.

## 2. The value

At frames 24 and 12 the request returns the rig, the retarget and the sample
together, with no error (test):

- `timestamp`, `rotations` and `translations` equal the retarget's, `operator==`
  field by field. The timestamp is 1.0 and 0.5;
- `joints` equals the skeleton's authored `joints` token for token, in order;
- every entry of `scales` is `(1, 1, 1)`, the arm's included.

The seam test says the same over plain values, including an empty rig and an
empty pose: the empty sample is an answer, the animation of a skeleton with no
joints (test). The node declares no `computeTime`. A frame change reaches it
across the link to the retarget and does not report the rig (test).

**It reads the skeleton once, not counted.** Every other fan-in in both bundles
reads its relationship twice, because a target that answers nothing vanishes
without a word (the blending report §2). Here the retarget has already read
`vrm:skeleton` through the map, and the map refuses anything but exactly one
skeleton. The one route past the map is a driver's override of the retarget
(§5). There, a skeleton that did not come back is refused by the size of what
did come back.

## 3. Authored, it is what UsdSkel resolves

The suite authors the node's value the way `WriteAnimation` does. That means
`joints` and `scales` once, `rotations` and `translations` at
`timestamp × 24`, and a `SkelBindingAPI` applied on the target skeleton binding
the new animation. It then asks a fresh `UsdSkelCache` for the skeleton's
joint-local transforms at frame 24 (test, probe):

| Authored | UsdSkel's joint-local transforms |
| --- | --- |
| the node's value | exactly `UsdSkelMakeTransforms(translations, rotations, scales)` over the value, every joint (`!=` on `GfMatrix4d`, no tolerance); the spine differs from its rest |
| the same, `scales` never authored | **the rig's rest**, every joint, exactly |
| the same with `scales`, rotations and translations one joint short | **the rig's rest**, every joint, exactly |

The second row is what `WriteAnimation`'s own comment warns of ("an animation
without it binds cleanly … and then resolves no joint transforms at all"),
measured on this node's value. It is why `scales` is a field and not something
each writer has to remember to add. The third row is why the node refuses a pose
that does not pair with the rig (§5). Answered, that pose would not bake to a
wrong pose. It would bake to the rig standing still, and nothing would report
it. Both rest rows are asserted, so the day UsdSkel resolves either one
differently, the suite goes red.

UsdSkel also posts a warning while building the query: the fixture's skeleton
states no `bindTransforms`. That warning is about the fixture and not the
value, and the suite prints it.

## 4. What the identity scale costs on a scaled rest

At frame 0 the clip stands at its own rest, and the retarget lands every mapped
joint on the rig's rest. That is the case where a bake should reproduce the rig
as it stands. Authored and resolved as in §3 (test):

- every joint but the arm resolves to its rest transform within 1e-6;
- the arm resolves to its rest **with the scale divided out**: each of the three
  basis rows has length 2.000 at rest and 1.000 in the bake, and otherwise the
  two matrices agree within 1e-6.

UsdSkel takes an animated joint's local transform from the animation whole. A
sample that states every joint, as every bake does, therefore replaces each
joint's rest scale with the one it states. `vrm.computeTargetSkeleton` already
drops rest scale (a `TargetJoint` has no field for it), so the node could not
carry it if it tried. The offline tool authors the same constant `(1, 1, 1)`
array (`StageIo.cpp`, `WriteAnimation`) (read). **The two implementations agree,
so P0-6 has nothing to classify here.** The question is P1-2's. Its text,
"always author identity scale", was written against the scale-less animation
that resolves to rest, and it does not mention a rig whose rest is scaled.

**Can the importer produce such a rig?** The rest transforms are the glTF nodes'
local transforms, so the skin joints' `scale` answers it without a stage
(measured, over every `.vrm` in the committed corpus except the malformed ones):

| File | Skin joints | Scaled | Largest deviation from 1 | Humanoid bones among them |
| --- | --- | --- | --- | --- |
| `spec-samples/vrm1/seed-san/Seed-san.vrm` | 128 | 7: `bag_rope_L`, `bag_rope_R`, `hair_A`, `hair_D`, `hair_E`, `hair_E.001`, `hair_subB` | 1.38e-3 (`hair_E`, z) | none |
| `VRM1_Constraint_Twist_Sample.vrm` | 154 | 0 | — | — |
| the fixtures | 0–5 each | 0 | — | — |

So the importer can produce it: it happens on a real spec avatar, but on
secondary joints only, and at 0.14% at most. That size is invisible to a viewer
and is not something a check should quietly accept. A rig that rests at a real
scale, say a centimetre-unit export with a 100× root, would be drawn at a
different size by every bake. A skinned mesh bound to such a joint would shrink
around it. `AliciaSolid.vrm` was not scanned; it is fetch-gated and was not
present.

What P1-2 has to decide, now that it is measured: author the rig's rest scale in
`scales` (which means carrying scale in `TargetJoint`, since the node cannot see
it now), refuse a rig with a non-unit rest scale, or keep identity and say what
it costs. The node follows the rule as written, and so does the tool.

## 5. A driver's retarget, and the refusals

A `RetargetedPose` handed to `vrm.humanoidRetarget` through
`ComputeWithOverrides` reaches the node as the retarget's own answer would:
its arrays and timestamp, the rig's joints and identity scales (test). That is
how a filtered, blended or held retarget becomes a sample. It is also the only
way to produce the two refusals that need a pose the retarget itself never
answers:

| The node reads | What comes back |
| --- | --- |
| no retarget (the default time code, or a root-motion statement the retarget refuses) | **no value**, and `the humanoid's vrm.humanoidRetarget answered nothing`, beside the retarget's own reason |
| an overridden pose one joint short (6 rotations, 6 translations, 7 joints) | **no value**, and an error naming all three counts |
| an overridden pose whose two arrays disagree | **no value**, the same error (seam) |
| an overridden pose, with `vrm:skeleton` set to target nothing | **no value**: `'vrm:skeleton' brought back 0 skeletons`. The map refuses, and the overridden retarget still answers |

With the count check disabled, the seam suite and the built suite both went red.
The built one failed with a value where a refusal belonged: a six-joint pose
under seven joint tokens, which §3 shows would bake to the rest (negative).
Without the scales, both suites went red too (negative).

No override survives its call (test).

## 6. Registration

The retarget report measured that a bundle **reading** a value type must
register it (§3 there). The output side behaves the same way, more loudly. With
`RegisterType(vrmRetarget::JointLocalTransforms{})` removed (negative):

```text
fatal: Type 'vrmRetarget::JointLocalTransforms' not registered with TfType. Use
ExecTypeRegistry::RegisterType<T>() to register execution value types.
```

That fatal error is followed by a segfault, in **six of the seven** `execVrm`
suites, every one that loads the bundle. That includes `execVrm_humanoid`,
which never asks for this computation. `execVrm_rig`, which links no exec,
passed. So a computation's result type fails at the same moment as its input
types, when the bundle's computations are registered, and it takes every
sibling computation down with it.

## 7. Invalidation

Recorded by the request's value callback after `ChangeTime(24)` (test):

| Edit | Rig | Retarget | Sample |
| --- | --- | --- | --- |
| `ChangeTime` (time callback) | no | yes | yes |
| `vrm:retarget:rootMotion` created as `ignore` | no | yes | yes, and **nothing else** |
| a key of the clip (the head, 45° about +Y) | no | yes | yes |
| the rig's `Root` rest translated to `(0, 0, 0.5)` | yes | yes | yes, with `Root`'s translation `(0, 0, 0.5)` |

The last row is the rest edit reaching the sample by two routes: through the
retarget, which carries an undriven joint's rest, and directly through the
skeleton the tokens are read from.

## 8. Where a sample is placed in time

`JointLocalTransforms` carries the retarget's timestamp in seconds. An
animation places a sample at a time code instead, and the writer converts one to
the other. `motion_retarget` does the conversion as `timestamp × rate`, where
`timestamp` was `timeCode / rate` when the clip was read (`StageIo.cpp`, lines
849 and 1096) (read). In doubles, that round trip does not always come back to
the frame (measured):

| Rate | Frames in 0–99 999 that do not come back |
| --- | --- |
| 24 | 0 |
| 30, 60, 120 | 3 273 (first: 31, 62, 123) |
| 25, 50 | 9 175 (first: 7, 14, 28) |

This is visible in a real bake. A 30 fps scratch clip keyed at 0, 31 and 62,
retargeted onto the design triplet's avatar by the built `motion_retarget`,
writes time samples at `0`, `31.000000000000004` and `62.00000000000001`, and
an `endTimeCode` of `62.00000000000001`. Read back at the integer frame, 31
happens to come back bit for bit. At 62 the hips rotation is
`(1, 0, 1.7439344e-16, 0)` where the key is `(1, 0, 0, 0)`, because the frame
now sits 1e-14 before a sample and USD interpolates. (measured)

Nobody can see that, and it does not break a viewer. What it breaks is an exact
comparison at a key time, and exact comparison at key times is how P0-6 has to
compare, because between keys the answer belongs to USD (the sampling report).
exec has no such problem: execMotion computes the same timestamp,
`timeCode / rate`, and nobody multiplies it back. So the parity harness must
read the bake **at the bake's own time samples**, not at the clip's frames. The
tool's fix is to author at the time code it read rather than rebuilding one from
seconds, and that is a tool change for P0-6 to choose, not this node's. The
fixtures here count at 24 per second, which is why no suite ever saw it.

## 9. What this adds to P0-6's table

| The stage or invocation states | `motion_retarget` | `execVrm` |
| --- | --- | --- |
| a clip at a rate where `(f / r) × r ≠ f` (30, 60, 120, 25, 50) | places the sample at the rebuilt time code, off the frame by ~1e-14 | answers the frame's own sample, stamped `f / r` |
| a rig with a scaled rest | bakes scale 1 | answers scale 1 — **agree**; P1-2's question (§4) |

The first row is the rounding kind in the plan's classification, which is the
second cheapest to rule out. It only has to be ruled out once, by comparing at
the bake's own sample times.

## 10. What this changes in the plan

1. **P0-5 is complete**: five planned nodes and the two it needed. What remains
   in the plan is P0-6, P0-7 and P0-4's carried items.
2. **The ninth boundary finding, the smallest.** The shape of a bake, meaning
   the rig's tokens beside the arrays plus identity scales, is stated offline
   in only one place: two lines of `WriteAnimation`, in a tool. `vrmRetarget`
   had no type for it. The library gains the type, for the registry. The rule
   stays two lines in the seam and two lines in the tool. The ask is that the
   tool author from the library's value, so that P1-2's "OpenExec and offline
   behave identically" is one statement
   ([boundary consolidation](../../roadmap/boundary-consolidation.md) §1).
3. **P1-2 gains a measured case** (§4), and the plan's text for it has to say
   what a scaled rest does.
4. **P0-6's harness gains an instruction**: compare a bake at its own time
   samples (§8).

## 11. What this did not do

- It did not compare against a `motion_retarget` bake of the same fixture. The
  tool reads the avatar and the clip as two stages, and this fixture is one.
  §3 compares the node's value with UsdSkel's resolution of that same value,
  which is the half that belongs to this node. The parity run is P0-6's.
- It did not change the tool. The time-code rounding (§8) and the shared shape
  (§10.2) are both tool changes, and P0-6 decides whether to make them.
- It did not decide P1-2 (§4).
- It did not scan `AliciaSolid.vrm` or any VRoid export. Both are fetch-gated,
  and neither was present.
- It ran on Windows only. The committed suites run on all three lanes.
