# OpenUSD 26.08 OpenExec, the retarget's diagnostics as values

- Date: 2026-09-13
- Version exercised: **OpenUSD 26.08**, the pinned `cy2026`/`usd` runtime. Like
  [the parity report](26.08-openexec-parity.md), this run used a local build of
  that release adopted as the runtime, not the published GHCR leaf.
- Occasion: [the OpenExec plan](../../archive/motion-split/openexec-foundation.md) §6, P0-6's
  diagnostics row. The parity report left it open (§6 there): the tool named the
  bone a rig drops and exec could not. P1-1's first half then froze the
  `VRM_RETARGET_*` codes as values the same day, so what remained was an exec
  node answering them and the harness comparing the two lists.
- Method: **run, against the tool.** **(test)** is asserted by one of
  `execVrm_rig`, `execVrm_diagnostics` or the five `workspace_exec_parity_*`
  CTest names. **(negative)** is a committed negative pair. **(measured)** is a
  throwaway run, not committed. **(read)** is read off the source and not run.
- What this does **not** supersede: any earlier report. It closes the row the
  parity report's §6 and §7 row 24 left open, and replaces none of their text.

## TL;DR

1. **The diagnostics agree, line for line, on every case.** Exec answers the
   frozen codes as a value, and merged over a clip's keys the list is the one
   `motion_retarget` prints, down to the detail text: none on the fixture rig,
   `UNBOUND_DRIVEN_BONE upperChest` on Seed-san, and fourteen
   `MISSING_REQUIRED_BONE` on the design rig, twice. (test)
2. **The harness sees a missing diagnostic, and only that.** With one coded line
   taken out of the tool's log, the run fails on exactly that line, and no
   rotation or translation diverges. (test, negative)
3. **Two computations, split where the library splits the report.**
   `vrm.computeRigDiagnostics` is `DiagnoseRig`, reads no clip, moves with no
   frame, and answers at the default time code. `vrm.computeRetargetDiagnostics`
   is that list, then what retargeting this sample reported. (test)
4. **A refusal nothing invalidates is posted once.** The rig's report refuses at
   the compute that arms a request. That is the compute a driver discards,
   because the retarget refuses there by design. At every frame after, only the
   missing value says so. The harness now keeps the arming compute's errors.
   (test)
5. **The eleventh boundary finding: diagnosing repeats the retarget.** The
   library reports a pose's diagnostics only while retargeting it, so the node
   runs the retarget a second time. That adds 23–25 µs a frame on the fixture
   rig and 50–60 µs on Seed-san, against a 4–6 µs floor for a cached second
   `Compute`. It is also why a driver's override of the retarget is not
   diagnosed. (measured, test)
6. **Two codes can never come back through exec.** `DUPLICATE_TARGET` is
   refused upstream by the map, where the tool reports it and bakes.
   `INVALID_ROOT_JOINT` is refused upstream by the statements, and the tool
   refuses it too. (test)
7. **It holds from the installed product.** The artifact-only exec smoke ran
   all five cases from a product installed outside the repository, the
   diagnostics comparison and its negative pair included, on this workstation.
   (measured)

## 1. What ran

Two computations joined `execVrm`, both on the applied `VrmHumanoidAPI`, both
answering `vrmRetarget::RetargetDiagnostics`. That type is P1-1's list of
`RetargetDiagnostic` values, each code and subject kept once and compared
exactly. It is registered as the bundle's seventh value type.

| Computation | Reads | Is |
| --- | --- | --- |
| `vrm.computeRigDiagnostics` | the map, the rig across `vrm:skeleton`, the four `vrm:retarget:*` statements | `DiagnoseRig(rig, map, options)` |
| `vrm.computeRetargetDiagnostics` | `vrm.computeRigDiagnostics`, and everything `vrm.humanoidRetarget` reads | the rig's list, then `PoseRetargeter::Retarget(pose, &list)` for the sample the retarget retargets |

The retarget's inputs are declared once, in a lambda both registrations call,
so the two cannot read two different clips. The retarget's refusals moved into
one reporter the three nodes share, and every refusal string the earlier suites
match came through unchanged (test: 20 exec and parity cases green after the
refactor, before anything new was asserted).

`exec_parity` takes a new `--tool-log`, the tool's own output while it wrote
the bake. It requests the diagnostics beside the joint transforms, as a second
request so each is timed alone, and merges the answers over the keys in order.
It reads the tool's lines of the form `motion_retarget: [CODE] …` and keeps the
ones whose code the library raises. Then it compares exec's list, formatted by
the same `FormatRetargetDiagnostic`, with those lines: whole lines, in order,
exactly. A code only a caller raises (a time range, an output path) is
reported beside the comparison and not counted, because it describes the tool's
own stage and file system. `--quiet` beside `--tool-log` is refused, since an
empty log would read as disagreement.

## 2. The answer: the lists agree

| Case | Exec | The tool | Agree |
| --- | --- | --- | --- |
| `recorded_fixture` | 0 | 0 | yes, and asserted empty so it is not counted as coverage |
| `recorded_root_motion`, each of four bakes | 0 | 0 | yes |
| `recorded_real_avatar` | 1: `UNBOUND_DRIVEN_BONE upperChest` | the same line | yes |
| `vrma_walk` | 14 `MISSING_REQUIRED_BONE`, `neck` through `rightHand` | the same 14, in the same order | yes |
| `generated_thirty_fps` | the same 14 (the same design rig) | the same 14 | yes |

(test)

This was the expected answer, for the parity report's reason: both sides call
one library with inputs that are bit-identical by construction. The tool calls
the clip overload, which reports `DiagnoseRig` and then every sample into one
list. Exec answers `DiagnoseRig` plus one sample at each key, and
`RetargetDiagnostics::Merge` over the keys rebuilds the clip overload's order
exactly. The seam suite asserts that equality on its own: a two-sample clip
whose second sample drives a bone the first does not merges to the clip
overload's list, and a one-sample answer equals a one-sample clip's (test).

**Seed-san is the row the parity report could not close.** There the tool said
"the clip drives bones the target rig does not map: upperChest", and exec posted
four executor warnings that could not tell a driven bone from an undriven one.
Both now report one line, and it is the same line.

**The root-motion variants still move translations and nothing else.** Held
against the default bake, exec under each statement diverges in translation
only, and the diagnostics agree. The fixture binds its hips, and a rig that
binds them has nothing to say about where the root lands (test).

## 3. What the harness can see

A diagnostics comparison that agrees everywhere is indistinguishable from one
that stopped comparing, so one difference was put in front of it and
committed (test, negative).

The driver takes Seed-san's bake and the tool's log, removes the one line
naming `subject=upperChest`, and runs the harness again. It has to fail, and it
does. It names exactly that line as exec's alone and nothing as the tool's
alone. No rotation or translation diverges and exec refuses nothing. So the two
comparisons are independent: a missing diagnostic moves no value,
and a value difference would not hide in the diagnostics.

## 4. A refusal nothing invalidates is posted once

The suite's first draft read the rig report's refusal errors at a frame, as
every earlier refusal case does, and found none (test, and the reason the
assertion is written the way it is).

A refusal is posted when its node computes. A node nothing invalidates computes
once. The rig's report reads nothing that moves with time, so it computes, and
refuses, at the compute that arms the request. That compute runs at the default
time code, where the retarget refuses by design, and every driver so far
discards its errors: the parity harness, `ArmAt` in every exec suite. At each
frame after that the rig report is a cached empty value, and no error says why.
The same holds for the humanoid map: a duplicate binding is posted by the map
and by the rig report at arming, and neither is posted again at a frame (test).

The sample's report is different. It moves with the frame, so it refuses again
at every one, for the retarget's reason, under its own name (test).

This is a driver-contract line rather than a defect. A driver has to keep the
arming compute's errors, because for a node that nothing invalidates they are
the only record of its refusal. The harness now does: it reports them as
`arming_errors` beside `refusal_reasons`, which are read at the first refused
key. It is filed with the driver contract in
[boundary consolidation](../../archive/motion-split/boundary-consolidation.md) §1.

## 5. Time and invalidation

| Edit | Rig report | Sample report |
| --- | --- | --- |
| a frame change | not reported | reported |
| a key of the clip (the head turned 45° at frame 24) | not reported | reported, and the value unchanged: the head is bound either way |
| a binding (the head unbound) | reported, and it gains `MISSING_REQUIRED_BONE head` | reported, and it gains that and `UNBOUND_DRIVEN_BONE head`: one bone, two codes |
| a root-motion statement (`ignore`) | reported, and the value unchanged: the hips are bound | reported |
| the rig's joint order (head stated before its parent) | reported, and it names `INVALID_HIERARCHY` on the head's token | reported |

(test)

The rig report answers where the sample's cannot. At the default time code, and
on a humanoid whose `vrm:retarget:sourceSkeleton` has been removed, it answers
the same list as at a frame. The sample report is refused for the retarget's
reason (test).

One property of exec's invalidation cost a red run and is now in the suite's
comment: **an edit is reported only for a value that is cached.** An edit that
lands on a report nobody recomputed since the previous edit is reported to
nothing, so the suite computes between edits. That fits the filtering report's
"a request is armed by its first `Compute`", one level down (test).

## 6. The eleventh boundary finding: diagnosing repeats the retarget

`PoseRetargeter` has one way to report a pose's diagnostics, and it is to
retarget the pose: `Retarget(pose, &diagnostics)`. `DiagnoseRig` is the rig's
half on its own. The pose's half, which reports a bone the pose drives that the
rig does not bind, has no call of its own. A computation answers one value, so
the node that answers the diagnostics cannot share the retarget node's work.
It repeats the retarget, correction included.

The seam test pins that repeating it costs the pose nothing: the retarget
answers the same bits with a list to fill as without one (test). What it costs
in time, with the joint transforms and the diagnostics asked for as two
requests at each of 853 keys (measured, three runs; the floor, three more):

| Rig | Values, per frame | Diagnostics, per frame | A cached second `Compute` |
| --- | --- | --- | --- |
| fixture rig, 23 joints | 68–70 µs | 23–25 µs | 4–5 µs |
| Seed-san, 128 joints | 128–141 µs | 50–60 µs | 5–6 µs |

The floor was measured by pointing the second request at
`vrm.computeRigDiagnostics`, which is cached at every key, in a throwaway build
of the harness. Everything above it is the second retarget and the copies of
its inputs.

**It has a behavioural cost as well.** The node retargets the *stage's* sample,
not the retarget node's answer. So a driver's override of `vrm.humanoidRetarget`
reaches the joint transforms and does not reach the diagnostics, which still
describe the pose the stage states (test). A driver's override of the *pose*,
`vrm.computeBoundPose`, does reach them: a live pose driving `leftLowerArm` is
reported like the clip's own, which is the case the library's per-sample report
exists for (test).

The ask ([boundary consolidation](../../archive/motion-split/boundary-consolidation.md) §1)
is a per-pose counterpart to `DiagnoseRig`: the rule `Retarget` applies, callable
without retargeting, and called by `Retarget` itself, so it has one
implementation. This is the eighth finding's kind, the correction recomputed
per frame, one method over.

## 7. What still cannot agree, and why that is not a row

| Code | Tool | Exec | Why |
| --- | --- | --- | --- |
| `DUPLICATE_TARGET` | reports it, the later bone winning, and bakes | never: `vrm.computeHumanoidMap` refuses two bones on one joint, so both reports refuse | the parity table's row 3, now a code rather than a sentence (test) |
| `INVALID_ROOT_JOINT` | never: `--root-joint` naming no joint exits before the retarget | never: the statement is refused as `UnknownRootJoint` | unreachable on both sides; the library raises it for a caller that builds options by hand (test) |
| `INVALID_HIERARCHY` | reports it | reports it | reachable on both; no producer authors a skeleton out of order, so no parity case carries it (test, exec side) |
| `TIME_RANGE_DERIVED`, `OUTPUT_COLLIDES_WITH_INPUT` | raises them | never | caller-raised: the tool's stage and file system. The harness reports them beside the comparison (read) |
| `NON_UNIT_SCALE` | never | never | frozen for P1-2, raised by nothing yet (read) |

None of these is a disagreement the harness can observe. Each is a code one side
cannot reach, for a reason stated in the plan's table or in P1-1.

## 8. What this changes in the plan

1. **P0-6's diagnostics row is closed.** Offline and exec agree on values
   exactly and on diagnostics line for line, on the same recorded input and
   from the installed product. What stays open of P0-6 is the rows no producer
   reaches (the parity report §9, item 3), each asserted on the exec side and
   read on the tool's.
2. **P1-1's "exec answering the retarget codes" is done.** What P1-1 still owes
   is the CLI exit codes and the `VRM_OPENEXEC_*` table.
3. **The driver contract gains a line**: keep the arming compute's errors (§4).
4. **An eleventh row in boundary consolidation §1** (§6).

## 9. What this did not do

- It ran on Windows only. The cases are in the root workspace suite and in
  `release.yml`'s artifact-only smoke, so Linux and macOS run them next.
- It did not compare expression or look-at diagnostics. Those still report in
  prose (`ExpressionDiagnostics`, `LookAtDiagnostics`), and exec computes
  neither.
- It did not change `motion_retarget` or `vrmRetarget`. The tool's output was
  already the frozen format. The library's missing per-pose call is an ask
  (§6), not a change here.
- It did not add a `VRM_OPENEXEC_*` code. Those are raised by a driver around a
  request, and this harness still reports refusals as text.
