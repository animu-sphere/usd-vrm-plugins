# OpenUSD 26.08 OpenExec, a node that samples what a driver hands it

- Date: 2026-09-12
- Version exercised: **OpenUSD 26.08** — the pinned `cy2026`/`usd` runtime, the
  same artifact [the migration audit](26.08-openexec-migration.md) read and the
  [mechanism](26.08-openexec-mechanism.md), [sampling](26.08-openexec-sampling.md),
  [filtering](26.08-openexec-filtering.md) and
  [root-motion](26.08-openexec-root-motion.md) reports ran.
- Occasion: [the OpenExec plan](../../roadmap/openexec-foundation.md) §6, P0-4 —
  `motion.interpolatePose`, the fourth real computation. It is the first node
  whose **input** a driver hands in, rather than whose previous answer a driver
  feeds back: a timestamped history of poses, the "immutable snapshot" motion
  policy §11.4 puts between a live source's buffer and every computation. Every
  earlier node read the clip, or the graph's own last answer; this one reads
  something neither the scene nor the graph contains.
- Method: **run, not read.** Two vehicles, both committed: the
  `execMotion_interpolate` CTest target
  ([plugins/execMotion/tests/](../../../plugins/execMotion/tests/)), which drives
  the shipped bundle through `PXR_PLUGINPATH_NAME` without linking it, over
  `sampled_clip.usda` and `unrated_clip.usda`; and `execMotion_pose`, which holds
  the seam with no stage. Every claim marked **(test)** is asserted in one of
  the two. §4's two override cases were first run as **(probe)** prints, to
  read what 26.08 does before asserting it, and are asserted now. §7 is marked
  **(negative)**: measured by deleting a line, rebuilding and watching the suite
  go red — as was the seam's one refusal, whose removal turns both suites red.
- What this does **not** supersede: any earlier report. It answers one item the
  root-motion report left open ([§8](26.08-openexec-root-motion.md#8-what-this-did-not-do):
  whether a value key of a type other than a pose overrides the same way) and
  adds what none of them could reach: a second override key, an override of the
  wrong type, and a result type with an absent state of its own.

## TL;DR

1. **A snapshot enters the graph as an override on a key whose type is a whole
   history.** `motion.poseHistory` answers a `motion::HumanoidAnimation`, a
   driver substitutes its buffered samples for it, and the substitute reaches
   the dependent and is visible as the key's own value — the same behaviour the
   filtering report measured for a pose-typed key, now for a key whose value is a
   `std::vector` of poses. (test)
2. **Two overrides of two keys in one call each reach only their own
   dependents.** `motion.priorPose` and `motion.poseHistory`, substituted
   together: the filter steps from the first, the history is sampled from the
   second, and neither leaks into the other's dependents. (test)
3. **An override of the wrong type is dropped, not refused — and so is an empty
   one.** 26.08 posts a coding error naming the key and both types and then
   computes the key's **ordinary value**, so every dependent answers as though
   nobody had overridden anything. An empty `VtValue` is a value of type `void`
   and takes the same path: a driver cannot push an *absence* into a key. (test)
4. **The first result in the bundle with an absent state of its own.** The node
   answers `motion::PoseSampleResult`, whose `Unavailable` says "the history
   holds nothing" as a value. So an empty history is an **answer**, not a
   refusal — the bundle's refusal rule applied rather than bent: refuse only
   where an answer would be indistinguishable from a measurement. (test)
5. **The node is a wrapper, cleanly — and it returns the library's type whole,
   because a pose alone would lie.** `motion::ClipSource::Sample` stamps its
   answer at the requested instant whether the history reached it or not, so a
   held pose and a sampled one carry the same timestamp; the status and the lag
   are the only fields that tell them apart. Registering the type needed an
   `operator==` on `PoseSampleResult` — the v0.6.0 ask, answered for the first
   time in `motionRuntime` rather than `motionCore`. (test)
6. **The fourth boundary finding, and the first where the wrapper works and
   costs.** The status-carrying sampler exists only as a method on a *source
   object* that owns its animation, so every evaluation copies the history into
   one; the free function beneath it, `motion::SampleAnimation`, returns the pose
   without the status. The time-order precondition that function's binary search
   relies on is stated and checked nowhere (§6).
7. **An undeclared input reaches the node's own refusal, and nothing else.**
   Deleting the history's `.Inputs()` declaration: the bundle compiles, the
   request is valid, the callback runs with a null pointer, and the node's
   refusal is the only report. (negative)

## 1. What the node answers

The pose a history states at the instant the system is evaluating, as
`motion::ClipSource` answers it, over the history `motion.poseHistory` holds:

| History | Instant | Result |
| --- | --- | --- |
| not overridden — the clip's own pose, as a history of one | its own | `Sampled`, that pose, lag 0 — so un-overridden the node **is** `motion.sampleAnimation` |
| two samples bracketing the instant | between them | `Sampled`, `motion::LerpPose` between them, stamped at the instant, lag = instant − newest (negative: the source is ahead) |
| samples ending before the instant | past the newest | `Held`, the newest sample's values, **stamped at the instant**, lag positive |
| samples starting after the instant | before the oldest | `Held`, the oldest sample's values |
| empty | any | `Unavailable`, no pose, lag 0 — an answer (§3) |
| timestamps decreasing somewhere | any | **no value**, and a posted error naming the computation |
| any | none — the clip states no rate | **no value**: the sampler refused, and so does this node (§5) |

A bone one bracketing sample reports and the other does not is **held** at the
value it was reported with, never faded — the library's `LerpPose` rule,
arriving through the wrapper unchanged. **(test)**

## 2. A snapshot is an override, and a driver now holds two things

`motion.poseHistory` is the second value key in the bundle whose purpose is to
be replaced, and it is a different kind of thing from the first:

| Key | What a driver puts there | What it is |
| --- | --- | --- |
| `motion.priorPose` | the previous frame's answer | the graph's own output, **fed back** — the state a recurrence needs ([filtering report](26.08-openexec-filtering.md) §5) |
| `motion.poseHistory` | its buffer's samples | the source's input, **handed in** — the snapshot a computation evaluates instead of reaching for a buffer (motion policy §11.4) |

Both are overrides because an override is the one channel through which a value
the scene does not state can reach a computation. The alternatives are the ones
the purity rule already refused for the filter: a buffer held in the callback is
state invalidation cannot see, and an authored history would put a live
source's samples into the scene.

**The ordinary value is the clip's own pose as a history of one**, spanning its
own instant. Sampled at that instant it answers that pose, so an un-overridden
node passes the sampler through exactly as an un-overridden `motion.filterPose`
does — special-cased in neither. **(test)**

`motion::HumanoidAnimation` registered with no work: it has carried an exact
`operator==` since v0.6.0, and its `std::vector` of poses is not a `VtArray`, so
the registry's `!VtIsArray` assertion does not apply. An override holding one
reaches the key and its dependent exactly as a pose-typed override does, which
closes the root-motion report's open question for a second registered type.
**(test)**

**Two overrides, one call.** A request over `motion.filterPose`,
`motion.interpolatePose` and both override keys, handed a prior pose and a
history together in one `ComputeWithOverrides`: each key reports its own
substitute, the filtered hips sit strictly between the prior's origin and the
clip's position and nowhere near the history's, and the sampled answer is the
history's. **(test)** So the driver contract the root-motion report shortened to
"one previous answer per prim" gains a line of a different kind: **one previous
answer and one snapshot per prim** — the first for the nodes that recur, the
second for the node that samples.

## 3. An empty history is an answer

Every refusal in this bundle sets **no value**, because every earlier result
type had a legitimate answer that a default-constructed value would collide
with ([root-motion report §6](26.08-openexec-root-motion.md#6-a-refusal-has-to-be-an-empty-value)).
`motion::PoseSampleResult` is the first type here where the library already
spelled "nothing" as a value: `Unavailable`, carrying no pose.

So a history holding no samples is not refused. The node answers `Unavailable`,
posts no error, and a consumer can tell it from every sampled or held answer by
the status alone. **(test)** That is the absent-input rule doing what it says
rather than an exception to it: refuse where an answer would be
indistinguishable from a measurement, and an `Unavailable` result is
distinguishable by construction.

The one refusal the node has is a history whose timestamps **decrease**
somewhere. There the library would answer — its binary search would bracket the
instant with two samples that do not surround it — and the answer would be a
pose nobody measured. **Repeated** timestamps are not refused: the library's
search answers them deterministically, and `PoseBuffer::Push`'s
strictly-increasing rule is about filling a buffer, not about what can be
sampled. A check stricter than the library's own need would be a policy of the
bundle's. **(test)**

The distinction the two answers draw is worth stating once: `Unavailable` is
*the answer is nothing*; a refusal is *there is no answer to this input*. A
default-constructed `PoseSampleResult` is `Unavailable`, so a refusal still has
to be an empty value, and is.

## 4. A wrongly typed override is dropped, not refused

`ExecUsdSystem::ComputeWithOverrides` documents that "an override value … must
have the same type as the computed value" and that "otherwise, a coding error is
emitted". It does not say what the dependents then see. Measured, first as a
**(probe)** and now asserted:

| Override on `motion.poseHistory` | Posted | The key's value | The node's answer |
| --- | --- | --- | --- |
| a `motion::HumanoidPose` | `TF_DIAGNOSTIC_CODING_ERROR_TYPE`: *Expected override of value key '/Clip [motion.poseHistory]' to have type 'motion::HumanoidAnimation'; got 'motion::HumanoidPose'* | its **ordinary** value — the clip's pose as a history of one | `Sampled`, the clip's pose |
| an empty `VtValue` | the same error, with *got 'void'* | its ordinary value | `Sampled`, the clip's pose |

**(test)** Two consequences, and neither is the bundle's to fix:

- **A driver that got the type wrong gets a plausible answer.** It is the shape
  the bundle refuses to produce itself — a value no consumer can tell from the
  one it asked for — and the bundle cannot prevent it here, because the
  substitution is rejected before any callback runs. The coding error is the
  only report, so a driver has to treat a dirty `TfErrorMark` around
  `ComputeWithOverrides` as a failed frame. That is the second driver-contract
  line this node adds.
- **An override cannot carry an absence.** The one way a dependent is handed no
  value is that the key's own callback set none. So the node's defensive check
  for a missing history is unreachable through overrides — and reachable the
  other way, §7.

## 5. Where the instant comes from

The node samples the history at `motion.sampleAnimation`'s timestamp — the
seconds that node already converted the evaluated frame into — rather than
reading `computeTime` and `motion:timeCodesPerSecond` a second time. The
conversion keeps one home, the node declares no `computeTime` (and is reported
when the frame moves all the same, through both of its inputs), and a clip that
states no rate reaches it by **propagation**: the sampler refuses, the history
forwards the absence without a word of its own, and this node refuses naming
itself. **(test)**

A driver's history does **not** rescue that clip. With no rate there is no
instant, whatever the history holds, and the node refuses with a history
supplied exactly as it does without one. **(test)**

## 6. The wrapper, and what it costs

`motion.interpolatePose` is the first node in the bundle that is **one library
call and nothing else**: the history is checked for order and handed to a
`motion::ClipSource` constructed on the spot, which is asked `Sample(instant)`
once and destroyed. `motion.filterPose` composes two calls, a seed and a step,
to stand in for a missing signature; `motion.extractRootMotion` has no call to
make at all. This one found the call it wanted. The local source is the shape
`motion.filterPose` gives its `PoseFilter`, and pure for the same reason — it
sees exactly the value it was handed.

**The finding is what the shape costs.** The status-carrying answer —
`IMotionSource`'s, and the one the motion contract says a caller needs — exists
only as a method on a source object, and `ClipSource` *owns* the animation it
serves. So every evaluation copies the whole history into a local source to ask
one question. The free function beneath it, `motion::SampleAnimation`, takes the
animation by reference and would cost nothing — and returns the pose without
the status, which §1's hold row shows a consumer cannot do without.

Two smaller facts sit beside it:

- **The time-order precondition is nobody's.** `SampleAnimation` binary-searches
  the samples and so needs them sorted; neither its header nor
  `HumanoidAnimation`'s says so, and nothing checks it. The bundle's one refusal
  (§3) is that precondition, enforced at the one boundary where a driver's value
  enters.
- **The bracket-and-hold search is written twice**, once in
  `PoseBuffer::Sample` and once in `SampleAnimation`, whose header says it
  follows "the same hold-at-the-edges rule". The two agree today.

The ask for [boundary consolidation](../../roadmap/boundary-consolidation.md):
a free `SampleClip(const HumanoidAnimation&, double) -> PoseSampleResult` that
`ClipSource::Sample` calls, with the ordering precondition stated on it — so the
status-carrying answer is reachable without a copy, and the rule has one
implementation.

**What this does not claim.** It is not a defect in `ClipSource`: a source that
owns its clip is right to, for the playback it was written for. The finding is
that the answer has no home outside it.

## 7. An undeclared input reaches the node's own refusal (negative)

The history input declares as `Computation<motion::HumanoidAnimation>(...)` and
is read with `GetInputValuePtr`. Deleting the declaration and leaving the read:
the bundle compiles, `BuildRequest` returns a valid request, the callback runs,
the pointer is **null** — and the node's *"no history came back from
motion.poseHistory"* refusal is the only thing anywhere that reports it. The
suite went red on the first assertion that a value came back.

The root-motion report measured the same property on an attribute input
([§3](26.08-openexec-root-motion.md#3-an-undeclared-input-is-silent-negative)),
where the missing declaration fell into a *default* and was caught by the one
test that checked the policy arrived. Here it falls into a *refusal*, which is
the better failure: a node that refuses on a null it cannot otherwise explain
turns a missing declaration into a visible error rather than a quiet default.
With §4 it also settles what the check is for — not an override, which cannot
reach it, but a declaration nobody made.

## 8. What this changes in the plan

1. **P0-4 has one node left.** `motion.blendPoses`, the one that wants two
   *poses from two places* — fan-in — which is where §5.1 of the migration audit
   has always said the connection rule would bite.
2. **The driver contract gains two lines**, and P0-6's harness is still the
   first client that needs them written down: hold one previous answer *and one
   snapshot* per prim (§2), and treat a coding error around
   `ComputeWithOverrides` as a failed frame, because a wrongly typed override
   answers plausibly (§4).
3. **A fourth boundary finding**, the first where the wrapper works and the
   finding is its cost: `SampleClip(animation, t) -> PoseSampleResult` as a free
   function, and the ordering precondition stated on it (§6).
4. **P0-6 gains an instrument it did not have.** The sampling report left parity
   with two samplers to compare — USD's interpolation between a clip's keys, and
   `motion::SampleAnimation`'s — and no way to run the second inside exec. A
   driver that supplies a clip's own key poses as the history now evaluates the
   library's sampler in the same graph as USD's, at the same instant. That is an
   expectation about the harness, not a measurement here.
5. **`PoseSampleResult` joins the comparison contract.** It has an exact
   `operator==` for the reason `motionCore`'s aggregates do, and no
   `NearlyEqual`: nothing yet asks whether two sample results are the same
   motion ([MOTION_CONTRACT.md](../../design/MOTION_CONTRACT.md#comparison-semantics-v060)).

## 9. What this did not do

- It did not **extrapolate**. `ClipSource` never answers `Extrapolated`; a
  driver wanting a live session's latency-hiding past the newest sample gets a
  hold here, and the lag that says how stale it is. `LiveCaptureSource` does
  extrapolate, and is a capture session rather than an answer to one question —
  the same shape as the root-motion report's finding, not measured again.
- It did not measure the **copy's cost**. §6 is a statement about what the call
  shape forces, not a timing; the performance baseline is P1-3 of the plan's
  `ExecIr` track.
- It did not sample an overridden history at the **default time code**, where
  the instant is 0 s. The status would say `Held` for any history starting
  later, but that is read off the library, not run.
- It did not apply a **start offset**. `ClipSource::SetStartOffset` shifts a clip
  along the consumer's clock, and the node leaves it at the library's own zero;
  nothing a clip states selects one, and a driver's samples are already on the
  consumer's clock.
- It did not test fan-in, `Relationship().TargetedObjects<T>()`, or two
  connections into one input. `blendPoses` is still where those land.
- It did not run against a **packaged** bundle. Like the five suites before it,
  `execMotion_interpolate` loads a built tree; the artifact-only run is P0-3's.
