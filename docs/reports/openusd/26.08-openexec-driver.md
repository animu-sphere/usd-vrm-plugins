# OpenUSD 26.08 OpenExec, the driver contract and the `VRM_OPENEXEC_*` codes

- Date: 2026-09-14
- Version exercised: **OpenUSD 26.08**, the pinned `cy2026`/`usd` runtime. Like
  [the diagnostics report](26.08-openexec-diagnostics.md), this run used a local
  build of that release adopted as the runtime, not the published GHCR leaf.
- Occasion: [the OpenExec plan](../../roadmap/openexec-foundation.md) §6, where
  two items were waiting on the same thing. P0-4 owed a **written driver
  contract**, whose rules six reports had found one at a time. P1-1 owed the
  **`VRM_OPENEXEC_*` table**, which the plan could not freeze until something
  raised the codes. This report covers the driver that closes both.
- Method: **run.** **(test)** is asserted by `exec_driver_contract` (CTest
  `workspace_exec_driver`) or by the five `workspace_exec_parity_*` cases.
  **(negative)** is a mutation run: one check of the driver disabled, rebuilt,
  and the suite required to fail. It is not committed. **(measured)** is a
  throwaway run, not committed. **(read)** is read off the 26.08 source and not
  run.
- What this does **not** supersede: any earlier report. It collects the driver
  lines from the filtering, root-motion, interpolation, blending, retarget and
  diagnostics reports into one contract, adds two lines of its own (§3, §4),
  and replaces none of their text.

## TL;DR

1. **The driver contract is written, and it is code.** Ten rules in
   [MOTION_CONTRACT.md](../../design/MOTION_CONTRACT.md#openexec-driver-contract-after-v080).
   `tests/parity/ExecDriver` implements them, and the parity harness now drives
   exec through it. (test)
2. **The three codes are raised, each by the failure it names and held to its
   key.** In a request where a computation nobody registers sits beside one
   that answers, the driver names the missing key and still answers the other.
   (test)
3. **An override of a key nothing compiled is skipped without a word, even a
   mistyped one.** Exec reaches its type check only for a compiled output. So
   the driver requests every key it overrides. (read, test)
4. **A request whose every key expired reports itself valid.** Exec discards
   such a request, and discarding clears the bits `IsValid()` reads. This is
   the mechanism report's `InvalidateAll` shape, reached by a resync. A request
   that still has a live key does report itself invalid. (read, test)
5. **The codes never come from exec's text.** They come from four checks: a
   runtime error or a coding error, a path lookup under exec's own rule, the
   type each key is declared with, and one-key probes that run only after a
   compute posted a coding error. Exec's text travels in the detail. (test)
6. **The driver adds no measurable cost per frame.** 59–66 µs on the fixture rig
   and 126–132 µs on Seed-san, inside the ranges the parity and diagnostics
   reports measured without it. (measured)
7. **The harness now names a missing bundle.** With `execVrm` out of the
   session, the run fails with two `VRM_OPENEXEC_COMPUTATION_UNAVAILABLE`
   lines. Before, it showed empty values and free-text coding errors. (measured)
8. **Every check is load-bearing, after one fix.** With any one of thirteen
   checks disabled, the suite goes red, and twelve of them fail at that
   check's own assertion. In the first draft one mutation passed, because the
   assertion for one route matched a word that both routes' details shared.
   (negative)

## 1. What ran

`ExecDriver` holds a stage, one `ExecUsdSystem` and the requests declared on
it. A **key** is a prim computation by path, with the type its computation
answers. The type is a `std::type_info` because a bundle's `TfType` does not
exist until the bundle has loaded, and a key is declared before the first
compute loads it. An **override** is a key and a value. A **frame** is one
evaluation's answer:

| Field | Holds |
| --- | --- |
| `values` | one per requested key; an empty value is no answer |
| `refusals` | what computations posted as runtime errors, the arming compute's included |
| `errors` | every other error exec posted that no code accounts for, verbatim; a frame with one has failed |
| `diagnostics` | the `VRM_OPENEXEC_*` codes raised about this frame, a standing unavailable key included |

`Add` declares a request and arms it. `Evaluate` takes a frame through the rules
in the order a frame meets them:

1. A key an override names joins the request (rule 7).
2. Each provider is looked up by path. A change since the build rebuilds the
   request. A request that reports itself invalid is rebuilt as
   `INVALIDATED` (rule 10), whether or not it was being rebuilt anyway.
3. `ChangeTime`, before anything computes (rule 4).
4. Each override is checked against its declared type (rule 6). A frame
   refused here computes nothing and arms nothing.
5. The request is computed, overrides and all. When it has to be built, that
   compute is the arm, so its refusals are kept and they are this frame's own
   (rules 2 and 3). An override of a key the build found unavailable fails the
   frame.
6. A coding error rebuilds the request once, which tells `INVALIDATED` from a
   key that is now unavailable. The driver then probes each override alone for
   `TYPE_MISMATCH` (rules 8 and 10).
7. Each answer is checked against its declared type.

*Corrected by review before merge.* The first version armed a rebuilt
request with a plain compute and then computed the frame with its overrides.
So a frame that answered because of an override also carried the refusals of
the graph without it. It also judged a key on the pseudo-root (`/`, where the
stage's own computations live) unavailable, and it looked for an expiry only
when the request was not being rebuilt for another reason. Each of the three
has a test now.

`exec_parity` now arms its two requests through `Add` and keeps both arming
frames. It evaluates each key through `Evaluate` and reports the driver's lines
as `openexec_diagnostics`, and an error among them fails the run.
`exec_driver_contract` runs against execMotion alone, over the filter fixture,
in these sections:

| Section | What it holds |
| --- | --- |
| the table | three strings, their round trip, severities, the formatted line, "once per code and subject" |
| arming | the history sampler's refusal at the default time code, kept by the arming frame, which does not fail |
| a computation nobody registers | `COMPUTATION_UNAVAILABLE` on that key alone, with exec's "Failed to find computation" in the detail; the other key answers, and the key stays reported on every frame |
| a provider that is not there | `COMPUTATION_UNAVAILABLE` from the path lookup, and nothing handed to exec |
| a provider that goes and comes back | unavailable while inactive, silent when back, `INVALIDATED` through `IsValid()` when toggled between two frames; then the one-key case of §4, raw and through the driver |
| a mistyped override | `TYPE_MISMATCH` before the call, for a wrong type and for an empty value; then the same override handed to exec directly, which answers anyway |
| an override exec rejects | a wrong **declaration**: exec's check fires, the driver names that key, and the other override is not named |
| an answer of another type | `TYPE_MISMATCH`, value withheld |
| an override nothing compiled | §3, raw and through the driver |
| a request exec stopped answering | `InvalidateAll` behind the driver's back; `INVALIDATED` on both keys, the answer equal to the one before, so the instant was named again |
| a frame reports its own refusals | a clip that states no rate refuses un-overridden; with its sample handed in, the frame answers and carries no refusal |
| a stage computation | `computeTime` on the pseudo-root answers the evaluated time code, and nothing is reported unavailable |
| an override reaches its dependent | the positive control: a previous pose steps the filter, and the sampler beside it is unchanged |

## 2. The three codes

| Code | Produced in the suite by | Held to |
| --- | --- | --- |
| `COMPUTATION_UNAVAILABLE` | `motion.noSuchComputation` beside `motion.sampleAnimation`; a key on `/NoSuchPrim`; a deactivated prim | the key: exactly one diagnostic, and the key beside it answering (test) |
| `TYPE_MISMATCH` | a `HumanoidAnimation` handed to `motion.priorPose`; an empty value; `motion.priorPose` declared as a `HumanoidAnimation`; `motion.sampleAnimation` declared as one | the key, and never the correct override beside it (test) |
| `INVALIDATED` | `InvalidateAll`; a prim toggled between two frames, with two keys and with one | each key of the request, recoverable, with the rebuilt request's answer equal to the old one (test) |

Two severities and one recovery: the two errors end a frame's answer, and
`INVALIDATED` is a warning the driver recovered from. It is still reported,
because a caller holding requests of its own is holding one that exec has
stopped answering.

## 3. An override of a key nothing compiled is skipped, mistyped or not

`ExecSystem::_ComputeWithOverrides` resolves each override to an output key and
looks for the compiled output (read):

> Find the compiled output for the output key. If it does not exist, then we
> silently skip this override.

The type check is below that line. So on a system that has compiled the
sampler and nothing that reads `motion.priorPose`, a `HumanoidAnimation` handed
to `motion.priorPose` posts nothing and changes nothing. **(test)** The
interpolation report measured the loud half of this: a mistyped override of a
key a request reads is dropped with a coding error. This is the quiet half.

Through the driver, the key joins the request the first time an override names
it. That compiles the key, and it puts the key through the same availability
probe as any requested key. With `motion.priorPose` declared as a
`HumanoidAnimation` and handed one, the driver's own check passes, exec's check
fires, and the driver names the key. **(test)** Joining costs one rebuild the
first time a key is named. It does not make the override reach anything that
does not depend on the key, which is still the caller's to get right (rule 7).

The one uncompiled case exec does report is a key whose computation is not
defined for its provider: "Cannot override value for value key …, because the
computation was not defined for the provider." (read). A joined key reaches the
driver's probe first, so that case arrives as `COMPUTATION_UNAVAILABLE` before
exec is asked.

## 4. A request whose every key expired reports itself valid

`ExecUsdRequest::IsValid()` is `_impl && !_impl->GetExpiredIndices().IsAnySet()`.
When a resync makes a key's provider invalid, exec sets that key's bit. When
every bit is set it discards the request, and `Discard()` ends with
`_expired.Resize(0)`, so no bit is set any more (read). **(test)** A one-key
request on `/Other`, with `/Other` deactivated, reports itself valid. A two-key
request on `/Clip` and `/Other`, with only `/Other` toggled, reports itself
invalid, and the driver rebuilds it before computing.

**The first probe found this, not the source.** The suite's first version put
one key on `/Clip` and toggled `/Clip`. `IsValid()` read true even straight
after the deactivation. So the rebuild came from the other route, after a
compute had answered nothing and posted "Failed verification". The mechanism
report found that shape for `InvalidateAll`. This is the same shape, reached by
a scene edit. Rule 10 therefore names both, and the driver has two routes into
`INVALIDATED`, each with a detail of its own.

That second point cost a false green, which the mutation run found (§7). The
two details first shared the word "resynced". The assertion for the `IsValid()`
route looked for that word, so it also passed when that route was disabled.
Each route's detail now has a phrase the other lacks, and the suite asserts
that phrase.

## 5. Classifying without reading the text

26.08 gives a caller one structured fact about each error: its diagnostic type.
Every refusal in both bundles is a `TF_RUNTIME_ERROR` beside an empty output.
Exec's complaints about a request are coding errors, and a failed `TF_VERIFY`
is posted as a coding error too (read: `Tf_FailedVerifyHelper`). The driver
splits on that fact and on nothing else in the error. Everything past the split
is a question the driver asks itself:

| After | The driver asks | And concludes |
| --- | --- | --- |
| any build | is there a prim at the path, valid, active, loaded and defined? (exec's own `_IsValidVisitor` rule) | no: `COMPUTATION_UNAVAILABLE`, and the key is not handed to exec |
| an arm that posted a coding error | computed alone, does this key, which answered nothing, post one too? | yes: `COMPUTATION_UNAVAILABLE`, and the request is built again without it |
| a compute that posted a coding error | rebuilt, does the request answer cleanly where it answered nothing, with no new unavailable key? | yes: `INVALIDATED` |
| a coding error still standing, with overrides | handed alone, does this override post one? | yes: `TYPE_MISMATCH` |

The probes run only after a coding error, so a clean frame pays for none of
them. Exec's text is kept for a person. With `execVrm` out of the session, the
detail of each missing key reads `Failed to find computation
'vrm.computeJointLocalTransforms' on provider '/Parity/Humanoid'; Failed
verification: ' _resultOutputs.size() == 1 ' -- Expected exactly one output for
value key …; got '0'`. That is two coding errors for one missing key, and the
second is a `TF_VERIFY` that only a probe can attribute. (measured)

## 6. What it costs

Three runs of each case through the driver, against the figures the parity and
diagnostics reports measured without one, on the same workstation:

| Case | Values, per frame | Before | Diagnostics, per frame | Before |
| --- | --- | --- | --- | --- |
| fixture rig, 23 joints | 59–66 µs | 60–72 µs | 22–24 µs | 23–25 µs |
| Seed-san, 128 joints | 126–132 µs | 128–141 µs | 51–53 µs | 50–60 µs |

The driver adds a path lookup per key, an error mark and a type comparison per
answer. That is below the run-to-run spread. (measured)

## 7. Every check turns the suite red

Each row disables one check in `ExecDriver.cpp`, rebuilds, and requires
`workspace_exec_driver` to fail. The build output was required to show the
driver recompiled, so that no row passed on a stale binary. (negative)

| Check disabled | Fails at |
| --- | --- |
| an override held to its declared type | a mistyped override: the empty value is not named as one |
| override keys joining the request | an override nothing compiled |
| the one-key probe at arming | a computation nobody registers |
| rebuilding a request that answered nothing | the one-key resync, through the driver |
| `IsValid()` before computing | the two-key resync's detail |
| each override probed alone | an override exec rejects |
| each answer held to its declared type | an answer of another type |
| keeping the arm's refusals | arming |
| `ChangeTime` before computing | arming: the first frame at 50 answers nothing |
| the path lookup | a provider that is not there |
| the expiry looked for when the request is rebuilt anyway | the resync in a frame that joins a key |
| arming with the frame's own overrides | an override exec rejects: the frame computed without it and saw nothing to reject |
| the pseudo-root as a provider | a stage computation |

With the override pre-check disabled, the mistyped `HumanoidAnimation` is still
named, by the override probe, because exec rejects it. Only the empty value,
whose detail is the pre-check's own, turns the suite red. The two checks cover
the same failure one after the other.

## 8. What this changes in the plan

1. **P0-4's driver contract is written.** What remains of P0-4 is the producer
   half of the rate and the two policies (BND-0), and a decision on what a
   one-joint clip's fallback-filled root means.
2. **P1-1 is complete.** The `VRM_RETARGET_*` codes and the exit codes were
   frozen already, and the `VRM_OPENEXEC_*` table is now frozen and raised.
   `NON_UNIT_SCALE` waits for P1-2, which decides what raises it.
3. **Boundary consolidation's driver-contract row has its answer**: the
   contract, in the motion contract, followed by the harness's driver.
4. **The `ExecIr` track's evaluation client (its P0-6) starts from this
   driver.** That is where batch requests, invalidation callbacks and a result
   dump belong, and where `exec_driver` becomes a workspace identity.

## 9. What this did not do

- It ran on Windows only. `workspace_exec_driver` is in the root suite, so
  Linux and macOS run it next. The artifact-only exec smoke passed from the
  installed product with the harness on the driver, negative case included.
  That product was packaged at the previous change, and this change alters the
  harness and not the product.
- It declares no attribute keys. Every value the harness asks for is a prim
  computation, and the display route's `computeValue` is driven by
  `usdExecImaging`, not by a driver.
- It registers no invalidation callbacks. A driver that redraws on
  invalidation is the evaluation client's.
- It does not check rule 9. A driver cannot know the instant the other sources
  of a blend were sampled at. The blend refuses a pose stamped elsewhere itself
  ([blending report §5](26.08-openexec-blending.md)).
- It did not change either bundle or `motion_retarget`. Exit code 6 stays
  reserved, since the tool evaluates nothing through OpenExec.
