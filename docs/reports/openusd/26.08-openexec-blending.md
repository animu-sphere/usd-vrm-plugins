# OpenUSD 26.08 OpenExec, a node that reads poses from several prims

- Date: 2026-09-13
- Version exercised: **OpenUSD 26.08**, the pinned `cy2026`/`usd` runtime. This
  is the same release [the migration audit](26.08-openexec-migration.md) read
  and the [mechanism](26.08-openexec-mechanism.md),
  [sampling](26.08-openexec-sampling.md), [filtering](26.08-openexec-filtering.md),
  [root-motion](26.08-openexec-root-motion.md) and
  [interpolation](26.08-openexec-interpolation.md) reports ran. This run used a
  local build of that release adopted as the runtime, not the published GHCR
  leaf.
- Occasion: [the OpenExec plan](../../roadmap/openexec-foundation.md) §6, P0-4.
  `motion.blendPoses` is the fifth and last real computation. It is the first
  node that reads poses from **more than one prim**. The plan scheduled it last
  because this is where a fan-in surprise would show up
  ([§5](../../roadmap/openexec-foundation.md#5-2608-features-this-plan-leans-on),
  connection dataflow).
- Method: **read, then run.** Two source files predicted two silent behaviours
  before any code was written: `pxr/exec/exec/inputResolver.cpp` at `v26.08`
  (`_TraverseToRelationshipTargetedObjects`) and `pxr/exec/vdf/readIterator.h`
  (`_AdvanceConnection`). Two committed suites then measured them. The first is
  the `execMotion_blend` CTest target
  ([plugins/execMotion/tests/](../../../plugins/execMotion/tests/)). It drives
  the shipped bundle through `PXR_PLUGINPATH_NAME` without linking it, over
  `blended_clips.usda`. The second is `execMotion_pose`, which tests the seam
  with no stage. Every claim marked **(test)** is asserted in one of them. The
  relationship-edit invalidation in §3 ran first as a **(probe)** print and is
  now an assertion. Claims marked **(negative)** were measured by disabling a
  line, rebuilding (with a `Building CXX object` line confirming it), watching
  the suites go red, and restoring the line.
- What this does **not** supersede: any earlier report. It corrects one
  sentence of the plan (§1). It reaches something none of the earlier reports
  could: inputs from other prims, and an override on one prim reaching a node on
  another.

## TL;DR

1. **A relationship fan-in arrives in the relationship's authored target
   order.** This holds at first compile, after an edit that reverses the targets
   while both source nodes are already compiled, and in a fresh system. So it is
   safe to pair a weight with its source by position. The plan's line "fan-in is
   reachable only through relationships with no deterministic ordering" mixed up
   two accessors: the audit's "no deterministic ordering" is
   `IncomingConnections`'s, not `Relationship().TargetedObjects`'s. (test)
2. **Two kinds of source vanish from a fan-in without a word.** A target that
   does not provide the computation (not a clip, or not a prim) is skipped while
   the network compiles. A source whose computation **refused** is skipped by
   the read iterator. So the poses that come back cannot say how many sources
   there were. With the node's count check disabled, a blend whose second clip
   refused answered **the first clip exactly** (45.0°), with no error anywhere.
   (negative)
3. **The node counts its targets a second time and refuses a mismatch.** The
   same relationship is read for the builtin `computePath`, which every object
   on the stage provides. A target naming nothing on the stage is missing from
   both reads, so it surfaces as a weight count that disagrees. (test)
4. **Invalidation crosses the relationship in all three forms.** The blend
   declares no `computeTime` and reads no keyed attribute, and it is reported
   when the frame moves. An authored weight reaches its value callback. **An
   edit of the relationship's targets** also reaches the value callback, with
   no request rebuilt. (test)
5. **An override on one prim reaches a dependent on another.** Overriding
   `/Turn [motion.sampleAnimation]` changes `/Blend [motion.blendPoses]`. This is
   how a pose a driver holds, rather than one a clip states, gets into a blend.
   (test)
6. **The sources must share one instant, and the library would not require
   it.** Every source is sampled at one frame and converts it to seconds at its
   own rate. Two clips at 50 and 100 time codes per second are at 1.0 s and
   0.5 s on frame 50. With the check disabled, the blend came back stamped
   **0.625 s**, a second neither clip was sampled at. (negative)
7. **The fifth boundary finding: the wrapper works and the library's answer is
   wrong in three places.** Over nothing weighted, `motion::BlendPoses` answers
   a default pose stamped 0.0. It takes a NaN weight through to NaN rotations.
   It interpolates its sources' timestamps as though they were samples in time.
   And its fold depends on the order it is given: three sources reversed land
   **4.247°** apart (§6). (test)

## 1. What the node answers, and how the sources reach it

`motion.blendPoses` is registered on `UsdSkelAnimation`, like every node here,
and the prim it runs on states two things:

```usda
def SkelAnimation "Blend"
{
    rel motion:blend:sources = [</Walk>, </Turn>]
    custom float[] motion:blend:weights = [0.25, 0.75]
}
```

It reads each target's `motion.sampleAnimation`, which is the pose that clip
states at the evaluated frame. It hands those poses to the N-way
`motion::BlendPoses`, each with the weight at the same position. That one
library call is the whole node.

| Blend | Result |
| --- | --- |
| the fixture's: `/Walk` at 0.25, `/Turn` at 0.75, frame 50 | head at **78.75°** (`/Turn` folded into `/Walk` at three quarters), hips at (1.5, 0.125, 0.25), stamped 1.0 s, spine and chest taken from `/Walk`, the only source that reports them |
| weights `[1, 0]` | the first target's pose, **bit for bit**: the fold seeds with it and never folds in a zero weight |
| a negative weight | the library's zero, as `BlendPoses` documents, so this is an answer |
| the default time code | an answer: `/Walk` resolves to no bones, `/Turn` to its defaults, both are stamped 0.0, and the blend is `/Turn`'s pose |
| a target that is not a clip, a source that refused | **no value**, and an error naming the computation and every target (§2) |
| weights that do not pair one to one, **absent weights** included | **no value**, and an error giving both counts |
| a weight that is not finite | **no value** |
| sources at two instants, or at a non-finite one | **no value** (§5) |
| nothing positive | **no value**, because the library would answer a pose stamped 0.0 (§6) |
| an empty relationship | **no value**: there is nothing to blend |

Every row is **(test)**. At the default time code this node **answers**, where
`motion.interpolatePose` refuses. That node samples a timeline and needs an
instant. This one combines what its sources answered, and at the default time
code they answered. The request's arming compute is therefore not a refusal
here.

**A relationship, not connections, and that choice was forced.** 26.08's
`computeValue` forwards across exactly one connection and falls back silently to
the attribute's own value when there are two
([audit §5.1](26.08-openexec-migration.md#51-the-connection-rule-the-plan-half-guessed)).
A relationship carries fan-in as a first-class input: `Relationship(name)` then
`.TargetedObjects<T>(computation)`, read with a `VdfReadIterator<T>` that
yields one value per target. So this node avoids the connection rule rather than
testing it (§8).

**The fan-in's order is the authored order.** With weights `[1, 0]` the blend
is exactly the first target's pose, so the order is the only thing that decides
it. The test checks three cases:

- targets authored `[</Walk>, </Turn>]`: the blend is `/Walk`;
- the targets **edited** to `[</Turn>, </Walk>]` on a live system: the blend is
  `/Turn`;
- a **fresh** system opened on the edited stage: the blend is `/Turn`.

**(test)** The second case matters most. Both source nodes already existed in
the compiled network, so if the order came from when each node was compiled
rather than from the relationship, `/Walk` would still be first.

That corrects one sentence of the plan: "Fan-in is reachable only through
relationships with no deterministic ordering". The audit's table gives "no
deterministic ordering" to `IncomingConnections` only. The resolver walks
`GetForwardedTargets` in order, and the order survives into the input's
connections. That is measured here for a relationship. It is not claimed for
`IncomingConnections`, which this report did not run.

## 2. Two silent drops, and the count that closes them

Reading the source predicted both drops before anything ran:

- `_TraverseToRelationshipTargetedObjects` loops over the relationship's
  forwarded targets. It `continue`s past a path that names no object and past
  an object whose `_FindComputationDefinition` comes back empty. No error is
  posted; that target simply gets no output key. So a target that is an
  `Xform`, or anything other than a `UsdSkelAnimation`, **is not an input at
  all**.
- `VdfReadIterator::_AdvanceConnection` moves past any connection whose source
  "provide[s] no values", in the words of its own comment. A source that
  refused with `SetEmptyOutput` provides none. So a source that **refused**
  **is skipped while reading**.

Both drops leave the iterator shorter than the relationship, and nothing
anywhere reports it. A blend that paired weights with whatever came back would
put a weight on the wrong clip and answer confidently. **Measured (negative):**
the node's count check was disabled and `/Turn`'s rate cleared, so its sampler
refused. The blend of `[/Walk, /Turn]` at `[0.25, 0.75]` then answered
`/Walk` at 45.0°, **equal to `/Walk`'s pose bit for bit**. The fan-in had held
one pose, the 0.25 weight paired with it, and a blend of one pose is that pose.
The suite went red first on the other drop, a target that is not a clip, which
fails the same way.

**The count.** The node reads the same relationship a second time, for the
builtin `computePath`. Every object that exists provides `computePath`, so this
read yields one `SdfPath` per target that names something. When it disagrees
with the number of poses that came back, the node refuses. The error lists every
target by path, because the fan-in hands back values and not the objects they
came from, so the node cannot say which target dropped out. **(test)**

The two reads are two inputs over one relationship. They arrive under their own
names (`motion:blend:sourcePaths`, `motion:blend:sourcePoses`) because each input
would otherwise be named after the computation it reads.

**A target naming nothing on the stage** is missing from both reads. It is not
a source at all, as far as the node can tell. It still shows up because the
weights are authored one per target, so three weights against two sources is a
count mismatch, and that is how it is refused. **(test)** That is the only way
it can be detected. A blend whose author wrote weights only for the targets
that exist would blend them, which is the correct answer for what can be seen.

**Absent weights are refused, not defaulted.** `motion::WeightedPose` defaults
its weight to 1.0, and an even blend would be a plausible default. But the
callback cannot tell an absent `float[]` from an authored empty one: both
arrive as an iterator already at its end. So defaulting the absent case would
also default the empty one, and a blend that *stated* it has no weights would be
blended anyway. That is the "never default a value the clip stated" half of the
bundle's rule ([root-motion report §5](26.08-openexec-root-motion.md)). A third
case now has the "absent looks like something else" property, after an undeclared input and
a missing attribute. **(test)**

## 3. Invalidation crosses the relationship

| Change | Reaches the blend | How |
| --- | --- | --- |
| the frame moves | yes: reported to the **time** callback | the node declares no `computeTime` and the fixture's weights are not keyed, so time dependence comes only from `/Walk`, across the relationship |
| an authored weight | yes: reported to the **value** callback | the weights are the node's own attribute input |
| **the relationship's targets are edited** | yes: reported to the **value** callback, with no request rebuilt, and the next compute answers from the new order | exec journals the relationship's targets while it resolves the fan-in, so an edit to them uncompiles the input |

All three are **(test)**. The last one first ran as a probe print, because
nothing in the headers says a relationship edit is reported as a value
invalidation rather than silently recompiled. It is reported, so a driver that
redraws on value invalidation also redraws when the sources change.

The filtering report measured that time dependence propagates across a
`Computation<T>()` link on one prim
([§2](26.08-openexec-filtering.md)). Across a relationship to another prim it
propagates the same way.

## 4. An override reaches across prims

A value key can be overridden whether or not it is meant to be. So a driver
holding a pose, for example a live source's, hands it to a blend by overriding
one **source's** `motion.sampleAnimation`:

| Override on `/Turn [motion.sampleAnimation]` | `/Blend [motion.blendPoses]` |
| --- | --- |
| a pose stamped at the instant `/Walk` was sampled at (1.0 s), head at 0°, hips at (4, 0, 0) | `/Walk` with the override folded in at 0.75: head at 11.25°, hips at (3, 0.125, 0.25) |
| the same pose stamped 0.98 s | **no value**, and the instant error |

**(test)** The override is visible as `/Turn`'s own value and reaches a node
on a different prim through the relationship. The interpolation report measured
"an override reaches every dependent of the key it names" within one prim
([§2](26.08-openexec-interpolation.md)). Across a relationship the same holds.

That adds one line to the driver contract. **A pose handed to a blend's source
has to be stamped at the instant the other sources were sampled at.** In
practice that means the evaluated frame converted at the clip's rate. A driver
that stamps with its own clock is refused, and the reason is §5's.

## 5. One instant

A blend combines sources **at one instant**. The library treats a blend as a
fold of `motion::LerpPose` calls, and `LerpPose` interpolates the timestamp,
which is right for two samples in time and wrong for two sources. The node
therefore requires every source to be stamped at the same finite second and
refuses otherwise:

- **Exactly equal, not nearly.** Every source converts the same frame, so two
  clips at one rate produce the same bits. Any difference at all means two
  rates, and a tolerance would amount to a policy on how far apart two clocks
  may be.
- **Finite as well as equal.** Equality alone lets an infinity through, because
  sources all stamped +inf agree exactly. A NaN never agrees, even with itself.
- **Every source, weighted or not.** A clock disagreement is a defect of the
  stage, not of one frame's weights. If only weighted sources were checked, a
  weight animating up from zero would hit the refusal partway through a
  sequence instead of from the first frame. **(test)**

**Measured (negative):** `/Turn` was set to 100 time codes per second and the
check disabled. On frame 50, `/Walk` was at 1.0 s, `/Turn` at 0.5 s, and the
blend at **0.625 s**, the timestamp the fold interpolates at three quarters. No
source was sampled at that second, and nothing in the value would say so. The
check restored, the blend is refused there. On frame 0 it **answers**, because
frame 0 is second 0 at every rate. The check is on the seconds the sources
state, not on the rates behind them. **(test)**

## 6. The wrapper, and the fifth boundary finding

The node is one library call, like `motion.interpolatePose`, and this time the
call costs no copy: `BlendPoses` takes a vector of `WeightedPose` by reference.
The finding is not in the call's cost. It is in the library's answer, in three
places, each pinned in `execMotion_pose` against the library's current
behaviour:

- **Nothing weighted gives a default pose stamped 0.0.** The header documents
  that when the total weight is zero, or the list is empty, the result is a
  default-constructed pose. The sources were sampled at 1.0 s and the answer
  says 0.0, a second nobody sampled, and nothing in the pose says it is not a
  blend. **(test)**
- **A NaN weight becomes NaN rotations.** `std::max(NaN, 0.0f)` returns the NaN,
  it passes the `weight <= 0` skip, it enters the running total, and every
  following fold step interpolates at `w / NaN`. The head comes back with a NaN
  real part. **(test)**
- **Timestamps are interpolated, not required to agree.** This is §5, seen from
  the library side. `LerpPose`'s timestamp rule is right for interpolating in
  time, and `BlendPoses` reuses it for combining sources at one instant, where
  the answer should be that instant or a refusal.

Beside those three, one property that is not a defect but is not stated
either: **the answer depends on the order.** The header says "successive
pairwise interpolation", which is the mechanism. It does not say what that
implies: three sources turning one bone 90° about X, Y and Z at equal weights
land **4.247°** apart when their order is reversed, even with each weight moved
along with its source. **(test)** So the fan-in's order matters for the answer
itself, not only for the pairing, and §1's measurement is load-bearing twice.

The ask for [boundary consolidation](../../roadmap/boundary-consolidation.md):
an N-way blend that says **there is nothing to blend** rather than returning a
stamped default (an optional result, or a result type with an absent state as
`PoseSampleResult` has). It should state finite weights as a precondition, and
either require its sources to share an instant or say in its header that it
interpolates between them. Its header should also state the order dependence.
The node refuses all four of these cases today, so a library that handled them
would let the refusals become answers.

**What this does not claim.** It is not a defect in `LerpPose`, whose timestamp
rule is correct for what it was written for. The finding is that `BlendPoses`
reuses that rule for a different question.

## 7. What the chain cannot do yet

This is an observation about the bundle, not a measurement of 26.08. Every
downstream node here (`motion.filterPose`, `motion.extractRootMotion`,
`motion.interpolatePose`) reads `motion.sampleAnimation` **on its own prim, by
name**. So a blend's answer cannot be filtered, have its root extracted, or be
sampled in the graph: `/Blend [motion.filterPose]` filters `/Blend`'s own clip,
which states none. That was never a goal of P0-4, whose nodes are specified one
by one, but it is the first time two nodes could usefully compose and cannot.

The mechanism that would let them is the one this node uses: a node that took
its input pose through a relationship with one target could take it from a
sampler, a blend, or a live source's override without knowing which. That is an
expectation about `execVrm`'s retarget node (P0-5), which has to choose a pose
to retarget. It is not a measurement.

## 8. What this changes in the plan

1. **P0-4's five nodes exist.** `motion.sampleAnimation`, `motion.filterPose`,
   `motion.extractRootMotion`, `motion.interpolatePose` and `motion.blendPoses`,
   together with the two override keys and the identity computation. What is
   left of P0-4 is not a node: the producer half of the rate and the two
   policies, the written driver contract, and packaged discovery.
2. **The plan's fan-in sentence is corrected.** Relationship targets arrive in
   authored order (§1). What has no deterministic ordering is
   `IncomingConnections`, which nothing here uses.
3. **The driver contract gains a line**, and P0-6's harness is still the first
   client that needs it written down: a pose handed to a source's key is
   stamped at the instant the other sources were sampled at (§4), or the blend
   is refused.
4. **A fifth boundary finding**, about the library's answer rather than the
   call's cost: `BlendPoses` over nothing weighted, over a non-finite weight,
   and over sources at different instants, and the order dependence its header
   does not state (§6).
5. **P0-5 gets a design question from this node, not a measurement:** whether
   a node takes its input pose by name on its own prim, as every node here does,
   or through a relationship, as this one does (§7).

## 9. What this did not do

- It did not use **connections**. The two-connection `computeValue` fallback
  ([audit §5.1](26.08-openexec-migration.md#51-the-connection-rule-the-plan-half-guessed))
  is avoided by using a relationship, not tested. No node in the bundle reads
  through a connection.
- It did not measure **`IncomingConnections`'** ordering, which the audit reads
  as nondeterministic.
- It did not measure a relationship that **targets another relationship**
  (forwarding, which the resolver applies transitively), or one that names the
  **same target twice**.
- It did not measure **nested blends**. A blend that targets another blend
  reads that prim's `motion.sampleAnimation`, not its blend. Unless that prim
  is also a clip, its sampler would refuse and the outer blend would be refused
  as a source that answered nothing (§2). That is a prediction from the code,
  not a run; §7 is the reason it is not a composition.
- It did not time anything. The fan-in reads the relationship twice, and what
  that costs belongs to the performance baseline, P1-3 of the plan's `ExecIr`
  track.
- It did not run against a **packaged** bundle. Like the six suites before it,
  `execMotion_blend` loads a built tree; the artifact-only run is P0-3's.
