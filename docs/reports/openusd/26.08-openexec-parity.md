# OpenUSD 26.08 OpenExec, parity with the offline bake

- Date: 2026-09-13
- Version exercised: **OpenUSD 26.08**, the pinned `cy2026`/`usd` runtime. Like
  [the joint-transforms report](26.08-openexec-joint-transforms.md), this run
  used a local build of that release adopted as the runtime, not the published
  GHCR leaf.
- Occasion: [the OpenExec plan](../../roadmap/openexec-foundation.md) §6, P0-6.
  P0-5 finished `execVrm`, so both bundles exist; this is the first time either
  is compared with `motion_retarget` on the same input.
- Method: **run, against the tool.** Everything marked **(test)** is asserted
  by one of the five `workspace_exec_parity_*` CTest names, which run
  `motion_bvh_convert`, `motion_retarget` and a new harness, `exec_parity`,
  over the same avatar and clip. **(negative)** claims are either committed
  negative pairs in those tests, or a throwaway run with one input changed.
  **(measured)** is a throwaway run, not committed. **(read)** is read off the
  source and not run.
- What this does **not** supersede: any earlier report. §7 collects the rows
  four of them left for P0-6, and replaces none of their text.

## TL;DR

1. **Parity holds bit for bit on every input.** 414 598 values, rotations and
   translations, across five cases: the recorded mocopi export on the fixture
   rig and on `Seed-san.vrm`, the four root-motion statements, the design
   triplet's walk read through the VRMA reader, and a generated 30 fps clip.
   Every one is `==`. No quaternion sign flip, no rounding. (test)
2. **So the classification's cheap categories are empty, except one.** The only
   value that is not exact is where the tool puts a sample in time, and only on
   a clip keyed at integer frames at a rate like 30: frames 31 and 62 bake
   2.37e-16 s late. The recorded input never shows it, because its keys are
   already `frameTime × 50`, and those round-trip. The harness compares at the
   bake's own samples, so the placement costs nothing. (test, measured)
3. **The harness can tell a difference.** Exec under each root-motion statement,
   held against the *default* bake, diverges in translation only: 852, 1 704
   and 852 values. A map one bone short diverges on exactly that joint. With the
   gaze left in the tool's bake, exactly the two eye joints diverge. (test,
   negative)
4. **Parity holds given five statements the harness makes on the stage**: the
   rate, the source skeleton, the map, the rig, and the root-motion policy. The
   tool takes them from its command line or a second stage. Exec takes them
   from a prim, and no producer authors them yet. (test)
5. **Diagnostics do not agree, and that is the one parity item this run leaves
   open.** The tool names the clip bone a rig drops (`upperChest` on Seed-san)
   and the required bones a rig lacks. Exec says neither. It posts one executor
   warning per unauthored bone attribute, and that warning cannot tell a bone
   the clip drives from one it does not. (test, measured)
6. **The tenth boundary finding.** The rules for which humanoid, which rig and
   which clip a stage means exist only in the tool. The harness restates them
   so it compares the same input. (read)
7. **Exec's cost per frame, driver included**: 60–72 µs for a `ChangeTime` and a
   `Compute` on a 23-joint rig, 128 µs on Seed-san's 128. That is the whole
   chain, `motion.sampleAnimation` through `vrm.computeJointLocalTransforms`,
   with the retarget's per-frame correction recompute inside it (the retarget
   report, §2). (measured)

## 1. What ran

`exec_parity` is a C++ harness in `tests/parity/`. It is handed the tool's own
arguments (`--avatar`, `--animation`, `--humanoid-map`, the root-motion flags)
and the bake the tool wrote from them. It evaluates the same inputs through
both exec bundles and compares, sample by sample. A Python driver runs the tools
and gives both programs one argument list, so they cannot be given different
flags. Neither bundle is linked: both are found through `PXR_PLUGINPATH_NAME`,
as in every exec suite.

**One stage, built from the tool's two.** The tool opens the avatar and the clip
as two stages. Exec evaluates one. So the harness builds an anonymous layer that
**sublayers** the avatar's layer and the clip's layer. A sublayer keeps every
path the tool saw at the path exec sees, where a reference would move one of
them under a new prim. The layer's `timeCodesPerSecond` is the clip's, so the
clip's time samples cross the sublayer unscaled. The two layers may not share a
root prim name, and the harness refuses one that does.

**The tool's discovery rules, applied to the stages the tool opens.** The tool's
humanoid is the first prim stating `vrm:humanBones:hips`. Its rig is `--skeleton`,
else that humanoid's `vrm:skeleton`, else the first skeleton on the avatar's
stage. Its clip skeleton is `--clip-skeleton`, else the first skeleton on the
clip's stage, and its animation is that skeleton's binding. The harness applies
each rule to the avatar or the clip opened **alone**. On the composed stage,
"the first skeleton" could be the clip's.

| Case | Avatar | Clip | Rate | Samples × joints |
| --- | --- | --- | --- | --- |
| `recorded_fixture` | `tests/motion/fixtures/humanoid_avatar.usda`, the 22-bone map beside it | `mocopi-mobile-arm-raise-turn.bvh` through `motion_bvh_convert` and the shipped profile | 50 | 853 × 23 |
| `recorded_root_motion` | the same | the same, baked four times: the default, `ignore`, `root` onto `Root`, and a 0.5 scale with the target's height kept | 50 | 853 × 23, four times |
| `recorded_real_avatar` | `Seed-san.vrm`, through `usdVrmFileFormat`, its own humanoid | the same | 50 | 853 × 128 |
| `vrma_walk` | the design triplet's `avatar.usda`, its 3-bone map | `canonical_walk.vrma`, through `usdVrmaFileFormat` | 30 | 2 × 4 |
| `generated_thirty_fps` | the same | `tests/parity/fixtures/thirty_fps_clip.usda`, keyed at 0, 31 and 62 | 30 | 3 × 4 |

The harness requests `vrm.computeJointLocalTransforms` on the humanoid, arms the
request with one compute at the default time code, where the retarget refuses by
design (the retarget report, §5), then calls `ChangeTime` and `Compute` once per
clip key. Each key is the union of the animation's rotation and translation
time samples, the instants exec's sampler reads.

## 2. The answer: exact

| Case | Rotations | Translations | Joints, scales | Exec refusals |
| --- | --- | --- | --- | --- |
| `recorded_fixture` | 19 619 exact | 19 619 exact | equal, 853 of 853 | 0 |
| `recorded_root_motion`, each of four | 19 619 exact | 19 619 exact | equal | 0 |
| `recorded_real_avatar` | 109 184 exact | 109 184 exact | equal | 0 |
| `vrma_walk` | 8 exact | 8 exact | equal | 0 |
| `generated_thirty_fps` | 12 exact | 12 exact | equal | 0 |

*Exact* means `==` on the float components, with no tolerance (test). Each case
also asserts that its samples move away from the first one. A pair of
implementations that both answered the rest pose would agree everywhere, so
parity over a still clip proves nothing (test).

This was the expected answer, and the reason is structural rather than lucky.
Both sides call one library, `vrmRetarget::PoseRetargeter`, once per sample,
with inputs that are bit-identical by construction:

- the target rig is decomposed by the same arithmetic, line for line (the
  humanoid report, §7);
- the clip's rest is assigned to bones by the same rule (the correction report,
  §7);
- the pose is the clip's attribute value at the key, normalized the same way
  and stamped `key / rate` on both sides;
- the four root-motion options are the tool's flags, word for word.

`motion_retarget` constructs one `PoseRetargeter` and calls it per sample. The
node constructs one per evaluation. The constructor is deterministic, so that
changes the cost (the retarget report's 17.7 µs of 21.2 µs) and not the value.

**Seed-san is the case that carries weight.** It has 128 joints, 77 of them
outside the humanoid; two unbound twist joints between bound ones; no
`upperChest` for a bone the clip drives; and seven joints whose rest is scaled
(the joint-transforms report, §4). All four are where two implementations of
"which joint gets what" could disagree, and they do not. Both bakes write scale
1 on the seven scaled joints: that is P1-2's question, not a divergence.

## 3. Where a sample is placed

The tool reads a key at time code `f` as `f / rate` seconds and writes it back
at `(f / rate) × rate`. That is not always `f` (the joint-transforms report,
§8). The harness therefore pairs the clip's keys with the bake's samples by
index, and compares exec's answer at `f` with what the bake states at its own
sample `t`. The distance `|t − f| / rate` is reported on its own, as
**placement**:

| Case | Placement exact | Placement a rounding away | Worst |
| --- | --- | --- | --- |
| every recorded case | 853 | 0 | 0 |
| `vrma_walk` | 2 | 0 | 0 |
| `generated_thirty_fps` | 1 (frame 0) | 2 (31, 62) | 2.37e-16 s |

**The recorded input never shows it (test).** `motion_bvh_convert` writes each
key at `timestamp × 50`, with `timestamp = frame × frameTime`. Those time codes
are already not integers, and they survive `/ 50 × 50` unchanged, all 853 of
them. The VRMA walk's keys are 0 and 30 at 30 fps, and `30 / 30 × 30` is 30.
So the rounding the joint-transforms report measured needs an integer-keyed clip
at 25, 30, 50, 60 or 120. Without the generated fixture, no case here would
exercise the rule.

**What the rule is worth (test).** The harness also reads the bake at the clip's
own frame and classifies that comparison beside the real one:

| `generated_thirty_fps` | At the bake's samples | At the clip's frames |
| --- | --- | --- |
| rotations | 12 exact | 10 exact, **2 not** |
| translations | 12 exact | 12 exact |

The two rotations that differ are the hips and the chest at frame 62. There,
the bake's sample sits 1e-14 frames later, so USD interpolates from the key at
31. They differ in their bits and are **0 radians apart** as `AngleBetween`
measures, because the dot product rounds to exactly 1 in float. So they fall in
the contract's *rounding* class with a worst angle of 0. The rule turns that
class into *exact*. It costs nothing, and without it every such comparison would
need a tolerance.

**The tool is not changed here.** The joint-transforms report named the fix:
author at the time code the tool read, not one rebuilt from seconds. Parity does
not need it, because comparing at the bake's own samples is exact. It stays the
ninth boundary finding's ask
([boundary consolidation](../../roadmap/boundary-consolidation.md) §1).

## 4. What the harness can see

A harness that agrees with everything is indistinguishable from one that stopped
comparing. Three differences were put in front of it.

**The root-motion statements, against the default bake (test, a committed
negative pair).** For each variant the driver bakes with the variant's flags
and compares that bake with exec under the same statements. That comparison is
exact. It also checks that the variant's bake differs from the default bake, so
the flags did something. Then it runs exec under the variant's statements
against the **default** bake. That run must diverge, and only in translation:

| Statement | Translation values that diverge from the default bake | Worst | Rotations |
| --- | --- | --- | --- |
| `rootMotion = ignore` | 852: the hips, every sample after the first | 0.0711 m | exact |
| `rootMotion = root`, `rootJoint = Root` | 1 704: the hips and `Root`, every sample after the first | 0.0711 m | exact |
| `translationScale = 0.5`, `preserveTargetHeight` | 852: the hips | 0.036 m | exact |

The first sample agrees in all three: there the clip's hips stand at their
rest, so there is no displacement to place.

**A map one bone short (negative).** The fixture was baked with its full
22-bone map, and exec was given the same map without `leftLowerArm`. Exactly
one joint diverged, `L_Forearm`, at 852 of 853 samples, worst 1.64 rad. Exec
holds it at its A-pose rest, `(0.924, 0, 0, −0.383)`. At the remaining sample,
the first, the bake's forearm is within the contract's tolerance of that rest,
so it is classed as rounding rather than divergence. The hand below it does not
diverge, because each bone's local rotation is retargeted on its own. This is also what *unbound-bone behaviour* looks like when it is
compared rather than read: identical on both sides when they are given the same
map (§2), and localized to the joint when they are not.

**A gaze (negative).** `tools/motionRetarget/tests/fixtures/gazing_clip.usda`
names a look-at target. Its `gazing_avatar.usda` aims bone eyes, and the tool
writes those eye rotations **into the joint arrays**. Exec has no gaze node yet:
look-at computations are the `ExecIr` track's P1-2. On a copy of the avatar
with `VrmHumanoidAPI` applied (see below), exactly the two eye joints diverged,
at both samples, worst 0.0964 rad. Re-baked with `--no-look-at`, every value was
exact. So the gaze is attributable to one stage of the tool that exec does not
implement, and the harness accepts `--no-look-at` as narrowing the tool toward
exec.

That copy was needed because **two of the tool's own fixtures state human bones
without the schema**. `gazing_avatar.usda` and `gazing_expression_avatar.usda`
author `vrm:humanBones:*` on a plain `Scope`. The tool reads them, and exec
cannot see them (the humanoid report, §2). The harness refuses such an avatar
by name. This is the humanoid report's fifth row, observed on committed data for
the first time.

## 5. What the harness had to state

Parity is conditional. Each row is something the tool takes from somewhere
other than a prim, which exec must be given on one:

| Stated by the harness | On | Where the tool takes it | In which cases |
| --- | --- | --- | --- |
| `motion:timeCodesPerSecond`, the clip stage's rate | the clip's animation | the clip stage's metadata | all five |
| `vrm:retarget:sourceSkeleton` | the humanoid | it opens the clip as its own stage | all five |
| `vrm:humanBones:*`, on a new `/Parity/Humanoid` with `VrmHumanoidAPI` | a prim the harness defines | `--humanoid-map`, a JSON file | the fixture rig and the walk rig, which have no humanoid |
| `vrm:skeleton` | the humanoid | `--skeleton`, else the first skeleton on the stage | the same two |
| `vrm:retarget:rootMotion`, `rootJoint`, `translationScale`, `preserveTargetHeight` | the humanoid | the four flags | `recorded_root_motion` |

The harness states a value only where the stage does not already. An avatar's
own humanoid keeps its own `vrm:skeleton`, and a clip that states a rate keeps
it. On Seed-san it stated two things, the rate and the source skeleton, because
the importer authors everything else (test).

These are the plan's §9 items, and this run answers one question for each: the
**harness** authors them onto the stage it compares. That answer is enough for
P0-6 and is not a contract. Which producer states them, and whether the rate
shim belongs on a clip at all, is BND-0's to decide.

## 6. Diagnostics

The plan lists diagnostics among the things parity compares. They do not agree:

| Input | `motion_retarget` says | Exec says |
| --- | --- | --- |
| Seed-san, a clip driving `upperChest` | `warning: the clip drives bones the target rig does not map: upperChest` | four `No value set for output Exec_AttributeInputNode …vrm:humanBones:<bone>` warnings: `jaw`, `leftEye`, `rightEye`, `upperChest` |
| the design rig, 3 bones bound | `warning: the target rig maps no joint for required bones: neck, head, …` (14 bones) | 52 of the same executor warnings, one per unauthored bone, and nothing about "required" |
| Seed-san, a look-at rig and a clip with no gaze | `note: the avatar declares a look-at configuration and the clip names no target` | nothing; exec has no gaze node |
| every clip, at the arming compute | nothing | `No value set for output …rotations` and `…translations` once: the default time code resolves a clip that keys only time samples to nothing (the sampling report, §4) |

So the tool reports what matters to someone baking. Exec reports what the
executor filled in, and **it cannot say which of four unbound bones the clip
actually drives**. `PoseRetargeter::Retarget` fills a `RetargetDiagnostics`
when it is handed one, and `vrm.humanoidRetarget` hands it none (read): a
computation has no channel for a warning except `TF_WARN`, which a caller of
`Compute` never sees in its result.

This is not a numerical divergence, and P0-6 does not need to close it to claim
parity of values. It is P1-1's: the frozen `VRM_RETARGET_*` codes are what both
sides would report. The ask this run adds is that the codes be computable **as
a value**, so a node can answer them beside the pose rather than log them.

## 8. The tenth boundary finding

To compare the same input, the harness had to restate three rules from
`tools/motionRetarget/src/StageIo.cpp`: which prim is the humanoid, which
skeleton is the rig, and which skeleton and animation are the clip. They are
the questions a stage answers before any retarget. They exist only in a tool,
and no library states them. That is the sampler's finding a fourth time, one
level up: not how to read a value, but **which** prim to read it from. BND-1's
reference pipeline is the next consumer that needs them. The ask
([boundary consolidation](../../roadmap/boundary-consolidation.md) §1) is one
statement of those rules that the tool and a pipeline both call. Or else the
decision that the stage names them (§5) and nothing discovers them at all, which
is the direction every exec relationship already points.

## 9. What this changes in the plan

1. **P0-6 is in progress, and its value half is done.** Offline and exec agree
   on the same recorded input, exactly rather than under `NearlyEqual`. That
   meets the release gate's parity line on the one host it has run on, and is
   stronger than the line asks. A gaze does not agree, and the gate does not ask
   it to: look-at is outside the foundation (the plan's §6, "not a gate here").
2. **The tolerance is written into the contract, and this run did not need
   it.** [MOTION_CONTRACT.md](../../design/MOTION_CONTRACT.md) now says how
   parity compares: at the bake's own samples, joint by joint, under
   `MotionTolerance`'s angle, distance and time, each difference classified and
   none widened.
3. **What is left of P0-6**: diagnostics (§6, with P1-1), and the rows no
   producer can reach (§7, 1–3, 6–7, 9–11, 13–15). Each of those is already
   asserted on the exec side by its own suite. The tool side of each was read,
   not run, and whether P0-6 needs them run is a decision, not a gap.
4. **`RetargetedPose` does not need a `NearlyEqual`.** MOTION_CONTRACT left the
   choice to P0-6: compare retargeted poses, or the arrays a bake authors from
   them. It compares the arrays, `JointLocalTransforms`, against what the bake
   states.
5. **The rate and the source skeleton have an owner for parity, and not yet a
   contract** (§5). The plan's §9 records that the harness states them.
6. **A tenth row in boundary consolidation §1** (§8), and a sharpened ask for
   P1-1 (§6).

## 10. What this did not do

- It ran on Windows only. The five cases are in the root workspace suite, so the
  Linux and macOS lanes run them, and their first run there is the next
  measurement.
- It used one recorded input. The only recorded capture this repository may
  redistribute is the mocopi BVH export. The five device sessions and the
  VRChat OSC session are manifests with no bytes (the plan's release gate still
  names "the same recorded input", and this is it). A live trace through
  `motion_capture` is not a case yet.
- It did not run from **packaged** bundles. Like every exec suite, the harness
  loads built trees through `PXR_PLUGINPATH_NAME`. The artifact-only run is
  P0-3's.
- It did not compare expressions or a gaze, which exec does not compute yet, and
  it compares no blend-shape weights at all.
- It did not compare a filtered, blended or held pose. Those reach the retarget
  only as a driver's override, and the tool has no counterpart to compare with.
- It did not change the tool (§3) or decide P1-2 (§2).
