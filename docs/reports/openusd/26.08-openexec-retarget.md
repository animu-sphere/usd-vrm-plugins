# OpenUSD 26.08 OpenExec, a humanoid retarget across two bundles

- Date: 2026-09-13
- Version exercised: **OpenUSD 26.08**, the pinned `cy2026`/`usd` runtime. Like
  [the correction report](26.08-openexec-rest-correction.md), this run used a
  local build of that release adopted as the runtime, not the published GHCR
  leaf.
- Occasion: [the OpenExec plan](../../roadmap/openexec-foundation.md) §6, P0-5.
  `vrm.humanoidRetarget` is `execVrm`'s fourth node of five, and the first
  computation in either bundle that reads a value **the other bundle
  computes**. It needed a fifth computation the plan did not list,
  `vrm.computeBoundPose`.
- Method: **run, one node on from the correction report.** Everything marked
  **(test)** is asserted by `execVrm_retarget`, which drives both built bundles
  through `PXR_PLUGINPATH_NAME` without linking either, over
  `retargeted_rig.usda`, or by `execVrm_rig`, which tests the seam with no
  stage. **(negative)** claims were measured by changing one line, rebuilding (a
  `Building CXX object` line confirming it), watching suites go red, and
  restoring it. **(probe)** claims were printed by the suite before the code
  that answers them existed. **(measured)** is a throwaway timing harness, run
  three times and not committed. **(read)** is read off the source and not run.
- What this does **not** supersede: any earlier report. §4 narrows one sentence
  of [the humanoid report](26.08-openexec-humanoid.md) §4 and says where.

## TL;DR

1. **The node is one library call, and the call recomputes a value the graph
   already caches.** The retarget equals `vrmRetarget::PoseRetargeter` over the
   rig, the map, the clip's rest and the root-motion options, bit for bit. Every
   mapped joint's rotation is exactly the cached `vrm.computeRestPoseCorrection`
   applied to the clip's rotation. The retargeter computes that correction
   again when it is constructed, which is **84% of the node's cost** on a full
   humanoid: 21.2 µs per evaluation against 1.9 µs for the retarget alone.
   (test, measured)
2. **A value crosses from one bundle to the other unchanged, and exec says
   nothing when the other bundle is missing.** `motion.sampleAnimation`
   (`execMotion`) reaches `vrm.computeBoundPose` (`execVrm`) across
   `skel:animationSource`, and the retarget one relationship further. Without
   `execMotion` in the session the animation drops out of the fan-in silently.
   The bound pose's own count is the only thing that notices. (test, negative)
3. **A bundle that reads a value type has to register it itself.** Without
   `execVrm`'s own `RegisterType(motion::HumanoidPose{})`, every session that
   does not load `execMotion` first loses **every** `execVrm` computation to a
   fatal error at registration. The one suite that loads both bundles stayed
   green. (negative)
4. **The fallback follows the attribute's existence, not its schema.** A
   `vrm:retarget:*` attribute declared with no value, or blocked, reaches a
   callback as the type's fallback beside an executor warning, although no
   schema defines it. So a valueless `translationScale` is **0**, and is
   pinned. (probe, then test)
5. **At the default time code the retarget refuses.** The sampler answers an
   empty pose there, which is harmless. Retargeted, it becomes the rig's whole
   rest pose at 0 seconds, which is not. (probe, then test)
6. **Invalidation reaches the retarget from the frame, a key, the binding, the
   source and the statements, with no request rebuilt**, and a driver's pose
   handed to either bundle's key reaches it too. (test)

## 1. What ran

`vrmRetarget::RetargetedPose` registers as an execution value type. That needed
an exact `operator==` in `vrmRetarget` over the timestamp and both arrays, in
the rig's joint order. Two computations are new:

| Computation | On | Reads | Answers |
| --- | --- | --- | --- |
| `vrm.computeBoundPose` | `UsdSkelSkeleton` | `computePath` and `motion.sampleAnimation` across `skel:animationSource` | the bound animation's pose, forwarded |
| `vrm.humanoidRetarget` | applied `VrmHumanoidAPI` | `vrm.computeHumanoidMap`; `vrm.computeTargetSkeleton` across `vrm:skeleton`; `computePath`, `vrm.computeTargetSkeleton` and `vrm.computeBoundPose` across `vrm:retarget:sourceSkeleton`; four `vrm:retarget:*` attributes; `computeTime` | `vrmRetarget::RetargetedPose` |

**Why a fifth node.** An exec input traverses one relationship. The retarget
needs two: the humanoid names the clip's skeleton, and the skeleton names its
animation through UsdSkel's own binding. The correction report chose the skeleton
because it is the one prim from which both halves of a clip can be reached. The
second hop is therefore a computation on the skeleton, and `execVrm` owns that
schema. The result is that one relationship on the humanoid says which clip
drives it. The rest a correction reads and the pose a retarget reads cannot come
from two different clips.

The fixture is `corrected_rig.usda`'s rig (hips turned 90° about +Y, arm turned
90° about +Z) with each semantic source skeleton now bound to an animation.
`/Clip/Animation` is keyed at frames 0 and 24 at 24 frames per second. At frame
24 the spine is turned 30° about +X, the left arm 90° about +Z, and the hips
moved from `(0, 1, 0)` to `(0.5, 1.1, 0.2)`. It also drives `rightUpperArm`, which
the humanoid does not bind. `/Posed/Animation` holds its non-identity rest,
unkeyed.

## 2. The wrapper, and what it costs

At frame 24 the request returns the rig, the map, the correction, the sampled
pose, the bound pose and the retarget together, with no error (test):

- the bound pose equals the sampled pose, `operator==`;
- the retarget equals `PoseRetargeter(target, map, clipRest).Retarget(sampled)`,
  `operator==`, and again at frame 12, between the keys;
- for every mapped bone, the joint's rotation equals
  `correction.Apply(bone, sampled.localRotations[bone])` exactly, where
  `correction` is `vrm.computeRestPoseCorrection` from the same request;
- from the definition: the spine and the arm keep their world-space deltas
  under the turned hips, bones at their clip rest land on the rig's rest, the
  joint no bone binds stays at rest, and the hips carry the clip's root delta,
  `(0.5, 1.1, 0.2)`. The timestamp is 1.0.

The third bullet is the **eighth boundary finding**, and the first whose cost is
repeated work rather than a copy. The correction report read the problem off the
API. `PoseRetargeter` computes its correction in its constructor, and no
constructor or free function accepts one. A wrapper therefore constructs a
retargeter for each evaluation, and this node is evaluated on every frame the
clip moves. The value `vrm.computeRestPoseCorrection` caches per rig edit is
computed again, every frame, next to the cached copy.

**Measured on a full VRM 1.0 humanoid** (measured). The rig has one joint per
bone of the vocabulary under a `Root`, parented by `motion::HumanBoneParent`,
with every rest turned 10°. All 55 bones are mapped and the source rest is
identity. The harness runs 20 000 evaluations, three times, on the Windows
workstation in Release:

| Per evaluation | Round 1 | Round 2 | Round 3 |
| --- | --- | --- | --- |
| construct + retarget (what the node does) | 21.28 µs | 21.06 µs | 21.19 µs |
| retarget only, retargeter built once | 2.03 µs | 1.86 µs | 1.84 µs |
| `ComputeRestPoseCorrection` alone | 17.94 µs | 17.41 µs | 17.71 µs |

So the correction is about 84% of the node's cost and the retarget about 9%.
The absolute numbers are small next to a frame. The ratio is what the
performance baseline (the plan's §7, P1-3) multiplies by the number of avatars.
The ask for [boundary consolidation](../../roadmap/boundary-consolidation.md) §1
is a retargeter, or a free per-pose function beside it, that takes the
correction as an input. The node could then read the cached value it currently
recomputes.

## 3. A value that crosses bundles

`vrm.computeBoundPose` reads `motion.sampleAnimation` by name. That computation
is `execMotion`'s, registered on `UsdSkelAnimation`, a schema `execVrm` may not
declare. The value crosses the link unchanged (test). Time dependence crosses it
too: a frame change reports the sampler, the bound pose and the retarget, and
not the rig, the map or the correction (test).

**Without `execMotion` in the session, exec says nothing** (test, run as
`execVrm_retarget_without_exec_motion`). With `PXR_PLUGINPATH_NAME` set to
`execVrm` and `vrmSchema` only, the correction still computes. The bound pose
and the retarget are refused, and the only errors are ours:

```text
vrm.computeBoundPose: 'skel:animationSource' targets </Clip/Animation>, which answered
no motion.sampleAnimation -- it is not a UsdSkelAnimation, execMotion is not in the
session, or its sampler refused; no pose was forwarded
vrm.humanoidRetarget: the source skeleton </Clip/HumanoidSkeleton> answered no
vrm.computeBoundPose; no pose was retargeted
```

A computation no plugin provides is treated like a prim that is not an
animation: it is dropped from the fan-in while the network compiles. That is
unlike a missing schema bundle, which exec reports as a coding error at
metadata read (the humanoid report §6). **The second read of the relationship
is what makes the error point at the right cause** (negative). With the count
taken from the poses that came back, a session with no `execMotion` was told
the skeleton "is bound to no animation". A binding to a SkelRoot got the same
message. So the relationship is read twice here, as every other fan-in in both
bundles is. `requires.bundles` now names `execMotion`, and WORKSPACE.md §2 has
the runtime edge.

**A bundle that reads a value type registers it too** (negative).
`TargetedObjects<T>` checks that `T` is registered at the moment the reading
bundle's computations are registered. With `execVrm`'s own
`RegisterType(motion::HumanoidPose{})` removed:

- every session in this bundle's suites that does not include `execMotion`
  failed with `fatal: Type 'motion::HumanoidPose' not registered with TfType`,
  and lost **every** `execVrm` computation, including `vrm.computeTargetSkeleton`
  on the typed skeleton. That covers `execVrm_humanoid`, `execVrm_correction`,
  both `without` entries, and a segfault in two of them;
- `execVrm_retarget`, the one suite that loads both bundles, **stayed green**.
  In that session `execMotion`'s registration came first. Why it came first was
  not investigated.

The suites that run without `execMotion` are the ones that catch it. 26.08
allows several plugins to register one type provided the fallbacks agree
(`VdfExecutionTypeRegistry::_Define` verifies it), and both bundles register
`motion::HumanoidPose{}`. (read, then negative)

## 4. The fallback follows existence, not schema

The humanoid report §4 says *an attribute a schema defines and the stage gives
no value* reaches a callback as one element of the type's fallback, beside an
executor warning. It contrasts that with *an attribute the prim does not have
at all*, which arrives as no value. The four `vrm:retarget:*` attributes are
defined by no schema, and they show that the dividing line is whether the
attribute exists, not whether a schema defines it (probe, then test):

| The humanoid | Arrives as | The node |
| --- | --- | --- |
| no `vrm:retarget:translationScale` | no value | the library's 1.0 |
| `custom float vrm:retarget:translationScale`, no value | `0.0f`, and `No value set for output Exec_AttributeInputNode …translationScale` | **answered with a scale of 0** |
| the same, authored `2` and then blocked | the same | the same |
| `custom token vrm:retarget:rootMotion`, no value | the empty token, and the warning | refused: the empty token names no mode |

The report's sentence holds for what it measured: every attribute it tried was
a schema's. What changes is the rule a node applies. **Any attribute a node
reads owes a fallback decision, not only a schema attribute.**

Three of the four statements answer it harmlessly. The empty mode token is
refused. An empty root joint names no joint, and under `root` that is refused
too. A `false` height flag is the library's default. **The scale is the one
where the fallback is a believable number.** A scale of 0 pins the receiving
joint at its rest, and the node cannot refuse it without also refusing an
authored 0, which `motion_retarget --translation-scale 0` accepts. So it is
answered and pinned. This is the one-joint skeleton's situation (the humanoid
report §4) on a statement instead of a rig, and it joins P0-7's upstream ask: an
input with no value should reach a callback as no value.

## 5. The default time code

Every request is armed at the default time code (the filtering report §4). The
probe printed what the chain answered there before any check existed:

```text
probe: at the default time code the sampler answered and the retarget answered
probe:   sampled bones 0, hasPosition 0, t=0; retargeted t=0, hips (0 1 0)
```

The sampler's answer is the one the sampling report recorded (§4): a clip that
authors only time samples resolves to nothing, so the pose is empty and stamped
0.0. That is harmless while it stays a pose, because nobody takes a pose naming
no bone for a frame. **Retargeted, it is the rig's whole rest pose, every joint
filled in, at 0 seconds**, which is a believable answer for an instant nobody
named. The retarget is where the empty pose becomes numbers, so the retarget is
where the refusal goes. It reads `computeTime` for that one fact, and declaring
it costs nothing, because the pose's time dependence already reaches it.
`motion.interpolatePose` refuses the default time code for the same reason
(the interpolation report §5). (test)

The refusal is checked **after** every statement. A request armed on a stage
with a wrong statement still reports the statement at arming, rather than
saying only "call ChangeTime" (test, seam).

## 6. Invalidation

The request's value callback records which keys each edit reports, after
`ChangeTime(24)` (test):

| Edit | Sampled | Bound | Map | Correction | Retarget | Value |
| --- | --- | --- | --- | --- | --- | --- |
| `ChangeTime` (time callback) | yes | yes | no | no | yes | the frame-24 pose |
| `vrm:retarget:rootMotion` created as `ignore` | no | no | no | no | **only this** | hips at the rig's rest |
| a key of the clip (the head, 45° about +Y) | yes | yes | no | no | yes | the head's world delta |
| the clip skeleton's `skel:animationSource` → `/Posed/Animation` | no | yes | — | no | yes | the posed animation, read by leaf |
| `vrm:retarget:sourceSkeleton` → `/Posed/HumanoidSkeleton` | — | — | no | yes | yes | every mapped joint at the rig's rest |

The second row adds an attribute the network had no input node for, and still
reaches only the retarget, with no request rebuilt. The last row is the reason
the pose comes through the skeleton. Switching the one relationship moves the
rest and the motion together, and a clip held at its own rest lands the posed
arm's −90° about Z on the rig's +90°. That needs both halves of the posed clip.

## 7. The root-motion statements

The four attributes are `motion_retarget`'s four flags, word for word, so a
stage and an invocation that mean the same retarget say it in the same words.
At frame 24, against `ResolveRootTranslation`'s definition (test):

| Stated | Hips translation | `Root` translation |
| --- | --- | --- |
| nothing (the library's `hips`) | rest + delta | rest |
| `ignore` | rest | rest |
| `root` onto `Root` | rest | the delta |
| `translationScale = 2` | rest + 2 × delta | rest |
| `preserveTargetHeight = true` | rest + delta with y zeroed | rest |
| `hips`, with a `rootJoint` naming no joint | rest + delta: the joint is not read | rest |

Refused, each with the tool's own reason where it has one (test): a mode that is
none of the three, `root` with no joint, `root` onto `J_Bip_C_Hips` (a joint
leaf, where the tool resolves the full path exactly), and a scale that is not a
finite number.

## 8. Which pose

`motion.blendPoses` left this node a question: every downstream node reads the
sampler on its own prim by name, so what does a retarget retarget? **The clip's
own sample**, `motion.sampleAnimation` on the bound animation. That is the pose
`motion_retarget` retargets, and P0-6 compares the two.

A filtered or blended pose reaches the retarget only as a driver's override,
and it does reach it. A pose handed to `motion.sampleAnimation` on the clip, or
to `vrm.computeBoundPose` on its skeleton, comes back from the retarget as the
library's answer over that pose. It does not survive the call (test). Selecting
a filter or a blend **in the graph** would need a node that takes its pose from
a relationship without knowing which computation is behind it. 26.08 names the
computation at registration, so that is still open. It is a design question for
the `ExecIr` track's switch controller (the plan's §7, P0-4) rather than for
this node.

## 9. What this adds to P0-6's table

None of these is numerical, and none is reachable from what the importer and
`usdVrmaFileFormat` author:

| The stage or invocation states | `motion_retarget` | `execVrm` |
| --- | --- | --- |
| a clip skeleton with no `skel:animationSource`, on a stage with exactly one animation | uses that animation | refuses the bound pose and the retarget |
| `--translation-scale nan` / `translationScale = nan` | accepts it; `std::stod` parses `nan` (read) | refuses |
| a declared, valueless `translationScale` | not expressible | a scale of 0, pinned (§4) |
| the default time code | not applicable: the tool samples at key times | refuses (§5) |

The tool's fallback in the first row is `ReadClip`'s "exactly one
UsdSkelAnimation on the stage". It is the stage search that the relationships
exist to replace, and a computation has no stage to search.

## 10. What this changes in the plan

1. **P0-5 has four of its five nodes, and a fifth it needed.**
   `vrm.computeJointLocalTransforms` remains. The retarget already answers in
   joint-local rotations and translations, so that node is now the question of
   what shape a `UsdSkelAnimation` sample is (scales included), not a second
   retarget.
2. **The bundle graph gains a runtime edge, `execVrm -> execMotion`.** It is not
   a link edge. It is in the manifest's `requires.bundles`, in WORKSPACE.md §2,
   and in PACKAGE_CONTRACT.md §4.1, and it is measured by leaving it unmet.
3. **The eighth boundary finding**, with a number (§2).
4. **A driver-contract line**: call `ChangeTime` before expecting a retarget.
   It sits beside "compute once to arm a request", which every request already
   needs.
5. **The plan's §9 fallback item widens** from schema attributes to every
   attribute a node reads (§4). The four root-motion attributes join the
   source relationship as conventions no producer authors.

## 11. What this did not do

- It did not build `vrm.computeJointLocalTransforms`.
- It did not run a real `.vrma` beside a real `.vrm` on one stage. The fixture's
  `/Clip` reproduces what the reader authors, including `SkelBindingAPI` and
  `skel:animationSource` on the skeleton.
- It did not run `motion_retarget` over `retargeted_rig.usda`. The §9 table
  comes from reading `ReadClip` and `Options.cpp`; the parity run is P0-6's.
- It did not find out why `execMotion`'s type registration came first in the
  session that loads both bundles (§3). The measured consequence is that a
  suite composing both bundles cannot catch a missing registration.
- It did not load either bundle from a packaged artifact; that is P0-3's smoke.
- It ran on Windows only. The committed suites run on all three lanes. The
  timing in §2 is one workstation's and is not asserted anywhere.
