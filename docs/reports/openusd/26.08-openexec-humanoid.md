# OpenUSD 26.08 OpenExec, a rig and a humanoid on this workspace's own schema

- Date: 2026-09-13
- Version exercised: **OpenUSD 26.08**, the pinned `cy2026`/`usd` runtime — the
  release [the migration audit](26.08-openexec-migration.md) read and every
  earlier report in this series ran. Like the
  [blending report](26.08-openexec-blending.md), this run used a local build of
  that release adopted as the runtime, not the published GHCR leaf.
- Occasion: [the OpenExec plan](../../roadmap/openexec-foundation.md) §6, P0-5.
  `plugins/execVrm` is the second exec bundle, and `vrm.computeTargetSkeleton`
  and `vrm.computeHumanoidMap` are its first two computations. They are the
  first computations in this repository registered on an **applied API schema**,
  and the first on a schema this workspace **defines itself** (`VrmHumanoidAPI`,
  from `vrmSchema`).
- Method: **read, then run.** `pxr/exec/vdf/parallelExecutorEngineBase.h`,
  `pxr/exec/exec/typeRegistry.cpp` and `pxr/exec/exec/pluginData.cpp` at
  `v26.08` explain §4 and §6; they were read *after* the first run printed what
  they explain, not before. Two committed suites measure everything marked
  **(test)**: `execVrm_humanoid` drives the built bundle through
  `PXR_PLUGINPATH_NAME` without linking it, over `humanoid_rig.usda`, and runs a
  second time as `execVrm_humanoid_without_schema` under an environment that
  registers no `vrmSchema`; `execVrm_rig` tests the seam with no stage. Claims
  marked **(negative)** were measured by disabling one line, rebuilding (a
  `Building CXX object` line confirming it), watching a suite go red, and
  restoring it. One claim about `execMotion` is marked **(probe)**: a throwaway
  case added to `execMotion_sample`, run once and removed, and §4 says what it
  did.
- What this does **not** supersede: any earlier report. It **narrows** one
  finding of [the sampling report](26.08-openexec-sampling.md) (§4 below) and
  finds that one sentence of `execMotion`'s own documentation is false for one
  clip shape.

## TL;DR

1. **An attribute a schema defines and the stage gives no value reaches a
   callback as ONE element of the type's fallback, not as nothing.** The
   executor posts a `TF_WARN` ("No value set for output") and fills the input
   with Sdf's default for the type: an empty token, an identity matrix, a zero
   vector, an identity quaternion. Unauthored and value-blocked arrive the same
   way; an authored empty array arrives as zero elements. The sampling report's
   "a missing input has no value" is true of an attribute the prim does not have
   at all, and false of one its schema defines. (test)
2. **So an absent value is recognised by what it is, not by its absence**, and
   in one rig shape it cannot be recognised at all. A skeleton that authors no
   `joints` arrives as one joint named `""`, and is refused for that. A one-joint
   skeleton with no rest pose arrives as one joint and one identity matrix, and
   is answered as identity. And a one-joint *clip* with nothing keyed comes out
   of `execMotion`'s `motion.sampleAnimation` with its hips at identity and its
   root **at the origin**. (test, probe)
3. **A computation on an applied API schema from this workspace's own schema
   bundle resolves on a prim another plugin types.** The importer's humanoid is
   a `UsdGeomScope`, which `execGeom` declares; the map computes on it through
   `VrmHumanoidAPI`. A prim carrying every attribute and *not* the schema has no
   map — the offline tool finds a humanoid by attribute and would read it. (test)
4. **That bundle is a runtime requirement, not a link one.** exec resolves
   `UsdVrmHumanoidAPI` by type name when it reads the Exec block. Without
   `vrmSchema` in the session the skeleton still computes and the humanoid map is
   "not found", after a chain of five coding errors of exec's own. (test)
5. **Fifty-five inputs declared in a loop work, and the names are the schema's.**
   `Inputs()` appends on every call. motionCore's bone vocabulary and
   `VrmHumanoidAPI`'s `vrm:humanBones:*` properties are the same 55 names, read
   off the schema's prim definition. (test)
6. **Invalidation follows the relationship across schemas**, and it follows the
   dependency rather than the value: a rest-transform edit reports the map,
   whose value does not change. A retargeted `vrm:skeleton` reaches the map with
   no request rebuilt. (test)

## 1. What ran

`plugins/execVrm` registers `vrmRetarget::TargetSkeleton` and
`vrmRetarget::HumanoidMap` as execution value types — which needed an exact
`operator==` on both, and on `TargetJoint`, added to `vrmRetarget` for this
bundle — and two computations:

| Computation | Registered on | Reads | Answers |
| --- | --- | --- | --- |
| `vrm.computeTargetSkeleton` | `UsdSkelSkeleton` (typed) | `joints`, `restTransforms` | the rig as `vrmRetarget` reads it: tokens, parents from the joint paths, each rest transform decomposed with scale and shear dropped |
| `vrm.computeHumanoidMap` | `UsdVrmHumanoidAPI` (applied) | the 55 `vrm:humanBones:*` tokens, and `vrm.computeTargetSkeleton` and `computePath` across `vrm:skeleton` | `HumanoidMap::SetJointToken` for each binding against the one skeleton the relationship reaches |

Both refuse execMotion's way: a `TF_RUNTIME_ERROR` naming the computation and
`SetEmptyOutput`, because an empty skeleton and an empty map are both answers
([root-motion report §6](26.08-openexec-root-motion.md)).

The fixture mirrors the importer's layout — `SkelRoot "Asset"`, the skeleton
under `skel`, the humanoid under `rig` as a `Scope` with `VrmHumanoidAPI`
applied — with VRoid joint names, so a map that resolved `hips` by looking for a
joint called hips would find nothing, and one rest transform turned 90° about +Z
and scaled by 2, which has to decompose to `(0.70710678, 0, 0, 0.70710678)` with
the scale gone. Six bones are bound. A seventh attribute,
`vrm:humanBones:leftUpperArmTwist`, is not a bone of the vocabulary and names the
hips joint on purpose: a node that read it would bind two bones to one joint and
refuse. (test)

## 2. An applied schema from this workspace, on a prim another plugin types

[The mechanism report](26.08-openexec-mechanism.md) §3 measured the route on a
throwaway probe with `UsdSkelBindingAPI` on a `UsdGeomXform`. Here it is the
real case: `VrmHumanoidAPI`, a schema `vrmSchema` generates, applied to a
`UsdGeomScope`, whose typed schema `execGeom` declares. The map computes, and
declaring `UsdVrmHumanoidAPI` in execVrm's `Info.Exec.Schemas` collides with
nothing — the only other Exec blocks in the pinned runtime are `execGeom`'s and
`execIr`'s. (test)

**The schema is the route, not the attributes.** A `Scope` carrying
`vrm:humanBones:hips` and `vrm:skeleton` with no `VrmHumanoidAPI` applied has no
`vrm.computeHumanoidMap` — an empty value and a coding error, the shape every
"computation not found" takes. `tools/motionRetarget` finds a humanoid by
`HasAttribute("vrm:humanBones:hips")` and would read that prim. The importer
always applies the schema, so this is a divergence on hand-authored stages only,
and it is the first P0-6 has to classify that is about *which prim is a
humanoid* rather than about a value. (test)

## 3. Fifty-five inputs, and whose names they are

`VrmHumanoidAPI` spells a binding as one attribute per bone, so the node declares
one input per bone. `ExecPrimComputationBuilder::Inputs` appends on every call
(`computationBuilders.h`: each argument becomes one `_AddInputKey`), so the
registration keeps the builder in a variable and declares the 55 in a loop over
motionCore's vocabulary rather than spelling them. It compiles, the request is
valid, and each of the six authored bindings arrives. (test)

The names are built as `vrm:humanBones:` + `motion::HumanBoneName(bone)`, and an
input declared for an attribute the schema does not define would never carry a
value with nothing reporting it
([root-motion report §3](26.08-openexec-root-motion.md)). So the suite reads
`VrmHumanoidAPI`'s prim definition from the schema registry and compares both
lists both ways: **55 and 55, identical.** That is the one comparison that
catches either side growing a bone the other lacks. (test)

## 4. An attribute the schema defines and the stage leaves empty is a value

The first run of `execVrm_humanoid` printed 49 warnings like this one, per
compute:

```text
Warning: in _ComputeNode at line 1898 of pxr/exec/vdf/parallelExecutorEngineBase.h
  -- No value set for output Exec_AttributeInputNode
     /Asset/rig/Humanoid.vrm:humanBones:leftHand [__computeResolvedValue][out]
     of type TfToken named out
```

— one for each of the 49 bones the fixture does not author. And the refusal for
a value-blocked `restTransforms` said the skeleton stated 7 joints and **1**
rest transform, where the suite had expected 0.

The source explains both. Every attribute a prim's schema defines has an
`Exec_AttributeInputNode` whether or not the stage gives it a value. When its
`computeResolvedValue` produces nothing, `_ComputeNode` warns and then **fills
the output with a default value** (`VdfExecutionTypeRegistry::FillVector`, one
element, since an array input is boxed by element). The default is the fallback
the type was registered with, and `ExecTypeRegistry`'s constructor registers
every Sdf value type with `SdfValueTypeName::GetDefaultValue()`
(`exec/typeRegistry.cpp`) — an empty token, an identity matrix, a zero vector,
an identity quaternion. So the callback receives one element of that fallback.

Measured on the built bundle (test):

| The stage states | The callback receives | Warnings |
| --- | --- | --- |
| a bone the humanoid does not author | the empty token | one per bone: **49** on the first compute, 49 distinct, **0** on a cached recompute |
| a bone value-blocked | the empty token | one |
| `restTransforms` value-blocked on a 7-joint skeleton | **one** identity matrix — refused, 7 against 1 | one, naming `Skeleton.restTransforms` |
| a `Skeleton` authoring nothing | **one** empty joint token and **one** identity matrix — the counts pair | two |
| `joints = []` and `restTransforms = []` authored | zero elements of each — the empty skeleton, answered | none |
| one joint and no `restTransforms` | one joint and one identity matrix — **answered as identity** | one |

**What this narrows.** [The sampling report](26.08-openexec-sampling.md) §2
measured that `.Required()` does not refuse a missing attribute and the callback
runs "with an input that has no value". That attribute was `motion:timeCodesPerSecond`
— a custom one the prim does not have at all, which compiles to no input node,
so the pointer is null. It is **not** what happens to an attribute the prim's
schema defines: that one has a value, and the value is the fallback. The
root-motion report's "a callback cannot tell *absent* from *not asked for*" gains
a third member for schema attributes — it cannot tell *absent* from *the
fallback* either.

**What it decides in this bundle.** Neither node can ask whether a value was
authored — exec's builtins are `computeTime`, `computeValue`,
`computeResolvedValue` and `computePath`, and none says so — so an absent value
is recognised by what it arrives as:

- **An empty joint token is refused** (`vrm.computeTargetSkeleton`). No UsdSkel
  skeleton has one, and it is exactly what an unauthored `joints` becomes.
  (negative: with the check disabled, the bare skeleton answered a one-joint
  skeleton whose joint is named nothing, and both suites went red.)
- **An empty binding token binds nothing** (`vrm.computeHumanoidMap`) — which
  had been chosen for parity with the offline tool before this was measured, and
  is now forced: refusing it would refuse every humanoid that does not bind all
  55 bones. An unauthored bone and an authored `""` are one value by the time
  they arrive.
- **A one-joint skeleton with no rest pose is answered as identity**, because
  from inside the callback it *is* an authored identity rest. The offline tool
  answers it the same way, with a warning, so it is not a P0-6 divergence; it is
  pinned in `execVrm_humanoid` so a change in the fallback turns it red.

**What it means one bundle over (probe).** `UsdSkelAnimation`'s `rotations` and
`translations` are schema attributes too. A throwaway case added to
`execMotion_sample` — an in-memory `SkelAnimation` with `joints = ["hips"]`, a
rate of 50 and nothing else authored, sampled at frame 0 — answered
`validRotations = 1`, hips `(1, 0, 0, 0)`, **`root.hasPosition = 1` at
`(0, 0, 0)`**: a rotation and a root nobody stated. The same case with two
joints answered no bones and no root, because one fallback element does not pair
with two joints. So `ExecMotionPose.h`'s "a clip that authors no translations
produces a pose with no root position" is **false for a one-joint clip**, and
nothing in the callback can make it true — the fallback and an authored origin
are the same value. It is recorded there rather than fixed, and the case was
removed from the suite after the run; a committed assertion belongs with a
decision about it (§8).

**The cost in warnings is real on a real avatar.** An imported VRM authors the
bones its source file maps and no others, so every compute of its humanoid map
warns once per unmapped bone — the fingers of a rig without them, the jaw, the
eyes. The map is `uniform` and cached, so that is once per edit rather than per
frame, and the warnings are the executor's, not ours. A fallback of `""` on
each `vrm:humanBones:*` in `vrmSchema` would silence them, and would make "an
unbound bone reads as the empty token" a statement of the schema rather than of
the executor (§8).

## 5. Invalidation across a relationship and across schemas

`vrm.computeHumanoidMap` is registered on an applied schema and reads a
computation registered on a typed one, on another prim, through `vrm:skeleton`.
The request's value callback records which of its two keys each edit reports
(test):

| Edit | Skeleton reported | Map reported | Recomputed |
| --- | --- | --- | --- |
| nothing (recompute) | no | no | identical values |
| `ChangeTime` | no | no | identical values — every input of both is `uniform` |
| rebind `head` to `Root` | **no** | yes | head at index 0 |
| move a rest translation | yes | **yes** | a new skeleton; the **same** map |
| `vrm:skeleton` → a second skeleton with the joints reversed | — | yes | every index follows: hips 5, upper arm 0, head 6 — no request rebuilt |

The fourth row is the one worth keeping: a rest transform moves no joint index,
and the map is reported anyway. **Invalidation follows the dependency, not the
value**, so a consumer of the map pays a recompute for every rest-pose edit. The
last row is [the blending report](26.08-openexec-blending.md) §3's relationship
edit, measured across two schemas rather than within one.

The relationship is read twice, as `motion.blendPoses` reads its own, because a
target that provides no `vrm.computeTargetSkeleton` and one whose skeleton
refused both vanish from the fan-in
([blending report §2](26.08-openexec-blending.md)). Here the count decides the
answer rather than only the message. (negative: with the count taken from the
skeletons that came back, `vrm:skeleton = [</Asset/skel/Skeleton>, </Asset/skel>]`
— a skeleton and a `Scope` — **answered a map** against the skeleton, where the
humanoid had named two objects; with one target that refused, the map still
refused, but as "reaches nothing".) (test for the refusals: no target, a target
naming no prim, two targets, a target that is not a skeleton, and a skeleton that
refused.)

## 6. The schema bundle is a runtime edge, not a link one

execVrm links nothing of `vrmSchema` — no library, no generated class, no
`UsdVrmTokens`. What it needs is the **type name**: exec's `_ReadPluginMetadata`
resolves each key of `Info.Exec.Schemas` with `TfType::FindByName`
(`exec/pluginData.cpp`), and `UsdVrmHumanoidAPI` is declared by vrmSchema's
plugInfo `Types` block. `execVrm_humanoid_without_schema` runs the suite's
binary with `PXR_PLUGINPATH_NAME` **set** — not prepended — to execVrm's
resources alone (test):

```text
Unknown schema type name 'UsdVrmHumanoidAPI' encountered when reading Exec plugInfo.
Attempt to build computations for unknown schema type name 'UsdVrmHumanoidAPI'.
Attempt to register computation 'vrm.computeHumanoidMap' using an unknown schema type.
Failed to find computation 'vrm.computeHumanoidMap' on provider '/Asset/rig/Humanoid'
Failed verification: ' _resultOutputs.size() == 1 ' -- Expected exactly one output
  for value key '/Asset/rig/Humanoid [vrm.computeHumanoidMap]'; got '0'
```

and `vrm.computeTargetSkeleton` still answers its seven joints, because
`UsdSkelSkeleton` needs nothing of `vrmSchema`. So a missing schema bundle loses
exactly the computations on its schemas, as a chain of coding errors and an
empty value, never a load failure — the same shape as a missing Exec block, one
level down. That is what `requires.bundles: vrmSchema` in execVrm's manifest
states, and the suite refuses to run the measurement at all if the schema
registry does know `VrmHumanoidAPI`, since it would then measure nothing.

## 7. The wrapper, the sixth boundary finding, and what P0-6 inherits

`vrm.computeHumanoidMap` is `HumanoidMap::SetJointToken` per binding against one
skeleton: a wrapper, asserted as one in `execVrm_rig`, where the node's map is
compared to the library's own over the same bindings.

`vrm.computeTargetSkeleton` is the plan's **sixth boundary finding, and of the
sampler's kind**: building a `TargetSkeleton` from a skeleton's rest transforms
exists in `tools/motionRetarget`'s `StageIo.cpp` (`ReadSkeletonRest`,
`DecomposeRest`), in a tool a bundle cannot call, and the half that is plain
arithmetic — matrix to rotation and translation — has no `vrmRetarget` entry
point. The decomposition is in the seam, matched to the tool's line for line so
the two cannot differ by a normalization step. The ask for
[boundary consolidation](../../roadmap/boundary-consolidation.md) §1 is a
`TargetSkeleton` built from tokens and rest matrices, beside the class.

**Five places this bundle and the offline tool answer differently**, each a
statement the stage makes that the tool tolerates and the bundle refuses or
cannot see. None is numerical; all are P0-6's *missing-field semantics* category,
and none is reachable from what the importer authors:

| The stage states | `motion_retarget` | `execVrm` |
| --- | --- | --- |
| a skeleton whose `restTransforms` do not pair with its joints | assumes identity rest, warns | refuses the skeleton, and the map by propagation |
| a binding to a joint the skeleton lacks | warns, leaves the bone unmapped | refuses the map, naming the bone |
| two bones on one joint | bakes it; the later binding wins, with a warning | refuses the map, naming both |
| no `vrm:skeleton` | the first skeleton on the stage | refuses — a computation has no stage to search |
| the attributes without `VrmHumanoidAPI` | reads them | no computation on that prim (§2) |

## 8. What this changes in the plan

1. **P0-5 starts, with two of its five nodes.** `vrm.computeTargetSkeleton` and
   `vrm.computeHumanoidMap` are in; `vrm.computeRestPoseCorrection`,
   `vrm.humanoidRetarget` and `vrm.computeJointLocalTransforms` remain.
2. **Every node that reads a schema attribute owes a decision about the
   fallback**, the way every node already owes its own refusal
   ([sampling report §2](26.08-openexec-sampling.md)). For each such input:
   what does one fallback element look like against the others it pairs with,
   and is there a shape where it pairs? `motion.sampleAnimation` has one (§4); it
   is recorded in its header, and P0-6 inherits it as a known divergence on
   one-joint clips.
3. **A candidate schema change, not taken here:** a fallback of `""` on each
   `vrm:humanBones:*` in `vrmSchema`. It would silence one executor warning per
   unbound bone per map compute and put the "unbound reads as empty" rule in the
   schema. It changes what `UsdAttribute::Get` returns for an unauthored bone
   from *no value* to `""`, which `tools/motionRetarget`'s reader already treats
   as unbound — but it is a schema-contract question, and it belongs with
   BND-0's producer contract rather than in a node's PR.
4. **An upstream ask to file with P0-7's**: an input that computes no value
   should reach a callback as no value — or exec should offer a builtin that says
   whether an attribute has one. As 26.08 stands, a callback cannot distinguish
   an absent schema attribute from its fallback, and the only evidence is a
   warning it never sees.
5. **P0-6's harness owns a table it did not have**: the five divergences in §7.

## 9. What this did not do

- It did not build `vrm.humanoidRetarget` or run anything through
  `vrmRetarget::PoseRetargeter`. The map and the skeleton are the retargeter's
  inputs; whether they are the *right* inputs for a real avatar is the next
  node's measurement.
- It did not run an imported `.vrm`. The fixture mirrors the importer's layout
  and the §4 warning count on a real avatar is inferred from it, not measured.
- It did not test the other `Vrm*API` schemas the workspace contract reserves
  for this bundle, and execVrm does not declare them yet.
- It did not commit the `execMotion` one-joint case (§4, probe), and it did not
  measure `scales` or `blendShapeWeights`, which no node reads.
- It did not load the bundle from a **packaged** artifact; like execMotion's
  suites it loads the built tree, and P0-3's artifact-only smoke is where
  packaged discovery belongs.
- It ran on Windows only. The fallback path is platform-independent source; the
  committed suites run on all three lanes.
