# OpenUSD 26.08 OpenExec, a node that answers with something else

- Date: 2026-09-06
- Version exercised: **OpenUSD 26.08** — the pinned `cy2026`/`usd` runtime, the
  same artifact [the migration audit](26.08-openexec-migration.md) read and the
  [mechanism](26.08-openexec-mechanism.md), [sampling](26.08-openexec-sampling.md)
  and [filtering](26.08-openexec-filtering.md) reports ran.
- Occasion: [the OpenExec plan](../../roadmap/openexec-foundation.md) §6, P0-4 —
  `motion.extractRootMotion`, the third real computation and the first whose
  **result is not a pose**. Everything the bundle had produced until now was a
  `motion::HumanoidPose`, so nothing had yet said whether a bundle may register
  a second value type, or whether a computation may answer in a type other than
  the one it reads. It is also the first node whose policy has three settings
  rather than a number, which is what made the third answer to "what does an
  absent input cost" reachable.
- Method: **run, not read.** Two vehicles, both committed: the `execMotion_root`
  CTest target ([plugins/execMotion/tests/](../../../plugins/execMotion/tests/)),
  which drives the shipped bundle through `PXR_PLUGINPATH_NAME` without linking
  it, over `rooted_clip.usda` and `sampled_clip.usda` — the same clip with and
  without an authored intake policy; and `execMotion_pose`, which holds the
  seam's arithmetic with no stage. Every claim marked **(test)** is asserted in
  one of the two. §3 is marked **(negative)**: it was measured by deleting a
  line, rebuilding and watching the suite go red, which is also how this node's
  two policy paths were checked — the clip's stated token and the library's
  default each turn a suite red when the code that carries them is removed.
- What this does **not** supersede: any earlier report. This one adds what the
  first three could not reach: a second registered type, a dependent whose type
  differs from its input's, and one override serving two nodes. §6 **corrects**
  one sentence of the sampling report — the shape a refusal takes — and corrects
  it here rather than there, because an audit is history.

## TL;DR

1. **A bundle registers more than one execution value type, and a computation
   may answer in a type other than the one it reads.** `motion.extractRootMotion`
   consumes a `motion::HumanoidPose` and returns a `motion::RootMotion`; one
   request hands back both, side by side, out of the same `ExecUsdCacheView`.
   (test)
2. **Time dependence follows the *link*, not the type.** The filtering report
   measured a dependent inheriting its input's time dependence; this node
   inherits it across a change of result type, declaring no `computeTime` of its
   own. (test)
3. **An input the callback reads but `.Inputs()` does not declare is not an
   error.** The request compiles, the callback runs, and `GetInputValuePtr`
   returns null — so the node silently takes its default path. Nothing in the
   builder, the compile or the run says the declaration is missing. (negative)
4. **A scalar `TfToken` attribute arrives through `GetInputValuePtr<TfToken>`
   with no registration of its own**, the way `float` and `bool` do — the
   `VdfReadIterator` treatment is for *array*-valued inputs, not for the token
   type. (test)
5. **One override drives every node that depends on the key it names.** A single
   `motion.priorPose` substitution, in one `ComputeWithOverrides`, steps the
   filter and derives the velocity together. A driver does not have to know
   which nodes wanted the previous frame. (test)
6. **A missing input now has three answers in this bundle, and the third is
   both.** The rate is refused when absent; the filter's cutoff is defaulted
   when absent; the intake policy is defaulted when **absent** and refused when
   **stated and unrecognized**. The rule underneath is one rule: what an absent
   value costs decides — and a value the clip *stated* that this layer cannot
   honour is never a default.
7. **A refusal has to set no value at all.** A default-constructed result is
   indistinguishable from an answer for both of this bundle's types — a cleared
   `motion::RootMotion` *is* `ignore`'s answer, bit for bit. 26.08's
   void-callback form plus `VdfContext::SetEmptyOutput` is the channel, an empty
   `VtValue` is what reaches the caller, and the absence propagates to
   dependents. Found by review of this change; §6. (test)
8. **The third "not a wrapper" finding, and the first where the wrapper idiom
   was tried and failed.** The rule this node applies lives in
   `LiveCaptureSource::_Condition`, a private method of a capture *session*.
   Composing it the way `motion.filterPose` composes `PoseFilter` — push the
   prior, push the pose, read the head — gives the **wrong answer in the
   ordinary case**, because `Push` refuses a non-increasing timestamp where
   `PoseFilter` reseeds (§5).

## 1. What the node answers

Where the body is at the evaluated frame, under the intake policy the clip
states — `motion::RootMotionIntake`, the library's own enum, reached as a token:

| `motion:root:intake` | What comes back |
| --- | --- |
| absent | `motion::LiveCaptureConfig`'s own default, which is `deriveVelocity` |
| `passthrough` | the root the pose carries, unchanged |
| `ignore` | a cleared `motion::RootMotion` — every presence flag false |
| `deriveVelocity` | `passthrough`, plus a linear velocity where the pose has a position, reported none, and there is a prior position and time between the two |
| anything else | **no value at all**, and a posted error naming the computation (§6) |

`ignore` clears rather than zeroes, and the distinction is the whole reason
`RootMotion` carries presence flags: a cleared root says *this clip does not
place the body*, and a zero position with `hasPosition` set says *the body is at
the origin*. Only the first leaves a rig its own placement.

## 2. Two value types, and a dependent of another type

`ExecTypeRegistry::RegisterType` is called twice in one `TF_REGISTRY_FUNCTION`,
for `motion::HumanoidPose` and `motion::RootMotion`. Both satisfy the registry's
two requirements — not a `VtArray`, and equality comparable, which `motionCore`
has carried since v0.6.0 — and nothing else was needed: no second registry
function, no ordering between them, no per-type plugin metadata.

The computation then declares `.Callback<motion::RootMotion>` over inputs that
include `Computation<motion::HumanoidPose>(...)`. The request compiles, and one
`ExecUsdCacheView` returns a `VtValue` holding a pose at one index and one
holding a root motion at another. **(test)**

That the two types differ is asserted rather than assumed, on both indices, for
a reason the compiler cannot help with: a callback's declared result type and
what it actually returns meet on the far side of a `VtValue`, so a drift between
them is a run-time surprise in the consumer and not a build error here.

## 3. An undeclared input is silent (negative)

The intake attribute is read in the callback with
`ctx.GetInputValuePtr<TfToken>(_tokens->rootIntake)` and declared at the bottom
with `AttributeValue<TfToken>(_tokens->rootIntake)`. Deleting the declaration
and leaving the read:

- the bundle **compiles**;
- `BuildRequest` returns a request whose `IsValid()` is **true**;
- the callback **runs**; and
- the pointer comes back **null**, so the node takes its absent-value path.

The clip's `passthrough` then reached nothing and the suite failed on the one
assertion that says the policy arrived — which is what the negative verification
was for. Nothing anywhere reported a missing declaration.

This is the third shape of the same 26.08 property. The mechanism report found a
`.Required()` stage metadatum that yields no value; the sampling report found a
`.Required()` attribute that is missing from the stage and yields no value; this
is an input that was never declared at all. **An exec callback cannot tell
"absent" from "not asked for"**, and the consequence for this plan is unchanged
and now general: a node's own refusal is the only refusal there is, and a test
that never removes the declaration cannot see the difference.

## 4. A token input, and one override for two nodes

A scalar `TfToken` attribute declares as `AttributeValue<TfToken>(name)` and
arrives through `GetInputValuePtr<TfToken>`, with no `RegisterType` of its own —
the same as `float` and `bool` in the filtering report. The `VdfReadIterator`
treatment the same type gets for `joints` belongs to the *array*, not to the
token. **(test)**

The override half is a driver property rather than a type one.
`motion.filterPose` and `motion.extractRootMotion` both want the previous
frame's answer, and both read it from `motion.priorPose`. One request asking for
both, one `ComputeWithOverrides` supplying one pose: the filter takes its step
and the root derives its velocity, in the same call, from the same substituted
value. **(test)**

So the driver contract the filtering report asked for gets simpler rather than
longer: a driver holds **one** previous answer per prim and substitutes it once
per frame, whatever the request happens to contain. The alternative — a prior
per node — would put back exactly the hand-kept, out-of-step state the purity
rule pushed out of the graph.

## 5. The wrapper idiom, tried and failed

`motion.filterPose` is a wrapper by composition: `motion::PoseFilter` has no
one-step entry point, so the bundle constructs one, seeds it with the prior pose
and steps it with the current one. The same move was tried here first, and it
does not transfer.

The rule this node applies is `motionRuntime`'s — it is written down in the
[motion contract](../../design/MOTION_CONTRACT.md) and implemented in
`LiveCaptureSource::_Condition`, which is **private**, on a class that is a
capture *session*: it owns a pose buffer, a smoothing filter, held-bone state
and statistics. Composing a per-frame answer out of it would mean constructing a
session per callback, pushing `prior` and then `pose`, and reading the buffer
head. And it gives the wrong answer in this bundle's **ordinary** case:

| | two poses at the same instant |
| --- | --- |
| `motion::PoseFilter::Apply` | **reseeds** — the pose is returned unchanged, which is exactly what an un-overridden node should answer |
| `LiveCaptureSource::Push` | **refuses** the second frame, so the buffer head is the *prior* and the composed answer is the previous frame's root |

An un-overridden `motion.priorPose` forwards the clip's own pose, so the two
instants are the same instant — the common case, not an edge one. The idiom
would need a bundle-invented fallback to correct for the refusal, at which point
the composition is no longer the library's answer.

So the derivation is three lines in `execMotion`'s seam, matched condition for
condition to the library's, asserted in `execMotion_pose` against the definition
— distance over the seconds between two instants — rather than against the
library. It is recorded as a finding rather than hidden, and the ask is in §6.

**What this does not claim.** It is not a defect in `LiveCaptureSource`: a class
that refuses a repeated timestamp is right to, for the stream it was written
for. The finding is that the *rule* has no home outside it.

## 6. A refusal has to be an empty value

This section was added after the rest of the report: **review of the change
found that the node's refusal was indistinguishable from one of its own answers**,
and the finding is worth more than the fix.

The refusal originally returned a default-constructed `motion::RootMotion`, in
the shape every earlier node here used. But a cleared `RootMotion` is
`motion:root:intake = "ignore"`'s legitimate answer, **bit for bit** — and it is
also what a pose carrying no position produces, and what the default time code
produces. So a clip that misspelled `passthrough` posted a `TfError` and then
handed every consumer a value that reads exactly like a deliberate *this clip
does not place the body*. That is the mirror image of the mistake §1's table
refuses to make, and it inverts the argument the node was designed on: the rate
is refused rather than defaulted precisely because a guessed second cannot be
told from a measured one.

**26.08 has a channel for it, and it is documented.** `.Callback<T>` accepts a
callback returning `void`, which must set its result through
`VdfContext::SetOutput`, `VdfContext::SetEmptyOutput`, or a write iterator. A
refusal calls `SetEmptyOutput`, and `ExecUsdCacheView::Get` then returns an
**empty `VtValue`** — measured, not assumed. **(test)**

An empty value is the one shape no computation in this bundle ever produces as
an answer, which is what makes it the only refusal that stays distinguishable.
So the shape is now the bundle's rather than this node's, and the earlier nodes
moved to it:

| Node | Refuses when | Used to answer with | Now answers with |
| --- | --- | --- | --- |
| `motion.sampleAnimation` | the clip states no usable rate | a default `HumanoidPose` | no value |
| `motion.priorPose` | the pose it forwards is absent | a default `HumanoidPose` | no value |
| `motion.filterPose` | there is no pose to filter | a default `HumanoidPose` | no value |
| `motion.extractRootMotion` | the pose is absent, or the intake token names no policy | a cleared `RootMotion` | no value |

`motion.identityPose` has no refusal to express and keeps the value-returning
form, so **both callback forms are live in one bundle** — also measured.

**A refusal propagates**, and that is the second measurement here. A clip with no
rate now reaches a caller as a refusal at `motion.sampleAnimation` *and* at
`motion.filterPose`, rather than as a filtered version of a pose nobody sampled:
the dependent's `GetInputValuePtr` returns null, it posts its own error, and it
sets no value in turn. **(test)** The empty value crosses the computation-to-
computation link the same way a value does.

**What this corrects in an earlier report.** [The sampling
report](26.08-openexec-sampling.md) recorded this node's refusal as "an empty
pose", which was accurate on the day it was written and is no longer the
behaviour. The 26.08 claims it makes are untouched — what changed is this
bundle, not the release — and the audits are history rather than a manual, so it
is corrected here instead of edited there.

**What is still not distinguishable.** An empty value is also what an
*unregistered* computation returns ([the mechanism
report](26.08-openexec-mechanism.md)), and what a request whose plugin failed to
load returns. A consumer telling a refusal from a missing plugin still has to
read the `TfError`; what it no longer has to do is tell a refusal from an answer.

## 7. What this changes in the plan

1. **P0-4's remaining nodes may answer in new types.** §2 removes the last
   reason to route everything through `HumanoidPose`: `motion.interpolatePose`
   and `motion.blendPoses` are pose-valued anyway, but the constraint that
   decided that is now measured rather than assumed.
2. **The driver contract shrinks by one line.** §4 says a driver holds one
   previous answer per prim, not one per node — which is what the contract
   should say when P0-6's parity harness needs it written down.
3. **A third boundary finding, with the wrapper route ruled out rather than
   skipped.** §5's ask: a stateless
   `ConditionRootMotion(prior, pose, intake)` free function beside the session
   class, so the rule has one implementation again. It is the same *kind* of ask
   as `Step(prior, pose, options)` and it is stronger, because here the
   composition was tried and produces a wrong answer rather than an awkward one.
   [Boundary consolidation](../../roadmap/boundary-consolidation.md) is the
   track that acts on it.
4. **`motion:root:intake` joins the producer contract's list**, beside
   `motion:timeCodesPerSecond` and `motion:filter:*`. Like the filter policy and
   unlike the rate it is a *policy* rather than a shim for an upstream gap, and
   whether policy belongs on a clip at all is
   [BND-0](../../roadmap/boundary-consolidation.md)'s question.
5. **The absent-input rule is general enough to state once.** §6 of the TL;DR:
   default where an absent value selects the library's documented behaviour,
   refuse where it would produce a number no consumer can tell from a measured
   one — and always refuse a value the clip stated that this layer cannot
   honour. Every node in P0-4 and P0-5 answers it with that rule rather than
   with a preference.

## 8. What this did not do

- It did not test fan-in, `Relationship().TargetedObjects<T>()`, or two
  connections into one input. `blendPoses` is still where those land.
- It did not measure a computation reading **two** other computations of
  different types, only one of each.
- It did not measure an override of a `motion::RootMotion` value key — the
  override path was exercised on the pose type only, and whether a second
  registered type overrides the same way is untested.
- It did not run against a **packaged** bundle. Like the three suites before it,
  `execMotion_root` loads a built tree through `PXR_PLUGINPATH_NAME`; the
  artifact-only run is still P0-3's.
- It did not compare the derived velocity against a live session's. That is
  P0-6 parity's, and this is now the **fourth** known divergence on its list
  after the two samplers and the filter's dropped state — though this one is
  expected to be an equality, since the two implementations are the same three
  lines.
