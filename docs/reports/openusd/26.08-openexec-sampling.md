# OpenUSD 26.08 OpenExec, sampling a clip

- Date: 2026-09-06
- Version exercised: **OpenUSD 26.08** — the pinned `cy2026`/`usd` runtime, the
  same artifact [the migration audit](26.08-openexec-migration.md) read and
  [the mechanism report](26.08-openexec-mechanism.md) ran.
- Occasion: [the OpenExec plan](../../roadmap/openexec-foundation.md) §6, P0-4 —
  the first computation with an algorithm behind it, `motion.sampleAnimation`.
  The mechanism report ended with a question this one had to answer before that
  node could be written: where the frame-to-seconds rate enters
  ([§5](26.08-openexec-mechanism.md#5-a-computation-is-given-a-frame-and-cannot-find-the-rate),
  §6.5).
- Method: **run, not read.** One vehicle, and it is committed: the
  `execMotion_sample` CTest target
  ([plugins/execMotion/tests/](../../../plugins/execMotion/tests/)), which drives
  the shipped bundle through `PXR_PLUGINPATH_NAME` without linking it, over two
  fixtures — a clip that states its rate and one that does not. Every claim here
  is asserted there, so the day one changes upstream is a red lane rather than a
  stale paragraph. No probe was needed this time.
- What this does **not** supersede: either earlier report. The migration audit
  stays the source for value types, connection dataflow, `ExecIr` and the Hydra
  path; the mechanism report stays the source for schema declaration,
  invalidation and the timestamp constraint. This one extends the last of those
  to a second kind of input, and measures three behaviours neither could have.

## TL;DR

1. **`.Required()` does not refuse a missing *attribute* either.** The mechanism
   report found that a `.Required()` stage metadatum resolves and carries no
   value; the same is now measured for an attribute the stage does not have at
   all. The request compiles, `IsValid()` is true, and the callback runs with an
   input that has no value. **In 26.08 a missing input is the callback's problem,
   not the compiler's** — so every node that needs something has to check for it
   and refuse.
2. **A time-sampled input makes a value key time-dependent, and the request is
   told.** `ChangeTime` reports `motion.sampleAnimation` to the time callback and
   goes on reporting nothing for `motion.identityPose`, whose only input is a
   `uniform` array. The two assertions are the same measurement from opposite
   sides.
3. **The default time code resolves a keyed clip to nothing.** A system evaluates
   at `UsdTimeCode::Default()` until `ChangeTime` is called, and a clip that
   authors only time samples has no value there — so the first compute of a
   freshly built request over a real clip returns an *empty* pose, not the first
   frame.
4. **Between two keys, the answer is USD's.** An exec input arrives already
   resolved at the evaluated frame, and 26.08 interpolates a `quatf[]` by slerp:
   a 90° turn read halfway between its two keys is 45°. So an exec sampler is not
   `motion::SampleAnimation`, and P0-6 parity has two samplers to compare rather
   than one implementation to check.

## 1. What ran

`plugins/execMotion` gained `motion.sampleAnimation` on `UsdSkelAnimation`: it
reads `joints`, `rotations`, `translations` and `motion:timeCodesPerSecond` off
the clip plus the builtin `computeTime`, and returns the `motion::HumanoidPose`
the clip states at the frame the system is evaluating, stamped in seconds.

The fixtures are a clip whose head turns 90° about +Y between frame 0 and frame
100 at 50 time codes per second, and a byte-identical copy of it with the rate
attribute removed. The stage metadatum `timeCodesPerSecond = 50` is present in
**both**, which is the point of the second one: the number a computation needs is
right there on the stage, `UsdStage::GetTimeCodesPerSecond()` reports it, and exec
delivers none of it to a callback.

| Step | Result |
| --- | --- |
| request compile | one value key, `(prim, "motion.sampleAnimation")`, `IsValid()` true |
| compute at the default time code | a pose with **no** bones, no root and no timestamp (§4) |
| `ChangeTime(0)`, compute | four bones, head at 0°, root at the origin, timestamp `0.0`; the time callback fires (§3) |
| `ChangeTime(100)`, compute | head at 90°, root at `(0, 1, 2)`, timestamp **2.0 s** — 100 frames at 50 fps |
| `ChangeTime(50)`, compute | head at 45°, root at `(0, 0.5, 1)`, timestamp 1.0 s — a frame nothing keyed (§5) |
| recompute at the same frame | identical value |
| the clip with no rate | the request compiles, the callback runs, and it refuses (§2) |

## 2. `.Required()` does not refuse a missing attribute

**(test)** `motion:timeCodesPerSecond` is declared
`AttributeValue<double>(...).Required()`, the unrated fixture's prim does not
have the attribute, and:

- `BuildRequest` succeeds and `ExecUsdRequest::IsValid()` returns `true`;
- `Compute` runs the callback;
- `ctx.GetInputValuePtr<double>()` for that input returns **null**.

This is the same shape the mechanism report measured for a `.Required()` stage
metadatum ([§5](26.08-openexec-mechanism.md#5-a-computation-is-given-a-frame-and-cannot-find-the-rate)),
on a different kind of input — and the metadata case could still be read as
"metadata is not really an input". An attribute is, so the reading that survives
both is the general one: **in 26.08 `.Required()` does not fail a request whose
input is absent.**

The consequence is a rule for every node in this plan, not a note about one:
a computation that needs a value must check for it and refuse, because nothing
upstream of the callback will. `motion.sampleAnimation` posts a `TF_RUNTIME_ERROR`
naming itself and returns a default-constructed pose; the test asserts the error
text as well as the empty pose, so an unrelated failure that merely dirtied the
error mark cannot pass for this refusal.

Asserted rather than described, in both directions: the suite asserts the request
*is* valid, so the day `.Required()` starts refusing is a red test with a message
saying the callback's own refusal can be simplified.

## 3. Time dependence is declared by the inputs, not by the node

**(test)** `motion.identityPose` reads one `uniform` array and is reported to
**no** time callback when the frame moves — the mechanism report asserts that.
`motion.sampleAnimation` reads two time-sampled arrays and **is** reported, from
the first `ChangeTime` onward. Neither computation says anything about time in
its registration beyond the inputs it declares, and `motion.sampleAnimation`'s
`computeTime` input is not what makes the difference: the identity node could
declare it and still change with nothing.

That is the behaviour the plan wanted and it is worth having measured, because it
is the property that makes a per-frame evaluation cheap: a node whose inputs do
not vary with time is not recomputed when time moves, and nobody has to annotate
it.

## 4. The default time code is not frame zero

**(test)** An `ExecUsdSystem` evaluates at `UsdTimeCode::Default()` until
`ChangeTime` is called. A `UsdSkelAnimation` that authors `rotations` and
`translations` as time samples and no default value has **nothing** to resolve
there, so `motion.sampleAnimation` receives empty arrays and returns a pose with
no bones, no root position and no timestamp.

Two things follow. The first is for callers: the first `Compute` after
`BuildRequest` is at the default time, so a client that forgets `ChangeTime` gets
an empty pose rather than the clip's first frame — and after
`Diagnostics::InvalidateAll()`, which resets the system's time
([mechanism report §4](26.08-openexec-mechanism.md#4-invalidateall-expires-requests-and-forgets-the-time)),
it gets one again.

The second is why the node stamps nothing there. `UsdTimeCode::GetValue()` is a
coding error on the default time code, so `IsNumeric()` has to be checked first;
and having checked it, a pose resolved outside a timeline has no frame to
convert. `motion::HumanoidPose::timestamp` has no absent state, so 0.0 is what it
carries — which costs nothing here, because frame 0 converts to 0.0 at every
rate. "No time" and "the first frame" are the same *stamp*; what differs is which
values USD resolved, and that happened before the callback ran.

## 5. Between two keys, the answer is USD's

**(test)** The fixture keys the head at identity on frame 0 and at 90° about +Y
on frame 100, and keys nothing between. Read at frame 50 through exec, the head
is at **45.0°** and the hips are at `(0, 0.5, 1)`: the quaternion array is
interpolated by slerp and the vector array linearly, as
`pxr/usd/usd/interpolation.h` documents.

An exec input arrives **already resolved at the evaluated time**, which is what
makes this USD's answer rather than the bundle's: there is no way for a
computation to see the clip's other samples. So `motion.sampleAnimation` is **not
a wrapper over `motion::SampleAnimation`** — that function is handed a whole
`motion::HumanoidAnimation` and performs its own lookup with a hold-at-the-edges
rule — and the plan's "every node is a thin wrapper" prediction does not survive
contact with this node.

That is a finding about the boundary rather than about OpenUSD, and it is exactly
the kind [the boundary track](../../roadmap/boundary-consolidation.md) was
scheduled to collect: reading a `UsdSkelAnimation` into a canonical pose *does*
exist in this repository, in `tools/motionRetarget`'s `StageIo.cpp` — in a tool,
where a bundle cannot call it. `execMotion` therefore keeps its own seam over
plain values, and the duplication is recorded rather than hidden.

For P0-6 the consequence is concrete: parity has **two samplers** to compare, not
one implementation to check, and they can legitimately differ between keys. The
comparison has to be made at the clip's own key times, or the difference it
measures will be USD's interpolation and not the retarget's.

## 6. What this changes in the plan

1. **P0-4's rate question is answered**, and the answer is an authored attribute
   rather than a conversion applied on the way out. The reason is the *next*
   node: `motion.filterPose` wraps `motion::PoseFilter`, whose cutoff is
   frame-rate independent because it derives each step's weight from the elapsed
   time between poses — a pose stamped after it leaves the graph reaches that
   filter as time zero. So the rate must be inside the graph.
2. **The producer half is now a contract ask.** `motion:timeCodesPerSecond` is a
   shim for §2's gap and nothing in this repository authors it: the fixtures do,
   and P0-6 parity needs a real clip that does. It is in
   [the plan](../../roadmap/openexec-foundation.md) §9.
3. **Every node in P0-4 and P0-5 owes a refusal.** §2 makes a missing input the
   callback's problem, so "declare it `.Required()`" is not a plan for anything a
   node cannot compute without.
4. **P0-6 gains a method constraint**, from §5: compare at key times, or measure
   USD's interpolation by mistake.

## 7. What this did not do

- It did not test fan-in, `Relationship().TargetedObjects<T>()` or the
  two-connection silent fallback. `blendPoses` is still where those land.
- It did not measure performance, threading, or concurrent evaluation.
- It did not establish **why** `.Required()` does not refuse — whether the
  builder drops the requirement, whether an absent attribute is a valid input
  with no value by design, or whether requiring is enforced somewhere this
  registration did not look. The consequence for the nodes is the same in every
  case, which is why the cause was not chased further.
- It did not sample a clip that authors *default* values beside its time samples,
  which is the one shape §4's "empty at the default time" claim does not cover.
- It ran on Windows only. Nothing measured here is plausibly platform-specific,
  and the committed suite runs on all three lanes and will say so.
