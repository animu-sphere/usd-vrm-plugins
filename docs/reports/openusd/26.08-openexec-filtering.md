# OpenUSD 26.08 OpenExec, a node that needs the last frame

- Date: 2026-09-06
- Version exercised: **OpenUSD 26.08** — the pinned `cy2026`/`usd` runtime, the
  same artifact [the migration audit](26.08-openexec-migration.md) read and
  [the mechanism](26.08-openexec-mechanism.md) and
  [sampling](26.08-openexec-sampling.md) reports ran.
- Occasion: [the OpenExec plan](../../roadmap/openexec-foundation.md) §6, P0-4 —
  `motion.filterPose`, the second real computation and the first that is a
  **recurrence**: `motion::PoseFilter` derives each step's weight from the time
  elapsed since the pose before it, so the node needs a value from a frame it
  is not being evaluated at. The sampling report established that a callback
  cannot see one ([§5](26.08-openexec-sampling.md#5-between-two-keys-the-answer-is-usds)).
  This report is what happened when a node needed it anyway.
- Method: **run, not read.** One vehicle, committed: the `execMotion_filter`
  CTest target ([plugins/execMotion/tests/](../../../plugins/execMotion/tests/)),
  which drives the shipped bundle through `PXR_PLUGINPATH_NAME` without linking
  it, over `filtered_clip.usda` and `sampled_clip.usda` — the same clip with and
  without an authored filter policy. Every claim marked **(test)** is asserted
  there. The seam's own arithmetic is in `execMotion_pose`, which needs no stage.
- What this does **not** supersede: any earlier report. The migration audit stays
  the source for value types and connection dataflow, the mechanism report for
  schema declaration and invalidation, the sampling report for inputs and time.
  This one adds what those three could not reach: chaining one computation into
  another, and supplying a value the graph has no way to derive.

## TL;DR

1. **A computation consumes another computation on the same prim, and the
   registered aggregate crosses that boundary unchanged.** `Computation<T>(name)`
   resolves locally, the request compiles, and `motion::HumanoidPose` arrives at
   the second callback as the first one returned it. The plan's chain is
   therefore expressible as links rather than as one node.
2. **Time dependence propagates across that link.** `motion.filterPose` declares
   neither `computeTime` nor any time-sampled attribute, and it is still reported
   to the request's time callback when the frame moves — because the node it
   reads is time dependent. A downstream node does **not** have to declare
   `computeTime` to be re-evaluated per frame, which makes the sampling report's
   "declare it only if you use it" rule free to follow rather than costly.
3. **A request reports nothing until it has been computed once.** `BuildRequest`
   registers the interest; the *first* `Compute` is what arms it. A `ChangeTime`
   before any compute reaches no callback at all. This one cost a red run.
4. **`ComputeWithOverrides` is how a value the graph cannot derive gets in.** An
   override on one value key is seen by every computation that depends on it, is
   visible as that key's own value in the returned view, does not leak into the
   sibling keys, and does not survive the call.
5. **So a recurrence lives outside the graph, by construction.** The filter's
   state is not held in the callback — it could not be, and stay pure — it is
   handed in as the value of a node that exists to be overridden. Exec does the
   step; the driver owns the sequence. For a live source that is where the state
   already is, in `motionRuntime`'s pose buffer.
6. **`float` and `bool` are pre-registered execution value types.** An attribute
   input of either declares and arrives with no `ExecTypeRegistry::RegisterType`
   of its own.
7. **A pose is not the whole of a filter's state, and the difference is
   measured.** `PoseFilter` keeps a dropped bone's history in its state and out
   of its result, so a bone returning after a missing frame is smoothed there and
   passed through here — 23.8° against 45.0°. Bounded to live sources; a clip's
   bones cannot drop out (§7).

## 1. The shape the problem forced

`motion::PoseFilter::Apply` is a streaming operator: it holds the previous pose
and returns a blend whose weight is `1 - exp(-2π · cutoff · dt)`, where `dt` is
the seconds between that pose and this one. Three ways to give a computation
that history were available on paper, and two are refused before any
measurement:

- **A static in the callback.** Forbidden by exec's cache-safety contract and by
  the motion policy's §11.4 purity rule for the same reason: a value read from
  anywhere but a declared input is invisible to invalidation, so the first stale
  answer would be indistinguishable from a correct one.
- **An authored "previous pose" attribute.** That puts a derived value into the
  scene, and the scene is the one thing every consumer is entitled to read as
  input rather than as cache.
- **An input evaluated at another time.** There is none.
  `Exec_ComputationBuilderValueSpecifier` carries a provider path and a traversal
  and no time at all, and an attribute input arrives already resolved at the
  frame the system is evaluating (sampling report §5).

What is left is to pass the state in — which means the graph has to have a place
to put it. That place is a computation, `motion.priorPose`, whose ordinary value
is the clip's own pose at the evaluated frame and whose purpose is to be
replaced by the caller.

## 2. A computation reads another computation

**(test)** `motion.filterPose` declares:

```cpp
.Inputs(
    Computation<motion::HumanoidPose>(_tokens->sampleAnimation).Required(),
    Computation<motion::HumanoidPose>(_tokens->priorPose).Required(),
    AttributeValue<float>(_tokens->cutoffHz),
    AttributeValue<bool>(_tokens->filterRootPosition),
    AttributeValue<bool>(_tokens->filterRootOrientation));
```

and the request compiles, evaluates, and hands the second callback exactly the
`motion::HumanoidPose` the first one returned. Three things follow that the
earlier reports could only assume.

The **registered aggregate is the currency of the graph**, not only of the
boundary out to a client: it crosses a node-to-node link with no packing, no
element type and no mask. That is what the migration audit's §4 value-type rule
buys, and it is why the plan's chain can be links rather than one large node.

The link is **`Computation<T>()`, not a connection.** 26.08's builtin
`computeValue` forwards across exactly one connection between same-typed
*attributes* and falls back silently at two (migration audit §5.1); none of that
is involved here, because a local computation input is resolved by name on the
provider prim. The connection rule remains what `blendPoses` will have to face.

And the two links are **separately requestable**. All three keys —
`motion.filterPose`, `motion.sampleAnimation`, `motion.priorPose` — are in one
request, which is how the suite can assert that the filtered pose is a step
between two poses it also holds, rather than a plausible number.

## 3. Time dependence follows the link

**(test)** `motion.filterPose` declares no `computeTime` and no attribute that
carries a time sample; its two pose inputs are computations and its three policy
inputs are `custom` scalars with no keys. When the request's frame moves, the
node **is** reported to the time-change callback.

That extends the sampling report's §3 across a node boundary: a value key is
reported when an input value changes between the old time and the new one, and a
*computed* input counts. The consequence for the plan is a relief rather than a
constraint. §3 warned that declaring `computeTime` out of habit costs a recompute
on every frame change; the worry was that a node which genuinely needs the frame
would have to declare it, and every node downstream would then declare it too, to
stay in step. It does not: the dependency is enough. `motion.filterPose` reads
the frame nowhere and is still re-evaluated exactly when the pose it reads
changes.

## 4. A request is armed by its first compute

**(test, and it cost a red run)** The first version of the suite built a request,
called `ChangeTime`, and asserted the time callback had fired. It had not — no
value key was reported, and nothing else was wrong: the same assertion passes
once a single `Compute` runs before the frame moves.

`ExecUsdSystem::BuildRequest`'s documentation says clients "must call Compute()
again to renew their interest" in *future* invalidation after being notified. The
same sentence turns out to describe the first notification too: building a
request expresses what to compute, and computing is what expresses interest in
being told it changed. The three earlier suites never saw this because each of
them computes at the default time code before moving the frame — for a reason
that has nothing to do with invalidation (the sampling report's §4: the default
time code is where a keyed clip resolves to nothing, and they assert that).

A client that builds a request, moves the frame, and waits for a callback before
computing therefore waits forever. That is worth stating plainly, because it is
the shape a naive event-driven driver would take.

## 5. `ComputeWithOverrides` substitutes a computed value

**(test)** `ExecUsdSystem::ComputeWithOverrides(request, {{key, value}})` with
`key = (/Clip, motion.priorPose)`:

| | measured |
| --- | --- |
| reaches the node that *depends* on the key | yes — `motion.filterPose` filters against the supplied pose |
| is visible as the key's own value in the view | yes — `view.Get(kPrior)` is the override, verbatim |
| leaks into sibling keys | no — `motion.sampleAnimation` is unchanged in the same view |
| survives the call | no — the next plain `Compute` is back to the computed value |

The type rule is enforced as documented (an override must hold what the
computation produces, and `motion::HumanoidPose` is what a `VtValue` carries
here because it is a registered execution value type).

That is the whole mechanism the recurrence needs, and it is worth being precise
about what it is *not*: it is not state in the graph. Each `ComputeWithOverrides`
is one evaluation with one substituted value, and the sequence — this frame's
prior pose is the last frame's filtered pose — is a loop in the caller. Exec
never sees two frames at once.

## 6. What the node ships as

```text
motion.sampleAnimation ─┬─────────────────────────────► motion.filterPose
                        └─► motion.priorPose ──────────►      │
                                    ▲                          ▼
                          ComputeWithOverrides        one PoseFilter step
                           (the driver's loop)
```

Un-overridden, `motion.priorPose` forwards the sampled pose, so the filter
smooths the clip against itself: `dt` is zero, `PoseFilter` reseeds and returns
its argument, and `motion.filterPose` **is** `motion.sampleAnimation`. Nothing in
the bundle special-cases that; it is the library's documented answer to a
non-increasing timestamp, and the suite asserts the equality rather than the
reasoning.

Overridden with a pose one frame back, the head lands at `weight` of the 45° the
clip states at frame 50, with `weight` computed in the test from the library's
published definition rather than by calling the library. At the clip's authored
12 Hz over a 0.02 s step that is 0.7786; at `PoseFilter`'s own default of 6 Hz,
which is what a clip stating no policy gets, it is 0.5295. Both are asserted, and
so is the fact that they differ — an expected value produced by the function
under test would have asserted that the library equals itself.

## 7. What the round trip through a pose costs

**(test, in `execMotion_pose`, which needs no stage)** One thing does not survive
being carried as a pose, and it is worth a section because P0-6 is scheduled to
compare these two answers.

`motion::PoseFilter` retains a state strictly richer than the pose it returns.
A bone a pose does not report keeps its stored rotation **in the state** and
stays out of the **result**, which is what lets a brief dropout resume from the
last real sample instead of restarting. Only a result can travel back in as the
next prior pose, so the retained half is dropped at the boundary.

Driven over three instants one frame apart at 50 Hz — head at identity, head
absent, head at 45° — the two disagree on the third:

| | head on the dropout frame | head on the frame after |
| --- | --- | --- |
| `motion::PoseFilter`, streamed | absent | **23.8°** — slerped from the head it kept |
| `FilteredPose`, result fed back as prior | absent | **45.0°** — passed through |

Both are asserted, including the inequality, so the day either side changes this
is a red suite rather than a stale paragraph.

The cost is bounded and it is not the clip's: a `UsdSkelAnimation`'s `joints` are
`uniform`, so no bone drops out of a clip-sourced pose and the two answers cannot
diverge there. It is real for a **live source**, which is what a filter in this
layer is for. Reproducing the carry-forward rule inside `execMotion` would be the
second algorithm the wrapper rule forbids, so §8's ask is sharpened instead: a
one-step entry point has to hand back the *state* as well as the result.

## 8. What this changes in the plan

1. **P0-4's remaining nodes may chain.** §2 and §3 together say a node may read
   another node's result and inherit its time dependency, so
   `extractRootMotion` and `interpolatePose` do not have to re-read the clip.
2. **A driver contract is now a real thing to write.** §4 and §5 are both
   properties a client has to know — compute once to arm the request, and step
   the recurrence through overrides — and neither is discoverable from the
   bundle's computations. P0-6's parity harness is the first client that will
   need them written down.
3. **A boundary finding, for the track scheduled to act on them.**
   `motion::PoseFilter` has no stateless one-step entry point, so `execMotion`
   composes one out of two `Apply` calls (seed, then step). It is a wrapper — the
   algorithm stays in the library, which is the rule that matters — but the idiom
   is a workaround for a missing signature, and a `Step(prior, pose, options)`
   free function is the ask — one that returns the **state** beside the result,
   because §7 is what a caller loses when it can only carry the result. It is the
   second finding of this kind from this plan, after the sampling report's
   duplicate clip reader.
4. **`motion:filter:*` joins the producer contract's list.** Like
   `motion:timeCodesPerSecond`, nothing in this repository authors these
   attributes yet; unlike it, they are a *policy* rather than a shim for an
   upstream gap, and the question of whether policy belongs on a clip at all is
   [BND-0](../../roadmap/boundary-consolidation.md)'s.

## 9. What this did not do

- It did not test fan-in, `Relationship().TargetedObjects<T>()`, or two
  connections into one input. `blendPoses` is still where those land.
- It did not measure more than one override at a time, an override of a key that
  is *not* in the request, or an override of a value key that is itself computed
  from another override.
- It did not measure concurrency: nothing here ran two computes at once, and the
  filter's purity is an argument rather than a measurement on that axis.
- It did not measure whether `ComputeWithOverrides` invalidates or pollutes the
  persistent cache beyond the one assertion that the next plain `Compute` is
  unchanged — which is the property a driver depends on, and not the same as
  knowing what the executor did with it.
- It did not put a real filtered pose in front of an eye. Whether 6 Hz or 12 Hz
  is the right cutoff for a clip is a look question, and P0-7's display smoke is
  where a pose becomes something to look at.
- It ran on Windows only. Nothing measured here is plausibly platform-specific,
  and the committed suite runs on all three lanes and will say so.
