# OpenUSD 26.08 OpenExec, a rest-pose correction between two rigs on one stage

- Date: 2026-09-13
- Version exercised: **OpenUSD 26.08**, the pinned `cy2026`/`usd` runtime. Like
  [the humanoid report](26.08-openexec-humanoid.md), this run used a local build
  of that release adopted as the runtime, not the published GHCR leaf.
- Occasion: [the OpenExec plan](../../roadmap/openexec-foundation.md) §6, P0-5.
  `vrm.computeRestPoseCorrection` is `execVrm`'s third computation and the first
  that reads **two rigs**: the humanoid's own, and the one a clip was authored
  against.
- Method: **run, one node on from the humanoid report.** Everything marked
  **(test)** is asserted by `execVrm_correction`, which drives the built bundle
  through `PXR_PLUGINPATH_NAME` without linking it, over `corrected_rig.usda`,
  or by `execVrm_rig`, which tests the seam with no stage. The one claim marked
  **(negative)** was measured by changing one line, rebuilding (a
  `Building CXX object` line confirming it), watching the suite go red, and
  restoring it.
- What this does **not** supersede: any earlier report. It repeats two of the
  humanoid report's findings on a second relationship, and says so where it
  does.

## TL;DR

1. **The node is one library call.** Its answer equals
   `vrmRetarget::ComputeRestPoseCorrection` over the rigs the bundle itself
   computed, bit for bit. (test)
2. **One computation serves both rigs.** The node reads a computation on its own
   prim and `vrm.computeTargetSkeleton` on two other prims, through two
   relationships. The second relationship, `vrm:retarget:sourceSkeleton`, is
   defined by no schema and is read like `vrm:skeleton`. So both rigs of a
   retarget are decomposed by one implementation. (test)
3. **A path to nothing arrives exactly as no relationship does**, so an absent
   source is refused. The library has a default source rest (all identity), but
   defaulting here would give a misspelled source that rest with no error.
   (test)
4. **Invalidation follows the dependency, not the value, on a third node.** A
   clip's rest *translation* reports the correction, whose value is rotations
   only and does not change. A change to the source relationship's target
   reaches it with no request rebuilt. No time change reports it. (test)
5. **The source is read by name and the target never is.** Naming the avatar's
   own skeleton as the source is refused: none of its joint names is a bone.
   Naming one bone at two joints is refused too, where the offline tool keeps
   the later one without a word. (test)
6. **The seventh boundary finding** is the sampler's kind a third time. Reading
   a clip's rest pose off its skeleton exists only in `tools/motionRetarget`.
   And the node the plan puts next cannot use this one as a wrapper:
   `PoseRetargeter` computes its own correction and takes none.

## 1. What ran

`vrmRetarget::RestPoseCorrection` registers as an execution value type. That
needed an exact `operator==` in `vrmRetarget`, over `pre`, `post` and the
`identity` flags. `Apply` reads the flags first, so two corrections that differ
only there are different values. One computation is registered on the applied
`VrmHumanoidAPI`:

| Reads | Across | What it is |
| --- | --- | --- |
| `vrm.computeHumanoidMap` | the prim itself | which joint each bone drives |
| `vrm.computeTargetSkeleton` | `vrm:skeleton` | the rig the map's indices count into, read again because a map carries no skeleton |
| `computePath` and `vrm.computeTargetSkeleton` | `vrm:retarget:sourceSkeleton` | the skeleton the clip was authored against, counted twice as `vrm:skeleton` is |

The source relationship names a **skeleton**, not an animation. A
`UsdSkelAnimation` states no rest, and UsdSkel binds in the other direction: the
skeleton names its animation in `skel:animationSource`. From the skeleton, both
halves of a clip can be reached; from the animation, only one can. The
relationship is a convention of this bundle, like `motion:timeCodesPerSecond` is
`execMotion`'s. Nothing in the repository authors it yet.

The fixture puts three rigs on one stage. `/Asset` is the humanoid report's rig
with its hips turned 90° about +Y, so every bone below the hips needs a
correction although only the arm is turned itself. `/Clip/HumanoidSkeleton` is
the shape `usdVrmaFileFormat` authors: joint leaves named after bones, identity
rests. `/Posed/HumanoidSkeleton` has a non-identity rest under a `Reference`
joint that is not a bone.

## 2. One computation, two rigs, three inputs

The request asks for both skeletons, the map and the correction. They compute
together with no error. The correction equals the library's answer over the
target skeleton and map that came back beside it, with the clip's rest written
from the fixture. Four things are checked from the definition as well as from
the library:

- a sample at the clip's rest lands on each mapped joint's own rest;
- the **spine is corrected** under the turned hips, although its own rest is
  identity, because the correction reads the accumulated chain;
- a rotation away from the rest keeps its world-space delta;
- an unmapped bone stays identity.

With `vrm:retarget:sourceSkeleton` changed to `/Posed`, the posed arm's −90° rest
lands on the rig's +90°. (test)

Reading the source through `vrm.computeTargetSkeleton`, not a second decoder,
means both rigs are decomposed by the same line of arithmetic. The seam adds only
the bone assignment. That assignment follows `ReadClip` line for line: a joint's
leaf names its bone, and the leaf of its parent *path* names the bone's parent.
A joint that is not a bone fills no slot, so `/Posed`'s `Reference` rest, turned
about +X, is dropped. That comes from `SourceRestPose`'s shape, one slot per
bone. The tool drops it the same way, so it is not a divergence. (test)

**A sign, measured by accident.** `GfMatrix4d::ExtractRotationQuat` chooses the
quaternion's sign by branch, so the posed arm's −90° about Z decomposes as
`(-0.7071, 0, 0, 0.7071)`, not `(0.7071, 0, 0, -0.7071)`. Both are the same
rest. The exact `operator==` treats them as different, so the suite compares a
hand-written expectation by orientation. This is P0-6's cheapest parity
category, *quaternion sign only*, produced inside one bundle before any second
implementation is involved.

## 3. An absent source is refused, and why it cannot be defaulted

The library's default `SourceRestPose` is every bone at identity with no
parents, which is `usdVrmaFileFormat`'s rest. `PoseRetargeter` takes it as a
default argument. So the rule both exec bundles follow would ordinarily default
an absent source: default where an absent value selects the library's documented
behaviour.

It does not apply here, and the reason is measured. A relationship whose one
target names no prim provides neither `computePath` nor
`vrm.computeTargetSkeleton`. It is missing from both reads, and the node receives
exactly what it receives when the relationship is not authored: a count of zero.
The suite runs both cases and asserts the same error for each. A default would
therefore give a misspelled source path the identity rest with no error. That
breaks the other half of the rule: never default a value the scene stated that
this layer cannot honour. Absence is refused so that a dangling path is refused
too. (test)

**A path to nothing is still invisible beside a real source.** The humanoid
report pinned this for `vrm:skeleton`, and it holds here too. With
`[</Clip/HumanoidSkeleton>, </Clip/Nowhere>]`, in either order, the relationship
reads as naming one object and the correction is answered. `execVrm_correction`
asserts that answer. (test)

**The second read is what makes the count mean anything.** A SkelRoot provides
no `vrm.computeTargetSkeleton`, so it is dropped from the fan-in while the
network compiles. A source naming the clip skeleton and `/Clip` therefore returns
one skeleton, and only the path count shows that two objects were named.
(negative: with the count taken from the skeletons that came back, that source
**was answered** against the skeleton; with `/Clip` alone, the refusal said
"reaches nothing" instead of naming the prim that answered nothing.)

## 4. Invalidation from three rigs' statements

The request's value callback records which keys each edit reports (test):

| Edit | Target | Source | Map | Correction | Value |
| --- | --- | --- | --- | --- | --- |
| nothing (recompute) | no | no | no | no | identical |
| `ChangeTime` | no | no | no | no | identical — every input is `uniform` |
| a clip rest **translation** | no | yes | no | **yes** | **unchanged** |
| a clip rest rotation | no | yes | **no** | yes | the spine's correction moves |
| unbind `head` | no | no | yes | yes | head identity |
| a target rest | yes | no | yes | yes | hips identity |
| `vrm:retarget:sourceSkeleton` → `/Posed` | — | — | no | yes | the posed correction, no request rebuilt |

The third row is the humanoid report's finding one node on. A correction contains
rotations only, so moving where the clip's head sits changes nothing in it. It
is still reported, because it reads the skeleton that moved. Whatever consumes a
correction will be recomputed for every rest edit of either rig. That is cheap
while the edits are rare, and it is a question for the performance baseline
(the plan's §7, P1-3), not a defect.

The fourth row is the one that justifies a separate node: an edit the map does
not read does not report the map. The seventh row is the blending report's
relationship edit, measured on a relationship no schema defines.

## 5. Which side is read by name

**The source is a semantic skeleton, so its joint leaves name its bones.** That
is the motion contract's statement about a semantic clip.
`motion.sampleAnimation` reads an animation's joints the same way. The target is
never read by name: its bones are the humanoid's bindings. Two refusals follow
from that split (test):

- **The avatar's own skeleton, named as the source**, is refused as naming no
  human bone. Its joints are VRoid's names, and `Root` is not a bone either. This
  is what naming the wrong rig looks like, and without the refusal it would be
  read as an all-identity rest that no consumer could tell from a measured one.
- **One bone at two joints**, such as `hips` beside `Reference/hips`, is refused,
  and every joint concerned is named. `ReadClip` fills slots in joint order, so
  the tool keeps the later rest and says nothing.

## 6. What the fallback does to a source

`vrm.computeTargetSkeleton`'s fallback cases carry over one node, unchanged
(test):

- a source skeleton whose `restTransforms` are blocked is refused by that
  computation, disappears from the fan-in, and the count turns the gap into a
  refusal that names the path;
- a one-joint source (`joints = ["hips"]`) with no rest arrives as one identity
  matrix and is answered as the library's default rest. From inside the callback
  it *is* an authored identity. The offline tool reads it the same way.

The node reads no schema attribute directly, so it adds no fallback decision of
its own. The humanoid report's §8.2 obligation passes to it only through the
computations it reads.

## 7. The wrapper, the seventh finding, and what the next node inherits

`vrm.computeRestPoseCorrection` is `ComputeRestPoseCorrection` and nothing more.
`execVrm_rig` asserts this over the seam's own reading of the source, bit for
bit, and over a rest written from its definition, as orientations.

**The seventh boundary finding** is the sampler's kind a third time. Reading a
clip's rest pose off its skeleton, with each bone's slot taken from a joint leaf
and its parent from the parent path's leaf, exists only in
`tools/motionRetarget`'s `ReadClip`. Only that assignment is in the seam; the
decomposition comes from `vrm.computeTargetSkeleton`. The ask for
[boundary consolidation](../../roadmap/boundary-consolidation.md) is a
`SourceRestPose` built from a semantic skeleton's tokens and decomposed rests,
beside the struct, which the tool and the bundle both call.

**What `vrm.humanoidRetarget` inherits, read off the API rather than measured.**
`PoseRetargeter`'s constructor computes its own correction from the source rest,
skeleton and map, and no constructor or free function accepts a correction that
is already computed. A retarget node that wraps `PoseRetargeter` would therefore
redo, on every evaluation, the correction this node caches per rig edit. The
cached value would feed nothing, and the plan's reason for making it a separate
node (§4 above) would be lost. The next node has to measure this. It will
probably become the ask that `PoseRetargeter`, or a free per-pose function beside
it, take the correction as an input.

**Four places this bundle and the offline tool answer differently**, added to
the humanoid report's five for P0-6. None is numerical, and none is reachable
from what the importer and `usdVrmaFileFormat` author:

| The stage states | `motion_retarget` | `execVrm` |
| --- | --- | --- |
| a clip skeleton whose `restTransforms` do not pair with its joints | assumes identity rest, warns | refuses the source, and the correction |
| one bone at two joints of the clip skeleton | the later joint's rest, silently | refuses, naming every joint |
| no `vrm:retarget:sourceSkeleton` | not asked — the tool opens the clip as its own stage | refuses |
| a source path naming no prim | not applicable | refused alone, invisible beside a real source (§3) |

The last two are about stage shape rather than missing fields. The tool reads two
stages; exec reads one stage, which has to say where the clip's skeleton is.
P0-6's harness has to author that relationship on the stage it compares, or a
producer has to (the plan's §9).

## 8. What this changes in the plan

1. **P0-5 has three of its five nodes.** `vrm.humanoidRetarget` and
   `vrm.computeJointLocalTransforms` remain. The first now has a question to
   answer before it can be a wrapper (§7).
2. **A second relationship convention to write down.** Like
   `motion:timeCodesPerSecond`, `vrm:retarget:sourceSkeleton` is something no
   producer authors, and P0-6 needs it on every stage it compares. It joins the
   rate in the plan's §9.
3. **The absent-input rule gains a reason to refuse where a library default
   exists.** When a value arrives through a relationship, *absent* and *dangling*
   are one value, so a default would cover a misspelling. It sits beside
   `execMotion`'s rule, "default where an absent value selects the library's
   documented behaviour", as its first stated exception.

## 9. What this did not do

- It did not build `vrm.humanoidRetarget`, or measure the cost §7 reads off the
  API.
- It did not run a real `.vrma` beside a real `.vrm` on one stage. The fixture's
  `/Clip` reproduces the shape the reader authors, and the importer's rig with a
  turned hips stands in for an avatar whose rest is not identity.
- It did not run `motion_retarget` over `corrected_rig.usda`. The §7 table comes
  from reading `ReadClip`, not from a parity run, which is P0-6's to make.
- It did not load the bundle from a packaged artifact; that is P0-3's smoke.
- It ran on Windows only. The committed suites run on all three lanes.
