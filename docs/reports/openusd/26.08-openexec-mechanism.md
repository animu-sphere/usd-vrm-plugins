# OpenUSD 26.08 OpenExec, run rather than read

- Date: 2026-09-06
- Version exercised: **OpenUSD 26.08** — the pinned `cy2026`/`usd` runtime, the
  same artifact [the migration audit](26.08-openexec-migration.md) read.
- Occasion: [the OpenExec plan](../../roadmap/openexec-foundation.md) §6, P0-4
  step 1 — *mechanism before behaviour*: register nothing real, so that a
  failure is attributable to the mechanism and not to an algorithm.
- Method: **run, not read**, which is the one thing the migration audit said it
  had not done ([§10](26.08-openexec-migration.md#10-what-this-audit-did-not-do)).
  Two vehicles, and the difference between them matters:
  - the committed `execMotion_mechanism` CTest target
    ([plugins/execMotion/tests/](../../../plugins/execMotion/tests/)), which
    runs on every lane and is where a claim marked **(test)** below comes from;
  - a throwaway plugin and host, built against the same prefix and then thrown
    away, for the questions a shipped bundle cannot answer about itself — and
    for one it could until the answer turned out to require a wrong number
    (§4). Claims marked **(probe)** come from it, and each says what the probe
    did.
- What this does **not** supersede: the migration audit. That report is still
  the source for value types, connection dataflow, `ExecIr`, and the Hydra path.
  This one corrects three of its statements and adds four facts it could not
  have read.

## TL;DR

The mechanism works, end to end, exactly as the audit predicted it would: a
`motionCore` aggregate registers as an execution value type and crosses a
computation boundary unchanged, a plugin's computations are discovered lazily
through its `plugInfo.json`, a request compiles, computes, caches, and is
invalidated by an authored change.

Four things the audit could not have read, in descending order of how much they
change the plan:

1. **A schema may be declared by exactly one plugin.** `execGeom` owns
   `UsdGeomXformable`; a second declarer is refused with a coding error and its
   computations for that schema are never registered. This is a hard constraint
   between `execMotion` and `execVrm` — and it retires the migration audit's
   preferred option for the display slice as written.
2. **An applied API schema reaches a prim whose typed schema belongs to someone
   else.** That is the route around (1), and the one `execVrm` will take.
3. **`Diagnostics::InvalidateAll()` expires every outstanding request** — while
   `ExecUsdRequest::IsValid()` goes on returning true, which its own header
   documents as "Compute is allowed". It **also resets the system's time**.
4. **A computation cannot learn the stage's `timeCodesPerSecond`**, so it cannot
   turn the frame exec hands it into the second every canonical motion value is
   expressed in. That is a constraint on `motion.sampleAnimation`, not a
   curiosity: the rate has to be *given* to the exec layer.

## 1. What ran

`plugins/execMotion` registers `motion::HumanoidPose` with
`ExecTypeRegistry::RegisterType` and one computation, `motion.identityPose`, for
`UsdSkelAnimation`. The computation reads the clip's `joints` — that is its only
input — and returns the identity pose over the canonical bones those joint paths
name. There is no algorithm in it on purpose, and §5 says why there is no time
in it either.

The test executable does **not** link the plugin. It reaches the computation only
through `PXR_PLUGINPATH_NAME` and the staged `plugInfo.json`, which is the path a
packaged bundle takes — and moving that file aside turns the test red with
`Failed to find computation 'motion.identityPose' on provider '/Clip'`, which is
the audit's §2.1 prediction confirmed: a missing `Info.Exec.Schemas` block is not
a load error, it is a computation that does not exist.

**(test)** The following all hold on the pinned runtime:

| Step | Result |
| --- | --- |
| type registration for a canonical aggregate | `motion::HumanoidPose` — a struct of `std::array`, `std::bitset`, `std::optional` and `std::vector` — registers and crosses back out unchanged |
| an array-valued USD input | `joints` declared with its **element** type (`TfToken`) and read with `VdfReadIterator<TfToken>`, exactly as §4 of the audit prescribed |
| request compile | one value key, `(prim, "motion.identityPose")`, `IsValid()` true |
| compute | the pose names four bones and skips the joint path that names none |
| recompute, nothing changed | no invalidation reported, identical value |
| authored-value invalidation | appending a joint fires the value callback; the recompute sees five bones |
| a time change | `ChangeTime` reports **nothing** for a value key whose inputs do not change with time, which is the header's own promise and the check that this computation has not silently acquired a time dependency |
| an unregistered computation | an empty value plus a coding error — caught with a `TfErrorMark`, never a load failure |

A computation name with a dot in it (`motion.identityPose`) is fine; the plan's
`<layer>.<verb>` spelling needs no change.

## 2. A schema belongs to one plugin

**(probe)** The first spike registered its computation for `UsdGeomXformable`,
because that is the schema the migration audit's §9.6 option (a) names. It never
ran. Three diagnostics, in this order:

```text
Coding Error: ... Failed to find computation 'computeSpikePose' on provider '/Root'
Coding Error: in _ReadPluginMetadata at line 142 of .../exec/pluginData.cpp --
    Plugin ' ' declares schema execSpike as UsdGeomXformableallowing plugin
    computations, but plugin 'execGeom' already declared this schema.
Coding Error: ... Expected exactly one output for value key '/Root [computeSpikePose]'; got '0'
```

Registering the same computation for `UsdSkelAnimation` instead — a schema no
shipped plugin declares — made every step pass unchanged. So the rule is about
the *declaration*, not about the computation or the callback.

Two refinements, both measured:

- **The loss is per schema, not per plugin.** A `plugInfo.json` declaring
  `UsdGeomXformable` (taken), `UsdSkelSkeleton` and `UsdSkelBindingAPI` still
  registered the computations for the second and third; only the colliding
  schema's were dropped, and the coding error was still emitted. A bundle that
  names five schemas and collides on one keeps four.
- **The message's arguments are garbled** — the plugin name is blank, the field
  labelled "schema" holds the plugin's name, the schema name runs into the next
  word. Worth an upstream nit; it does not affect the behaviour, but it does
  affect how long it takes to recognise.

`execGeom` declares `UsdGeomXformable` and `UsdGeomScope`, and `execIr` declares
its own; those are the only `Exec` blocks in the pinned runtime, so every other
schema is free — for exactly one taker.

## 3. An applied API schema is the way around it

**(probe)** A computation registered for `UsdSkelBindingAPI` — an *applied API*
schema — resolved on a prim whose type is `UsdGeomXform`, and computed from that
prim's own attribute. The plugin declared only `UsdSkelBindingAPI` and
`UsdSkelSkeleton`; it never declared `UsdGeomXformable`, which it may not.

That is the mechanism `execVrm` needs. It also means the schema partition
between our two bundles is a design decision rather than an accident, and it is
made in [WORKSPACE.md §2](../../architecture/WORKSPACE.md): `execMotion` owns
`UsdSkelAnimation`, `execVrm` owns the `Vrm*API` applied schemas and
`UsdSkelSkeleton`, and neither declares the other's.

**(probe)** The cache is real in the strong sense as well: a counter exported
from the probe plugin showed the callback ran **once** across two `Compute()`
calls with no intervening change, and again after an authored change. The
committed test asserts only the observable half — no invalidation reported, and
an identical value — because a shipped plugin should not export a counter, and a
callback that carried one would violate exec's own purity contract.

## 4. `InvalidateAll()` expires requests, and forgets the time

**(test)** `ExecSystem::Diagnostics::InvalidateAll()` is the plan's "explicit
invalidation" step. It does two things beyond dropping cached values, and the API
announces neither:

1. **Every outstanding request is expired.** `ExecUsdRequest::IsValid()` keeps
   returning `true` — and its header defines that as "calling PrepareRequest or
   Compute is allowed" — while `Compute()` on such a request posts
   `Failed verification: '_system'` twice and returns a cache view that extracts
   nothing. The caller has to rebuild the request. Nothing in the request or
   system headers says so, and `IsValid()` is precisely the call a caller would
   use to find out.
2. **(probe) The system's time is reset.** A request rebuilt after
   `InvalidateAll()` evaluates at the **default** time code, not at the time the
   system was last given, so a pose computed through it carried a different
   timestamp than the one before the invalidation; re-issuing `ChangeTime`
   restored it. This one is marked *(probe)* on purpose. It was measured while
   `motion.identityPose` still took `computeTime` and wrote the frame into the
   pose — and writing a frame into a field that means seconds is the defect §5
   describes, so the witness was removed with it. Retaining the assertion would
   have meant retaining a wrong number and a time dependency this computation
   does not have.

The first is asserted in `execMotion_mechanism` rather than only described, so
the day it changes upstream is a red test rather than a silent behaviour swap.
The stage survives either way: an authored change made before the invalidation is
still there afterwards, which is the half that does behave as the name
suggests.

## 5. A computation is given a frame and cannot find the rate

**(test)** `Stage().Computation<EfTime>(ExecBuiltinComputations->computeTime)`
works as documented and is how a computation gets a time. Two things about that
time cost this bundle its timestamp.

`EfTime` carries a `UsdTimeCode`, and `UsdTimeCode::GetValue()` is a coding error
on the default time code — which is what a system evaluates at until `ChangeTime`
is called, so it is the common case rather than an edge one. Any computation that
reads time must check `IsNumeric()` first.

**And a time code is a frame, while every canonical motion value is in seconds.**
`motion::HumanoidPose::timestamp` is seconds; `tools/motionRetarget` converts
with `stage->GetTimeCodesPerSecond()` because it holds the stage. A computation
does not, and 26.08 offers it no way to ask:

- `Stage().Metadata<double>(SdfFieldKeys->TimeCodesPerSecond)` **compiles and is
  accepted by the builder**;
- adding `.Required()` — documented as turning a missing input into a compile
  error rather than silence — **does not refuse it either**;
- and `GetInputValuePtr<double>` for it still returns null at evaluation, on a
  stage that has `SetTimeCodesPerSecond(50)` authored and reports 50 through
  `UsdStage::GetTimeCodesPerSecond()`.

So the input resolves and carries no value, which is the worst of the three
possible outcomes: a callback that used it would silently apply whatever fallback
its author chose. `motion.identityPose` therefore carries **no timestamp at all**
— a pose that says nothing about time, rather than a pose asserting a second
computed from a rate nobody supplied — and it declares no time input, because the
identity pose is the same pose at every frame and declaring `computeTime` would
tell exec otherwise.

This is the first hard constraint on the real nodes. `motion.sampleAnimation`
samples a clip *at a time* and must produce a pose stamped in seconds, so the
rate has to reach it as an explicit input: authored where a computation can see
it, or applied by the caller after the value crosses back out. It cannot be
discovered inside the computation, and a node that guessed would put a wrong
second into canonical motion where nothing downstream could distinguish it from a
measured one.

## 6. What this changes in the plan

1. **P0-4 gains a decision it did not have: `execMotion` owns
   `UsdSkelAnimation`.** Its computations register there and nowhere else, and
   the manifest says so in `provides:`.
2. **P0-5 must change.** The migration audit's
   [§9.4](26.08-openexec-migration.md#9-what-this-changes-in-the-plan) tells
   `execVrm` to name `UsdSkelSkeleton` **and `UsdSkelAnimation`** in its own
   plugInfo. It may not name the second: `execMotion` has it, and the collision
   would cost `execVrm` every computation it registered there, silently. What
   `execVrm` does instead is reach an animation through an input accessor, and
   register its own computations on the `Vrm*API` applied schemas and on
   `UsdSkelSkeleton`.
3. **P0-7's preferred option is not available as written.** §9.6 option (a) —
   "prove the mechanism on `UsdGeomXformable`" — cannot mean *our* computation on
   that schema, because `execGeom` declares it. The display slice must instead
   apply an API schema of ours to the Xformable prim (§3 above), or drive
   `execGeom`'s existing computations. Option (c), the upstream ask, is
   unaffected and now has a second thing to ask for.
4. **P1-1 gains a diagnostic to own.** `VRM_OPENEXEC_INVALIDATED` was already
   ours to produce; §4 says what it has to cover — a request that reports itself
   valid and is not. A caller that rebuilds a request without restating the time
   computes the wrong frame with nothing in the log.
5. **P0-4's node signatures gain a rate.** §5 makes the frame-to-seconds
   conversion the caller's, not the computation's, for every node that stamps a
   pose. Decide where the rate enters — an authored attribute a computation can
   read, or a conversion applied to the value on its way out — before
   `motion.sampleAnimation` is written, because both alternatives are cheap now
   and one of them becomes a signature change later.
6. **The audit's "one plugin declares a schema" gap is closed**, and the
   `allowsPluginComputations: false` reading in §2.1 stands: a schema can be
   closed by its declarer. What §2.1 did not say is that being *open* is also
   exclusive.

## 7. What this did not do

- It did not run `usdExecImaging`, Hydra, or any display path. P0-7 is untouched
  except for the constraint in §6.3.
- It did not exercise multi-input fan-in, `Relationship().TargetedObjects<T>()`,
  `IncomingConnections<T>()`, or the two-connection silent fallback the audit
  documents in §5.1. `blendPoses` is where those land, and it is last in P0-4's
  order for that reason.
- It did not measure performance, threading, or concurrent evaluation of a
  callback, which the header requires be thread safe.
- It did not test `ComputeWithOverrides`, dispatched computations, or attribute
  expressions.
- It did not establish *why* stage metadata resolves to no value (§5) — whether
  the field is unreachable through a prim provider, whether `Stage()` resolves to
  the pseudo-root and layer metadata does not live there, or whether metadata
  inputs need something this registration did not do. The consequence for the
  node signatures is the same in every case, which is why the cause was not
  chased further; a fix upstream would change it.
- It ran on Windows only. Nothing measured here is plausibly platform-specific,
  but the committed half runs on all three lanes and will say so.
